# Data model

The PostgreSQL schema (`migrations/001_initial.sql`, the whole MVP schema; `002` widens the audit metadata allowlist; `003` adds the installation and repository state; `004` allows the account type `Other`; `005` adds `sessions.verified_emails`; `007` adds `installation_admin_seen`; `009` scopes `erase_signer_pii` to one installation; `010` adds `purge_signer_network_metadata`; `011` adds `cla_drafts`; `012` adds `allowlist_entries.login_snapshot`; `013` lets `erase_signer_pii` reach an allowlisted account that never signed; `014` adds `signer_pii.ip_address` and `user_agent`; `015` adds `signatures_user_signed_at_idx`; `018` adds `merge_group_evaluations`; `019` adds `repositories.public_verification`) and the immutability, erasure and role rules around it. Identity, the immutable signature core and the erasable `signer_pii` table are hard rules 4 and 5 in [`CLAUDE.md`](../CLAUDE.md); authorization and privacy are in [`security.md`](security.md).

| Table | Purpose and key constraints |
|---|---|
| `users` | GitHub account snapshot. `github_id` bigint UNIQUE is the identity key; login, name and avatar are display snapshots only, upserted at every login (login, name, avatar_url and `updated_at` refreshed; no other column) |
| `sessions` | Server-side sessions: `session_hash` (hex SHA-256 of the 256-bit cookie id; the id itself is never stored), idle and absolute expiry, CSRF secret, and `verified_emails` jsonb not null default `'[]'` (an array of at most 20 `{email, primary}`: the verified addresses GitHub reported at login, kept for the sign page because no user token is stored). That column is personal data and lives only as long as the row: logout, expiry, the purge and `erase_signer_pii` delete it. At most 10 sessions per user (the 11th creation deletes the oldest), and each creation deletes up to 100 expired rows. A session holds no installation: it says nothing about tenants. A revoked App authorization deletes every session of that `users.github_id` (no schema change; the `users` row stays) |
| `installations` | GitHub App installation: `github_installation_id` UNIQUE, account id, login, type (`Organization`, `User` or `Other`, the last for an enterprise), `suspended_at`; `admission_status` (default `rejected`: a row nobody decided on is never evaluated), `admission_reason` (`account_not_allowed` or `policy_changed`), `admission_decided_at`, `deleted_at` (uninstall) and `last_synced_at` (set only when a sync writes). The runtime role has no DELETE or TRUNCATE on it |
| `repositories` | Installation, `github_repo_id`, `full_name` snapshot, `enabled`, active CLA document, `public_verification` (boolean, default false, migration 019, E22-S02: the maintainers' opt-in to the public signature check and the badges; audited as `repository.public_verification_changed`), `removed_at`. Unique (`installation_id`, `github_repo_id`) plus a partial unique index on `github_repo_id` where `removed_at` is null: a repository is active under at most one installation, and a transfer is a new row under the new tenant. `removed_at` is set by the sync, by an access-lost refresh, and by the new tenant's sync on another tenant's active row (a transfer; the only write into another tenant's row, `removed_at` alone plus an audit row under that tenant). The runtime role has no DELETE or TRUNCATE on it |
| `cla_documents` | Named CLA per installation or repo; kind is individual or corporate. `installation_id` and `kind` never change (trigger). The active version only moves forward: it must be the document's highest (major, minor) |
| `cla_versions` | Immutable once published (DB trigger): unique (document, major, minor), `content_md`, `content_sha256`, publisher, rationale, `published_at`. The document points at the active version; a rollback publishes a new version, never reactivates an old one (a trigger refuses to point at anything but the highest version). `published_at` must be within five minutes of the database clock |
| `cla_drafts` | The one work-in-progress text of a document (E12-S03), mutable and outside the immutability triggers: primary key `document_id`, `installation_id`, `content_md`, `revision` (1 on the first save, +1 on each, written in one statement guarded by `where revision = $expected`), `updated_by` (a `users` id) and `updated_at`. The composite foreign key (`document_id`, `installation_id`) to `cla_documents (id, installation_id)` is `on delete restrict`. `cla_app` has select, insert, update and delete (granted only when the role exists). Publishing from the draft deletes it; no contributor-facing route reads it. |
| `signatures` | Immutable core: user id, version, text hash, consent text id, `signed_at` UTC, signer type, source repo and PR, plus `revoked_at`, `revoked_by`, reason (the only mutable columns; the reason is a code from a fixed set, never free text, because a revoked row can never be scrubbed). The document's kind must equal `signer_type` (composite foreign key), `revoked_at` cannot precede `signed_at`, and `signed_at` must be within five minutes of the database clock. Partial unique index on (user, document, major) where not revoked. The sign request carries the version id and hash, verified server-side. `consent_text_id` is an id of the registry `CONSENT_TEXTS` in `src/shared/consent.ts` (ids are never edited or removed, new wording is a new id such as `individual-v2`, and the web carries no copy of the text). Index `signatures_user_signed_at_idx` on (user, signed_at desc, id desc) serves the list of a person's own signatures (migration 015) |
| `signer_pii` | Erasable personal data for a signature: name, verified email and login snapshots, and, only when `RECORD_NETWORK_METADATA` is `true`, `ip_address inet` and `user_agent text` (check: at most 512 characters; migration 014; both `NULL` otherwise, and neither is on `signatures` or `audit_log`). Split out so GDPR erasure never touches the immutable core; `erase_signer_pii` removes the row, `purge_signer_network_metadata` blanks the two network columns after `NETWORK_METADATA_RETENTION_DAYS` |
| `commit_overrides` | Audited maintainer override per (repo, commit SHA); never implies a signature |
| `corporate_agreements`, `corporate_approvals` | Phase 2: company CCLA and manager-approved employees |
| `allowlist_entries` | Scope (installation or repo), kind (user, bot, org members), numeric GitHub id, never a login string. A `user` entry also covers `Organization` and `Mannequin` accounts by id, a `bot` entry covers `Bot` and `Unknown`, `org_members` covers only `User` and `Unknown` (never a bot); ties go to repository scope, then kind user, bot, org_members, then the lowest id. `login_snapshot` (migration 012, text, null, checked against the shape of a GitHub login, up to 39 letters, digits and hyphens with an optional `[bot]`) is the login the entry was made under, shown to the maintainers and never used for matching or written to `audit_log`; the erasure sets it to null for the person's entries in one installation, with or without a signature, and the purge of the network metadata leaves it. A removed entry is deleted (the runtime role holds `DELETE` on this table); its history is the audit row `allowlist_entry.deleted`. Its statements, and those of the lists, the attach and the enable, are in the registries of the cross-tenant tests (`tenant-registry-allowlist/`, `-listing/`, `-attach/` and `-enabled/`) |
| `pr_evaluations` | Unique (repo, PR number, head SHA): result, details, `check_run_id`, `comment_id`. `details` is written only by `toStoredDetails` (version 1, bounded lists, `omitted` counts), see [the evaluation engine](architecture.md#the-evaluation-engine). `check_run_id` and `comment_id` are written only through `adapters/db/pr-evaluation-links.ts` (E09-S04): one update each, the column and `updated_at` and never `result` or `details`, which the evaluation job keeps; rows are never deleted. `hasNewerHeadRow` compares `updated_at` of the rows of one pull request, and `findRowsForSha` marks a row `superseded` the same way, so the reporter can tell the pull requests that stand at a head SHA from the ones that moved on |
| `merge_group_evaluations` | The evaluation of a merge queue's group (E22-S01, migration 018), a tenant table: `installation_id` with a composite foreign key to `repositories (id, installation_id)` (`on delete restrict`), `head_sha` and `base_sha` (40 or 64 lower-case hex), `result` (`in_progress`, `success`, `failure`), `details` jsonb (version 1: numeric pull request numbers, outcomes and codes of a closed set, never a name, login or email), `check_run_id`, `destroyed_at`. Unique (`repository_id`, `head_sha`): two deliveries for one SHA leave one row, and the same SHA in two tenants is two rows. `destroyed_at` is set when GitHub took the group down; a `destroyed` delivery that arrives before any job creates the row as a tombstone (`in_progress`, no details), and every write that gives a group a verdict is conditional on `destroyed_at is null`. `cla_app` may select, insert and update; there is no DELETE grant and no job removes a row. No personal data, so erasure does not touch it |
| `webhook_deliveries` | `delivery_id` PK for idempotency (GitHub reuses the id on redelivery), event, action, received and processed times. A row exists only for a delivery that starts a job (a ping or an ignored delivery inserts none) and holds no payload. `processed_at` is set by the job layer through `markDeliveryProcessed` (E07-S03) or, when a limit (a rate limit window) dropped the send of a row just recorded, in the recording transaction; a live job under the same key leaves it null |
| `audit_log` | Append-only: actor numeric id, action, subject ids, metadata. **No personal data**: metadata is a flat object whose keys come from a fixed list and whose values are integers, booleans, null, lists of integers or lower-case codes (`audit_metadata_is_clean`); a new key needs a migration, see below. Tenant reads (the viewer, E16-S02) use `audit_log_installation_occurred_at_idx`; rows with a null installation are read with the owner role only; there is no index on the subject |
| `installation_admin_seen` | The ledger of org admins (E11-S07, migration 007): the numeric GitHub id of a person a live lookup last saw as an admin of an organisation, and when (`seen_at`). Primary key (`installation_id`, `user_github_id`), foreign key to `installations` on delete restrict, `cla_app` may select, insert, update and delete. Numeric ids only: it is not signer data, so erasure does not touch it. An entry older than 14 days is never read; there is no purge job yet (a retention job or the erasure of E16 may delete a person's rows). See [`security.md`](security.md#auth-model) |
| `pgboss.*` | The queue schema, owned by pg-boss and by the migration owner (see below). Outside `schema_migrations`: `yarn db:migrate` installs and upgrades it |

Immutability is enforced by DB triggers that block `UPDATE` (beyond the allowed columns), `DELETE` and `TRUNCATE`; the runtime DB role does not own the tables, so it cannot disable triggers. The identity columns the rest of the schema hangs on (`users.github_id`, `installations.github_installation_id` and `account_id`, `repositories.github_repo_id` and `installation_id`, `cla_documents.installation_id` and `kind`) cannot be updated either, although the runtime role may update the other columns of those tables: re-pointing a GitHub id would re-attribute every signature that references the row. Erasure goes through one audited SQL function, `erase_signer_pii(person, actor, installation)` (migration 009): it is scoped to one installation, so one org admin's request cannot reach another org's data. It deletes the person's `signer_pii` rows of that installation, clears `allowlist_entries.login_snapshot` where the column exists, scrubs the display snapshot in `users` and deletes the person's sessions only when no `signer_pii` row of the person is left in any tenant, appends `signer_pii.erased` and keeps the minimal signature core (GDPR Art. 17(3)(e), legal claims). The operator's command (`erase.ts`, E22-S05) calls it once per installation in which the person has a signature or an allowlist entry that still shows their login, each call in its own transaction and with its own `signer_pii.erased` row, so a person who signed in two orgs gets two rows; a rerun writes a row with zero deleted rows for an installation that was done. The optional network values are changed by one other function only: `purge_signer_network_metadata(cutoff)` (migration 010, `security definer`; the runtime role has no `update` on `signer_pii`) sets `ip_address` and `user_agent` to null on rows older than the cutoff and, when it changed any, appends one instance-level audit row `network_metadata.purged` with `{ rows }`. Retention is a setting of the instance, so the purge is instance-wide and no tenant's audit viewer shows its row. A `signer_pii` row cannot be stored for a signature that predates the person's erasure (trigger), so a signing request that was in flight during the erasure cannot write the data back. The acting administrator is a required argument; it is the caller's attribution, which the database cannot verify, and the audit row is append-only rather than hash-chained. Other text that is not signer data and is outside erasure: `installations.account_login` and `repositories.full_name` (public names of the maintainers' accounts and repositories; for a user-type installation that is the maintainer's own login) and `commit_overrides.reason` (a maintainer's note); the full inventory of personal-data columns is in [`privacy.md`](privacy.md). `pr_evaluations.details` holds numeric ids and codes only: its strict schema in `src/shared/pr-evaluation-details.ts` leaves no field for a name, login or email, and `parseStoredDetails` never throws on an old or unknown row.

`migrations/001_initial.sql` creates every table above except `corporate_agreements`, `corporate_approvals` (phase 2) and `pgboss.*` (pg-boss creates its own schema). Tenant tables carry `installation_id` and tie it to their parent with composite foreign keys, so a row can never point at another tenant's repository or document. Two roles: the migration owner (`MIGRATION_DATABASE_URL`) owns the schema; the runtime role `cla_app` (`DATABASE_URL`) gets only the privileges it needs, granted by the migration when the role exists. The runner (`src/server/adapters/db/migrator.ts`) holds a session advisory lock, applies each file in its own transaction, records a SHA-256 checksum in `schema_migrations`, and refuses to run when an applied file changed, went missing or sorts before an applied one. bigint columns come back as JS numbers (GitHub ids are far below 2^53) and a value outside the safe range throws instead of rounding.

**The job queue schema (E07-S01).** pg-boss creates and migrates its own `pgboss` schema, as the owner, in the second step of `yarn db:migrate` (after the SQL files and the grants of the first step): the step installs or upgrades the schema, creates the queues with their policy and bounds (and the scheduler queue `__pgboss__send-it`), converges the options of a queue that exists with `updateQueue`, and prints `job queues: up to date`, `job queues created: a, b` or `job queues updated`. The runtime role `cla_app` gets `usage` on the schema, `select`, `insert`, `update` and `delete` on all its tables, `usage` on its sequences, `execute` on its functions and default privileges for the objects a later upgrade creates; it has no `CREATE`, no `TRUNCATE` and owns nothing, so it cannot disable a trigger. pg-boss's `createQueue` is plain DML unless a queue is partitioned, but only the owner creates queues. Migrations 001 to 004 were not touched and no SQL migration was needed for the queue itself; the pg-boss schema has its own version table and is forward-only like ours (an upgrade is a new build plus `yarn db:migrate`). A database that has not run the step makes the server exit 1 at boot naming the missing queues.

**Roles and provisioning (E19-S03).** The two roles, the database and the `pgboss` schema are created by `scripts/provision-database.sh` with `scripts/provision-database.sql` (the compose stack runs them on the first start of an empty volume; an operator's own server runs them by hand): `cla_owner` and `cla_app` are `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS` and members of neither; the database is `UTF8` and owned by `cla_owner`, `PUBLIC` has no `CONNECT` or `CREATE` on it or `CREATE` on the schema `public`, and `cla_app` has only `CONNECT`; the schema `pgboss` is owned by `cla_owner` with `USAGE` for `cla_app` and default privileges (for the objects the owner creates in that schema only) that give `cla_app` the table, sequence and function access pg-boss needs. The script sets no default privileges on application tables, so the explicit grants of the migrations stay the only table access and the immutable tables never gain write access by default. A second run changes nothing, and nothing is ever dropped.

`pr_evaluations.result` accepts `in_progress`, `success`, `failure` and `cancelled` (`migrations/008_pr_evaluation_cancelled.sql`; the number follows `007`, because the runner refuses a migration that sorts before an applied one). `cancelled` is a lifecycle state set by the `close-pr` job and the sweep's reaper, never produced by the evaluation engine, and a `cancelled` row is not final: a reopened pull request is evaluated again from it. The evaluation, close and dead-letter jobs needed no other change: `cla_app` already had `select`, `insert` and `update` on `pr_evaluations` and read access to the policy tables.

Audit metadata is an allowlist of 31 keys: the 12 of `migrations/001_initial.sql` plus 19 added by `migrations/002_audit_metadata_allowlist.sql`, which replaces `audit_metadata_is_clean` (`create or replace`; 001 is never edited, and rows already written are not re-checked). Values are integers, booleans, `null`, lists of at most 100 integers, or codes of 1 to 64 characters from `[a-z0-9_.:-]` that never look like an IP address (four dotted numbers with an optional port, or only hex digits, dots and at least two colons). The writer also caps the serialised metadata at 2,048 bytes; the database does not check that. The key list is `AUDIT_METADATA_KEYS` in `src/shared/audit.ts` and the value rules are in `src/shared/audit-metadata.ts`. A new key needs a new forward-only migration that replaces the function again plus the constant: `migration-002-audit-metadata.test.ts` compares the key list of the newest migration that defines the function with the constant and fails until both agree, and a shared case table (`src/shared/test-support.ts`) keeps the SQL and zod value rules equal. Personal data (`name`, `email`, `login`, `avatar_url`) and free text (`reason`, `message`, `title`, `text`) are never keys. Migration numbers go in merge order: another branch that adds a migration with the same number renumbers whichever merges second.

The audit actions the installation lifecycle writes are all system actions (actor null, tenant-scoped, subject `installation` with the GitHub installation id, or `repository` with the GitHub repo id; never a name or login): `installation.admitted` (metadata `account_id`, `account_type`), `installation.rejected` (`account_id`, `account_type`, `reason_code` of `account_not_allowed` or `policy_changed`), `installation.updated` (`account_id`, `account_type`; the account snapshot changed in a way no other row records), `installation.deleted` (`account_id`, `account_type`, `count`), `installation.suspended` and `installation.unsuspended` (`account_id`, `account_type`), `repository.added` and `repository.renamed` (no metadata) and `repository.removed` (`reason_code` of `not_listed`, `access_lost` or `transferred`), and `installation.sync_failed` (written by the dead-letter handler of `sync-installation`: metadata `reason_code` `retries_exhausted`, no personal data); `account_type` is the lower-case code `organization`, `user` or `other`. These needed no new metadata key.

The CLA document actions are performed by a person and belong to a tenant (subject `cla_document` or `cla_version` with our row ids; never a name, text or rationale): `cla_document.created` (`document_id`, `repository_id`, `kind`) and `cla_document.renamed` (`document_id`; a rename to the name the document already has changes nothing and writes no row), `cla_draft.saved` (`document_id`, `revision`) and `cla_draft.discarded` (`document_id`, `revision` that was discarded; discarding when there is no draft writes no row), and `cla_version.published` (`document_id`, `version_id`, `major`, `minor`, `bump`, `affected_signatures`, and `rolled_back_from_version_id` for a rollback). The signing action is `signature.created` (subject `signature` with our row id; metadata `document_id`, `version_id`, `major`, `source_repository_id`, `source_pr_number`, and never a name, address, login, address of the request or user agent). A version read joins `users` for the publisher snapshot (an erased publisher shows `erased-<github id>`) and counts live signatures with the installation id in the statement.

The audit actions of epic E22: `repository.public_verification_changed` (a person, tenant-scoped, subject the repository's GitHub id, metadata `repository_id` and the new flag `enabled`) and `retention.swept` (instance-level: no actor and no installation, the two counts `webhook_deliveries` and `sessions` as the only metadata, written only by a run that deleted something). The retention sweep deletes from `webhook_deliveries` and `sessions` only (the runtime role already held `delete` on both, and the sweep names no other table), and `merge_group_evaluations` (migration 018) takes no `delete` grant at all.

Revocation is prospective: `revoked_at` marks the signature invalid for *future* PRs; contributions already accepted stay licensed. Network metadata (IP, user agent) is **off by default**; if enabled it needs a documented legitimate interest and short retention (Art. 5(1)(c), 5(1)(e)).
