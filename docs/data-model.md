# Data model

The PostgreSQL schema (`migrations/001_initial.sql`, the whole MVP schema; `002` widens the audit metadata allowlist; `003` adds the installation and repository state; `004` allows the account type `Other`) and the immutability, erasure and role rules around it. Identity, the immutable signature core and the erasable `signer_pii` table are hard rules 4 and 5 in [`CLAUDE.md`](../CLAUDE.md); authorization and privacy are in [`security.md`](security.md).

| Table | Purpose and key constraints |
|---|---|
| `users` | GitHub account snapshot. `github_id` bigint UNIQUE is the identity key; login, name and avatar are display snapshots only |
| `sessions` | Server-side sessions: hashed session id, expiry, CSRF secret |
| `installations` | GitHub App installation: `github_installation_id` UNIQUE, account id, login, type (`Organization`, `User` or `Other`, the last for an enterprise), `suspended_at`; `admission_status` (default `rejected`: a row nobody decided on is never evaluated), `admission_reason` (`account_not_allowed` or `policy_changed`), `admission_decided_at`, `deleted_at` (uninstall) and `last_synced_at` (set only when a sync writes). The runtime role has no DELETE or TRUNCATE on it |
| `repositories` | Installation, `github_repo_id`, `full_name` snapshot, `enabled`, active CLA document, `removed_at`. Unique (`installation_id`, `github_repo_id`) plus a partial unique index on `github_repo_id` where `removed_at` is null: a repository is active under at most one installation, and a transfer is a new row under the new tenant. `removed_at` is set by the sync, by an access-lost refresh, and by the new tenant's sync on another tenant's active row (a transfer; the only write into another tenant's row, `removed_at` alone plus an audit row under that tenant). The runtime role has no DELETE or TRUNCATE on it |
| `cla_documents` | Named CLA per installation or repo; kind is individual or corporate. `installation_id` and `kind` never change (trigger). The active version only moves forward: it must be the document's highest (major, minor) |
| `cla_versions` | Immutable once published (DB trigger): unique (document, major, minor), `content_md`, `content_sha256`, publisher, rationale, `published_at`. The document points at the active version; a rollback publishes a new version, never reactivates an old one (a trigger refuses to point at anything but the highest version). `published_at` must be within five minutes of the database clock |
| `signatures` | Immutable core: user id, version, text hash, consent text id, `signed_at` UTC, signer type, source repo and PR, plus `revoked_at`, `revoked_by`, reason (the only mutable columns; the reason is a code from a fixed set, never free text, because a revoked row can never be scrubbed). The document's kind must equal `signer_type` (composite foreign key), `revoked_at` cannot precede `signed_at`, and `signed_at` must be within five minutes of the database clock. Partial unique index on (user, document, major) where not revoked. The sign request carries the version id and hash, verified server-side |
| `signer_pii` | Erasable personal data for a signature: name, verified email and login snapshots. Split out so GDPR erasure never touches the immutable core |
| `commit_overrides` | Audited maintainer override per (repo, commit SHA); never implies a signature |
| `corporate_agreements`, `corporate_approvals` | Phase 2: company CCLA and manager-approved employees |
| `allowlist_entries` | Scope (installation or repo), kind (user, bot, org members), numeric GitHub id, never a login string. A `user` entry also covers `Organization` and `Mannequin` accounts by id, a `bot` entry covers `Bot` and `Unknown`, `org_members` covers only `User` and `Unknown` (never a bot); ties go to repository scope, then kind user, bot, org_members, then the lowest id |
| `pr_evaluations` | Unique (repo, PR number, head SHA): result, details, `check_run_id`, `comment_id`. `details` is written only by `toStoredDetails` (version 1, bounded lists, `omitted` counts), see [the evaluation engine](architecture.md#the-evaluation-engine) |
| `webhook_deliveries` | `delivery_id` PK for idempotency (GitHub reuses the id on redelivery), event, action, received and processed times. A row exists only for a delivery that starts a job (a ping or an ignored delivery inserts none) and holds no payload. `processed_at` is set by the job layer through `markDeliveryProcessed` (E07-S03) or, when a dedupe window dropped the send of a row just recorded, in the recording transaction; a live job under the same key leaves it null |
| `audit_log` | Append-only: actor numeric id, action, subject ids, metadata. **No personal data**: metadata is a flat object whose keys come from a fixed list and whose values are integers, booleans, null, lists of integers or lower-case codes (`audit_metadata_is_clean`); a new key needs a migration, see below |
| `pgboss.*` | Queue schema owned by pg-boss |

Immutability is enforced by DB triggers that block `UPDATE` (beyond the allowed columns), `DELETE` and `TRUNCATE`; the runtime DB role does not own the tables, so it cannot disable triggers. The identity columns the rest of the schema hangs on (`users.github_id`, `installations.github_installation_id` and `account_id`, `repositories.github_repo_id` and `installation_id`, `cla_documents.installation_id` and `kind`) cannot be updated either, although the runtime role may update the other columns of those tables: re-pointing a GitHub id would re-attribute every signature that references the row. Erasure goes through one audited SQL function (`erase_signer_pii`) that deletes the person's `signer_pii` rows and sessions, scrubs the display snapshot in `users` and keeps the minimal signature core (GDPR Art. 17(3)(e), legal claims). A `signer_pii` row cannot be stored for a signature that predates the person's erasure (trigger), so a signing request that was in flight during the erasure cannot write the data back. The acting administrator is a required argument; it is the caller's attribution, which the database cannot verify, and the audit row is append-only rather than hash-chained. Other text that is not signer data and is outside erasure: `installations.account_login` and `repositories.full_name` (public names of the maintainers' accounts and repositories; for a user-type installation that is the maintainer's own login) and `commit_overrides.reason` (a maintainer's note). `pr_evaluations.details` holds numeric ids and codes only: its strict schema in `src/shared/pr-evaluation-details.ts` leaves no field for a name, login or email, and `parseStoredDetails` never throws on an old or unknown row.

`migrations/001_initial.sql` creates every table above except `corporate_agreements`, `corporate_approvals` (phase 2) and `pgboss.*` (pg-boss creates its own schema). Tenant tables carry `installation_id` and tie it to their parent with composite foreign keys, so a row can never point at another tenant's repository or document. Two roles: the migration owner (`MIGRATION_DATABASE_URL`) owns the schema; the runtime role `cla_app` (`DATABASE_URL`) gets only the privileges it needs, granted by the migration when the role exists. The runner (`src/server/adapters/db/migrator.ts`) holds a session advisory lock, applies each file in its own transaction, records a SHA-256 checksum in `schema_migrations`, and refuses to run when an applied file changed, went missing or sorts before an applied one. bigint columns come back as JS numbers (GitHub ids are far below 2^53) and a value outside the safe range throws instead of rounding.

Audit metadata is an allowlist of 31 keys: the 12 of `migrations/001_initial.sql` plus 19 added by `migrations/002_audit_metadata_allowlist.sql`, which replaces `audit_metadata_is_clean` (`create or replace`; 001 is never edited, and rows already written are not re-checked). Values are integers, booleans, `null`, lists of at most 100 integers, or codes of 1 to 64 characters from `[a-z0-9_.:-]` that never look like an IP address (four dotted numbers with an optional port, or only hex digits, dots and at least two colons). The writer also caps the serialised metadata at 2,048 bytes; the database does not check that. The key list is `AUDIT_METADATA_KEYS` in `src/shared/audit.ts` and the value rules are in `src/shared/audit-metadata.ts`. A new key needs a new forward-only migration that replaces the function again plus the constant: `migration-002-audit-metadata.test.ts` compares the key list of the newest migration that defines the function with the constant and fails until both agree, and a shared case table (`src/shared/test-support.ts`) keeps the SQL and zod value rules equal. Personal data (`name`, `email`, `login`, `avatar_url`) and free text (`reason`, `message`, `title`, `text`) are never keys. Migration numbers go in merge order: another branch that adds a migration with the same number renumbers whichever merges second.

The audit actions the installation lifecycle writes are all system actions (actor null, tenant-scoped, subject `installation` with the GitHub installation id, or `repository` with the GitHub repo id; never a name or login): `installation.admitted` (metadata `account_id`, `account_type`), `installation.rejected` (`account_id`, `account_type`, `reason_code` of `account_not_allowed` or `policy_changed`), `installation.updated` (`account_id`, `account_type`; the account snapshot changed in a way no other row records), `installation.deleted` (`account_id`, `account_type`, `count`), `installation.suspended` and `installation.unsuspended` (`account_id`, `account_type`), `repository.added` and `repository.renamed` (no metadata) and `repository.removed` (`reason_code` of `not_listed`, `access_lost` or `transferred`); `account_type` is the lower-case code `organization`, `user` or `other`. These needed no new metadata key.

Revocation is prospective: `revoked_at` marks the signature invalid for *future* PRs; contributions already accepted stay licensed. Network metadata (IP, user agent) is **off by default**; if enabled it needs a documented legitimate interest and short retention (Art. 5(1)(c), 5(1)(e)).
