# GitHub App

The permissions, events and check name of the GitHub App, and the rules for changing them. A story that changes the permission or event set updates this file in the same change (hard rule 10 in [`CLAUDE.md`](../CLAUDE.md)).

## Settings

| Setting | Value |
|---|---|
| Repository: Metadata | read (implicit) |
| Repository: Pull requests | read and write (list PRs and commits, post the comment) |
| Repository: Checks | write (Check Runs, receive `check_run.rerequested`) |
| Repository: Issues | read (receive `issue_comment` for `/recheck`) |
| Repository: Merge queues | read (receive `merge_group` events, E22-S01; optional: until an organisation owner accepts it no `merge_group` event arrives and pull request checks are unaffected) |
| Organization: Members | read (private membership for the org-member exemption, and the members probe that gates an `org_members` allowlist entry) |
| Account: Email addresses | read (verified emails at login, user token only) |
| Events | `pull_request` (opened, reopened, synchronize, edited, ready_for_review, closed), `check_run` and `check_suite` (rerequested: single and "Re-run all checks"), `issue_comment` (created only; handled when it is on a PR, the sender is not a Bot, and a line is exactly `/recheck`; rate-limited per PR), `merge_group` (checks_requested is evaluated, destroyed is recorded and ignored, any other action is ignored); `installation`, `installation_repositories` and `github_app_authorization` always arrive |
| Check name | `license/cla`, constant. Renaming breaks required-check rules. CLA Assistant posts a legacy status with the same context, and a same-named check and status must both pass: migrating repos must disable CLA Assistant first (or use a distinct check name for them). See [legacy-status-coexistence.md](legacy-status-coexistence.md). |
| Branch protection | Pin the required check to this app (ruleset `integration_id`) |

Gotchas worth remembering: the required check must have reported within 7 days to be selectable; passing conclusions are `success`, `skipped`, `neutral`; webhook response budget is 10 s so handlers only verify, dedupe and enqueue; installation tokens give 5,000 requests/hour (more on larger installs) so every request goes through the platform's own rate limiter (below), which honours `retry-after`.

## Rules

- Minimum permissions are in the table above. Do not add permissions without a reason recorded in that table.
- User tokens (`ghu_`) expire in 8 h and refresh tokens are single-use. We do not store them: the login uses a user token once, at the callback, and revokes it, so the App's expiring-token setting does not matter (refresh fields in the answer are parsed and dropped).
- The App's **Callback URL** must be `callbackUrl(config)` (`src/server/config/auth.ts`), that is `PUBLIC_BASE_URL` plus `/api/auth/callback`; the login sends the same value as `redirect_uri`, and the setup kit (E19) reuses the function. The login requests no scopes: a GitHub App's permissions come from the App.
- The App is created from a manifest (E19-S06) built by `buildAppManifest` (`src/server/domain/app-manifest.ts`) from `APP_PERMISSIONS`, `INSTALLATION_PERMISSIONS` and `APP_EVENTS` (`src/shared/github-app.ts`), never from literals; `setup-manifest-docs.test.ts` parses the Settings table above (the rows that start `Repository:`, `Organization:` and `Account:`, and the Events row up to its `; installation` clause), so keep that format when a row changes. The manifest's webhook is inactive when `PUBLIC_BASE_URL` is not `https` (GitHub cannot reach it), and the App is public only when the operator ticks "Let other organisations install this App" (`allowOtherAccounts`).
- Installation tokens: 1 h. App JWT: max 10 min; ours is RS256 with `iss` the App id as a string, `iat` now minus 60 s and `exp` now plus 540 s, reused for under 5 min. The mint (`POST /app/installations/{id}/access_tokens`) sends no body, so the token has the installation's full permissions; a 403 whose message says suspended maps to `InstallationSuspendedError` (verify the wording on a real suspended installation).
- Rate limits are handled by the platform's limiter (E05-S05), per installation: a 429, or a 403 with `retry-after` or `x-ratelimit-remaining: 0`, waits up to 60 s (twice); a longer wait raises `GitHubRateLimitedError { retryAfterSeconds, scope }` for the job layer. At most 10 requests are in flight per installation and 50 overall (GitHub allows 100), writes (the token mint included) start at least 1 s apart per installation, and a bucket of 900 points a minute per lane charges 1 for a read and 5 for a write.
- The members probe (E14-S05) is `GET /orgs/{org}/members?per_page=1` with the installation token (Members: read); the org is `account.login` of `GET /app/installations/{id}`. It answers `true` on a `200` and `false` on a `403` that is not a rate limit, is never cached and never uses `public_members`; a rate limit throws `GitHubRateLimitedError`, a 5xx, the 5 s timeout and a network error throw `GitHubUnavailableError`, a body of another shape throws `GitHubResponseError`, and an account that is not an organisation throws `GitHubNotFoundError`. The allowlist form runs it before it accepts an `org_members` entry and answers `422 members_permission_missing` when it is `false`.
- A login typed into the allowlist form is looked up with `GET /users/{login}` and the installation token (E14-S06): the login must have the shape of a GitHub login before any request is made, the segment is URL-encoded, and the answer is read with a schema (a positive integer `id`, a login of the same shape, a `type` of `User`, `Bot` or `Organization`), so a response with markup cannot reach the stored snapshot. A `404` is `422 github_account_not_found`, a rate limit is `503 github_rate_limited`, any other failure `502 github_unavailable`.
- A check and a commit status with the same name must both pass; we only create Check Runs. CLA Assistant posts a legacy status with context `license/cla`: repos migrating from it must disable it first, or use a distinct check name.
- Merge queues (E22-S01): a repository with a merge queue and a required `license/cla` check waits for the check on the head SHA of the merge group, so the App subscribes to `merge_group` and the permission "Merge queues: read". The permission is optional by nature: GitHub asks the organisation owner to accept it (an existing installation gets a prompt), and until then no `merge_group` event arrives and the checks of pull requests are unaffected. The webhook route records the delivery and enqueues `evaluate-merge-group` without asking GitHub anything: `checks_requested` becomes the job, `destroyed` is recorded as processed and marks the evaluation of the group destroyed (creating its row when no job has yet, so a job that runs after the group was taken down writes nothing), and any other action is a `202 ignored`. The job writes the Check Run `license/cla` on `merge_group.head_sha`, never on the head SHA of a member pull request. A repository whose enforcement is off is not evaluated (`skipped:repository_disabled`, no check is written), so a queue that requires the check there waits: switch enforcement on, or take the check out of the ruleset. A group whose pull requests cannot be determined (none found, more than 25) fails with "Could not determine the pull requests in this merge group". A group whose job died is failed with the hint to remove the pull request from the queue and add it again, since `/recheck` cannot be typed on a group.
- The public signature check (E22-S02) uses the same call: `GET /users/{login}` with the installation token of the repository's installation resolves the login someone asks about to its numeric id (case-insensitive; a `404` is a login nobody has, and the answer is `false`), and the answer is read with the schema of the allowlist form. The result, a miss as well as a hit, is cached in the process for 10 minutes under the lower-cased login, and the lookups that go to GitHub are limited to 30 a minute per installation, so the public endpoint cannot use up the rate limit that the evaluation jobs of the installation share. A `403`, a `429`, a `5xx` or an answer that is not an account makes the endpoint answer `503 upstream_unavailable` with `Retry-After` and is never cached.
- Corporate CLAs (E21): the `GitHubClient` port gained `getOrganizationAccount` (`GET /orgs/{org}`, the numeric id and type of an organisation a CLA manager approves) beside the existing user lookup, and the claim asks `GET /orgs/{org}/public_members/{username}` (204 means a public member); both use the installation token and need no new permission. A failure of either is told as `503 upstream_unavailable` with `Retry-After`. When an author is covered by a corporate approval, the Check Run summary and the pull request comment say "covered by a corporate CLA" and print no company, domain or organisation login, and an author uncovered only because the agreement is of an earlier major is told to ask the CLA manager to sign the current version.
- Checks must be reported on the latest head SHA. "Re-run all checks" sends `check_suite.rerequested`, a single re-run sends `check_run.rerequested`: handle both (Checks: write covers them).
- Webhook settings: the URL is `<PUBLIC_BASE_URL>/webhooks/github`, the content type must be `application/json` (form-encoded gives `415 webhook_unsupported_media_type`), and the secret is `GITHUB_WEBHOOK_SECRET` (rotate it by setting the new one, keeping the old one as `GITHUB_WEBHOOK_SECRET_PREVIOUS` until `webhook.secret_previous_used` stops). A delivery naming another App through `X-GitHub-Hook-Installation-Target-ID` or `-Type` gives `400 webhook_wrong_app`. The `Events` row above is the source of `SUBSCRIBED_EVENTS`: `webhook-events-docs.test.ts` parses it (event names in backticks), so keep that format.
- Webhook answers: `200 {status:'pong'}` for `ping`; `202 {status:'accepted'}` for a recorded delivery and `200 {status:'duplicate'}` for one recorded before; `202 {status:'ignored', reason}` for a delivery that starts no job, with the reasons of the routing table plus `installation_not_admitted`, `installation_deleted`, `installation_suspended`, `installation_unknown` and `repository_installation_mismatch` (the last two also start a `sync-installation` job); `429 webhook_throttled` and `503 webhook_timeout` (8 s deadline). With the job queue down or not migrated a delivery that starts a job gets `503 webhook_enqueue_failed`, and a redelivery from the App's Advanced tab requeues it once the queue is up.
- Roles (E11) are read with the installation token and numeric ids: `GET /orgs/{org}/memberships/{username}` (Members: read) and `GET /repos/{owner}/{repo}/collaborators/{username}/permission` (Metadata: read). A 403 that is a rate limit (`retry-after` or `x-ratelimit-remaining: 0`) is a rate limit; any other 403 is a missing permission, logged as `members_permission_missing` or `repository_permission_missing` with the numeric installation id, and resolves as not admin. The public-members endpoints are never used. A renamed repository or login answers 404 and fails closed until the next sync or login.
- Supporting PR comments needs only Pull requests: write; `issue_comment` events need Issues: read. The `recheck-comment` job fetches the comment again (`getIssueComment`, Issues: read, already listed); the Re-run of a check lists `GET /repos/{owner}/{repo}/commits/{sha}/pulls` (Pull requests: read); the sweep lists `GET /repos/{owner}/{repo}/pulls?state=open` (Pull requests: read). To verify on the real App: that GitHub lists a fork pull request for the SHA of its fork head.
- The evaluation reports through the `EvaluationReporter` port (`started`, `publish(target, evaluation, names)`, `failed`, `cancelled`, `enforcementDisabled`; `ReportTarget` names the repository, pull request, head SHA, trigger and the `pr_evaluations` row, and `DisplayNames` the logins and trailer names the job fetched, which one report uses and nothing stores). `CheckRunReporter` (`services/reporting/`) implements it and `boot-evaluation.ts` binds it whenever a GitHub App is configured. The Check Run belongs to the head SHA. This App's run is found in the listing `GET /repos/{owner}/{repo}/commits/{sha}/check-runs?check_name=license%2Fcla&filter=latest` (a run of another App with the same name never counts), created with `POST /repos/{owner}/{repo}/check-runs` and updated with `PATCH`, and a `PATCH` answered 404 or 422 creates a new run. Whether GitHub accepts a `PATCH` on a completed run is unverified against the real App (a maintainer step: the result goes in the pull request); the fallback keeps the check correct either way. A 422 is the adapter's `GitHubUnprocessableError`: the write is repeated once with the minimal output (the counts and the `/recheck` hint, no names), and a second 422 is a `ReportRejectedError`. A 403 on a Check Run call means Checks: write is missing: it is logged `checks_permission_missing` and is a `ReportRejectedError`.
- The Check Run calls use Checks: write only. `failed` completes the run as `failure` with the `/recheck` hint; `cancelled` completes a running run as `cancelled`, unless another open pull request stands at the same head SHA, in which case the run is left to it or completed with what the remaining rows say; `enforcementDisabled` completes it as `neutral`. All are idempotent, because the job calls them again on a retry.
- The pull request comment (E09-S07) needs Pull requests: write only, reads included: the search for the comment of the platform lists `GET /repos/{owner}/{repo}/issues/{n}/comments` (up to 5 pages of 100, oldest first); a comment is the platform's only when it begins with the marker and GitHub says it was posted through this App; it is created with `POST` (a failure only) or edited with `PATCH /repos/{owner}/{repo}/issues/comments/{id}`. A 403, 404 or 422 on the comment costs the comment only (`comment_skipped`). The rule for pull requests that share a head SHA asks `GET /repos/{owner}/{repo}/commits/{sha}/pulls` (Pull requests: read) which of them are open at the SHA. No new permission.
- Octokit calls time out after 5 s per attempt (GETs repeat twice after 1 s and 2 s) and the self-check and token requests after 10 s. A missing Members: read permission resolves as `permission_missing` (the author is not exempt: fail closed) and logs `members_permission_missing` with the numeric installation id.
- A per-commit override (E15-S05) checks that the commit exists in the repository with `GET /repos/{owner}/{repo}/commits/{ref}` and the installation token (`getCommit`, 5 s deadline); a `404` or `422` is `commit_not_found`, a rate limit `503 github_rate_limited`, any other failure `502 github_unavailable`. Open verification: GitHub documents this call under Repository: Contents: read, which is not in the table above. Check it on the real App before the first override is recorded: a missing permission is a `403` that is told as `502 github_unavailable`, not as a permission problem. The table stays as it is until it is confirmed.
- A revocation (E15-S03) is a re-evaluation trigger like a signature: the `evaluate-pr` jobs it sends carry the trigger `signature`, and above 100 pull requests the `sweep-repository` job carries the reason `signature_revoked`; an override recorded or removed sends the trigger `policy_change` and the reason `override_changed`, and the invalidation of a major the reason `signatures_invalidated`. None of them calls GitHub itself; the jobs read the pull request when they run.
- The App supports multiple private keys: deploy the new key before deleting the old one.
- Start-up checks the identity with `GET /app` (owner id and type, slug, permissions), keeps the owner id for the admission policy and compares the id with `GITHUB_APP_ID`. The slug is also what the public `GET /api/meta` (E17-S09) builds `installUrl` from (`https://github.com/apps/<slug>/installations/new`), read at each request because the check can succeed after the server is listening.
- Recommended visibility: Only on this account. For a public App, the instance admission policy (`GITHUB_ALLOWED_ACCOUNT_IDS`) is the second line; see [`operations.md`](operations.md).
- The sync warns (`installation.permissions_missing`) when an installation's `permissions` object lacks one of the minimum permissions above, by their API keys: `metadata`, `pull_requests`, `checks`, `issues`, `members`. The names follow GitHub's REST documentation and are unverified against a real installation payload.
- The noreply email form (`ID+login@users.noreply.github.com` for accounts created after 2017-07-18, legacy `login@users.noreply.github.com` for older ones, which names no id and is never resolved) was checked against GitHub's documentation on 2026-11-02, and the `web-flow` committer is account id 19864447 (`GET /users/web-flow`, same day); the evaluation engine relies on both (E08-S02, E08-S06).
