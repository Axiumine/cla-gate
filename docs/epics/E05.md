# E05 — GitHub App core

**Bounded Context:** BC-05
**Priority:** 🔴 Must have
**Status:** ⬜ Todo

**Goal:** One platform instance authenticates as one GitHub App and serves several GitHub orgs and accounts, each installation being a separate tenant keyed on its numeric installation id. Only accounts the operator admits are served; every other installation is recorded as rejected and never touched.
**Depends on:** E04
**Out of scope:** Webhook transport, HMAC and event routing (E06). Job queue, handler registration and the scheduled sweep that calls the reconciliation here (E07). PR, commit, Check Run and comment client methods (added to the port by E07 and E09). Login, user tokens and `GITHUB_CLIENT_*` (E10). The HTTP route and authorisation for toggling `enabled` (E14) and for the operator view of installations (E11 role check, E18 screen). GitHub Enterprise Server (github.com only). Automatic uninstall of rejected installations. Re-attaching documents and signatures of a deleted installation to a later installation of the same account (not done: a new installation is a new tenant).

**E05-S01 — GitHub App configuration and private key set** ⏳ In progress
Turns the optional GitHub placeholders from E04 into validated settings: the App id, the signing key and an optional previous key for rotation.
Acceptance criteria:
- `loadConfig` requires `GITHUB_APP_ID` (digits only, 1 to 20) and `GITHUB_APP_PRIVATE_KEY` when `NODE_ENV=production`. In `development` and `test` both stay optional and the GitHub adapter is simply not constructed when either is absent, so the E04 boot test and health routes still start without GitHub credentials.
- `GITHUB_APP_PRIVATE_KEY_PREVIOUS` is optional. It is the key kept during rotation (S02). Setting it equal to `GITHUB_APP_PRIVATE_KEY` is a `ConfigError` naming only the variable.
- A key is PEM, PKCS#1 (`-----BEGIN RSA PRIVATE KEY-----`) or PKCS#8 (`-----BEGIN PRIVATE KEY-----`), with real newlines or literal `\n` sequences (env files and `--env-file` cannot hold newlines). It is parsed once with `crypto.createPrivateKey`; anything that is not an RSA key of at least 2048 bits is a `ConfigError` naming the variable, never the value.
- Keys are held as `Secret` (E04): `String()`, template literals, `JSON.stringify`, `util.inspect` and pino all print `[REDACTED]`. Only the signer calls `reveal()`.
- Each key has a fingerprint in GitHub's display format: `SHA256:` plus base64 of the SHA-256 of the DER-encoded public key (verify once against the value on the App settings page). The fingerprint, never the key, appears in logs.
- The `docs/configuration.md` table gains `GITHUB_APP_PRIVATE_KEY_PREVIOUS` and states which GitHub variables are required in production, in the same change (hard rule 10).
- Test keys are generated at test time with `crypto.generateKeyPairSync`; no key material is committed (hard rule 7, Trivy secret scan).
- Table tests cover: missing id, non-numeric id, id of 21 digits, PKCS#1 and PKCS#8 keys, escaped-newline key, 1024-bit key, EC key, truncated PEM, equal current and previous key.
- Open: the fingerprint follows the documented `openssl` recipe (SPKI DER, SHA-256, base64; the test pins the format and it was compared once with the `openssl` command line) and is logged at start-up (`github.app_configured`), but the comparison with the value on the real App settings page needs the real App: the maintainer compares the logged fingerprint of the production key with the settings page, then marks this story done.

**E05-S02 — App JWT, key rotation and App identity check** ✅ Done
Acceptance criteria:
- `AppAuth.createJwt()` signs RS256 with `node:crypto` only (no JWT library). Header `{"alg":"RS256","typ":"JWT"}`; claims `iss` = the App id, `iat` = now minus 60 s, `exp` = now plus 540 s (GitHub's ceiling is 10 minutes, so `exp - iat` is 600 s at most). `iat` and `exp` are integer seconds. Time comes from an injected `Clock` port.
- A signed token verifies against the public half of the key in the test (`crypto.verify`), and a test pins the exact claims with a fixed clock. A JWT is reused for at most 5 minutes, then re-minted.
- Rotation: the key list is ordered (current, then previous). When GitHub answers an App-authenticated request with 401, the request is retried once with the next key. The key that worked is promoted for later calls and one WARN `github.app_key_fallback` carries the fingerprint of the key now in use. If every key is refused the call fails with `GitHubAuthError`.
- Start-up self-check: `GET /app` with a JWT. The returned `id` must equal `GITHUB_APP_ID`, otherwise start-up fails with an error naming `GITHUB_APP_ID`. `owner.id`, `owner.type`, `slug` and `permissions` are kept as the verified App identity (the owner id feeds the admission policy, S07).
- A 401 at the self-check is fatal in production. A network failure or 5xx at the self-check is not: the instance logs a WARN, starts, and repeats the check lazily on the first GitHub use, so a GitHub outage does not stop a restart.
- The JWT and the PEM never appear in an error message, log line or thrown cause. A test captures all log output of a failing rotation and greps for both.
- MSW tests at the HTTP boundary cover: current key accepted, current refused and previous accepted (promotion sticks, second call signs with the promoted key), both refused, id mismatch, owner missing from the response.

**E05-S03 — Installation token provider** ✅ Done
Acceptance criteria:
- `InstallationTokens.get(githubInstallationId)` mints a token with `POST /app/installations/{id}/access_tokens` (App JWT, no body, so the token carries the installation's full permissions). The response is parsed with zod: `token` (non-empty string) and `expires_at` (ISO datetime).
- Tokens are cached in memory per `github_installation_id` and refreshed when less than 5 minutes remain, so a 1 hour token is reused for about 55 minutes. A fake-clock test: requested at T and T+54 min gives one POST; requested at T+56 min gives a second.
- Single flight: 50 concurrent `get` calls for one installation produce exactly one POST (MSW handler with an artificial delay). Calls for two installations never wait on each other.
- Failures are not cached. A 404 raises `InstallationGoneError` and drops the entry. A 403 saying the installation is suspended raises `InstallationSuspendedError`. A 401 triggers the key fallback of S02 and then `GitHubAuthError`. A 5xx or network error raises `GitHubUnavailableError` after the retry rule of S04.
- `invalidate(githubInstallationId)` drops the entry. The client (S04) calls it when a request made with a cached token returns 401 and repeats that request once with a fresh token.
- The cache is bounded at 1,000 entries, expired entries evicted first. Tokens are never persisted (no column, no file) and never logged. A test runs a full mint-and-use cycle with pino output captured and asserts neither the token string nor the `ghs_` prefix appears.
- The provider takes an `InstallationGate` port (implemented in S07). With no gate wired it refuses every id, so a missing wiring fails closed.

**E05-S04 — GitHub client port, Octokit adapter and in-memory fake** ✅ Done
The only door to GitHub for the services. Later epics extend it; this story ships the methods the installation lifecycle needs.
Acceptance criteria:
- The port lives in `src/server/services/ports/github.ts` and the adapter in `src/server/adapters/github/`. `src/server/domain` and `src/shared` never import them (ESLint `no-restricted-imports` and Knip).
- Methods: `getApp()`, `getInstallation(githubInstallationId)` (resolves `null` on 404), `listInstallations()`, `listInstallationRepositories(githubInstallationId)`, `getRepositoryById(githubInstallationId, githubRepoId)` (resolves `null` on 404 or 403), `getOrgMembership(githubInstallationId, org, login)` (resolves `null` on 404; the zod schema keeps `state`, `role` and `user.id`). Calls are `GET /app`, `GET /app/installations/{id}`, `GET /app/installations?per_page=100`, `GET /installation/repositories?per_page=100`, `GET /repositories/{id}` and `GET /orgs/{org}/memberships/{username}` (Members: read). The membership call is the single adapter call that the exemption lookup (E07-S10) and the admin role (E11-S02) both reuse; no later epic adds a second one.
- Every response goes through a zod schema in `src/server/adapters/github/schemas.ts` that keeps only the fields used (ids, `login`, `type`, `full_name`, `suspended_at`, `permissions`). Account types other than `User` and `Organization` fail validation. A failure raises `GitHubResponseError` carrying the route template and the zod issue paths, never the body.
- Built on the `octokit` package (MIT, ESM only) with its retry plugin registered (set to no retries, because the adapter's own rule below decides) and its throttling plugin switched off since E05-S05 (the plugin keeps one set of limits per Octokit instance, the platform's are per installation, `rate-limiter.ts`); the dependency is justified in the PR (hard rule 8) and Knip stays clean. Requests send `User-Agent: cla-gate/<package version>` and `X-GitHub-Api-Version: 2022-11-28`.
- Pagination follows `Link: rel="next"` at 100 per page and stops at 100 pages. Past that it raises `GitHubResponseError` (`pagination_limit`) and never returns a silently truncated list, because a truncated repository list would mark repositories as removed.
- Error mapping: 401 `GitHubAuthError`, 404 `GitHubNotFoundError`, other 403 `GitHubForbiddenError`, 5xx and network `GitHubUnavailableError`. Only idempotent GETs are retried: 502, 503, 504 and network errors twice with 1 s and 2 s backoff plus up to 250 ms jitter. Non-GET requests are never retried by the adapter (E09 owns write idempotency).
- `FakeGitHub` in `src/server/services/test-support.ts` implements the port in memory, with scriptable installations and repositories and a recorder of every call (method, installation id). One shared contract suite runs against the fake and against the Octokit adapter backed by MSW.
- Extension rule recorded in a header comment: later epics add methods with their own zod schemas; no method returns a raw Octokit response.

**E05-S05 — Rate limits, secondary limits and retry-after** ✅ Done
Acceptance criteria:
- A 429, or a 403 carrying `retry-after`, waits that many seconds and repeats the request, at most twice, when the wait is 60 s or less. A longer wait raises `GitHubRateLimitedError { retryAfterSeconds, scope }` at once, without sleeping (the job layer, E07-S03, decides the retry).
- A 403 or 429 with `x-ratelimit-remaining: 0` waits until `x-ratelimit-reset` (epoch seconds) under the same 60 s rule, scope `primary`. A secondary-limit 403 without `retry-after` is treated as a 60 s wait. A 403 that is neither (a permission error) is `GitHubForbiddenError` and is not retried.
- Rate-limit state is kept per installation. When an installation is limited, requests of another installation are not delayed. A test with two installations asserts it.
- At most 10 requests are in flight per installation and 50 overall (GitHub allows 100 concurrent). A test fires 100 GETs and asserts the observed maximum in the MSW handler.
- Mutating requests (POST, PATCH, PUT, DELETE) to one installation are spaced at least 1 s apart. A conservative token bucket of 900 points per minute per installation charges 1 point per read and 5 per write.
- Each wait logs one WARN `github.rate_limited` with scope, wait seconds, the route template and the numeric installation id. No token, URL query or body is logged.
- Fake-timer tests cover: `retry-after: 2` succeeds after 2 s with two requests in total, `retry-after: 120` rejects immediately with `retryAfterSeconds: 120`, `x-ratelimit-reset` in 10 s and in 600 s, three consecutive 429s ending in `GitHubRateLimitedError`, and the 1 s write spacing.

**E05-S06 — Installation and repository state tables** ✅ Done
Acceptance criteria:
- One new forward-only migration (001 is never edited) adds to `installations`: `admission_status text not null default 'rejected'` with check in (`admitted`, `rejected`), `admission_reason text` with check null or in (`account_not_allowed`, `policy_changed`), `admission_decided_at timestamptz`, `deleted_at timestamptz` and `last_synced_at timestamptz`. The default is `rejected`, so a row inserted without a decision can never be evaluated.
- The same migration adds `repositories.removed_at timestamptz`, replaces the global `unique (github_repo_id)` by `unique (installation_id, github_repo_id)` plus a partial unique index on `github_repo_id` where `removed_at is null`. A repository is active under at most one installation, and a transfer can create a new row without touching the old tenant's row.
- Nothing is deleted: the runtime role `cla_app` keeps no DELETE on `installations` and `repositories`, so uninstall sets `deleted_at` and removal sets `removed_at`. A real-role test asserts a DELETE is refused. The migration weakens no immutability trigger, grant or foreign key of 001; the only constraint it relaxes is the global uniqueness above, which the partial index narrows instead of dropping.
- `src/server/adapters/db/schema.ts` is updated and `schema.test.ts` stays green against the live catalog. Existing tests of migration 001 pass unchanged.
- Repository functions (`upsertInstallation`, `findInstallationByGithubId`, `upsertRepositories`, `markRepositoriesRemoved`, `findActiveRepositoryByGithubId`) take the installation id and filter every query by it. Cross-tenant tests: with installations A and B each holding a repository, no function called with A's id returns or changes B's rows.
- `setRepositoryEnabled(installationId, githubRepoId, enabled, actorGithubId)` updates `repositories.enabled` and appends an `audit_log` row (`repository.enabled` or `repository.disabled`, `subject_type` `repository`, `subject_id` the GitHub repo id, metadata `{ repository_id, document_id }` with `document_id` only when enabling) through the E04-S09 writer, in the caller's transaction or its own when none is passed. It returns `{ changed }`, and E14-S03 and E14-S04 call it instead of writing the update and the audit row themselves. A removed or unknown repository raises `RepositoryNotFoundError`. A no-change call writes no audit row. New repositories are inserted with `enabled = false`. The route and role check are E14.
- Pure `evaluationEligibility(installation, repository)` in `src/server/domain/eligibility.ts` returns `{ eligible: true }` or `{ eligible: false, reason }` with `reason` one of `installation_rejected`, `installation_deleted`, `installation_suspended`, `repository_removed`, `repository_disabled`, checked in that order. A table test covers every combination of the five flags (32 rows).

**E05-S07 — Instance admission policy** ⬜ Todo
Decides which GitHub accounts this server serves. The instance serves several orgs; this is the operator's allowlist for them.
Acceptance criteria:
- `GITHUB_ALLOWED_ACCOUNT_IDS` is a comma-separated list of positive integers (whitespace trimmed, duplicates collapsed, at most 100). A login, a negative number, `0` or a value above `Number.MAX_SAFE_INTEGER` is a `ConfigError` naming the variable. Identity is the numeric account id, never a login.
- The effective policy is the configured ids plus the App owner's id from the S02 self-check. Unset or empty means the owner account only. There is no wildcard: opening a server to every account is not supported. Changing the list needs a restart, and the start-up log prints the effective ids.
- Pure `decideAdmission(accountId, policy)` in `src/server/domain/admission.ts` returns `{ admitted: true }` or `{ admitted: false, reason: 'account_not_allowed' }`. Table tests include the owner id, a listed id, an unlisted id, `0`, `-1`, `NaN`, a float, and an id given as a string (all refused).
- A rejected installation is stored as `admission_status = 'rejected'` with the reason and `admission_decided_at`, one `audit_log` row `installation.rejected` (`actor_github_id` null for the system, metadata `{ account_id, account_type, reason_code }`), and one WARN log line with the same numeric fields. It gets no `repositories` rows.
- Defence in depth: the `InstallationGate` consumed by S03 reads the stored row and refuses rejected, deleted, suspended and unknown installations before any HTTP call, raising `InstallationNotAdmittedError(reason)`. A test calls every installation-level port method for a rejected installation, asserts it throws, and asserts MSW saw no request and `FakeGitHub` recorded no call. No PR data is read and no Check Run or comment is created for a rejected installation.
- `listInstallationsForOperator()` returns for each installation: GitHub installation id, account id, account login (display snapshot), account type, admission status and reason, decided, suspended and deleted times, and repository counts. No personal data. This story ships no HTTP route: E11 owns the operator role check and E18 the screen.
- `docs/operations.md` documents multi-org operation: the recommended setup (App visibility "Only on this account" so GitHub refuses other accounts), that this policy is the second line for a public App, and the variable.

**E05-S08 — Installation lifecycle sync and reconciliation** ⬜ Todo
Acceptance criteria:
- `syncInstallation(githubInstallationId)` re-fetches state from GitHub and never trusts an event payload. It is idempotent: a second run on unchanged state writes no row and no audit entry.
- Steps. (1) `getInstallation`: a 404 marks an existing row `deleted_at` and all its repositories `removed_at`, appends `installation.deleted`, and keeps every row (signatures are retained); with no row it does nothing. (2) Upsert the account snapshot (account id, login, type, `suspended_at`). (3) Apply the S07 decision. A rejected installation stops here, with no repository listing and no token request.
- A suspension (`suspended_at` becomes non-null) appends `installation.suspended`; the repositories are not listed. An unsuspension appends `installation.unsuspended` and continues to the repository step.
- Admitted and active: list repositories and reconcile in one transaction. New ids are inserted with `enabled = false` (`repository.added`). Known ids get `full_name` refreshed. A repository previously removed and now listed has `removed_at` cleared (`repository.added`). A stored repository missing from the list gets `removed_at` set (`repository.removed`). A listing that raises (including `pagination_limit`) changes nothing.
- A per-installation advisory lock (`pg_advisory_xact_lock`) serialises concurrent syncs. A real-Postgres-only test runs 10 concurrent syncs of one installation and ends with one consistent row set and one audit row per transition.
- `reconcileInstallations()` pages `GET /app/installations` and runs `syncInstallation` for each. A stored, non-deleted installation absent from GitHub's list is confirmed with `getInstallation` and, on 404, marked deleted. It runs once in the background after start-up and E07-S08 calls it on every sweep. It also re-applies the admission policy to every installation: a newly allowed account becomes admitted and is synced; a no-longer-allowed account becomes rejected with reason `policy_changed`, each with its audit row.
- Missing permissions: when the installation's `permissions` lack any minimum from the `docs/github-app.md` table (`metadata` read, `pull_requests` write, `checks` write, `issues` read, `members` read), one WARN `installation.permissions_missing` lists the permission names. It does not block the sync (verify the key names against a real installation payload).
- Cross-tenant tests: a sync of installation A never creates, changes or removes a row of installation B, including when both listings contain the same repository id (the transfer case is S09). A 2,500-repository sync stays in one transaction with batched upserts of at most 500 rows.
- Job registration of `sync-installation` is E07-S03. This story ships the service and its tests against `FakeGitHub` and PGlite.

**E05-S09 — Repository rename, transfer and removal** ⬜ Todo
Acceptance criteria:
- `refreshRepositorySnapshot(githubInstallationId, githubRepoId)` calls `getRepositoryById`, updates `full_name` when it changed (rename, or owner change after a transfer) and appends `repository.renamed` with the numeric ids only, since names stay out of the audit log. A 404 or 403 sets `removed_at`. Calling it again changes nothing.
- No `repository` webhook subscription is added, so the `docs/github-app.md` Events row stays unchanged. Snapshots refresh through S08 (every sync and reconciliation), E07-S04 (the evaluation job re-fetches the repository and calls this function when the name differs) and the E07-S08 sweep.
- Transfer between two admitted tenants on this server: installation A's sync marks the repository removed under A. Installation B's sync inserts a new row under B, `enabled = false`, with no CLA document, allowlist, overrides or signature visibility. A's rows, documents and signatures stay under A, immutable. A cross-tenant test asserts B's queries never return A's rows.
- If B's sync runs before A's, the same transaction first sets `removed_at` on the other tenant's active row for that GitHub repo id and appends `repository.removed` (metadata `reason_code` `transferred`) under A, then inserts B's row. This is the only statement that writes another tenant's row. It touches `removed_at` alone and is covered by its own test, and only a repository listed by GitHub in B's own installation can trigger it.
- A transfer to an account that is rejected by the admission policy leaves the repository removed under the old tenant and unsynced anywhere else; no evaluation runs for it.
- `findActiveRepositoryByGithubId` returns at most one row (the partial unique index guarantees it) and `null` when every row is removed. A rename keeps the `repositories` row, its `pr_evaluations` and its Check Run name `license/cla`.
- Tests: rename, rename plus transfer in one step, access lost (404), access lost (403), removal then re-add under the same installation (`removed_at` cleared, `enabled` unchanged), and both orders of the two-tenant transfer.
