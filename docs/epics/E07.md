# E07 — Job queue, concurrency and reconciliation

**Bounded Context:** BC-04
**Priority:** 🔴 Must have
**Status:** ⬜ Todo

**Goal:** Every accepted delivery becomes a job that runs exactly one evaluation at a time per (repo, PR), always against fresh GitHub state, and can never leave a Check Run stuck `in_progress`. Missed deliveries are caught by a scheduled sweep.
**Depends on:** E04, E06
**Out of scope:** Writing the Check Run and the PR comment (E09; this epic calls an `EvaluationReporter` port). The decision rules (E08; this epic builds the facts and calls the evaluator). Installation and repository sync logic (E05-S08, E05-S09; the handler here only calls it). Session revocation handler (E10). Re-evaluating a contributor's open PRs after they sign (E13 enqueues `evaluate-pr` with trigger `signature`). Pruning `webhook_deliveries` (the MVP keeps the rows; E22-S04 owns the purge) and the retention of finished pg-boss jobs (set by the queue options of E07-S05). Redis or any second queue system.

**E07-S01 — pg-boss runtime on Postgres and the transactional producer** ✅ Done
Acceptance criteria:
- `pg-boss` is added with its justification (hard rule 8), pinned exactly after `yarn npm info pg-boss version`, MIT licence. No Redis. The queue lives in the `pgboss` schema of the same database.
- Schema and queues are created by the migration owner. `yarn db:migrate` (E04) gains a second step after the SQL files: pg-boss's own schema migration and `createQueue` for every name in a `QUEUES` constant (`evaluate-pr`, `evaluate-head-sha`, `close-pr`, `recheck-comment`, `sync-installation`, `revoke-user-sessions`, `sweep`, `sweep-installation`, `job-dead-letter`); later epics add the queue of a new job to the constant in the change that adds the job (E07-S09, E16-S05, E22-S04). In pg-boss 10 and later `createQueue` runs DDL (a partition per queue), so the runtime role cannot do it. Verify the option names and this behaviour against the pinned version.
- The runtime starts pg-boss as `cla_app` with schema creation and migration disabled. The migrate step grants `cla_app` only what pg-boss needs on schema `pgboss` (usage, table DML, sequences, functions) and `cla_app` still owns nothing. At boot the app checks that every queue in `QUEUES` exists and exits with the missing queue names if not.
- `PgBossEnqueuer` implements `JobEnqueuer` from E06-S06: `enqueue(tx, job, options)` sends through pg-boss's executor option bound to the Kysely transaction connection, so the job commits or rolls back with the `webhook_deliveries` row. `idempotencyKey` maps to a deterministic job id or singleton key, and `dedupeKey` plus `dedupeWindowSeconds` map to pg-boss's throttle window, returning `'deduplicated'` when the send is dropped.
- The shared `JobEnqueuer` contract suite from E06-S06 runs against this adapter on real Postgres: a rolled-back transaction leaves no job, a committed one leaves exactly one, a repeated idempotency key leaves one, a send inside a dedupe window is `'deduplicated'`.
- pg-boss starts after the database check and stops with the app (`onClose`). A pg-boss `error` event is logged and flips readiness.
- Coverage of the adapter code comes from unit tests with a fake boss so the 100% gate holds on PGlite. The behaviour tests above need real Postgres and are skipped when the suite runs on PGlite. The behaviour tests run in the advisory CI `postgres` job; promoting it to a required check is E20-S12, under the stability rule of CONTRIBUTING.md (E20-S09), not a side effect of this epic.
- `cla_app` cannot `ALTER` or `DROP` a pgboss table (asserted).

**E07-S02 — Serialisation policy per (repo, PR), decided by test** ✅ Done
Resolves the open question of the exact pg-boss policy for per-(repo, PR) serialisation without dropped sends (`docs/architecture.md` names candidates only).
Acceptance criteria:
- The key is `${githubRepoId}:${prNumber}`, applied to `evaluate-pr`. The properties to prove: P1, at most one `evaluate-pr` runs per key at any time. P2, no send is lost: after the last send of a key, at least one run of that key starts after it. P3, different keys run in parallel up to `WORKER_CONCURRENCY`. P4, a worker that dies mid-run does not block the key forever.
- Candidates are tried in this order against the pinned pg-boss docs and real Postgres: `singleton` with `singletonKey`, then `key_strict_fifo`, then any other policy the docs describe as queuing per key. The first that passes P1 to P4 is chosen. A test also confirms or corrects the `docs/architecture.md` claim that `short` and `exclusive` drop a second send, and the result is recorded in the PR.
- P1 test: 50 sends for one key and a handler that records concurrent executions with a deliberate delay. Maximum observed is 1.
- P2 test: the external state is a counter; the test increments it before each send; the handler stores the value it observed at start. After the queue drains, the last run saw the final value. 200 seeded random interleavings of sends, completions and retries; the seed is printed on failure.
- P3 test: 10 keys with 5 sends each at concurrency 5 reaches at least 2 keys running simultaneously. P4 test (failure injection): a handler killed mid-run is reclaimed after `expireInSeconds` (300) and the next send for that key runs.
- All of it runs on real Postgres only (PGlite is single connection) in the CI `postgres` job (advisory until E20-S12). The chosen policy is set in the queue definitions of S01's migrate step and as a typed constant.
- The decision lands in the same change: the concurrency bullet in `docs/architecture.md` names the chosen policy instead of the candidates, and `docs/operations.md` mentions it.

**E07-S03 — Worker pipeline, handler registry and graceful shutdown** ✅ Done
Acceptance criteria:
- Job data is an envelope `{ type, deliveryId?, ...ids }` validated by a zod schema per job type, built from the E06-S04 catalogue. An invalid payload fails permanently with `job_payload_invalid` (no retry; S05 sends it to the dead-letter queue).
- `registerHandlers` binds `evaluate-pr`, `evaluate-head-sha`, `close-pr`, `recheck-comment`, `sync-installation` (calls E05-S08 `syncInstallation`), `sweep` and `sweep-installation`. `revoke-user-sessions` has no consumer until E10 registers it; its queue keeps the jobs meanwhile. A test asserts the registry's keys are a subset of the catalogue and the five delivery-driven handlers above are present.
- `revoke-user-sessions` is bound with `createRevokeUserSessionsHandler` from `src/server/services/revoke-user-sessions.ts` (dependencies: the session store and a logger), built by E10-S07 with a local envelope schema. This story swaps that schema for the catalogue one, deletes the `src/server/services/revoke-user-sessions.ts!` entry in `knip.json` (and its mention in `docs/tooling-gotchas.md`), and finishes the open criteria of E10-S07 (queued jobs consumed on first start, success marks the delivery processed, retry and dead letter).
- A handler wrapper logs start, finish and duration with the job id, type and numeric ids (never a body or a token). When a job that carries a `deliveryId` succeeds it calls `markDeliveryProcessed` (E06-S06); a dead-lettered job does not.
- `WORKER_CONCURRENCY` (integer 1 to 32, default 4) sets how many jobs run at once. The `docs/configuration.md` table documents it in the same change.
- `GitHubRateLimitedError` (E05-S05) is not caught: the job fails and pg-boss's exponential backoff (S05) reschedules it, so a wait the client refused to sleep through does not hold a worker.
- Graceful shutdown on SIGTERM and SIGINT: stop accepting HTTP, then `boss.stop` with a graceful wait of 30 s so running jobs finish, then close the database. Handlers receive an `AbortSignal` that aborts at the deadline and is passed to the GitHub client, and an aborted job is retried after restart. Exit code is 0 after a clean drain and 1 after a forced abort.
- `/readyz` (E04) also reports not ready when pg-boss is not started or a declared queue is missing.
- Real-Postgres tests: a slow job finishes before the process exits on SIGTERM; a job stuck beyond 30 s is aborted and runs exactly once after restart; an unhandled rejection inside a handler fails that job and does not crash the process.

**E07-S04 — The `evaluate-pr` job: fresh state, head SHA discipline, signatures last** ✅ Done
The protocol around the pure engine, consuming E08 types and `evaluatePullRequest` (type-only import from `src/server/domain`, so E08-S01 must be merged first). The composition root binds the real evaluator and the E09 reporter; this story is verified with `FakeGitHub`, a stub evaluator and `FakeReporter`.
Acceptance criteria:
- Payload fields (`githubInstallationId`, `githubRepoId`, `prNumber`, `trigger`) are used only as keys. The handler loads the installation and repository by (installation id, repo id) filtering on the installation id. A repository of another installation ends the job as `skipped: repository_not_found` with no GitHub call. `evaluationEligibility` (E05-S06) not eligible also ends it as skipped, with the reason logged and no GitHub call.
- Order, enforced by a call-order test: (1) `getRepositoryById` and, if the name differs, `refreshRepositorySnapshot` (E05-S09; 404 ends the job); (2) fetch the PR: state, head SHA, base SHA, draft flag, opener id and type, commit count; a closed PR ends the job; (3) upsert `pr_evaluations (repository_id, pr_number, head_sha)` to `in_progress` and call `reporter.started`; (4) collect commits using the E08-S07 strategy; (5) read the policy facts: active document and major, allowlist entries (installation and repository scope), `commit_overrides` for the collected SHAs, org membership only for actors that have no signature fact and no `user` or `bot` allowlist match; (6) read the signatures last, in one query for the distinct actor ids on the active document, non-revoked; (7) run the evaluator; (8) fetch the PR again.
- Step 8 decides: if the head SHA changed or the PR is no longer open, the result is discarded. Nothing is written to `pr_evaluations`, the Check Run or the comment, and the job completes as `superseded` (the push that moved the head sent its own delivery). Otherwise persist the E08 stored details and the result to `pr_evaluations` and call `reporter.publish`. A push between step 8 and the write is accepted: the Check Run is per head SHA and the newer job overwrites.
- Idempotency: when a final (`success` or `failure`) row with a `check_run_id` already exists for the same head SHA and the trigger is `pull_request`, the job is a no-op. The triggers `recheck`, `check_rerequested`, `signature`, `sweep` and `policy_change` (E07-S09) always re-evaluate, and so does a row in `in_progress` or `cancelled`. Ten queued `edited` deliveries therefore collapse into one evaluation.
- The GitHub reads it needs (`getPullRequest`, `listPullRequestCommits`, `listRepositoryCommits`, `compareCommits`) and the org-member exemption lookup come from E07-S10, which must be merged first; this story only calls them.
- A commit listing whose size disagrees with the PR's `commits` count triggers one re-fetch of the PR (push in flight). If it still disagrees the job throws and is retried. The loop holds no rule of its own: it follows `planCommitListing`, checks a `pull_commits` result and a complete walk with `verifyListing`, maps settled results with `listingStateOf`, and treats `inconsistent` like a mismatch (refetch once, then throw). A history with several merge bases (a criss-cross merge) always ends as a mismatch and is dead-lettered with the `/recheck` hint.
- The org-member facts are complete or the job fails: the engine treats an organisation without a membership fact as having no members, so a failed lookup must throw instead of passing partial facts. The stored details are `toStoredDetails(evaluation)`; the row is bounded by the E08 schema, so the job writes it as it is.
- Cross-tenant tests: a job naming installation A and a repository of B reads and writes nothing of B; signatures and allowlist rows of B never reach the evaluator input.
- Failure-injection tests: a GitHub 500 at each of steps 1, 2, 4, 8 and a reporter error after the database write. The retry produces the same single `pr_evaluations` row and exactly one reporter publish per attempt that reached step 7. A real-Postgres test runs two jobs for one PR through the S02 policy and ends with the result of the newer head SHA.

**E07-S05 — Bounded retries and the dead-letter handler** ✅ Done
Acceptance criteria:
- Every queue is created with `retryLimit` 5, `retryDelay` 30 s, `retryBackoff` true and `expireInSeconds` 300, and with `job-dead-letter` as its dead-letter queue (`job-dead-letter` itself has none). A handler that always throws runs exactly 6 times (1 plus 5 retries), then one job reaches `job-dead-letter`. Verify the option semantics against the pinned pg-boss.
- Finished jobs do not pile up: every queue sets pg-boss's retention windows (archive after 7 days, delete after 14 days; verify the option names against the pinned version), so the `pgboss` tables stay bounded without a purge job of our own.
- Every job envelope carries its `type`, so a single dead-letter handler can tell what died.
- A `job_payload_invalid` job skips the retries: the original is completed with output `{ rejected: 'invalid_payload' }` and a copy is sent to `job-dead-letter`, so it never wastes the retry window.
- Dead `evaluate-pr` and `evaluate-head-sha`: if the installation and repository are still eligible, the handler resolves the head SHA from GitHub and calls `reporter.failed(headSha, 'evaluation_failed')`, which E09 renders as a Check Run `failure` whose summary tells the contributor to comment `/recheck`. It also sets the `pr_evaluations` row to `failure` with details `{ "code": "evaluation_failed" }`, which names no contributor.
- Dead `sync-installation`: append `installation.sync_failed` to `audit_log` (installation id, no personal data) and log at error. The E05-S08 reconciliation retries it later. Dead `recheck-comment`, `close-pr`, `sweep` and `sweep-installation`: log at error only.
- If the dead-letter handler itself cannot reach GitHub it fails and retries under the same bounds, then logs `dead_letter_unhandled` at error. There is no loop.
- The dead-letter handler never marks a delivery processed, so a redelivery from GitHub requeues it (E06-S06).
- Real-Postgres tests: the attempt count above; the dead-letter handler called once; the Check Run ends `failure` with the hint (via `FakeReporter`); GitHub down inside the handler; the invalid-payload shortcut.
- The `docs/operations.md` "Poison jobs" bullet is updated with the final numbers in the same change.

**E07-S06 — Pull request closed: prune pending work** ✅ Done
Acceptance criteria:
- A new forward-only migration extends the `pr_evaluations.result` check to (`in_progress`, `success`, `failure`, `cancelled`). `src/server/adapters/db/schema.ts` and its catalog test are updated. E08 never produces `cancelled`; it is a lifecycle state.
- The `close-pr` handler cancels the queued and retrying `evaluate-pr`, `evaluate-head-sha` and `recheck-comment` jobs of that (repo, PR) through the pg-boss API, not raw SQL. Running jobs are not interrupted: their step 2 or step 8 (S04) sees the closed PR and ends them.
- For each `pr_evaluations` row of the PR still `in_progress`, set `result = 'cancelled'` and call `reporter.cancelled(headSha)`, which E09 renders as the Check Run conclusion `cancelled`, so no check hangs on a closed PR. Rows with a final result are untouched.
- Merged and unmerged closes behave the same. A `reopened` delivery runs a normal evaluation: a `cancelled` row is re-evaluated and ends `success` or `failure`.
- Cross-tenant test: `close-pr` for installation A with a repo id of installation B cancels nothing of B.
- Tests: a queued job is cancelled, a running job finishes as `superseded`, two `close-pr` jobs for the same PR are idempotent, a close followed by a reopen, a PR with no rows.

**E07-S07 — Manual re-evaluation: `/recheck` and Re-run** ✅ Done
Acceptance criteria:
- Pure `isRecheckCommand(body)` in `src/server/domain/recheck.ts`: the body is split on `\n`, one trailing `\r` is removed per line, and a line must equal `/recheck` exactly (case sensitive, no other characters, no surrounding spaces). Lines inside fenced code blocks (` ``` ` or `~~~`) and quoted lines (starting `>`) do not count.
- Table tests (at least 20 rows): CRLF bodies, several lines, trailing space, leading space, `/Recheck`, `/recheck now`, `/rechecks`, quoted reply, fenced block, a fullwidth solidus lookalike, a zero-width character inside, empty body, the command as the last line without a final newline.
- The `recheck-comment` handler re-fetches the comment (`GET /repos/{owner}/{repo}/issues/comments/{id}`, a new port method). A 404 ends the job. It applies the authoritative rules to the fetched data, not to the payload: author type is not `Bot`, the issue is a pull request, the PR is open, the repository is eligible, and the body satisfies `isRecheckCommand`. Only then it enqueues `evaluate-pr` with trigger `recheck`.
- Rate limit: that enqueue uses `dedupeKey = recheck:${githubRepoId}:${prNumber}` and `dedupeWindowSeconds = 60`. A second command within 60 s is dropped silently and logged `recheck.rate_limited`; there is no reply comment (E09's PR comment states the limit). Any commenter may trigger it: it only re-evaluates, and the limit protects the API budget.
- The `evaluate-head-sha` handler (from `check_run` and `check_suite` rerequested) lists the pull requests for the SHA (`GET /repos/{owner}/{repo}/commits/{sha}/pulls`, new port method), keeps the open ones whose head SHA equals the given SHA (fork PRs included), caps at 20, and enqueues `evaluate-pr` with trigger `check_rerequested` under the same dedupe key and window. No matching PR ends the job.
- Tests: bot author, deleted comment, closed PR, disabled repository, rejected installation (no GitHub call after the eligibility check), two commands 10 s apart giving one evaluation, two commands 61 s apart (fake clock) giving two. The dedupe-window test runs on real Postgres.

**E07-S08 — Scheduled reconciliation sweep** ✅ Done
Acceptance criteria:
- `sweep` is scheduled by pg-boss's scheduler (cron) every `SWEEP_INTERVAL_MINUTES` (allowed values 0, 5, 10, 15, 20, 30, 60; default 30; 0 disables it). Any other value is a `ConfigError`. Only one `sweep` job can exist at a time. The `docs/configuration.md` table documents it.
- `sweep` calls `reconcileInstallations()` (E05-S08), then enqueues one `sweep-installation` job per admitted, non-suspended, non-deleted installation with a dedupe key per installation.
- `sweep-installation` lists the open PRs of each enabled, non-removed repository (`GET /repos/{owner}/{repo}/pulls?state=open`, 100 per page, at most 1,000 PRs per repository per run) and enqueues `evaluate-pr` with trigger `sweep` and a 5 minute dedupe window for each PR that has no final `pr_evaluations` row for its current head SHA, or has one `in_progress` for more than 30 minutes or `cancelled`. A PR with a final result for its head SHA is not enqueued.
- A reaper step finds `pr_evaluations` rows `in_progress` for more than 30 minutes and re-enqueues them under the same dedupe window; for a PR that is now closed it applies the S06 cancellation. This is what guarantees a check is never left `in_progress` after a lost job.
- Rejected, suspended and deleted installations are skipped before any GitHub call. A test with three installations (admitted, rejected, suspended) asserts `FakeGitHub` recorded calls for the admitted one only.
- Missed-delivery test: a PR opened with no webhook is evaluated after one sweep, exactly once, and a second sweep enqueues nothing for it.
- Cost is documented in `docs/operations.md`: roughly one request per enabled repository per run plus one per 100 open PRs, throttled by E05-S05, which is why the default interval is 30 minutes.
- Each `sweep-installation` runs independently, so one installation's rate limit or failure does not stop the others.

**E07-S09 — Repository-level jobs: sweep-repository, finalise-repository and finalise-check** ✅ Done
The job names that E12, E14 and E15 enqueue when a policy changes. This story owns their queues, envelopes and dedupe rules so no later epic invents a job type.
Acceptance criteria:
- `QUEUE_DEFINITIONS` (E07-S01, E07-S02: each entry is a name and a policy, and `QUEUES` is derived from it) gains `sweep-repository`, `finalise-repository` and `finalise-check`, each created by the migrate step with the bounds of E07-S05, and the dead-letter table of E07-S05 gains a row for each: a dead job of these types is logged at error only, because the next `/recheck`, sweep or re-enable repeats the work. The boot check (E07-S01) also covers them.
- `sweep-repository` has the envelope `{ type, githubInstallationId, githubRepoId, reason }` with `reason` in the closed set `repository_enabled`, `cla_version_published`, `cla_document_changed`, `allowlist_changed`, `signature_revoked`, `signatures_invalidated` and `override_changed` (the callers are E14-S02, S03 and S06, E12-S04, E15-S03 to S06). The enqueue uses `dedupeKey = sweep-repository:${githubRepoId}` with a 60 second window, so rapid edits collapse into one run; the run reads policy facts at run time, so one run covers both changes.
- The `sweep-repository` handler skips (no GitHub call) when `evaluationEligibility` (E05-S06) is not eligible. Otherwise it lists the open pull requests like E07-S08 (100 per page, at most 1,000 per run) and enqueues `evaluate-pr` with trigger `policy_change` for each, under `dedupeKey = policy_change:${githubRepoId}:${prNumber}` and a 60 second window. It never writes a Check Run or a comment itself.
- `finalise-repository` has the envelope `{ type, githubInstallationId, githubRepoId }` keyed per repository, and `finalise-check` has `{ type, githubInstallationId, githubRepoId, prNumber }` keyed by the same per-(repository, PR) key as `evaluate-pr` (E07-S02: a case in `serialisationKey` and the `singleton` policy in `QUEUE_DEFINITIONS`), so two finalisations of one pull request never overlap. A pg-boss policy holds within one queue only, so this alone does not make a finalisation wait for an `evaluate-pr` already in flight (found in E07-S02): this story or E14-S04 decides how a finalisation copes with that, for example by re-checking enforcement in the last step of the evaluation. This story ships the envelopes, queues and fakes; the two handlers are registered by E14-S04, and until then their queues keep the jobs, as for `revoke-user-sessions`.
- Tests: each envelope refuses an unknown reason and a string id; the dedupe window drops a second `sweep-repository` for one repository and not for another; a payload naming installation A and a repository of installation B enqueues nothing; a rejected, suspended or deleted installation ends the job with no GitHub call.

**E07-S10 — GitHub reads for evaluation and the org-member exemption lookup** ✅ Done
Built in two steps: E07-S04 needed the read side first, so it built the four port methods with their zod schemas, `FakeGitHub`, the contract cases and the MSW routes, and an uncached `OrgMembershipService`; this story added the cache (`org-membership-cache.ts`, one per process, built in `jobWorkers`), the typed contract fixtures (`adapters/github/membership-fixture`), the `/public_members/` guard of the mocked GitHubs (`adapters/github/public-members-guard`) and the 5 s attempt timeout of the client calls (`CLIENT_TIMEOUT_MS`; the self-check and the token requests keep 10 s). `isOrgMember` also takes the `login`, the handle GitHub's route needs; the numeric id still decides and keys the cache.
The read side of the evaluation job: the PR and commit calls it needs and the one service that decides whether an author is exempt as a member of the installing org.
Acceptance criteria:
- The port (E05-S04) gains `getPullRequest`, `listPullRequestCommits`, `listRepositoryCommits` and `compareCommits` (merge base), each with a zod schema that keeps only the fields used, in `FakeGitHub` and in the shared contract suite against the MSW-backed adapter. The adapter maps a commit `author` or `committer` that is `null`, `{}` or lacks a numeric `id` to `null`.
- `OrgMembershipService.isOrgMember({ githubInstallationId, userGithubId })` in `src/server/services` is built on `getOrgMembership` (E05-S04, the only adapter call for it). The org is the installation's own account (`installations.account_login`); an installation of type `User` returns `not_member` without any API call. The result is `member` only for HTTP 200 with `state: 'active'` and `user.id` equal to `userGithubId`: the login is only the lookup handle, and another id (a reused login), `state: 'pending'` or 404 is `not_member`.
- The 403 split uses the E05 classes: `x-ratelimit-remaining: 0` or `retry-after` surfaces as `GitHubRateLimitedError`; any other 403 resolves to `permission_missing` (E08 treats it as not exempt, fail closed) and logs `members_permission_missing` with the numeric installation id; 5xx, timeouts (5 s) and network errors surface as `GitHubUnavailableError`. The public-members endpoints are never used (an MSW handler fails the test on `/public_members/`).
- Exemption facts are cached in memory per `(installation id, user GitHub id)`: `member` for 10 minutes and `not_member` for 2 minutes, at most 10,000 entries with least-recently-used eviction; errors and `permission_missing` are never cached. Fake-timer tests hit the exact boundaries. The role cache of E11-S04 (60 seconds, keyed by role) is a separate cache by design, because the two serve different freshness needs; both read the same E05-S04 call.
- Cross-tenant test: a user cached as `member` for installation 1 gets a fresh lookup for installation 2 and can be `not_member` there, and the installation token used is always the one of the requesting installation. Contract fixtures (active, pending, 404, 403 permission, 403 rate limit, id mismatch) live next to the adapter, typed through the zod schema.
