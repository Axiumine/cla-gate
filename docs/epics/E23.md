# E23 — Self-hosted CI runners

**Bounded Context:** BC-08
**Priority:** 🔴 Must have
**Status:** ⏳ In progress

**Goal:** Every CI job of this repository runs on the maintainer's shared, persistent, self-hosted runners under one written policy that a reviewer and a guard script can check: literal runner labels, bounded and least-privileged jobs, tool state kept off the shared host, containers and ports that are random, free and loopback-only, and a fork pull request approval gate that is the one real protection. When this epic is done, adding a job means meeting the rules in [`docs/ci-runners.md`](../ci-runners.md), and a stranger's pull request reaches the host only after the maintainer has read its whole diff.
**Depends on:** E02, E04.
**Out of scope:** Ephemeral or per-job virtual-machine runners, and any change to the organisation's runner group. The maintainer decided on shared runners with the approval gate as the only protection (recorded in the policy, "Runner exposure"), so the residual exposure is a recorded decision, not a defect. Publishing a container image anywhere: the idea of a published image was rejected, so no job builds, pushes or scans one. The hosting of the GitHub App itself and production deployment (E19). The extended gates (Semgrep, Trivy, Stryker, Playwright, memlab, Qodana) and the promotion of checks to required (E20), which meet the policy through the link in their own stories. The application's own default port, a deployment setting that E19 owns.

**E23-S01 — Record the CI runner policy and the exposure decision** ✅ Done
The CI runs on shared, persistent, self-hosted runners. One document is the contract that every story adding a job, a container or a port links to.
Acceptance criteria:
- `docs/ci-runners.md` is the single source of truth for CI runner policy. It covers purpose and scope, runner exposure, fork pull request approval, where each job runs and why, the rules for adding a job, the guard, ports, containers and cleanup, known unknowns and risks, and a pointer to its history (`git log --follow -- docs/ci-runners.md`). Its scope is every workflow in `.github/workflows/`, `scripts/ci/`, the development database helper in `scripts/dev/` and the ports they use; the GitHub App's own hosting (E19) is outside it.
- The exposure is recorded as the maintainer's decision, quoted: "Runner exposure: shared runners with the approval gate as the only protection." The runners are organisation-level and persistent (not ephemeral), carry exactly the labels `self-hosted`, `Linux`, `X64`, also serve other repositories of the organisation, belong to the Default runner group of a free-plan organisation (nothing in a workflow can narrow it), and run a job as the runner user on a shared host: work directories, tool cache, Docker daemon, network and any credential stored there.
- The consequence is written plainly: approved fork code runs as the runner user on a host shared with other repositories, and the only barrier is the maintainer reading the pull request first. A `runs-on` expression is not a boundary, because on `pull_request` the workflow file comes from the pull request and its author picks the runner; a pattern that sends forks to a hosted runner and everyone else to a self-hosted one is forgeable and must not be copied.
- The table "Where each job runs and why" lists `static`, `coverage` and `postgres` on `[self-hosted, Linux, X64]`, `release.yml` and `scorecard.yml` (they do not exist) on GitHub-hosted `ubuntu-24.04`, and CodeQL default setup and Dependabot updates as run by GitHub. A job may use a GitHub-hosted runner only for a reason from the document's list (untrusted code that must not touch the shared host, a platform the self-hosted runners lack, a GitHub-run feature, a job that must work when the maintainer's infrastructure is down, a deliberate clean-room check), written in the workflow comment and in the table.
- The document records the break-glass for the case that every runner is offline (change `runs-on` of the three jobs to the literal `ubuntu-24.04` in a same-repository pull request, say in the pull request that it is temporary, revert it afterwards) and the list "Known unknowns and risks": runner capabilities unverified until the first run, a shared and persistent host, no isolation between repositories, same-repository and Dependabot pull requests not gated, the guard is not a boundary, a shared Docker daemon, cold caches.
- `docs/toolchain.md` (CI), `docs/decisions.md` (Decisions), `README.md` (Quality gates summary) and `docs/development.md` (Commands), `CONTRIBUTING.md` (Repository protection), `docs/tooling-gotchas.md` and `CLAUDE.md` (Branch protection) carry the matching pointer lines in the same change (hard rule 10), and the document's first lines tell a story that adds or changes a CI job to link it and to meet "Rules for adding a job".

**E23-S02 — Apply and verify the fork pull request approval policy** ✅ Done
The approval gate is the only protection between a stranger's pull request and the shared runners, so it is a repository setting that one read-only command verifies.
Acceptance criteria:
- The repository setting "Require approval for all external contributors" (`approval_policy` value `all_external_contributors`) was applied by the maintainer on 2026-11-01 (Settings, Actions, General, Fork pull request workflows). No workflow from a fork runs on any runner until the maintainer approves it.
- The verification command is in the policy: `gh api repos/Axiumine/cla-gate/actions/permissions/fork-pr-contributor-approval`, which must answer `{"approval_policy":"all_external_contributors"}`. It was run the same day with that answer, and it is read-only, so anyone can repeat it at any time.
- The policy says what to do when the answer is anything else: stop approving fork runs and fix the setting first. The setting exists only on GitHub, so no agent changes it; the repository holds the expected value and the command.
- The limits are written down next to the setting. It does not cover pull requests from branches of this repository, Dependabot's included, which need no approval. The listed mitigations are Yarn's one-day `npmMinimalAgeGate`, Dependabot's seven-day cooldown, third-party install scripts switched off (`enableScripts`) and reading the lockfile diff of dependency pull requests.
- `CONTRIBUTING.md` (Repository protection) names the setting and states that the fork approval gate is the only protection of the shared runners and that the whole diff is read before a fork run is approved.

**E23-S03 — Run the CI jobs on the shared runners with the hygiene rules** ✅ Done
`static`, `coverage` and `postgres` run on the maintainer's runners. Each job is bounded, least-privileged and leaves nothing behind.
Acceptance criteria:
- `.github/workflows/ci.yml` runs `static`, `coverage` and `postgres` with `runs-on: [self-hosted, Linux, X64]` spelled as that literal list, with `timeout-minutes` 15, 30 and 45 (`coverage` was 15 until a busy runner cancelled it once at that limit; `postgres` was 20 until the shared runners cancelled it twice at that limit while its tests still passed), workflow-level `permissions: contents: read` and nothing more, and no secrets, no `pull_request_target`, no `workflow_run`, and no job-level `uses`, `container` or `services`. The job names stay `static` and `coverage` (the required checks of E01-S03).
- The first step of every job is a fail-fast preflight. It prints `runner: <uname -sm>, user <id -un>` and fails with a clear `::error` message when `git`, `curl` or `tar` is missing or less than 4096 MiB are free in the workspace. The `postgres` job also fails when `docker info` cannot reach the daemon, and prints the Docker server version otherwise.
- Every `actions/checkout` has `persist-credentials: false` and `clean: true`. Every third-party Action is pinned by full commit SHA with the version in a comment. No step uses `sudo`, and nothing interpolates a branch name, PR title or other attacker-controlled field into a `run:` block; names of things a job creates on the host derive from `GITHUB_RUN_ID` and `GITHUB_RUN_ATTEMPT` passed through `env`.
- Whatever a job starts on the host is removed in an `if: always()` step. For `postgres` the condition is `always() && env.CLA_PG_CONTAINER != ''`, so a job that failed before the helper ran skips the cleanup instead of failing it.
- `scripts/ci/ci-workflow.test.ts`, `ci-preflight.test.ts` and `ci-tool-state.test.ts` run in the `coverage` job and pin these properties for `ci.yml`: the three jobs and the exact required names, the same allowed runner in all three jobs, a timeout on each, the preflight first, and the `postgres` job having no `services:` and publishing no port by itself. A test replays the break-glass edit (every `runs-on` becomes `ubuntu-24.04`) and shows that both the pins and the runner guard still accept it. A new workflow file has no such test, so the policy tells the reviewer to check it against the hygiene list.

**E23-S04 — Keep tool state in the runner temp directory and install no git hooks in CI** ✅ Done
On a persistent shared host, whatever a tool writes to the runner user's home or to `/tmp` outlives the job and is visible to other repositories.
Acceptance criteria:
- A step "Keep tool state in the runner temp directory" runs before checkout and writes six variables to `GITHUB_ENV`, all under `$RUNNER_TEMP`: `COREPACK_HOME`, `YARN_GLOBAL_FOLDER`, `npm_config_cache`, `XDG_DATA_HOME`, `XDG_CACHE_HOME` and `TMPDIR`. Corepack, Yarn, npm, Vitest's token, Biome's cache, Node's compile cache and the temp directories of tests therefore stay out of the shared home directory and `/tmp`.
- Corepack is installed with `npm install --global --prefix "$RUNNER_TEMP/npm-global" corepack@0.36.0` and that `bin` directory is added to `GITHUB_PATH`. It is never installed into the Node of the tool cache, because two jobs installing into one directory at the same time can leave it without the binary. The Yarn cache (`actions/cache`) lives under `$RUNNER_TEMP/yarn/cache` and starts cold on the first run.
- The root `postinstall` script is `node scripts/dev/install-hooks.ts`. It runs `lefthook install`, except when `CI` is set or there is no `.git`, and a failing `lefthook install` fails the Yarn install with the same exit code. The entry script is logic-free (the logic is in `scripts/dev/lib/install-hooks.ts`) and unit tests cover CI set, no `.git` and a normal checkout.
- The reason is written in the policy and in `docs/tooling-gotchas.md`: on a persistent workspace a hook outlives `node_modules`; the next run's checkout deletes `node_modules` (`git clean -ffdx`), then `git checkout` fires `post-checkout`, which with `assert_lefthook_installed: true` cannot find Lefthook and fails the checkout. CI repeats every hook check anyway.
- `scripts/ci/ci-tool-state.test.ts` fails for any job whose tool directories do not all point into `$RUNNER_TEMP`, or that installs Corepack anywhere but its own prefix on the `PATH`.

**E23-S05 — Pick random free loopback ports with one helper** ✅ Done
Docker's own port assignment is sequential and the host's ephemeral range is a sysctl, so the repository chooses its ports itself.
Acceptance criteria:
- `scripts/ci/lib/ports.ts` exports the range (`PORT_MIN` 32769, `PORT_MAX` 60999), `LOOPBACK` (`127.0.0.1`) and `pickSystemFreePort()`: a random draw with `crypto.randomInt`, a real probe that binds `127.0.0.1` exclusively, at most 50 draws, then a `PortError` that names the range and the attempt count. A random source that returns a number outside the range also throws.
- `yarn ci:port` (`scripts/ci/free-port.ts`, logic-free over `lib/free-port-cli.ts`) prints exactly one such port and exits 0.
- A retry helper restarts whatever needs the port with a new one when Docker or Compose reports the chosen port as taken ("port is already allocated", "address already in use", "ports are not available"), because the probe and the bind are two steps. It resets the failed attempt first and gives up with a `PortError` after the allowed attempts.
- The policy explains why Docker's own assignment is not enough (`-p 127.0.0.1::5432` hands out the next free port of the host's ephemeral range in sequence, so it is guessable), why a test never uses port 0 (the kernel draws from the same sysctl range), that every published port is bound with `-p 127.0.0.1:<port>:<container port>` and never `-p <port>:<container port>`, and that the runner needs no inbound port because it connects out over HTTPS.
- Unit tests, at 100% coverage with injected dependencies, cover the range edges, a taken port, exhaustion, an out-of-range random source, the retry and the real probe.

**E23-S06 — Run the postgres job against a container on a random loopback port** ✅ Done
The `postgres` job repeats the unit tests against a real PostgreSQL 18 server. It starts that server itself, because a `services:` block would publish a well-known port on all interfaces of a shared host.
Acceptance criteria:
- `yarn ci:postgres start` (`scripts/ci/postgres.ts`, logic-free over `lib/postgres-cli.ts`) runs the digest-pinned `postgres:18` image as `cla-pg-<run id>-<attempt>-<random>` with the label `cla-gate.ci=postgres`, published as `127.0.0.1:<port>:5432` on a free port from the helper of E23-S05, with a per-run random password. The workflow has no `services:` block.
- The password is masked with `::add-mask::` and reaches Docker through the child's environment (`--env POSTGRES_PASSWORD` without a value), never through argv, so it is not in the process list. `start` appends `CLA_PG_CONTAINER` to `GITHUB_ENV` before docker runs, waits for the health check over TCP rather than the init-time socket (120 seconds at most) and then appends `DATABASE_URL`.
- `start` retries with a new port, up to 5 times, when Docker reports the chosen one as taken. Any failure inside `start` removes the container again, except when `docker run` failed because the name was already taken: that container belongs to someone else and is left alone.
- `yarn ci:postgres stop`, run by the `if: always()` step, removes the container with its volume and is idempotent. It refuses a name that does not start with `cla-pg-`, inspects the container first and refuses one without the label `cla-gate.ci=postgres`, so other repositories' containers on the shared daemon are never touched.
- Container logs shown after a failed start are printed with a `| ` prefix and with control characters escaped, so nothing a container prints can pass for a workflow command. Leftovers of a killed runner are found with `docker ps -a --filter label=cla-gate.ci=postgres` and removed with `docker rm -f --volumes <name>`; nothing sweeps them automatically.
- The job runs `yarn test` with `DATABASE_URL` set. The Vitest global setup creates and drops a throw-away `cla_test_<hex>` database and runs the files one at a time; coverage stays with the `coverage` job. The helper is unit-tested at 100% coverage with an injected Docker, including the failure and the name-taken paths.

**E23-S07 — Guard the runner rules with yarn ci:runners** ✅ Done
Review reads the rules, and a script catches the mechanical part of them before a reviewer has to.
Acceptance criteria:
- `yarn ci:runners` (`scripts/ci/check-runners.ts`, logic in `scripts/ci/lib/`) reads every `.yml` and `.yaml` file directly inside `.github/workflows/` and prints one line per violation, `file: job "id": R1 message` (`file: workflow: R3 message` for a trigger). Exit codes: 0 ok, 1 violations, 2 unusable input (malformed YAML, a file that is not a workflow, a missing directory).
- R1: every job without `uses` has `runs-on` equal to the literal `ubuntu-24.04` or the literal list `[self-hosted, Linux, X64]`, exact, case-sensitive and in that order, with no expression, matrix value, `group` or `labels` object, `ubuntu-latest` or other label. R2: in every file whose name contains `release` or `scorecard` (any case, any position) every job is exactly `ubuntu-24.04`.
- R3: the triggers `pull_request_target` and `workflow_run` are forbidden. R4: every job has `timeout-minutes`, a positive number of at most 60 (an expression is rejected because it cannot be checked). R5: a top-level `permissions` key exists and holds `contents: read` and nothing else, release and scorecard files may add `security-events: write` and `id-token: write`, and a job-level `permissions` block is held to the same set.
- R6: a job-level `uses` (a reusable workflow) is rejected as unsupported. R7: a job-level `container:` or `services:` is rejected on any runner, because a container with `--privileged` or a bind mount of `/` defeats every other rule and `ports: 5432:5432` publishes a well-known port on all interfaces; containers start from a `run:` step through the `scripts/ci/` helpers.
- The YAML parser (`yaml`, ISC, a dev dependency) rejects duplicate keys, several documents in one file and alias bombs. A merge key (`<<`) is not expanded, so a job that relies on one fails R1. File and job names are escaped in the report so they cannot forge a line.
- The same script runs in the `static` job and in the `pre-push` hook (job `ci-runners` in the static-analysis group). Each rule has a passing and a failing test at 100% coverage, and Knip stays clean in both modes.
- The policy lists what the guard does not check (what a `run:` step executes, which third-party Actions are used, composite actions, the scripts a step calls, and the hygiene rules such as SHA pinning, `persist-credentials`, secrets, cleanup, preflight and tool state) and says it is not a security boundary: a pull request can edit it too, which is why the approval gate of E23-S02 comes first.

**E23-S08 — Start the development database and server on random loopback ports** ✅ Done
Development must not publish a well-known port either: the same helper that serves CI serves the developer.
Acceptance criteria:
- `yarn db:up` (`scripts/dev/db.ts up`) picks a random free loopback port, runs `docker compose` with `POSTGRES_PORT` set and remembers the port in the git-ignored `.local/db.json`. The file is validated with zod and is only a cache: a missing or unusable file means "no database recorded". `yarn db:url [app|owner]` prints the connection strings, and `yarn db:down [--volumes]` stops the container (`--volumes` also deletes the data). Exit codes: 0 ok, 1 failure (Docker, nothing recorded), 2 usage.
- `docker-compose.yml` publishes only `127.0.0.1:${POSTGRES_PORT:?...}:5432`, with no default, so running compose by hand without a port fails with a message instead of publishing 5432. The `5432` after the second colon is the container's own port. A test pins that the only published port is loopback-bound, comes from `POSTGRES_PORT` and has no default, and that the owner credentials, the database name and the runtime role equal the ones the helper and the init script use.
- `yarn dev` and `yarn db:migrate` go through `scripts/dev/db.ts run app|owner -- <command>`, which sets `DATABASE_URL` (the `cla_app` role) or `MIGRATION_DATABASE_URL` (the owner) from the remembered port or from an explicit variable. For `app` it also sets a random free `PORT` and prints `app: http://127.0.0.1:<port>` before the server starts; an explicit `PORT` wins, and `node --watch` restarts keep the port because it is chosen once.
- When Docker reports the chosen port as taken, `db:up` retries with a new one, as the helper of E23-S05 does for CI.
- The passwords in the compose file are well-known development defaults for a database that listens on loopback only, and are labelled as such. `README.md` and `docs/development.md` (Commands) describe `yarn db:up` instead of port 5432 in the same change.

- Test-only values stay and are listed as such: fake `host:port` strings such as `db.internal:5432`, `localhost:3000` and `127.0.0.1:1` (nothing listens there) in unit tests and in a doc comment in `boot.ts`, and the helper's own range fixtures. Nothing binds them.

Enforcement today is the compose test, rule R7 of the guard and review; no repository-wide scan is automated.

**E23-S10 — Give the maintainer a checklist for approving fork pull requests** ✅ Done
Approval is the control, so "read the whole diff" becomes steps that can be followed and repeated after every push.
Acceptance criteria:
- The policy's "Fork PR approval" section holds the checklist. It applies to every fork pull request and again after every push to it, and it starts from the rule that the whole diff is read first: not from a notification, a title or a description.
- The checklist says what to read: the entire diff, binary, generated and lockfile changes included; `.github/` (any workflow, composite action or `dependabot.yml`, and any workflow change from a fork is refused); `package.json` (every `scripts` entry, the root `postinstall`, `devEngines`, `packageManager`, `resolutions`); `.yarnrc.yml` and `yarn.lock` (new packages, changed `resolution:` lines, anything resolved from a URL, a git repository or a tarball); `lefthook.yml`, `.nvmrc` and `mise.toml`; every executable config file (`eslint.config.mjs`, `vitest.config.ts`, `knip.json`, `biome.json`, `fta.json`, `tsconfig*.json`, `docker-compose.yml`, `docker/`); and `scripts/` and all tests, setup files such as `global-setup.ts` included.
- It says what to refuse or ask about first: a new network call (`fetch`, `curl`, a download, a registry or URL change), a dependency added or changed without a stated reason or one that is not AGPLv3-compatible, any change to `.github/`, the runner guard, the hooks or the Yarn config, anything that reads outside the workspace (the environment, `~`, `/proc`, the Docker socket), and containers, background processes or listeners not started through the `scripts/ci/` helpers.
- Only then "Approve and run". When the contributor pushes again, the new diff is read before the new run is approved. The checklist says why: approved fork code runs as the runner user on a host shared with other repositories (E23-S01).
- `CONTRIBUTING.md` (Repository protection) points to the checklist. The policy states that the checklist does not cover same-repository and Dependabot pull requests (E23-S02).
