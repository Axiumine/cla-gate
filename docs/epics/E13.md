# E13 — Contributor signing flow

**Bounded Context:** BC-03
**Priority:** 🔴 Must have
**Status:** ⬜ Todo

**Goal:** A contributor who follows the sign link in the PR comment reads the exact CLA version, consents with a typed name and one verified GitHub email, and gets an immutable signature recorded against that exact text, after which the originating PR is re-evaluated. Signing is open to any authenticated GitHub user and is always scoped to the tenant (GitHub App installation) that owns the repository's CLA document, so one instance serving several orgs never mixes their signatures.
**Depends on:** E10, E12, E09
**Out of scope:** Login, sessions, CSRF and `return_to` handling (E10). Publishing, listing and rendering CLA documents and versions (E12; the sanitising markdown pipeline is used by the web screens in E18). The PR comment text and its sign link (E09). The sign page and "my signatures" screens (E18). Revocation and invalidation (E15). CSV export, data-subject export, erasure and retention purging (E16). Corporate signers and employee approval (E21). Per-PR evaluation logic (E08).

**E13-S01 — Consent text registry** ✅ Done
The consent sentence a signer agrees to is code, identified by an id, so a signature can prove which wording was on screen when it was made.
Acceptance criteria:
- `src/shared/consent.ts` exports a frozen `CONSENT_TEXTS` map from consent text id to `{ kind: 'individual', text: string }` and `CURRENT_CONSENT_ID`, a map from kind to the id offered today. The first entry is `individual-v1` and `CURRENT_CONSENT_ID.individual` points at it
- `individual-v1` is plain text of at most 600 characters stating that the signer has read the CLA version shown, agrees to be bound by it, and that the typed name and the selected verified email are stored with the signature. It is interface wording, not CLA text; the wording needs counsel review before release (tracked as an open question, not a blocker for this story)
- An existing id never changes meaning: a test pins the SHA-256 of every text with `toMatchInlineSnapshot`, so editing a published wording fails the test. New wording is a new id (`individual-v2`); old ids stay resolvable forever because old signatures reference them
- Every key matches `^[a-z0-9-]+-v[0-9]+$` and is 1 to 64 characters, so it always fits `signatures.consent_text_id` (non-empty text); a test iterates all keys, and another asserts every value of `CURRENT_CONSENT_ID` exists in `CONSENT_TEXTS`
- `getConsentText(id: string)` returns the entry, or `undefined` for an unknown id (no throw, no prototype lookups: `getConsentText('__proto__')` and `getConsentText('constructor')` return `undefined`)
- The server is the only source of the text shown on the sign page (returned by E13-S02); the web never carries its own copy, and the sign request (E13-S04) carries only the id

**E13-S02 — Sign page context endpoint** ✅ Done
Everything the sign page needs in one read: which CLA version applies to this repository, what the viewer already signed, and which verified emails can be chosen.
Acceptance criteria:
- `GET /api/sign/:githubRepoId` with optional `?pr=<n>`. `githubRepoId` is a positive integer (the numeric GitHub repository id, stable across renames); `pr` is an integer from 1 to 2147483647. Anything else is `400` with the standard error body
- A request without a valid session is `401`; the response never redirects. The SPA route `/sign/:githubRepoId` starts login with a relative `return_to` of `/sign/{githubRepoId}` plus `?pr=` only (E10 validates it). The GET performs no write: no row, no job, no audit entry
- The repository is found by `repositories.github_repo_id`, and every later read filters by that row's `installation_id`. An unknown repository, and a repository whose installation is suspended or not admitted by the instance admission policy, both return the same `404` body, so a visitor cannot tell which tenants exist
- A repository with no `cla_document_id`, or whose document has no `active_version_id`, returns `409` with `error.code` `no_active_cla`. Enablement is not required: a stale link to a repository that was disabled later still shows the document that is attached
- `200` body (`Cache-Control: no-store`, schema in `src/shared`):
  ```json
  {
    "repository": { "githubRepoId": 123, "fullName": "acme/widgets", "accountLogin": "acme" },
    "document": { "id": 7, "name": "Individual CLA" },
    "version": { "id": 31, "major": 2, "minor": 0, "contentMd": "...", "contentSha256": "<64 hex>", "rationale": "Clarified the patent grant", "publishedAt": "2026-11-01T10:00:00.000Z" },
    "consent": { "id": "individual-v1", "text": "..." },
    "emails": [{ "email": "ada@example.org", "primary": true }],
    "viewer": { "githubId": 1234, "login": "ada" },
    "pr": 45,
    "prUrl": "https://github.com/acme/widgets/pull/45",
    "state": "ready",
    "signature": null,
    "revoked": null,
    "canSign": true,
    "blockedReason": null
  }
  ```
  `contentMd` is the stored source text, never rendered server-side; `pr` is `null` when the query parameter is absent; `prUrl` is `https://github.com/<fullName>/pull/<pr>` built from the repository's `full_name` snapshot when `pr` is present, else `null`; `version.rationale` is the publisher's rationale of that version (the screen shows it only when `state` is `resign_required`)
- `state` is derived by one pure function: `already_signed` when a non-revoked signature exists for (viewer, document, active major), whatever its minor; `resign_required` when no such signature exists but a non-revoked one exists for a lower major; `ready` otherwise, including when the only signatures are revoked. `signature` carries `{ id, major, minor, signedAt }` of the covering or outdated active signature, else `null`; `revoked` carries `{ major, signedAt, revokedAt }` of the viewer's newest revoked signature on this document when `state` is `ready` and one exists, else `null` (the revocation reason code and the revoker are never exposed), which is what the notice "revocation applies to future pull requests only" needs
- `emails` is the viewer's verified addresses from the server-side session snapshot that E10 captured at login (never re-fetched, because no user token is stored). When the list is empty, `canSign` is `false` and `blockedReason` is `no_verified_email`; otherwise `canSign` is `true` and `blockedReason` is `null`
- Cross-tenant test (two tenants via `seedTenant(db, 1)` and `seedTenant(db, 2)`): the same viewer asking for tenant 1's repository never receives tenant 2's document, version or signatures, and a signature for tenant 2's document does not turn tenant 1's state into `already_signed`

**E13-S03 — Typed name and verified email validation** ⬜ Todo
The two free inputs of the consent form are validated by one shared schema and one pure function, so the browser and the server agree.
Acceptance criteria:
- `signerInputSchema` in `src/shared` parses `{ name, email }`. `name` is Unicode-normalised to NFC, trimmed, has internal whitespace runs collapsed to one space, and must then be 1 to 200 code points (counted with `[...name].length`, not UTF-16 units). Boundary tests: 0, 1, 200 and 201 code points, including a name made of astral characters
- A name containing a control character (Unicode `Cc`), U+2028, U+2029, or a bidirectional override or isolate (U+202A to U+202E, U+2066 to U+2069) is rejected with issue code `invalid_name`; the API maps it to `422`. Nothing else is rejected: hostile but printable names are stored verbatim after normalisation
- Hostile-name tests import `HOSTILE_NAMES` from `src/shared/hostile-names.ts` (E09-S01, the single corpus; this epic defines no list of its own): every entry parses to the same string (apart from NFC, trim and whitespace collapsing). Output neutralisation is the job of each output (E09 comment, E16 CSV, E18 screens), not of storage
- `resolveSignerEmail(verified, requested)` is a pure function in `src/server/domain`: it trims the request, compares case-insensitively against the verified list, and returns the address exactly as GitHub reported it (original casing), or a typed failure. It never accepts an address that is not in the list, and never returns an address the viewer did not request
- Failures: an address not in the verified list is `422` `email_not_verified`; an empty verified list is `422` `no_verified_email`. The error body never echoes the submitted name or email
- The stored email is at most 254 characters; a longer value cannot match any verified address and fails as `email_not_verified`. Format validation of the address is not attempted, because membership in the verified list is the only proof used
- Table-driven tests cover: case differences, surrounding whitespace, a lookalike with a Unicode homoglyph (not matched), an address that is verified for another viewer (not matched, since the list is per session), and duplicates in the list

**E13-S04 — Record a signature** ⬜ Todo
The write path: a verified, immutable signature plus its erasable personal data, in one transaction.
Acceptance criteria:
- `POST /api/sign`, behind the session, CSRF token and `Origin` checks of E10. Body (zod, `.strict()`):
  ```json
  {
    "githubRepoId": 123,
    "prNumber": 45,
    "versionId": 31,
    "contentSha256": "<64 lowercase hex>",
    "consentTextId": "individual-v1",
    "name": "Ada Lovelace",
    "email": "ada@example.org"
  }
  ```
  `prNumber` is optional (same range as `pr` in E13-S02); unknown keys are `400`
- Checks run in this order and stop at the first failure: schema (`400`); repository and tenant resolution with the same `404` as E13-S02; `no_active_cla` (`409`); `versionId` must equal the document's current `active_version_id`, else `409` `stale_version` with `current: { versionId, major, minor, contentSha256 }` so the page can reload; `contentSha256` must equal the stored `cla_versions.content_sha256`, else `422` `hash_mismatch`; `consentTextId` must equal `CURRENT_CONSENT_ID.individual`, else `409` `stale_consent`; a document whose `kind` is not `individual`, `409` `unsupported_document_kind` (corporate signing is E21); name and email per E13-S03. A `versionId` that belongs to another tenant's document fails exactly like an unknown id (`stale_version`), so it confirms nothing about that tenant
- One transaction inserts: a `signatures` row (`installation_id` of the repository, `user_id` of the session user, `document_id`, `version_id`, `major` and `content_sha256` copied from the version row, `consent_text_id`, `signer_type = 'individual'`, `source_repository_id` and `source_pr_number` from the request, `signed_at` from the database clock); a `signer_pii` row (`name`, the verified `email`, and the `login` snapshot from `users.login`); and one `audit_log` row `signature.created` (actor = viewer's GitHub id, `installation_id`, subject `signature`/id, metadata `{ document_id, version_id, major, source_repository_id, source_pr_number }` and no name, email or login). The audit row goes through the E04-S09 writer. Success is `201` with `{ "signature": { "id", "versionId", "major", "minor", "signedAt" }, "created": true }`, never with name or email
- Hostile-name test: every entry of `HOSTILE_NAMES` (E09-S01) is submitted, then read back from `signer_pii.name`, and equals the normalised input byte for byte; none is rejected, and none appears in any `signatures` or `audit_log` column
- Double submit is idempotent: the insert uses `on conflict` on the partial unique index `signatures_active_unique (user_id, document_id, major) where revoked_at is null`. When a non-revoked signature for that document and major already exists, nothing is written (no second `signer_pii`, no audit row, no job), the stored name and email are not overwritten, and the response is `200` with `created: false` and the existing signature. This also covers a minor bump: signing minor 1 of a major the viewer already signed returns the old signature instead of creating a second one
- Real-Postgres-only test (`test.skipIf(!realPostgres)`): 10 simultaneous identical requests and 10 simultaneous requests with different names produce exactly one `signatures` row, one `signer_pii` row and one audit row, with one `201` and nine `200`. A sequential PGlite test covers the same outcome
- A viewer whose earlier signature was revoked can sign again: the test revokes with a direct owner-role update (the revoke route ships in E15), then expects a new row with `201`, the revoked row untouched, and both rows present because the partial unique index only covers non-revoked rows
- `@fastify/rate-limit` allows 10 sign requests per minute per session user (keyed on the user id, not the IP); the 11th is `429` with `retry-after`
- Cross-tenant tests: a signature written for tenant 1's repository carries tenant 1's `installation_id` and never covers tenant 2's document; sending tenant 2's `githubRepoId` with tenant 1's `versionId` is `stale_version`

**E13-S05 — Optional network metadata on signatures** ⬜ Todo
IP address and user agent are off by default; a configuration flag switches recording on for operators who have documented a legitimate interest.
Acceptance criteria:
- A new environment variable `RECORD_NETWORK_METADATA` is validated by the zod env schema: `true` or `false`, default `false`; any other value is a start-up error that names the variable. It is documented in `.env.example` and in the `docs/configuration.md` table in the same change
- A forward-only migration adds `signer_pii.ip_address inet null` and `signer_pii.user_agent text null` with `check (user_agent is null or length(user_agent) <= 512)`. No network column is added to `signatures` or `audit_log`, so the immutable core and the audit trail stay free of it. The runtime role's existing table-level `insert` grant on `signer_pii` covers the new columns (proved in an `asRuntimeRole` test)
- With the flag `false` the sign handler does not read `request.ip` or the `User-Agent` header at all: a test passes a request double whose `ip` and `headers['user-agent']` getters throw and expects `201`. The stored columns stay `NULL`, and the log line of the request is unchanged (method and path only)
- With the flag `true` the handler stores `request.ip` as resolved by the `TRUST_PROXY` setting (E04) and the `User-Agent` header with control characters removed and truncated to 512 characters. A missing header stores `NULL`. Tests cover an IPv4 address, an IPv6 address, an IPv4-mapped IPv6 address, a 600 character user agent and a user agent with a newline
- The idempotent replay of E13-S04 neither overwrites nor adds network values; a second request from another address leaves the first stored address intact
- Network values never appear in `audit_log.metadata`, in logs, in the `201` and `200` bodies or in the own-signatures list (E13-S06); a test greps the audit row and the captured log output for the test IP and user agent
- Retention and purging of these columns belong to E16-S05; this story only guarantees that nothing is written when the flag is off

**E13-S06 — Own signatures list** ⬜ Todo
A signed-in contributor can see every CLA they signed, across all orgs on the instance, and whether each still covers them.
Acceptance criteria:
- `GET /api/me/signatures?limit=<1..100>&cursor=<opaque>` with a session; the user comes only from the session, there is no user id in the path or query. Default `limit` is 50. Order is `signed_at desc, id desc`; `cursor` is an opaque value encoding that pair, validated by zod, and a tampered cursor is `400`
- Each item: `id`, `installation: { accountLogin, accountType, suspended }`, `document: { id, name }`, `version: { id, major, minor }`, `signedAt`, `source: { repositoryFullName, prNumber } | null`, `state`, `revokedAt` (null unless revoked), and `resignPath` (`/sign/{githubRepoId}` or `null`). Names and emails, `signer_pii`, `revoke_reason` and `revoked_by` are never part of the item
- `state` comes from one pure function `signatureState(signature, activeMajor)`: `revoked` when `revoked_at` is set; `outdated` when not revoked and the signature's major is lower than the document's active major; `active` otherwise. Table tests cover each branch and a document without an active version
- `resignPath` is set for `outdated` and `revoked` items: the source repository's `github_repo_id` when it still exists, otherwise the lowest `github_repo_id` among repositories whose `cla_document_id` is that document, otherwise `null`
- Isolation test: with signatures of users 1 and 2 across tenants 1 and 2, user 1 sees exactly their own rows from both tenants and none of user 2's; a request carrying `?userId=2` or `?githubId=2` ignores the parameter (it is not in the schema, so `400`)
- Rows of a suspended installation stay listed with `installation.suspended: true`; signatures are retained (`docs/security.md`, Auth model: uninstall and suspend)
- A user without signatures gets `200` with `{ "items": [], "nextCursor": null }`. Pagination test with 120 rows and ties on `signed_at`: three pages, no duplicate, no gap

**E13-S07 — Re-evaluate pull requests after signing** ⬜ Todo
Signing must turn the red check green without waiting for the next push or the scheduled sweep.
Acceptance criteria:
- In the same database transaction as the insert of E13-S04, and only when `created` is `true`, the handler enqueues an `evaluate-pr` job (E07) for (`source_repository_id`, `source_pr_number`) when both are present. The job keys per (repository, PR) so a queued evaluation is never dropped (E07 policy)
- The handler also enqueues evaluation for the signer's other failing PRs in the same tenant: the latest `pr_evaluations` row per (repository, PR number) with `result = 'failure'`, in repositories whose `cla_document_id` is the signed document, where the recorded failure lists the signer's numeric GitHub id among the uncovered identities (read through the zod schema E08 exports for `pr_evaluations.details`). At most 25 PRs, newest `updated_at` first, the originating PR excluded and nothing enqueued twice. PRs beyond the cap are left to the E07 reconciliation sweep
- Every query in this story filters by the signature's `installation_id`; cross-tenant test: a failing PR of tenant 2 that lists the same numeric user id is never enqueued after the user signs for tenant 1
- Because enqueue and insert share one transaction, a failure injected into the enqueue rolls the signature back: the client gets `500`, no `signatures`, `signer_pii` or audit row remains, and a retry succeeds. The test covers it with an enqueue port that throws once
- The job cannot start before the signature is committed. The job re-fetches PR state and reads signatures last (E08), so an integration test with GitHub stubbed by MSW goes: PR evaluated to `failure` with a failing `license/cla` Check Run, viewer signs, job runs, the Check Run is updated to `success` (E09)
- A replayed request (`created: false`) enqueues nothing. A closed PR in the candidate set is harmless: the job sees the closed state at run time and does nothing. E15-S01 later narrows the candidate query to open PRs
- A signature without `prNumber` (signing from the dashboard) skips the originating-PR job but still runs the failing-PRs lookup
