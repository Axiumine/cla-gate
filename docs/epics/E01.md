# E01 — Repository governance and licensing

**Bounded Context:** BC-08
**Priority:** 🔴 Must have
**Status:** ✅ Done

**Goal:** The repository is public, licensed AGPL-3.0-only, and every change reaches `main` through a pull request whose required checks pass. A developer who self-hosts the platform can rely on its licence, its history and its written contract before any application code exists.
**Depends on:** none.
**Out of scope:** The content of the quality gates (E02), the structure-cap tool (E03), extended gates such as Semgrep, Trivy, Stryker, Playwright and Qodana, which become required checks later (E20), the AGPL section 13 source link in the web footer (E17), and everything about running the product on a server (E19). No container image or release artefact is published anywhere: operators build from the checkout.

---

**E01-S01 — Licence the repository under AGPL-3.0-only** ✅ Done
The platform is a network service that anyone may self-host. AGPL-3.0-only keeps modified copies open without restricting an unmodified install.
Acceptance criteria:
- `LICENSE` at the repository root is the unmodified text of the GNU Affero General Public License version 3 (19 November 2007).
- `package.json` has `"license": "AGPL-3.0-only"` and `"private": true`; the SPDX identifier is `AGPL-3.0-only` (never `-or-later`) in `package.json`, in every source header (E01-S02) and in README.md and CLAUDE.md.
- CONTRIBUTING.md, section "Licence and dependencies", fixes the dependency rule: every dependency must be AGPLv3-compatible (MIT, BSD, ISC, Apache-2.0, LGPL-3.0 and GPL-3.0 are fine, GPL-2.0-only is not). SSPL, BUSL, PolyForm and Apache-1.x are rejected, and no code is copied from an incompatible source.
- Hard rule 8 in CLAUDE.md makes the licence check part of the "new dependency needs justification" rule, together with Knip, Trivy and supply-chain cost.
- Dev-only tools under other compatible licences are accepted and recorded in `docs/tooling-gotchas.md` (SonarJS is LGPL-3.0-only, `eslint-plugin-no-unsanitized` is MPL-2.0).
- The Semgrep rules cache `rules/` is git-ignored and never committed, because the Semgrep Rules License forbids redistribution inside an AGPL repository (`docs/tooling-gotchas.md`, Semgrep).
- README.md, section "License", records why AGPL and not GPL: section 13 closes the hosted-fork gap, and running an unmodified copy for your own repositories needs nothing beyond the source link.
- The section 13 obligation is recorded as a product requirement (a visible footer link in the dashboard to the exact repository and commit); delivering it is E17.

**E01-S02 — Put an SPDX header on every source file** ✅ Done
Acceptance criteria:
- Every tracked `.ts` and `.mjs` file starts with `// SPDX-License-Identifier: AGPL-3.0-only` on line 1 and `// Copyright (C) 2026 Giovanni Manzoni` on line 2. This covers `scripts/`, `types/eslint-plugin-no-unsanitized.d.ts`, `vitest.config.ts` and `eslint.config.mjs`.
- Every tracked `.yml` file except `.yarnrc.yml` (`.github/workflows/ci.yml`, `.github/dependabot.yml`, `lefthook.yml`) and `mise.toml` carries the same two lines as `#` comments at the top.
- Exempt by nature: `LICENSE`, Markdown, JSON (`package.json`, `tsconfig*.json`, `biome.json`, `knip.json`, `fta.json`, `.code-caps-baseline.json`), `yarn.lock`, `.nvmrc`, `.gitignore` and the one-line `.yarnrc.yml`.
- Decision: file kinds added later use the same two lines in their own comment syntax (`--` for SQL migrations, `//` for `.tsx`), so the rule never has to be re-argued per file type.
- Verified when this epic closed: listing every tracked `.ts`, `.mjs`, `.yml` and `.toml` file whose first three lines lack `SPDX-License-Identifier: AGPL-3.0-only` returns only `.yarnrc.yml`.
- No automated check enforces the header today; the rule lives in the opening paragraphs of CLAUDE.md and in CONTRIBUTING.md ("Licence and dependencies") and is applied in review. A new file without it is a review finding, not a gate failure.

**E01-S03 — Protect `main` with required checks** ✅ Done
Acceptance criteria:
- The repository is `Axiumine/cla-gate`, public, with `main` as the default branch. CONTRIBUTING.md, section "Repository protection", records the settings as applied on 2026-11-01.
- Required status checks on `main` are exactly `static` and `coverage`, not strict, so a branch need not be up to date before merging.
- Linear history is required (squash or rebase merges only), force pushes and branch deletion are blocked, and conversation resolution is required.
- `enforce_admins` is on: the rules apply to the maintainer too, so there are no direct pushes to `main` and every change, documentation included, goes through a pull request.
- No review approval is required (single maintainer, self-approval is impossible); the protection therefore relies on the two checks, which must be real (E02-S08), never placeholders that always pass.
- The job names in `.github/workflows/ci.yml` are exactly `static` and `coverage`; renaming a job breaks the rule, and CLAUDE.md and CONTRIBUTING.md say so.
- Verification: the settings exist only on GitHub, so they are read back with `gh api repos/Axiumine/cla-gate/branches/main/protection`, which returns the required status check contexts `static` and `coverage`, linear history, `enforce_admins`, conversation resolution and blocked force pushes and deletions.
- The history after the initial commit is linear and each later commit carries its pull request number (`#1` documents the protection, `#2` scaffolds the tooling).
- CONTRIBUTING.md records the emergency unblock (`gh api -X DELETE repos/Axiumine/cla-gate/branches/main/protection/required_status_checks`, maintainer only, checks re-added afterwards).
- Rule for the future: `e2e`, `mutation`, `semgrep` and `trivy` become required checks only after they are stable in CI (E20), and any change to the protection updates CONTRIBUTING.md (and the Branch protection lines of CLAUDE.md when they change) in the same pull request.
- The runners behind the required checks, the fork pull request approval gate and the break-glass for the case that every runner is offline are defined in [CI runners, ports and fork approval](../ci-runners.md); the job names stay `static` and `coverage` whatever the runner.

**E01-S04 — Keep README.md and CLAUDE.md as the written contract** ✅ Done
README.md says what the product is and how to try it and maps the documents; CLAUDE.md is the short operating contract for humans and coding agents, and points to the documents that hold the rest.
Acceptance criteria:
- README.md is a landing page of at most 10240 bytes (`scripts/docs/doc-size.test.ts` enforces it): it holds the product scope (MVP, later, non-goals), a short numbered flow, the quick start, summaries of the architecture, the GitHub App and the quality gates, the documentation map, the roadmap and the licence. The detail lives in `docs/architecture.md` (stack, layering, sequence diagram), `docs/repository-layout.md`, `docs/security.md` (auth model with the role matrix, security and privacy), `docs/data-model.md` (the data model table), `docs/github-app.md` (the permission table), `docs/operations.md`, `docs/toolchain.md` (tool evaluation, hook pipeline, CI), `docs/decisions.md` (the decisions table, open questions), `docs/development.md` (development steps) and `docs/configuration.md`.
- CLAUDE.md is at most 6144 bytes (same test) and holds the ten hard rules, the cross-cutting rules, the branch protection summary and a table of the documents that hold the rest: the commands table with a `State` column (`exists` or `deferred`) in `docs/development.md`; the thresholds table, the TypeScript rules and the testing rules in `docs/quality-gates.md`; the architecture rules in `docs/architecture.md`; the tooling gotchas in `docs/tooling-gotchas.md`; the caps-tool description in `scripts/code-caps/README.md`; the repository protection in `CONTRIBUTING.md`; the GitHub App rules in `docs/github-app.md` (Rules).
- A deferred script is a contract: `docs/development.md` forbids adding a placeholder script for a tool that is not wired.
- Hard rule 10 ("Keep the documents true") and the last line of CLAUDE.md require a changed decision to update the document that owns it in the same change; hard rule 9 forbids committing or pushing unless asked and forbids rewriting history on shared branches.
- README.md and `docs/development.md` state the verification date (2026-11-01) for versions, flags and config keys, and `docs/development.md` says to re-check with `yarn npm info <pkg> version` before pinning.
- Every Markdown table in the project's Markdown files uses the `|---|---|` separator style, and `biome.json` switches the Markdown formatter and linter off so nothing rewrites it (E02-S03).
- Facts that were not verifiable at writing time are written as a Verify acceptance criterion in the story that owns them, or listed under "Open verifications without a story" in `docs/tooling-gotchas.md`, and are deleted when resolved, never silently assumed.

**E01-S05 — Define the gitignore policy** ✅ Done
The caps tool trusts `.gitignore` inside a git checkout, so the ignore file is part of the quality gate, not a convenience.
Acceptance criteria:
- `.gitignore` lists dependency and package-manager state: `node_modules/`, `.yarn/cache/`, `.yarn/unplugged/`, `.yarn/install-state.gz`, `.pnp.*`.
- `.gitignore` re-includes `!.yarnrc.yml`, and `.yarnrc.yml` is tracked: without it a clean checkout falls back to Yarn's PnP linker and ESLint and Vitest fail (`docs/tooling-gotchas.md`). Some global git ignores list that file, hence the explicit re-include.
- `.gitignore` lists every build and report output directory the caps tool would otherwise measure as source: `dist/`, `build/`, `coverage/`, `reports/`, `playwright-report/`, `test-results/`, `.stryker-tmp/`, `.vitest/`, plus `*.tsbuildinfo`. Each directory name in `OUTPUT_DIRS` of `scripts/code-caps/files.ts` appears in this list.
- Secrets never enter the repository: `.env`, `.env.*` (with `!.env.example` as the only tracked variant), `*.pem` and `*.key` are ignored.
- Editor, OS and local tool state (`.idea/`, `.vscode/`, `*.log`, `.DS_Store`, local tool directories) is ignored.
- The rule that "outputs must be listed" is written next to the list in `.gitignore` and in `scripts/code-caps/README.md`, so removing an entry is visibly a gate change.
- `git ls-files` shows `.yarnrc.yml` and no file under any ignored directory.

**E01-S06 — Keep dependencies and Actions current with Dependabot** ✅ Done
Acceptance criteria:
- `.github/dependabot.yml` is version 2 with two ecosystems on `/`: `github-actions` and `npm`, both `weekly` on Monday with `cooldown.default-days: 7`, on top of Yarn's one-day `npmMinimalAgeGate`.
- The `github-actions` ecosystem groups all updates into one pull request (`groups.github-actions`, pattern `*`) with commit prefix `ci`; because Actions are pinned to full commit SHAs, Dependabot rewrites the SHA and the version comment together.
- The `npm` ecosystem has `open-pull-requests-limit: 5` and commit prefix `deps`.
- `typescript` ignores `version-update:semver-major` and `version-update:semver-minor`, so the compiler stays on `~6.0.x` (`docs/quality-gates.md`, TypeScript); patch releases still arrive.
- Groups keep coupled packages together: `vitest` (`vitest` and `@vitest/*`, because `@vitest/coverage-v8` must match the exact Vitest version), `eslint` (`eslint`, `@eslint/*`, `eslint-plugin-*`, `typescript-eslint`) and `dev-tooling` (all other minor and patch updates).
- Dependabot only opens pull requests; nothing in the file merges anything, and every update must pass `static` and `coverage` like any other change (E01-S03).
- The file header explains why the cooldown and the SHA pinning exist, so a later reader does not remove either.
- Dependabot pull requests run the CI jobs on the shared self-hosted runners without fork approval, so the lockfile diff of a dependency pull request is read before it is merged and every Action stays pinned by full commit SHA, as [CI runners, ports and fork approval](../ci-runners.md) (Known unknowns and risks) requires.
