# E19 — Self-hosting kit

**Bounded Context:** BC-09
**Priority:** 🔴 Must have
**Status:** ⬜ Todo

**Goal:** Let any developer run the platform on their own server with one command, `docker compose up --build`, and finish with a working GitHub App created through GitHub's app-manifest flow. One instance runs per server with one GitHub App and serves several GitHub organisations and accounts (each installation is a tenant), and the operator never hand-assembles secrets, database roles or reverse-proxy rules.
**Depends on:** E04, E05, E17, E23.
**Out of scope:** Publishing images anywhere: the image is always built from the checkout, with no registry, no release-image workflow, no SBOM and no provenance attestation. Kubernetes manifests and Helm charts. Several application replicas on one database (a shared rate-limit store is not provided). A hosted service run by the project. The GitHub App core, login and webhook behaviour (E05, E06, E10), which this epic only provisions credentials for. Container and dependency scanners beyond the Dockerfile misconfiguration pass (E20).

---

**E19-S01 — Container image built from the checkout** ⬜ Todo
One image serves the API and the built single-page app from one origin. It is built locally by `docker compose up --build`; nothing is ever pushed.
Acceptance criteria:
- Multi-stage `Dockerfile` using the official Node image, Debian slim variant, pinned by exact tag and digest; `ARG NODE_VERSION` equals `.nvmrc` (a Vitest test fails when they differ). Stage `deps` installs Corepack (`npm install -g corepack@0.36.0 && corepack enable`), copies only `package.json`, `yarn.lock` and `.yarnrc.yml`, and runs `yarn install --immutable --mode=skip-build` (a Docker build context has no `.git`, so the `lefthook install` postinstall is skipped). Stage `build` runs `yarn build` (SPA to `dist/web`, server to `dist/server`). Stage `prod-deps` installs production dependencies only. Stage `runtime` is the final one.
- The `runtime` stage contains `dist/`, the production `node_modules`, `migrations/`, `package.json` and `LICENSE`, plus `libatomic1` if the base image lacks it (Node 26 links it). It contains no Yarn, no Corepack, no dev dependencies, no sources, tests, `.git`, `.env` or `secrets/`. Dependency layers depend only on the three lockfile inputs, so a source change does not reinstall packages.
- `USER 10001:10001` (numeric, so orchestrators can verify non-root); the application tree is owned by root and not writable by that user. `ENV NODE_ENV=production HOST=0.0.0.0 PORT=3000`, `EXPOSE 3000`, `CMD ["node", "dist/server/main.js"]` in exec form. The same image runs migrations with `node dist/server/migrate.js` from the directory that holds `migrations/`.
- `HEALTHCHECK --interval=15s --timeout=3s --start-period=20s --retries=3` runs `node dist/server/healthcheck.js`. `src/server/healthcheck.ts` is a logic-free entry point over a tested `checkHealth({ port, fetch, timeoutMs })`, which GETs `http://127.0.0.1:$PORT/healthz` and succeeds only on status 200 with body `{"status":"ok"}`. Unit tests: 200, 500, wrong body, timeout, connection refused. Liveness (`/healthz`) is chosen on purpose: a database outage must not mark the container unhealthy and trigger restarts; load balancers use `/readyz`.
- Read-only root filesystem friendly: the server writes nothing outside `/tmp` and logs JSON to stdout. The PR records a manual run with `--read-only --tmpfs /tmp`; E19-S08 automates the assertion.
- Build metadata: `ARG SOURCE_COMMIT=unknown` becomes `ENV SOURCE_COMMIT` (read by `/api/meta`, E17-S09); OCI labels `org.opencontainers.image.source`, `.revision`, `.licenses=AGPL-3.0-only` and `.title` are set. `SOURCE_URL` is not baked in; it stays a runtime variable so a fork can point at its own repository.
- `.dockerignore` excludes `.git`, `node_modules`, `dist`, `coverage`, `reports`, `.vitest`, `.stryker-tmp`, `e2e`, `playwright-report`, `test-results`, `.env*` (except `.env.example`), `secrets/`, `*.pem` and `*.tsbuildinfo`. A test asserts each entry, and that no `runtime` stage instruction copies the whole build context (`COPY . .` appears only in `build`).
- No publication path exists: a Vitest test scans `.github/`, `scripts/` and every `docker*.yml` (excluding the test file itself) and fails on `docker push`, `docker login`, `login-action`, `packages: write` or a `push: true` build option.
- The Dockerfile passes Trivy's misconfiguration pass with no finding and no `.trivyignore` entry (non-root user and `HEALTHCHECK` present). Until E20 wires `yarn trivy`, the PR description records a manual `trivy config .` result.
- Containers and ports of this story follow [CI runners, ports and fork approval](../ci-runners.md): the image is built from the checkout with no registry, the container-side port 3000 is not a host port, and every CI or test use of the image gets a random free loopback host port above 32768 and a per-run name, with cleanup in an `if: always()` step.

**E19-S02 — Secrets from files and start-up diagnostics** ⬜ Todo
Docker secrets arrive as files, and an operator needs to know exactly which setting is wrong without ever seeing a secret.
Acceptance criteria:
- For every secret variable `N` there is an `N_FILE` variant: at least `DATABASE_URL`, `MIGRATION_DATABASE_URL`, `SESSION_SECRET`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_WEBHOOK_SECRET`, `GITHUB_CLIENT_SECRET` and the new `SETUP_TOKEN`, plus the secret variables E05, E06 and E10 add (for example the previous webhook secret kept during rotation). The list is one exported `SECRET_VARIABLES` constant. A test walks the zod environment schema and fails when a field that produces a `Secret` has no `_FILE` entry, or when an entry has no schema field.
- Resolution happens once at start-up, before schema parsing, in `src/server/config/`: the file is read synchronously, one trailing `\n` or `\r\n` is removed and all other whitespace is kept, symlinks are followed, and the value is parsed exactly as if it had been in `N`. An empty file, or an empty `N_FILE`, counts as unset (the compose stack uses empty placeholder files for credentials that do not exist yet).
- Failures name the variable and the cause, never the content: both `N` and `N_FILE` set is `N, N_FILE: set only one`; a missing, unreadable or directory path is `N_FILE: cannot read /run/secrets/x (ENOENT)`; a file over 64 KiB is `N_FILE: file is larger than 64 KiB`. The migration entry point uses the same resolver for `MIGRATION_DATABASE_URL_FILE` and `DATABASE_URL_FILE`.
- `ConfigError` reports every invalid variable at once, one line each in the form `VARIABLE: <rule that failed>`, for example `PUBLIC_BASE_URL: must be an origin such as https://cla.example.com (scheme and host only); https is required when NODE_ENV=production`. It is printed to stderr as plain text before the logger exists and the process exits non-zero. Hostile test: for every variable, the value `LEAKCANARY-<name>` is invalid or supplied through a file, and the string `LEAKCANARY` never appears in stdout, stderr or the error object.
- Mode resolution returns `setup` or `normal`. When all five GitHub App variables (`GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_WEBHOOK_SECRET`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`) are set, the mode is `normal`. When none is set (after treating empty as unset), the mode is `setup` and `SETUP_TOKEN` (at least 32 characters) is required: `SETUP_TOKEN: required while no GitHub App is configured; set it, or set the GITHUB_* variables`. When only some are set, the error lists the missing ones. E05 makes the variables required; this story relaxes that to this single case. In `normal` mode a set `SETUP_TOKEN` is ignored with a logged warning that names the variable.
- Start-up database check: before listening, the server runs `select 1` as the runtime role, retrying 5 times with 2 s back-off. A failure prints `database: cannot connect (ECONNREFUSED); check DATABASE_URL and that the database is up`, using the error code only, never the connection string or driver message, and exits non-zero.
- Unit tests cover every branch (both set, file errors, trailing newline variants including `\r\n` only, placeholder file, all/none/partial GitHub variables, production without `SESSION_SECRET` in `normal` mode) and the `LEAKCANARY` guarantee. `docs/configuration.md` gains the `*_FILE` convention, `SETUP_TOKEN`, `SOURCE_URL` and `SOURCE_COMMIT` in the same change.

**E19-S03 — Idempotent database provisioning script** ⬜ Todo
One script defines the database and its two roles for every environment: the compose stack, an operator's existing server and a developer's LAN server.
Acceptance criteria:
- `scripts/provision-database.sh` (POSIX `sh`, executable) drives `psql` (version 15 or later, for `\getenv`) with `scripts/provision-database.sql`. Admin access comes from libpq's own variables (`PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE` defaulting to `postgres`, `PGSSLMODE`, `PGPASSWORD`, `PGPASSFILE`, `PGSERVICE`). When none of `PGPASSWORD`, `PGPASSFILE` or `PGSERVICE` is set and stdin is a terminal, the script prompts for the admin password with echo disabled; without a terminal libpq's rules apply (a local socket with trust or peer authentication needs no password, which is how the compose stack's first boot runs it).
- Secrets are never printed or stored: the admin password and the new role passwords travel only through the environment of the `psql` child and `\getenv`, never through argv (so not visible in `ps`), a temp file, a `-v` assignment, shell tracing (`set +x` is enforced) or psql history (`PSQL_HISTORY=/dev/null`, `-X`). A test runs the script with sentinel passwords and asserts the sentinels appear in none of stdout, stderr or the process arguments captured during the run.
- Inputs: `CLA_DB_NAME` (default `cla`), `CLA_OWNER_ROLE` (default `cla_owner`) and `CLA_OWNER_PASSWORD` and `CLA_APP_PASSWORD`, each also readable from `<NAME>_FILE` (same convention as E19-S02) or prompted twice on a terminal. The runtime role name is fixed at `cla_app` because migration 001 grants to that name. Passwords shorter than 16 characters and names not matching `^[a-z_][a-z0-9_]{0,62}$` exit 2 before any SQL runs; a hostile name such as `x"; drop database postgres; --` is rejected, and all identifiers reach SQL through `format('%I')`.
- End state on every run, with the second run printing `unchanged` for each step and exit code 0: `cla_owner` and `cla_app` are `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, neither is a member of the other; the database exists with `UTF8` and owner `cla_owner`; `PUBLIC` has no `CONNECT` or `CREATE` on it and `cla_app` has only `CONNECT`; `PUBLIC` has no `CREATE` on schema `public`; `cla_app` owns nothing and cannot create objects. The script sets no `ALTER DEFAULT PRIVILEGES` on application tables, so the explicit, minimal grants of the migrations stay the only table access and the immutable tables never gain write access by default.
- Role attributes are enforced even when the role pre-exists (a pre-existing superuser `cla_app` is corrected). Passwords are set on creation and re-set whenever supplied; an existing role with no supplied password keeps its password. Creating a role with no password source exits 2. A pre-existing database with a different owner exits 3 with "refusing to change the owner of an existing database"; the script never drops anything.
- Schema `pgboss` is created and owned by `cla_owner`, with `USAGE` for `cla_app` and default privileges (for objects the owner creates in that schema only) granting `cla_app` the table, sequence and function access pg-boss needs. E07 installs the queue tables as the owner role (a plain migration step or pg-boss's construction plan) so the runtime role never owns a table; if E07 decides otherwise, this bullet and `docs/data-model.md` change together.
- Output is one line per step and, at the end, connection string templates with a `<password>` placeholder: `DATABASE_URL=postgres://cla_app:<password>@HOST:PORT/cla` and `MIGRATION_DATABASE_URL=postgres://cla_owner:<password>@HOST:PORT/cla`, with a reminder to percent-encode special characters. Exit codes: 0 done, 2 invalid input, 3 refused because of a conflict, 4 connection or SQL error.
- `CLA_TEST_ROLE` and `CLA_TEST_PASSWORD` (or `_FILE`) optionally create a development-only role `LOGIN CREATEDB CREATEROLE NOSUPERUSER` that can create the throwaway test databases (E19-S10). It has no `CONNECT` on the application database, and the script refuses to create it when `NODE_ENV=production` is set.
- Real-Postgres-only tests (skipped without `CLA_ROLE_TESTS=1`, which CI sets against the disposable Postgres 18 container that `scripts/ci/postgres.ts` starts; roles are cluster-wide, so they must never run against a shared server): first run, second run (a `pg_roles`, `pg_database` and ACL snapshot is identical), password re-set, existing-superuser correction, owner conflict (exit 3), hostile names, missing password, `pgboss` privileges, and migrating afterwards as `cla_owner` so that `migration-001-runtime-role` assertions hold on a database provisioned by this script.
- CI jobs, containers and ports of this story follow [CI runners, ports and fork approval](../ci-runners.md): the real-Postgres role tests run only against the disposable container that `scripts/ci/postgres.ts` starts (random free loopback port above 32768, per-run name, cleanup in an `if: always()` step), never against a shared server.

**E19-S04 — Operator compose stack with migrations and secrets** ⬜ Todo
Acceptance criteria:
- `docker-compose.yml` becomes the operator stack (project name `cla-gate`). The existing development-database file moves to `docker-compose.dev.yml` (`yarn db:up` runs `docker compose -f docker-compose.dev.yml up -d --wait postgres` with `POSTGRES_PORT` set to a random free loopback port; the file keeps no default host port) and calls the provisioning script with its well-known development passwords, replacing `docker/postgres-init.sql` so the roles are defined in one place. `docs/development.md` (Setup and run, Commands) is updated in the same change.
- Service `postgres`: image `postgres:18`, `POSTGRES_PASSWORD_FILE` from a secret, the provisioning script mounted read-only into `/docker-entrypoint-initdb.d/` (it creates `cla`, `cla_owner`, `cla_app` and `pgboss` on the first start of an empty volume, reading the role passwords through `*_FILE`), volume `cla-postgres-data` at `/var/lib/postgresql`, `pg_isready` health check, no `ports:` entry. It sits on an `internal: true` network named `backend`.
- Service `migrate` (same build as `app`): `command: ["node", "dist/server/migrate.js"]`, `restart: "no"`, only the `migration_database_url` secret, `depends_on` `postgres` `service_healthy`. Service `app`: `depends_on` `migrate` `service_completed_successfully`, only `database_url`, `session_secret` and the GitHub credential secrets, joined to `backend` and to the default network (it needs outbound access to GitHub). The app container therefore never holds owner credentials, and a failed migration (including a refused checksum mismatch) stops the stack before the app starts. The migration runner's advisory lock makes concurrent runs safe.
- `app` and `migrate` set `read_only: true`, `tmpfs: [/tmp]`, `cap_drop: [ALL]`, `security_opt: ["no-new-privileges:true"]`, `init: true` and, for `app`, `restart: unless-stopped` and `stop_grace_period: 30s`. `app` publishes `${BIND_ADDRESS:-127.0.0.1}:${PORT:-3000}:3000` (loopback by default; the host-port default `3000` is the operator stack's deployment setting, the exception recorded in the CI runners policy, and CI, the smoke test and the tests override it with a random free loopback port), builds with `args: SOURCE_COMMIT: ${SOURCE_COMMIT:-unknown}` and is tagged `cla-gate:local`.
- The default network has an explicit subnet (`${EDGE_SUBNET:-172.30.30.0/24}`) and `app` gets `TRUST_PROXY: ${TRUST_PROXY:-172.30.30.0/24}`, so the compose proxy (E19-S05) and a proxy on the host (whose traffic arrives from the network gateway) are trusted while nothing outside the subnet is.
- `scripts/init-secrets.sh` (POSIX `sh`) creates `secrets/` (mode 0700) and, only for files that do not exist yet, generates: `db_admin_password`, `db_owner_password`, `db_app_password`, `session_secret`, `setup_token` (each 64 hex characters from `openssl rand -hex 32` or `/dev/urandom`), the derived `database_url` and `migration_database_url` (the passwords are URL-safe), and empty placeholders `github_app_private_key`, `github_webhook_secret`, `github_client_secret`, `github_app_private_key_previous` and `github_webhook_secret_previous` (the last two stay empty outside a key or secret rotation). Files are mode 0444 inside the 0700 directory, because a bind-mounted file secret keeps host ownership and the container user could not read a 0400 file; the `docs/operations.md` documents this trade-off. It also copies `.env.example` to `.env` when absent. It prints the names of the files it created, never a value, and tells the operator that the setup token is in `secrets/setup_token`.
- `.env.example` lists every non-secret variable the compose file reads or the application accepts (`PUBLIC_BASE_URL`, `BIND_ADDRESS`, `PORT`, `TRUST_PROXY`, `EDGE_SUBNET`, `LOG_LEVEL`, `SOURCE_URL`, `SOURCE_COMMIT`, `GITHUB_APP_ID`, `GITHUB_CLIENT_ID`, `GITHUB_ALLOWED_ACCOUNT_IDS`, `OPERATOR_GITHUB_IDS`, `RECORD_NETWORK_METADATA`, `NETWORK_METADATA_RETENTION_DAYS`, `WORKER_CONCURRENCY`, `SWEEP_INTERVAL_MINUTES`, `SESSION_IDLE_SECONDS`, `SESSION_ABSOLUTE_SECONDS`, `ACME_EMAIL`) with a comment and a safe default. `.gitignore` lists `.env` and `secrets/`. The Trivy secret scan reports nothing on the example files.
- Tests (Vitest, running `sh` in a temporary directory): `init-secrets.sh` creates every file once with the stated modes; a second run changes no file (contents and modification times); `database_url` contains the content of `db_app_password`; no generated value is printed; a pre-existing file is never overwritten. `docker compose config --quiet` is validated for the default profile in CI (E19-S08).
- Wiring test: every non-secret field of the zod environment schema appears in `.env.example` and is passed to `app` by `docker-compose.yml` (an `environment:` entry of the form `${NAME:-default}`), unless it is listed in a `NOT_FOR_COMPOSE` map in the test with a one-line reason (for example `NODE_ENV`, which the image sets). The test also fails when the compose file passes a variable the schema does not know, so a setting added to the code cannot be forgotten in the stack.
- With only `PUBLIC_BASE_URL` set to an `https` origin and the secrets initialised, `docker compose up --build` on a clean checkout starts `postgres`, runs `migrate` to completion and ends with `app` healthy in setup mode. The PR records this manual run; E19-S08 and E19-S12 automate it.
- Containers and ports of this story follow [CI runners, ports and fork approval](../ci-runners.md): the compose files that CI, the smoke test and development use publish only on random free loopback ports above 32768; the operator stack's host-port default `3000` is the recorded deployment exception and is never used in CI or tests.

**E19-S05 — Optional reverse proxy with automatic TLS** ⬜ Todo
Compose profile `tls`; operators with their own proxy skip it.
Acceptance criteria:
- Profile `tls` adds service `caddy` (official image at a pinned minor version; Apache-2.0, a separate container and not a code dependency) publishing 80/tcp, 443/tcp and 443/udp, with volumes `caddy-data` and `caddy-config` so certificates survive restarts, `docker/Caddyfile` mounted read-only, `read_only: true` with those volumes and `/tmp` writable, `cap_drop: [ALL]` plus `NET_BIND_SERVICE`, and `no-new-privileges`. It joins the default network only, so it cannot reach PostgreSQL.
- `docker/Caddyfile` uses `{$PUBLIC_BASE_URL}` as the site address (an `https://` origin; certificates are obtained automatically over ACME, the optional contact address comes from `ACME_EMAIL`), `reverse_proxy app:3000`, `encode zstd gzip` and removes the `Server` header. Plain HTTP redirects to HTTPS. Caddy keeps its default of trusting no upstream proxy, so it replaces any client-supplied `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host`.
- Request bodies pass through unmodified and without a size limit below GitHub's 25 MiB webhook maximum, so the HMAC over the raw body (E06) stays valid behind the proxy. Response compression applies to responses only.
- The application's own HSTS header (E04, https origins only) is the only one sent: a response through the proxy carries exactly one `Strict-Transport-Security` header.
- A named volume and `restart: unless-stopped` keep the certificate across `docker compose down`; only `down -v` removes it, and the operator guide (E19-S09) warns about Let's Encrypt rate limits when volumes are recreated repeatedly.
- With `PUBLIC_BASE_URL=https://localhost`, Caddy issues from its internal CA, which lets E19-S12 test the profile without public DNS. a short-lived `docker run --rm` of the pinned Caddy image with `caddy validate --config /etc/caddy/Caddyfile`, started from a `scripts/ci/` helper step with a per-run container name and no published port, passes in CI for that value and for `https://cla.example.com`.
- Profile `tls` starts and stops independently: `docker compose --profile tls up -d` adds only Caddy, and the default `docker compose up` never starts it or binds ports 80 and 443.
- Containers and ports of this story follow [CI runners, ports and fork approval](../ci-runners.md): the public ports 80 and 443 belong to the operator's deployment, while CI and tests never bind them and publish on random free loopback ports above 32768; every container started in CI has a per-run name and is removed in an `if: always()` step.

**E19-S06 — First-run setup API with the GitHub App manifest flow** ⬜ Todo
While no GitHub App is configured the server runs in setup mode (E19-S02) and offers a one-time flow that creates the single GitHub App of this instance in a few clicks, instead of a hand-filled form with six settings. Credentials pass through the process once and are never stored.
Acceptance criteria:
- Setup routes exist only in setup mode. `GET /api/setup/status` is always available and returns `200 {"mode":"setup"|"configured"}`; in `configured` mode every other `/api/setup/*` route, and the browser paths `/setup` and `/setup/callback`, answer `404` with the standard error envelope (test). Setup mode never starts without a `SETUP_TOKEN` (E19-S02).
- `POST /api/setup/unlock {"token"}` compares the SHA-256 digests of the supplied and configured tokens with `crypto.timingSafeEqual` and answers `204` plus a `__Host-cla_setup` cookie (`HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, 30 minutes idle, in-memory session, at most 3 live) and a CSRF token in the response body; a wrong token is `401 invalid_setup_token`. Failures are limited to 5 per minute per client address and 30 per 10 minutes globally (`429` with `Retry-After`; fake-timer test). Setup bodies are limited to 4 KiB.
- Every other setup `POST` requires the cookie, the CSRF token in `x-csrf-token` and an `Origin` header equal to `PUBLIC_BASE_URL`; each failure has its own code (`setup_locked`, `csrf_invalid`, `origin_mismatch`).
- `POST /api/setup/manifest {ownerType: "user"|"organisation", organisation?, appName, allowOtherAccounts}` (zod schema in `src/shared`) returns `200 {actionUrl, manifest, state}` with a random 256-bit `state` bound to the unlock session. `actionUrl` is `https://github.com/settings/apps/new?state=<state>` for a personal account or `https://github.com/organizations/<org>/settings/apps/new?state=<state>` for an organisation. The organisation must match GitHub's login rule `^[A-Za-z0-9](?:[A-Za-z0-9-]{0,37}[A-Za-z0-9])?$`; `appName` is 1 to 34 characters of `[A-Za-z0-9 -]`. Hostile inputs (`/`, `..`, `?`, `#`, unicode, HTML) are rejected with 400 before anything is built.
- The manifest is built from shared constants, never from literals in the setup code, and has this shape (the webhook path is `WEBHOOK_PATH` (`/webhooks/github`, `src/shared/routes.ts`, E06-S01) and the login callback path is the constant at which E10 registers its callback route; E06-S01 must have landed first, so this story never defines a second webhook path):
  ```json
  {
    "name": "<appName>",
    "url": "<PUBLIC_BASE_URL>",
    "hook_attributes": { "url": "<PUBLIC_BASE_URL><webhook path>", "active": true },
    "redirect_url": "<PUBLIC_BASE_URL>/setup/callback",
    "callback_urls": ["<PUBLIC_BASE_URL><login callback path>"],
    "setup_url": "<PUBLIC_BASE_URL>/",
    "setup_on_update": false,
    "public": false,
    "request_oauth_on_install": false,
    "default_permissions": { "metadata": "read", "pull_requests": "write", "checks": "write", "issues": "read", "members": "read", "emails": "read" },
    "default_events": ["pull_request", "check_run", "check_suite", "issue_comment"]
  }
  ```
  `public` is `true` only when `allowOtherAccounts` is set: a private App can be installed by its owner only, so serving several organisations from one instance needs a public App, and the instance's admission policy (not GitHub) then decides which organisations may use the server. `hook_attributes.active` is `false` when `PUBLIC_BASE_URL` is not an `https` origin (development, where GitHub cannot reach the server). Permission key names follow GitHub's App manifest reference.
- Tests assert that `hook_attributes.url` ends with `WEBHOOK_PATH` and that every entry of `callback_urls` equals the registered login callback route. A test compares the manifest permissions and events with the table in `docs/github-app.md` (parsed from the file) and fails when they differ, so permissions cannot change without the recorded reason in `docs/github-app.md` (Rules). The same shared constants are what E05 uses to verify the App's granted permissions.
- Route registration: the setup-mode routes join the closed constants of earlier epics instead of bypassing them. `/api/setup/status`, `/api/setup/unlock` and `/api/setup/manifest` are added to `PUBLIC_ROUTES` (E11-S01; they exist only in setup mode and have no session), form `SETUP_ROUTES` (E10-S03; CSRF is carried by the setup cookie instead of the session) and declare `config.auditExempt: 'setup'` (E04-S09; no actor exists before the App does). The route-table tests of E11-S01 and E04-S09 pass with no other exemption.

**E19-S07 — First-run setup page** ⬜ Todo
The browser side of E19-S06 and E19-S11 (build E19-S11 first), built on the shell and primitives of E17 (routes `/setup` and `/setup/callback`, `staticData.access: 'public'`).
Acceptance criteria:
- `/setup` asks for the status first: in `configured` mode it renders the shared not-found page. In `setup` mode it shows an unlock form (a password input labelled "Setup token", `autocomplete="off"`, the token located in `secrets/setup_token`, with the E19-S06 error codes mapped to catalog messages). The token is never placed in a URL.
- After unlocking, one form collects: personal account or organisation (the organisation login field appears only for the latter), the App name (default `CLA Gate <host>` sanitised to the allowed characters and 34 characters), and the checkbox "Let other organisations install this App". The checkbox text explains that an App owned by one account can only be installed by that account, that serving several organisations needs a public App, and that the instance's admission policy still decides which organisations may use this server. A warning appears when `PUBLIC_BASE_URL` is not `https` (webhook inactive, a tunnel is needed).
- "Create the GitHub App on GitHub" calls the manifest endpoint and then submits a real `<form method="post" action={actionUrl}>` with a hidden `manifest` input via `requestSubmit()` (no inline script). The client first checks that `actionUrl` starts with `https://github.com/`. For `/setup` and `/setup/callback` HTML responses only, the server sends `form-action 'self' https://github.com`; every other path keeps `form-action 'self'`, and the relaxation does not exist outside setup mode. Header tests cover both.
- `/setup/callback?code=…&state=…` reads the parameters, calls `history.replaceState` so they leave the address bar at once, and renders a "Get the credentials" button. **E19-S11 — Manifest conversion and one-time credentials** ⬜ Todo
The last step of the manifest flow: exchange GitHub's one-time code for the App credentials and hand them to the operator once. It is built before the setup page (E19-S07), whose credentials screen consumes this response.
Acceptance criteria:
- `POST /api/setup/convert {code, state}` requires `state` to equal, via `timingSafeEqual`, the unused state issued to this session and marks it consumed. `code` must match `^[A-Za-z0-9]{1,64}$`. The adapter `src/server/adapters/github/manifest-conversion.ts` (injected `fetch`, 10 s timeout, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version`, no `Authorization`) calls `POST https://api.github.com/app-manifests/{code}/conversions`, and the response is parsed with zod. Success is `200` with `Cache-Control: no-store` and the body `{appId, slug, htmlUrl, installUrl, clientId, clientSecret, webhookSecret, privateKeyPem}`.
- The credentials are returned once and kept nowhere: the handler holds them in memory only until the response is sent; nothing is written to the database, a file, a log line, a metric or an error report. Tests run a full flow against a fake GitHub and assert that the log output (with a capturing stream), every table of the PGlite database and the process-wide `fs` writes contain none of the secret strings.
- After a successful conversion `manifest` and `convert` answer `409 setup_already_issued` until the process restarts, so a second App is not created by accident. Mapped failures never echo GitHub's body: `404` becomes `400 setup_code_invalid` (used or older than one hour), a network error or `5xx` becomes `502 github_unreachable`, an unparsable body becomes `502 github_unexpected_response`. Structured log events `setup.unlock.ok`, `setup.unlock.failed`, `setup.manifest.issued` and `setup.credentials.issued` carry the request id only, and no `audit_log` row is written (no actor identity exists yet).
- Route registration: `/api/setup/convert` joins `PUBLIC_ROUTES`, `SETUP_ROUTES` and the `setup` audit exemption exactly as the other setup routes do (E19-S06), and its body limit is 4 KiB. The same route-table tests pass with no extra exemption, and the `Cache-Control: no-store` response is covered by a header test.
