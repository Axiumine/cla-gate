# E04 — Server foundation

**Bounded Context:** BC-01
**Priority:** 🔴 Must have
**Status:** ⏳ In progress

**Goal:** A Fastify server that boots from validated environment variables, talks to PostgreSQL 18 through Kysely, applies forward-only migrations and ships the whole MVP schema with its immutability guarantees, all at the repository's 100% gates. Every later epic builds on this server without touching its security-critical plumbing.
**Depends on:** E02.
**Out of scope:** GitHub App authentication and the instance-level admission policy that decides which GitHub orgs may use this server, including the table or setting it needs, which arrive as a new forward-only migration and not by editing 001 (E05, enforced in E11). Webhook intake (E06). The pg-boss schema and workers (E07). Cookies, sessions logic, CSRF and login (E10). Authorization (E11). The erasure workflow and audit screens (E16). Static serving of the SPA (E17). The application container and compose stack, with no published image (E19). Corporate CLA tables (E21). The work is on branch `feat/server-foundation`; nothing of it is merged to `main` yet.

**E04-S01 — Validate configuration from the environment and mask secrets** ⏳ In progress
The server reads only environment variables, validates them with zod at start-up and fails fast with variable names, never values. One platform instance runs on one server with one GitHub App, so the GitHub settings are single-valued and no per-tenant credential lives in the environment or the database.
Acceptance criteria:
- `loadConfig(env)` (`src/server/config/`) parses with a zod schema and returns a read-only `AppConfig`; no dotenv file is read, and an empty variable counts as unset.
- Defaults: `NODE_ENV` `development` (also `test`, `production`), `HOST` `127.0.0.1`, `PORT` `3000` (digits only, 0 to 65535, where 0 is an ephemeral port), `LOG_LEVEL` `info` (`fatal`, `error`, `warn`, `info`, `debug`, `trace`, `silent`), `TRUST_PROXY` `false`.
- `DATABASE_URL` is required and must be a `postgres://` or `postgresql://` URL. `PUBLIC_BASE_URL` is an origin only (`scheme://host[:port]`, no path, query or hash, normalised), defaults to `http://localhost:<PORT>`, and is required as `https://` when `NODE_ENV=production`, because session cookies will be `Secure` and `__Host-` prefixed.
- `TRUST_PROXY` accepts `true`, `false`, a hop count (1 to 3 digits) or a comma-separated list of IPv4 and IPv6 addresses and CIDRs with valid prefix lengths. Any other text is a start-up error naming `TRUST_PROXY`, so a typo never trusts every proxy.
- `SESSION_SECRET` is optional and, when set, at least 32 characters. `GITHUB_APP_ID` (digits, at most 20), `GITHUB_APP_PRIVATE_KEY`, `GITHUB_WEBHOOK_SECRET`, `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are optional placeholders that are validated when set; E05 and E10 make them required.
- Invalid input throws `ConfigError` whose message lists every invalid variable name, sorted, and never a value (a test sets a recognisable bad value and asserts it is absent from the message).
- `DATABASE_URL`, `SESSION_SECRET`, the GitHub private key, webhook secret and client secret are wrapped in a `Secret`: `String()`, template literals, `JSON.stringify` and `util.inspect` all print `[REDACTED]`, and `reveal()` is the only way to the value.
- `loadMigrateConfig(env)` returns the owner connection for `yarn db:migrate`: `MIGRATION_DATABASE_URL` wins when non-empty, otherwise `DATABASE_URL`, and a bad value reports the name of the variable that was used.
- This story creates the README `Configuration` section (a table of variable, default, where it is required and meaning) and `.env.example` with every variable above; a test parses the environment schema and fails when a variable is missing from either file. Every later story that adds a variable extends both in the same change (hard rule 10).
- Tests are table-driven per variable and include the secret-masking cases above; new dependencies are `zod` 4 and nothing else (MIT).
- Ports follow [CI runners, ports and fork approval](../ci-runners.md): the `PORT` default `3000` is the one recorded exception (a deployment default for `yarn start` and containers), no script, compose file, CI job or test starts anything on it, and `HOST` stays `127.0.0.1`; `yarn dev` and every test that listens take a random free loopback port above 32768, never port 0.

**E04-S02 — Connect to PostgreSQL 18 with Kysely in production and in tests** ⏳ In progress
New dependencies, all AGPL-compatible: `kysely` 0.29, `pg` 8 and `@types/pg` (MIT), and dev-only `@electric-sql/pglite` pinned exactly at `0.5.14` (Apache-2.0, PostgreSQL 18.6).
Acceptance criteria:
- `createPgDatabase({ connectionString, onError })` returns a `Kysely<Database>` over a `pg` pool with `max` 10, connect timeout 5000 ms and idle timeout 30,000 ms. The pool is lazy (nothing connects until the first query), idle-client errors go to `onError` instead of crashing the process, and `destroy()` ends the pool.
- A bigint (type oid 20) is parsed into a JS number by `parseInt8`, which throws `RangeError` outside the safe-integer range instead of rounding. Both drivers use it, so every GitHub id and identity key is a number and the two drivers return identical results.
- `src/server/adapters/db/schema.ts` is a hand-written `Database` interface for every table of migration 001; a test compares table and column names with the live catalog in both directions, so drift in either side fails.
- The PGlite adapter (an own Kysely dialect: parameterless statements go through `exec` so multi-statement migrations work, one connection queued by a mutex, transactions all-or-nothing, isolation level and access mode applied) is test-only. It sits outside the emitted build and Knip's production project.
- `test-support.ts` is the single way a test gets a database: `emptyTestDatabase()` and `migratedTestDatabase()` share one connection per test file and run `drop schema public cascade; create schema public` before each call. `seedTenant(db, n)` inserts an installation, repository, document and published version 1.0 with ids derived from `n`, so two tenants (`n = 1, 2`) coexist.
- The Vitest `server` project (node environment, `src/**/*.test.ts`, 30 s test and 60 s hook timeouts) uses a `globalSetup`. With `DATABASE_URL` set it creates a throw-away `cla_test_<hex>` database (the user needs CREATEDB), provides its URL to the tests, runs one file at a time and drops it with `with (force)` afterwards; it never touches the database named in the URL. Without `DATABASE_URL` the suite runs on in-memory PGlite.
- A test asserts the server is PostgreSQL 18 on both PGlite and a real server, and the pool tests cover laziness, an unreachable server rejecting with the connection error and idle errors reaching `onError`.
- The CI job `postgres` (not a required check) runs `yarn test` with `DATABASE_URL` against a `postgres:18` container pinned by tag and digest, started by `scripts/ci/postgres.ts` on a random free loopback port with no `services:` block (E23-S06); coverage stays the `coverage` job's responsibility. Open: the job was validated locally with the same helper commands and has not yet run on the self-hosted runners (E23-S11), which is why this story is not done.
- CI jobs, containers and ports of this story follow [CI runners, ports and fork approval](../ci-runners.md): the `postgres` job and the throw-away test database run on the shared self-hosted runners, in a container published only on a random free loopback port above 32768 with a per-run name, a timeout and cleanup in an `if: always()` step, never in a `services:` block.

**E04-S03 — Build the Fastify application with request ids, security headers, logging and one error contract** ⏳ In progress
New dependencies (MIT): `fastify` 5, `@fastify/helmet` 13, `fastify-type-provider-zod` 7, `pino` 10.
Acceptance criteria:
- `buildApp({ config, db, logger?, readinessTimeoutMs? })` returns a fully wired Fastify instance that is not listening (tests call `inject()`), uses the zod validator and serializer compilers so routes declare their contract with schemas shared through `src/shared`, and destroys the database on close.
- Request ids: a caller's `x-request-id` is kept only if it matches `^[A-Za-z0-9._-]{8,64}$`, otherwise a UUID is minted; the id is echoed in the `x-request-id` response header on every response, and a malformed id cannot forge log fields.
- Security headers on every response, errors and 404s included: CSP with `default-src`, `script-src`, `style-src`, `base-uri` and `form-action` set to `'self'`, `frame-ancestors 'none'` and `object-src 'none'` (no inline script or style), frameguard `deny`. HSTS (`max-age` 63,072,000, `includeSubDomains`) and `upgrade-insecure-requests` are sent only when `PUBLIC_BASE_URL` is `https://`.
- `trustProxy` comes from `TRUST_PROXY`: a boolean or address list passes through, and a hop count becomes the function `(address, hop) => hop < n` because Fastify's types list no number.
- The pino logger writes JSON lines with ISO timestamps at `LOG_LEVEL`, redacts `authorization`, `cookie` and `set-cookie` header paths, and serialises a request as method and path only (no query string, headers, body or client address, because network metadata is off unless a flag enables it) and a response as the status code only. An error is serialised as class, message, code and stack, never a database error's `detail`.
- One error handler decides what a client sees: `{ "error": { "code", "message", "requestId" } }` (`errorResponseSchema` in `src/shared/errors.ts`). A zod validation failure is 400, any other 4xx keeps its status, everything else is 500; `message` is the standard HTTP status text, `code` is its lower-case snake form (`bad_request`, `not_found`, `internal_server_error`), and no exception message, stack or validation detail is ever sent.
- Server errors are logged with the error; client errors are logged as `request rejected` with the status only; request bodies are never logged. Unknown routes return the same body with 404, and a body above Fastify's default limit (1 MiB; the test sends 2 MiB) returns 413 with the same body shape.
- Tests prove: a recognisable secret, cookie, authorization header, query value and request body never appear in the captured log lines, configuration secrets never appear in logs, and the HSTS and CSP headers differ correctly between an `http://` and an `https://` public URL.

**E04-S04 — Boot the server with health probes and graceful shutdown** ⏳ In progress
Acceptance criteria:
- `GET /healthz` returns 200 `{"status":"ok"}` without touching the database. `GET /readyz` returns 200 `{"status":"ready"}` when `select 1` answers within `readinessTimeoutMs` (default 2000) and otherwise 503 `{"status":"unavailable"}` with no reason in the body (a warning is logged). Both bodies are zod schemas in `src/shared/health.ts`.
- `/readyz` turns 503 when the database goes away mid-run and when it accepts connections but never answers; other methods on both routes get the standard 404 error body.
- `boot({ env, signals, createDb?, err? })` runs in this order: `loadConfig`, logger, database, `buildApp`, `listen` on `HOST` and `PORT`; it returns `{ address, close }`. The default database is node-postgres on `DATABASE_URL`, which operators point at the unprivileged `cla_app` role; the owner URL is read only by the migration CLI (E04-S05).
- An invalid configuration prints the invalid variable names to stderr (or the injected sink), sets exit code 1 and starts nothing. A port that is already taken logs a fatal error, closes the app (which destroys the database), sets exit code 1 and leaves nothing running.
- `SIGINT` and `SIGTERM` log `shutting down` and close the app, which stops accepting connections, drains in-flight requests and closes the pool; the handlers are removed, `close()` is safe to call twice, and a failing shutdown is logged and sets exit code 1.
- `src/server/main.ts` contains only `await boot({ env: process.env, signals: process })`, exports the handle for its test and stays in coverage scope: a boot test starts the server on PGlite, serves both health routes and shuts down on `SIGTERM`; another boots with an invalid environment and expects exit code 1.
- With the default database and an unreachable server the process is live but not ready (`/healthz` 200, `/readyz` 503), proven in a test.
- `yarn dev` runs `node --watch src/server/main.ts` through `scripts/dev/db.ts run app`, with `DATABASE_URL` pointing at the `cla_app` role of E04-S07's compose file on the port `yarn db:up` chose, and a random free loopback `PORT` (printed as `app: http://127.0.0.1:<port>`) unless `PORT` is set.
- Ports of this story follow [CI runners, ports and fork approval](../ci-runners.md): the server and `yarn dev` listen on a random free loopback port above 32768 chosen by the port helper, and the boot tests take their port from `pickSystemFreePort()`, never from 3000 or port 0.

**E04-S05 — Apply forward-only, checksummed migrations** ⏳ In progress
Acceptance criteria:
- Migrations are `migrations/NNN_snake_case.sql` (name matches `^(\d{3})_[a-z][a-z0-9_]*\.sql$`), loaded in plain code-point order. Other file types are ignored; a malformed `.sql` name, two files with the same number or a missing directory fails the load.
- `.gitattributes` sets `migrations/*.sql text eol=lf`, so a CRLF checkout cannot change a checksum. Each file carries a SHA-256 of its SQL text, which changes with a single byte.
- The runner keeps `schema_migrations (name text primary key, checksum text check (checksum ~ '^[0-9a-f]{64}$'), applied_at timestamptz)` and applies each pending migration plus its bookkeeping row in one transaction, so a failing migration rolls back by itself and keeps the earlier ones.
- The applied set must be exactly a prefix of the files on disk with equal checksums. An edited migration, a removed one, or a new one that sorts before an applied one makes `migrate()` throw `MigrationError` before anything runs; the message names the file and says to add a new migration, and never contains the SQL.
- A session-level advisory lock (key `7231955001`) on a dedicated connection serialises runners and is released afterwards, also when a migration fails. A test with concurrent runners shows every migration applied exactly once; the test that a runner waits while another session holds the lock runs only on real Postgres (`test.skipIf(!realPostgres)`), because PGlite has one connection.
- `yarn db:migrate` runs `src/server/migrate.ts`, which connects as the owner (`MIGRATION_DATABASE_URL`, falling back to `DATABASE_URL`), prints `migrations applied: <names>` or `migrations: up to date`, and exits 0 or 1. Production runs `node dist/server/migrate.js`.
- The CLI never prints a connection string or a stack trace: an unreachable database prints the error code (pg connection errors can have an empty message) and no password, and the connection is closed even when a migration fails.
- The server never migrates at start-up: it connects as `cla_app`, which cannot create tables, so migration is an explicit operator step (the compose flow that runs it is E19).

**E04-S06 — Create the MVP schema in migration 001** ⏳ In progress
Acceptance criteria:
- `migrations/001_initial.sql` creates `users`, `sessions`, `installations`, `repositories`, `cla_documents`, `cla_versions`, `signatures`, `signer_pii`, `commit_overrides`, `allowlist_entries`, `pr_evaluations`, `webhook_deliveries` and `audit_log`. It does not create `corporate_agreements` and `corporate_approvals` (E21) or `pgboss.*` (owned by pg-boss, E07).
- Identity is the numeric GitHub id: `users.github_id`, `installations.github_installation_id` and `repositories.github_repo_id` are `bigint`, unique and positive; logins, names and avatars are display snapshots; `allowlist_entries.github_id` is numeric and has `kind` in (`user`, `bot`, `org_members`), never a login string. `installations.account_type` is `Organization` or `User`.
- Each GitHub App installation, one per org or account, is a tenant row. Every tenant table carries `installation_id` and references its parent through a composite foreign key such as `(repository_id, installation_id)`, so a row cannot point at another tenant's repository, document or version. Cross-tenant tests (mandatory) assert foreign-key violation `23503` for a document in another tenant's repository, an evaluation, a commit override and an allowlist entry on another tenant's repository, a signature on another tenant's version, a repository's default document of another tenant and a document's active version of another tenant.
- `cla_versions` has `unique (document_id, major, minor)` and a check that `content_sha256` equals the SHA-256 of `content_md`; `signatures` ties version, document, major and hash through one composite foreign key and has the partial unique index on `(user_id, document_id, major) where revoked_at is null`. Tests show: one valid signature per person, document and major; a new signature is allowed after a revocation and for a new major; a minor revision is not a new signature.
- `webhook_deliveries.delivery_id` is the primary key (GitHub reuses it on redelivery) and has no payload column. `pr_evaluations` is unique on `(repository_id, pr_number, head_sha)` with `result` in (`in_progress`, `success`, `failure`). `commit_overrides` is unique on `(repository_id, commit_sha)` with a hex-SHA check. `allowlist_entries` is unique per scope even when `repository_id` is NULL (`unique nulls not distinct`).
- `sessions` stores only a 64-hex `session_hash`, a CSRF secret and idle and absolute expiry with `idle_expires_at <= absolute_expires_at` (E10 owns the behaviour). `signatures` carries `consent_text_id`, `signer_type` in (`individual`, `corporate`), `signed_at`, the optional source repository and PR, and a `revoke_reason` restricted to the fixed code set (`signer_request`, `maintainer_decision`, `legal_request`, `other`), never free text, because a revoked row can never be scrubbed.
- `audit_log` has numeric actor and subject ids, an `action` that matches `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$` and a `metadata` check (`audit_metadata_is_clean`) that is an allowlist, not a denylist: a flat object whose keys come from a fixed list (`count`, `signer_pii_rows`, `document_id`, `version_id`, `signature_id`, `repository_id`, `pr_number`, `major`, `minor`, `reason_code`, `kind`, `enabled`) and whose values are numbers, booleans, null or lower-case codes matching `^[a-z][a-z0-9_]{0,63}$`. A new key needs a new migration that replaces the function (E04-S09). Personal data columns exist only in `signer_pii` and the `users` snapshot (asserted by a test over the catalog; E10-S01 adds `sessions.verified_emails` and extends that test in the same change).
- Timestamps are `timestamptz`; foreign keys are `ON DELETE RESTRICT` unless the child is disposable (`sessions`); the two functions that run with elevated privilege or read other tables (`erase_signer_pii`, `cla_documents_guard_active_version`) pin `search_path` to this schema, `pg_catalog` and `pg_temp` last, while the remaining trigger and check functions touch only their own row and are not pinned. The file header states it is forward-only and never edited after merge.

**E04-S07 — Enforce immutability, audited erasure and the runtime role** ⏳ In progress
Acceptance criteria:
- A `forbid_modification()` trigger function raises `restrict_violation` (SQLSTATE `23001`) with a hint to insert a new row. `cla_versions` and `audit_log` reject `UPDATE`, `DELETE` and `TRUNCATE`; `signatures` rejects `DELETE` and `TRUNCATE`. Tests include `TRUNCATE ... CASCADE` from parent tables (`users`, `cla_documents`, `installations`), which must also reach the trigger.
- The only `UPDATE` `signatures` accepts sets `revoked_at`, `revoked_by` and `revoke_reason` once on a row that is not revoked. The rest of the row is compared as a whole (`to_jsonb` minus the revocation columns), so a column added later is immutable by default. A revoked row cannot be changed or un-revoked, and `revoked_at` and `revoked_by` are both set or both null.
- `erase_signer_pii(p_github_id, p_actor_github_id)` is `SECURITY DEFINER` with a pinned `search_path` and no `PUBLIC` execute. It deletes that person's `signer_pii` rows and `sessions` rows (a test shows erasure also ends the sessions), scrubs the `users` snapshot (login `erased-<id>`, name and avatar null), keeps every signature core row, appends one `signer_pii.erased` audit row holding ids and the row count only, and returns the count.
- Erasing an unknown person fails with `no_data_found` and writes no audit row; erasing twice is harmless. The audit workflow and UI that call it are E16.
- Three further guards of migration 001 are kept by every later migration, each with a rejecting test: identity columns never change by `UPDATE` (`users.github_id`, `installations.github_installation_id` and `account_id`, `repositories.github_repo_id` and `installation_id`, `cla_documents.installation_id` and `kind`; a repository transfer is a new row, E05-S09); a document's `active_version_id` can only move to its highest `(major, minor)` version, so a rollback is a new version (E12-S06); and `signed_at` and `published_at` must lie within five minutes of the database clock when the row is inserted.
- The migration owner owns every table and function. `cla_app` owns no table, no function and not the schema, and migration 001 grants it only: select, insert and update on `users`, `installations`, `repositories`, `cla_documents` and `pr_evaluations`; select, insert, update and delete on `sessions`, `webhook_deliveries` and `allowlist_entries`; select, insert and delete on `commit_overrides`; select and insert on `cla_versions`, `signatures`, `signer_pii` and `audit_log`; update of the three revocation columns; execute on `erase_signer_pii`.
- A test table proves `cla_app` gets SQLSTATE `42501` for `DELETE`, `UPDATE` and `TRUNCATE` of `signer_pii`, `DELETE` on `signatures` and `cla_versions` and `audit_log`, `UPDATE` of the signature core, `cla_versions` and `audit_log`, reading `schema_migrations`, disabling or dropping a trigger and creating a table. It can still do its daily work and erase through the function only.
- Grants are made only when the role `cla_app` exists (a notice otherwise), so a plain install and PGlite migrate without it; a test covers that path.
- `docker-compose.yml` (project `cla-gate`) defines only a development `postgres` service: image `postgres:18`, published only on loopback as `127.0.0.1:${POSTGRES_PORT}:5432` (5432 is the container's own port; `POSTGRES_PORT` has no default and `yarn db:up` sets a random free port above 32768), data volume at `/var/lib/postgresql`, `pg_isready` healthcheck. `cla_owner` (owner, `MIGRATION_DATABASE_URL`) comes from the image variables and `cla_app` (`nosuperuser nocreatedb nocreaterole noinherit`) from `docker/postgres-init.sql`. The dev passwords are labelled development-only, and the file defines no application service or image.
- The development database follows [CI runners, ports and fork approval](../ci-runners.md): it is published on `127.0.0.1` only, on a random free port above 32768 chosen by `yarn db:up`, never on 5432.

**E04-S09 — Audit writer, closed action set and route guard** ⬜ Todo
One function through which every mutation records who did what to which object, in the same transaction as the mutation, with no room for personal data. It lives in the foundation because E05 and E10 already write audit rows; E16 builds the viewer, the export and the erasure on top of it.
Acceptance criteria:
- `appendAudit(trx, entry)` lives in `src/server/services/audit.ts` and takes a Kysely `Transaction`, not the bare database handle: a type-level test (`expectTypeOf`) shows that passing the plain handle does not compile, so an audit row can never commit apart from its mutation. The module exports no update or delete function.
- `AuditEntry` is `{ action, installationId, actorGithubId, subject?: { type, id }, metadata? }`. `action` must be a member of `AUDIT_ACTIONS`, a closed `as const` tuple in `src/shared` that also matches the database check `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$` (a test validates every member against that regex). The tuple starts with the actions E05 writes (`installation.rejected`, `installation.deleted`, `installation.suspended`, `installation.unsuspended`, `repository.added`, `repository.removed`, `repository.renamed`, `repository.enabled`, `repository.disabled`); each later epic adds its own names in the change that adds the mutation, and E16-S01 checks the catalogue is complete.
- Metadata is parsed by a strict zod schema before the insert: keys come from the closed constant `AUDIT_METADATA_KEYS` in `src/shared`; values are integers, booleans, `null`, arrays of at most 100 integers, or strings of 1 to 64 characters matching `^[a-z0-9_.:-]+$` (enum-like codes and SHA hex); the serialised metadata is capped at 2,048 bytes. Keys `name`, `email`, `login`, `avatar_url`, `reason`, `message`, `title` and `text` are never members. A violation throws `AuditEntryInvalid`, which surfaces as `500` and rolls the mutation back.
- Migration 001 accepts only 12 keys and only strings of the form `^[a-z][a-z0-9_]{0,63}$`, so the keys and values that later epics write (account ids and types, scopes, hex commit SHAs, arrays of ids) would be refused by the database. A forward-only migration replaces `audit_metadata_is_clean` (`create or replace`) with an allowlist built from `AUDIT_METADATA_KEYS`, which is the 12 existing keys plus `account_id`, `account_type`, `scope`, `github_id`, `user_github_id`, `previous_document_id`, `source_repository_id`, `source_pr_number`, `revision`, `bump`, `affected_signatures`, `rolled_back_from_version_id`, `commit_sha`, `state`, `row_count`, `rows`, `signature_count`, `webhook_deliveries` and `sessions`, with the wider value rule above. It stays an allowlist, never a denylist, so no personal-data key can pass. A test asserts the SQL key list equals the TypeScript constant; a later key needs a new migration and the test fails until it exists.
- `actorGithubId` is required except for the actions in the exported set `SYSTEM_ACTIONS` (scheduled or webhook-driven: `network_metadata.purged` and the installation lifecycle actions of E05), where it may be `null`. `installationId` is required except for the actions in `INSTANCE_ACTIONS` (`data_export.created`, `network_metadata.purged`). `actorGithubId` is a branded `GithubId` type, so the `users.id` surrogate key cannot be passed as actor by accident (type-level test). Table tests cover each combination; a tenant-scoped action with a `null` installation fails.
- Failure injection: a writer whose insert throws after a mutation in the same transaction leaves neither row, and an exception thrown by the mutation after the audit insert removes the audit row too.
- Route guard test: every route registered under `/api` with method `POST`, `PUT`, `PATCH` or `DELETE` must declare `config.audit` (an `AUDIT_ACTIONS` member) or `config.auditExempt` with a reason from a closed list (`webhook`: HMAC route, audited by the lifecycle handlers it calls; `session`: login callback and logout; `setup`: the first-run setup routes of E19, which run before any actor exists). A route without either fails the test and the message names the route, so a later epic cannot add an unaudited mutation.
- Cross-tenant test: two tenants write entries with identical subject ids; the `installation_id` stored on each row is the caller's, and a query filtered by tenant 1 never returns tenant 2's row.
