# E22 — Merge queue, badge and public verification (later)

**Bounded Context:** BC-04 / BC-03
**Priority:** 🟢 Could have
**Status:** ✅ Done

**Goal:** Post-MVP (not in v0.1). Make `license/cla` work for repositories that use GitHub's merge queue, give projects and contributors an opt-in, privacy-preserving way to show and verify a valid signature (public endpoint and README badge), and finish the retention and erasure tooling that operators need to run a server responsibly.
**Depends on:** E09, E13.
**Out of scope:** Anything in the MVP; configuring the merge queue itself (maintainers enable it in GitHub rulesets); any endpoint that lists, searches or counts signers (enumeration is never offered); showing corporate coverage publicly (E21 approvals stay private); the audited erasure SQL function and the audit log themselves (E16); network-metadata retention (E16-S05); non-GitHub forges; legal advice on retention periods (defaults are operator defaults, GDPR choices need counsel).

**E22-S01 — Report `license/cla` for merge groups** ✅ Done
Post-MVP. With a merge queue and a required `license/cla` check, GitHub waits for the check on the merge group's head SHA; without it the queue stalls.
Acceptance criteria:
- The `docs/github-app.md` table moves "Merge queues: read" from Later to the permission set and adds the `merge_group` event (`checks_requested` handled, `destroyed` accepted and ignored). The setup instructions of E19 and the App manifest follow. Until an org owner accepts the new permission, no `merge_group` event arrives and pull request checks are unaffected; this is written in the operator notes.
- The webhook route of E06 accepts `merge_group`: HMAC check on the raw body first, then in one transaction the `webhook_deliveries` insert and the enqueue of `evaluate-merge-group` keyed by (repository, `merge_group.head_sha`). No GitHub API call runs in the request path. `destroyed` marks the delivery processed, sets `destroyed_at` on the matching evaluation row and enqueues nothing; any other action gets 2xx and is ignored.
- A migration adds `merge_group_evaluations` (`id`, `installation_id`, `repository_id`, `head_sha`, `base_sha`, `result` in (`in_progress`, `success`, `failure`), `details` jsonb, `check_run_id`, `destroyed_at`, timestamps) with unique (`repository_id`, `head_sha`) and a composite foreign key to `repositories (id, installation_id)`.
- Member pull requests are discovered by the rule that sanitised payload fixtures prove: PR numbers parsed from `head_ref` (`refs/heads/gh-readonly-queue/<base>/pr-<number>-<sha>`), completed by a commit-to-PR lookup over `base_sha...head_sha` when a group holds more than one PR. Fixtures for a group of one and of more than one PR are committed with the story, and the rule is added to "Open verifications without a story" in `docs/tooling-gotchas.md` until a real queue has been observed.
- The job re-fetches everything, runs the E08 engine for each member PR on its current opener and commits, and writes one Check Run named `license/cla` on `merge_group.head_sha` through E09's upsert: `success` only when every member PR passes. It re-checks `destroyed_at` immediately before writing and writes nothing for a destroyed group.
- Fail-closed rules: no resolvable member PR, or more than 25, ends in `failure` with the fixed summary "Could not determine the pull requests in this merge group". The summary lists failing PRs as `PR 123` in code spans (never `#123`) and uses E09's escaping for any name.
- The dead-letter handler sets the group's Check Run to `failure` with the hint "Remove the pull request from the merge queue and add it again" (`/recheck` cannot be typed on a merge group).
- Tests: cross-tenant (the same `head_sha` in repositories of two tenants yields two rows and two Check Runs); boundaries at 1, 25 and 26 member PRs; failure injection (GitHub 5xx while fetching a PR makes the job retry and never writes `success`); real Postgres only: two concurrent `checks_requested` deliveries for one SHA leave one evaluation row and one Check Run.
- Built as: migration `018_merge_group_evaluations.sql` (a tenant table, `cla_app` may select, insert and update, no DELETE; the `destroyed` delivery creates the row as a tombstone when no job has yet, because a delivery that is handled before the queued job runs would otherwise be lost and the job would report a group GitHub has already taken down). `APP_PERMISSIONS` gains `merge_queues: read` (not in `INSTALLATION_PERMISSIONS`: its absence is no warning) and `APP_EVENTS` gains `merge_group`. The route is `routeMergeGroup` (`domain/webhook-routing-merge-groups.ts`) in the routing table: `checks_requested` is the job `evaluate-merge-group` (strict envelope with the head and base SHAs and `tipPrNumber`, the number `tipPullRequestOf` reads from the name of the group's branch, absent when the name is not a merge queue's), `destroyed` is the new routing kind `destroyed` (a `DestroyedGroup`: numeric ids, both SHAs and the delivery id), which the tenant filter judges like a job (`tenantSubjectOf`) and `WebhookDeliveries.recordDestroyed` records, in one transaction, as a delivery finished at once, with `markGroupDestroyed` (an upsert on (`repository_id`, `head_sha`) found through the GitHub ids of the installation and the repository, so one tenant's delivery only reaches that tenant's group, keeping the first instant). The queue `evaluate-merge-group` is `singleton` keyed `${githubRepoId}:${headSha}`. The job is `evaluateMergeGroup` (`services/merge-group/`): tenant, repository, `startGroupEvaluation` (a destroyed group ends `skipped:merge_group_destroyed`), `discoverMembers` (`member-discovery.ts`: the tip pull request from the branch name, completed by `commits/{sha}/pulls` for each commit of `base...head` when there is more than one; none, more than 25 or more than 250 commits is `undetermined`), `evaluateMember` for each (at most five at once; a closed or missing member makes the group `undetermined`; a member that moved while its commits were read throws `MergeGroupMemberMovedError` and the queue retries), `finishGroupEvaluation` (conditional on `destroyed_at is null`: the check "immediately before writing") and `EvaluationReporter.mergeGroup`, whose implementation (`reporting/merge-group-report.ts`) reads the row once more and ends `skipped:merge_group_destroyed` for a group destroyed meanwhile before the single GitHub write. The words are `domain/reporting/merge-group-output.ts` (the summary "Could not determine the pull requests in this merge group", failing pull requests as `PR 123` in code spans through `renderName`); the dead-letter handler is `dead-letter-merge-group.ts` (`failGroupEvaluation` upserts a `failure` row for a group that is not destroyed and the run ends `failure` with "Remove the pull request from the merge queue and add it again"). A repository whose enforcement is off is `skipped:repository_disabled`: no Check Run is written for its groups (see `docs/github-app.md`). The two fixtures (a group of one pull request, `webhookFixture('merge_group')`, and of several, `mergeGroupOfSeveralFixture()`) are fictitious, built from the documented shape like every fixture.
- Tests: `domain/merge-group.test.ts`, `webhook-routing.test.ts` (the row of the table), `adapters/http/webhook-routes-merge-group.test.ts` (the real route: HMAC first, one job per `checks_requested`, a duplicate, `destroyed` with and without an earlier row, the other tenant, unknown and rejected installations, ignored actions), `services/webhook-deliveries-destroyed.test.ts`, `services/merge-group/` (`merge-group-rows.test.ts` with the tombstone, `member-discovery.test.ts`, `evaluate-merge-group.test.ts` with the boundaries at 1, 25 and 26, `evaluate-merge-group-failures.test.ts` with the GitHub failures, the destroyed group before, during and after the evaluation, and the skips, `evaluate-merge-group-tenancy.test.ts` with the same `head_sha` in two tenants giving two rows and two runs), `services/reporting/check-run-reporter-merge-group.test.ts` (the real reporter, including a group destroyed before the write), `services/dead-letter/dead-letter-merge-group.test.ts`, `services/job-handlers-merge-group.test.ts`, the registry and matrix entries (`tenant-jobs-fixture`, `tenant-registry`), and `adapters/jobs/merge-group-real.test.ts` (real Postgres only: two concurrent deliveries for one head SHA leave one row and one run, a second delivery waits behind the first and updates its run, and a group destroyed before its job ran is never evaluated).
- Not verified against a real merge queue (recorded in `docs/tooling-gotchas.md`, Open verifications without a story, until one has been observed): the member rule above, the permission key `merge_queues`, and that a `merge_group` delivery arrives after an organisation owner has accepted the permission.

**E22-S02 — Public signature-verification endpoint (opt-in)** ✅ Done
Post-MVP. Answers one question, "does this GitHub login have a valid signature for this project", and nothing else.
Acceptance criteria:
- A migration adds `repositories.public_verification boolean not null default false`. `PUT /api/installations/:installationId/repositories/:repositoryId/public-verification` with `{ "enabled": boolean }` needs the same role as the repository's other settings (`docs/security.md` role matrix, E11) and writes audit action `repository.public_verification_changed`.
- `GET /api/public/repos/:githubRepoId/signers/:login` needs no session and sets no cookie. `githubRepoId` must be a positive safe integer and `login` must match GitHub's login pattern (1 to 39 characters, letters, digits and single hyphens, no leading or trailing hyphen), otherwise 400 `invalid_input`.
- The response is 200 `{ "signed": true }` or `{ "signed": false }` and carries no name, email, date, version, document or id. It returns 404 `not_found` with an identical body when the repository is unknown, not enabled, has `public_verification = false`, or belongs to a suspended or removed installation.
- `signed` is true only when the login's current numeric id has an unrevoked individual signature on the repository's active document whose major equals the active major. The login is resolved with `GET /users/{login}` on the repository's installation token (case-insensitive; GitHub 404 gives `false`); nothing is keyed on a stored login. Never signed, revoked, outdated major and unknown login all return the same `false` body.
- Resolutions are cached in-process for 10 minutes, hits and misses alike, in an LRU of at most 10,000 entries. GitHub 403, 429 or 5xx gives 503 `upstream_unavailable` with `Retry-After`, never a guess.
- Rate limits use the Fastify rate-limit plugin with the `trustProxy` setting of E04: 30 requests per minute per client IP and 600 per minute per repository, then 429 `rate_limited` with `Retry-After`. The in-memory store is acceptable because one instance serves the server; the `docs/security.md` (Security and privacy) says so.
- Headers: `Cache-Control: public, max-age=300`, `Access-Control-Allow-Origin: *` (GET only), no `Set-Cookie`. The access log records the route template `/api/public/repos/:githubRepoId/signers/:login` and never the concrete login; a log-capturing test asserts it.
- Tests: the four `false` cases are byte-identical; cross-tenant (a login that signed only in tenant B is `false` for a repository of tenant A); `OctoCat` and `octocat` give the same answer; the 31st request in a minute from one IP is 429; a suspended installation turns a previously `true` answer into 404.
- Built as: migration `019_repositories_public_verification.sql`; the contract (paths, the strict `{ enabled }` body, the `{ signed }` answer, `PUBLIC_LOGIN_PATTERN`, the path-parameter schema) in `src/shared/public-verification.ts`. The opt-in is `repositoryPublicVerificationRoutes` (`repository-public-verification-routes.ts`), a `tenant` route in `write` mode resolved by `byRepositoryParam`, audited as `repository.public_verification_changed`; the service `setPublicVerification` takes the row lock of the repository (`lockRepositoryForDocumentChange`), judges the role with `requireActionRole` (the same rule as the attach and the enable), updates conditionally on the current value and appends the audit row in the same transaction; a call that asks for what already is answers `changed: false` and writes nothing; it makes no call to GitHub. The public call is `publicVerificationRoutes` (`public-verification-routes.ts`): `config.access: 'public'` and `session: 'none'` (on the closed `PUBLIC_ROUTES` list), no `HEAD` twin (`exposeHeadRoute: false`). The one decision is `verifySigner` (`services/public-verification.ts`, for the badges of E22-S03 to reuse), over `public-verification-queries.ts` (`findPublicRepository`, which meets every tenant by design and is pinned by its test; `hasCountingSignature`, which names the installation id, the document, `signer_type = 'individual'`, `revoked_at is null` and `major` equal to the active version's major). The repository is judged before GitHub is asked (a repository that may not be asked about is the 404 whatever the login is, and no lookup is made), the signature is read on every call, and only the login-to-id answer is cached (`public-login-cache.ts`: key the lower-cased login, 10 minutes, hits and misses, at most 10,000 entries with the least recently used out first, a failure never stored). Any failure of the lookup (403, 429, 5xx, an answer that is not an account, a refused token) is one `PublicVerificationUnavailableError`, mapped by `upstream-failure.ts` to `503 upstream_unavailable` with `Retry-After` (GitHub's wait, at most 300 s, else 30). The budgets are in `public-rate-limit.ts`: one `onRequest` hook over two limiters made once with `app.createRateLimit` (so the badges share the buckets), the client address first and then the repository (`repo:<id>`, one shared `repo:invalid` key for every spelling that is not an id), `429 rate_limited` with `Retry-After`; the address is `request.ip` under `TRUST_PROXY`. Those two bound one address and one repository, not the GitHub calls that many addresses and made-up logins could still cause on the one installation token, so a third budget bounds the installation (`public-lookup-budget.ts`, `LookupBudget`): a login that the cache does not know spends one of 30 lookups a minute of the installation (the key is its GitHub id from the database, never from the request; a window starts with the first lookup after the last ended; at most 10,000 windows are kept), a cached login is free, and a lookup beyond it is the same `PublicVerificationUnavailableError` as a GitHub outage (`503 upstream_unavailable` with `Retry-After` set to the end of the window, at most 300 s) without asking GitHub, so the evaluation jobs of the same installation keep their room. The badges share it. Headers are in `public-headers.ts`: `public, max-age=300` on a `200` only, `no-store` on every other answer, `Access-Control-Allow-Origin: *` on every answer of the call, no cookie. A path that never reaches the route (a bad percent-escape, a parameter over the router's length) is `400 invalid_input` too, from `framework-errors.ts`. The access log serializer (`logger.ts`) writes the route template of every request that matched a route of the public API, whatever its path looked like (the router reads `/api/%70ublic/` and `/API/public/` as the same route), and `/api/public/*` for a request that matched no route but reads as the public API once escapes are decoded (at most three times, a path still changing is masked), case is folded and doubled or backward slashes are flattened. The GitHub the lookups run on is `AppOptions.publicGitHub` (`Pick<GitHubClient, 'getUserAccount'>`, wired from the real client in `boot-app.ts`; a server with no GitHub App answers `503`). The 404 bodies are identical but for `requestId`, which every error body carries.
- Tests: `public-verification-routes*.test.ts` over `public-verification-fixture/` (answers and headers, hostile inputs, budgets and `TRUST_PROXY`, GitHub failures and the cache, the other tenant, the suspended and removed installation, the log), `repository-public-verification-*.test.ts` (roles, audit, idempotence, the other tenant's ids, a real-Postgres race of five calls), the services tests (`public-verification.test.ts`, `public-verification-queries.test.ts`, `public-login-cache.test.ts`, `public-lookup-budget.test.ts`), `public-verification-routes-budget.test.ts` (the 31st uncached lookup of one installation from many addresses is `503` and GitHub is not asked again, a cached login and the other installation are not affected), the logger tests for the spellings of a public path, the registry entries (`tenant-registry-public/`) and the matrix case (`cross-tenant-public-fixture/`).
- Documentation (written at the closing step of the epic, the story having been built under a freeze on `docs/`): the model of the public endpoint, the three budgets and the in-memory store (acceptable because one instance serves the server) in `docs/security.md`; the route, the `409` and the rules in `docs/architecture.md`; the column in `docs/data-model.md`; the lookup in `docs/github-app.md`; the decisions in `docs/decisions.md`.

**E22-S04 — Retention sweep for operational data** ✅ Done
Post-MVP. Operational rows that have no evidentiary value are purged on a schedule; evidence is never touched.
Acceptance criteria:
- A pg-boss scheduled job on the queue `retention-sweep`, added to `QUEUES` and registered through the E07 scheduler, runs daily (`17 3 * * *` UTC) with one active run at a time, and `node src/server/retention.ts [--dry-run]` runs the same code path by hand (dry run prints counts and deletes nothing).
- It deletes only `webhook_deliveries` rows whose `processed_at` is older than `RETENTION_WEBHOOK_DELIVERIES_DAYS` (default 30; zod rejects values below 7, safely above GitHub's 3-day redelivery window) and `sessions` rows that expired (idle or absolute) more than one day ago. It never touches `signatures`, `signer_pii`, `cla_versions`, `audit_log`, `pr_evaluations` (the record of why a PR was accepted, numeric ids only), `commit_overrides` or `pgboss.*`.
- Rows with `processed_at is null` are never deleted whatever their age (they are pending work); a session that is still valid is never deleted.
- Deletes run in batches of `RETENTION_BATCH_SIZE` (default 5,000) rows, each batch in its own transaction, so a long backlog cannot hold a long lock; a second run right after the first deletes nothing.
- No grant migration is needed: the runtime role already holds DELETE on `webhook_deliveries` and `sessions` (E04-S07), and an `asRuntimeRole` test asserts exactly that. This sweep is the only purge of `webhook_deliveries` (E06 and E07 keep the rows) and complements the opportunistic session purge of E10-S01, which runs only when someone logs in. A test shows the role still cannot delete from any immutable table and that the sweep issues no statement against them.
- Each run that deleted something writes one `audit_log` row `retention.swept` (no actor and no installation: the action joins `AUDIT_ACTIONS`, `SYSTEM_ACTIONS` and `INSTANCE_ACTIONS` of E04-S09; metadata `{ "webhook_deliveries": n, "sessions": m }`, numbers only); a dry run and an empty run write none.
- Boundary tests: a row exactly at the cutoff is kept and one second older is deleted. Failure injection: an error on the second batch leaves the first batch committed, logs no row data, and pg-boss retries within its bounded `retryLimit`. Real Postgres only: a webhook delivery inserted while the sweep runs is never lost, and a redelivery that reuses an already purged `delivery_id` inserts cleanly.
- `docs/operations.md` documents the settings as defaults, not legal advice, and lists what is and is not purged.
- Built as: the rule of the cutoffs is in `domain/retention.ts` (`deliveryCutoff`, `sessionCutoff`; the bounds of the days, 7 to 3650, and the one-day grace of a session); the two settings are `RETENTION_WEBHOOK_DELIVERIES_DAYS` (7 to 3650, default 30) and `RETENTION_BATCH_SIZE` (1 to 100,000, default 5,000), read by `config/retention-fields.ts` into `AppConfig.retention`. The sweep is `runRetentionSweep` (`services/retention/retention-sweep.ts`) over the two targets of `retention-queries.ts` (`WEBHOOK_DELIVERIES`, `SESSIONS`, the only tables it names): one statement per batch, `delete ... where key in (select key ... limit n for update skip locked)` returning a count, so a row a redelivery holds is left for the next run and no batch waits; the dry run counts with the same condition. Both cutoffs come from one reading of the clock, a row exactly at the cutoff stays, and a session is due when its idle or its absolute expiry is before the cutoff. Each batch is a transaction of its own; the audit row `retention.swept` (no installation, no actor, the two counts) is appended by `appendAudit` in a transaction after the last batch, only when something went, and a run that fails part-way still records what its committed batches deleted before it rethrows. The job is `retention-sweep` (a queue with the `exclusive` policy, a strict `{ type }` envelope, `retentionSweepHandler`, bound by `registerHandlers` through `HandlerDeps.retention` and wired in `boot-jobs.ts` in every mode, with or without a GitHub App; the dead-letter registry logs it). The daily schedule is `applyRetentionSchedule` (`adapters/jobs/retention-schedule.ts`: `17 3 * * *`, `tz: 'UTC'`, through the `options` parameter `Boss.schedule` now has); pg-boss's scheduler now starts whenever workers do, because the retention schedule needs it even when `SWEEP_INTERVAL_MINUTES` is 0. A server that is down at 03:17 skips that day (pg-boss's default for a missed occurrence). The command is `src/server/retention.ts`, a one-line entry over `runRetentionCli` (`adapters/db/retention-cli.ts`): it reads the configuration with `loadConfig`, connects with `DATABASE_URL`, prints one line of counts, and exits 0, 1 (invalid settings or a failure, printing the name and code of the error and never its text) or 2 (usage). `isProcessed` (`services/webhook-delivery-rows.ts`) treats a row that is gone as not processed: the sweep may delete an old row between the insert that met it and the read.

**E22-S05 — Operator erasure command** ✅ Done
Post-MVP. A safe command-line wrapper around the audited SQL function from E16, for a server operator who receives an erasure request.
Acceptance criteria:
- `node src/server/erase.ts --github-id <n> --actor-github-id <n>` is a dry run by default: it prints how many `signer_pii` rows exist for that person, how many signature cores would be kept, and whether the `users` snapshot is already scrubbed. `--execute` performs the erasure. Both ids must be positive safe integers; a usage error exits 2.
- The erasure itself is a loop over the installations in which the person has `signatures` or an allowlist entry that still shows their login (read as the runtime role; the function clears `allowlist_entries.login_snapshot` per installation, and a tenant where the person only appears on an allowlist is one such installation), calling `erase_signer_pii(github_id, actor_github_id, installation_id)` (E16-S04) once per installation, each call in its own transaction; the command contains no SQL that deletes or updates anything. A GitHub id is global, so the command covers every tenant on the server, which is what an operator-level request means (an org admin's request through E16-S04 is scoped to one tenant). The function writes one audit row `signer_pii.erased` per installation, with that installation's id.
- An unknown GitHub id exits 1 with the fixed message "no such user". A person who is already erased (zero `signer_pii` rows in every installation and login `erased-<id>`) prints "nothing to erase", exits 0, calls no function and writes no audit row, so a repeat is safe. The dry run prints the counts per installation.
- After the loop it re-reads and checks the post-conditions once: zero `signer_pii` rows for the person in any installation, `users.login = 'erased-<id>'`, signature count unchanged. Any mismatch exits 3 with the counts. A failure part-way through the loop exits 4 with the installations done and pending; a rerun is safe because finished installations have no rows left. When E21 is present the same check covers the corporate PII tables because the SQL function does.
- Output and logs contain counts and numeric ids only. A hostile-name test stores names such as `=cmd|' /C calc'!A0` and `Robert'); DROP TABLE users;--` in `signer_pii` and asserts they never appear in stdout, stderr or log lines.
- Tests: the runtime role cannot delete from `signer_pii` directly (the command works only through the function); the audit row written by the function contains no name, email or login; cross-tenant: erasing a person leaves other people's rows in the same tenants intact.
- `docs/operations.md` gets an "Erasure requests" section: how to run the command, that the signature core is retained under GDPR Art. 17(3)(e), and that legal review of retention is the operator's responsibility.
- Built as: the entry is `src/server/erase.ts` (logic-free, like `retention.ts`; a Knip entry), over `runEraseCli` (`adapters/db/erase-cli.ts`) and the connection helper that the retention command now shares (`adapters/db/cli-database.ts`: the options, the two sinks, `withDatabase`, and `failureLines`, which prints the name and the SQLSTATE of an error and never its message). Exit codes: 0 (dry run, erasure that held, "nothing to erase"), 1 ("no such user", an invalid environment, a failure of the first read), 2 usage, 3 the check after the loop did not hold (rows left per installation, snapshot, cores), 4 a call or the read after the loop failed (the line `installations done: ...; pending: ...`).
