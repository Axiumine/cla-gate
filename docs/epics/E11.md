# E11 — Authorization and tenant isolation

**Bounded Context:** BC-02
**Priority:** 🔴 Must have
**Status:** ⬜ Todo

**Goal:** Every request acts for exactly one tenant (one GitHub App installation, one org or account), and a person can do there only what GitHub says their numeric id may do. One instance serves several orgs, so isolation is enforced at four layers: a role decision derived from GitHub, one guard used by every route, installation-id-filtered data access, and composite foreign keys in the schema.
**Depends on:** E05, E10
**Out of scope:** Login and sessions (E10). Creating and syncing installation and repository rows, the admission policy itself and the state transitions suspend, delete and transfer (E05-S06 to E05-S09; this epic only decides what each state means for access). The installation and repository listing endpoints (E14-S01). Every feature route that uses the guards (E12 to E16). The operator screen (E18). Tenant-scoped data export or purge (E16).

---

**E11-S01 — Access declarations and the pure decision table** ✅ Done
No route can exist without saying who may call it, and the decision itself is a pure function.
Acceptance criteria:
- Every route declares `config.access` as one of `public`, `authenticated`, `webhook`, `operator` or `tenant` (E11-S05). The `onRoute` hook records the table; boot throws `RouteAccessError` naming every `METHOD path` that lacks a declaration, so a plugin cannot slip a route past the check. The shared not-found handler needs none.
- `PUBLIC_ROUTES` is a constant: `GET /healthz`, `GET /readyz`, `GET /api/auth/login`, `GET /api/auth/callback` and the static SPA handler (E17). `webhook` is exactly `POST /webhooks/github`. A test asserts the declared `public` and `webhook` sets equal the constants, so a new public route needs a deliberate, reviewed edit. Later stories extend the constant in their own change, each with a changed constant test: `GET /api/meta` (E17-S09) and the setup routes (E19-S06, registered in setup mode only).
- `authenticated` routes answer `401 unauthorized` through E10's `requireAuth` before any lookup. A route whose path has a tenant parameter (`:installationId`, `:repositoryId`, `:documentId`, `:signatureId`, `:entryId`) cannot be `authenticated`: a test over the route table fails with the route name. (Routes keyed by `:githubRepoId`, such as E13's, resolve the tenant themselves and return the uniform 404 of E11-S05.)
- The `docs/security.md` role matrix (Auth model) is the oracle for the decision table below:

  | Action | Required role |
  |---|---|
  | View signatures, export CSV, revoke, invalidate (installation-scoped CLA) | org admin of the installation |
  | Same, repo-scoped CLA | repo admin (an org admin also passes) |
  | Publish CLA version, edit allowlist, record override | same as above, by the scope of the CLA or repository |
  | Sign a CLA, view own signatures | any authenticated GitHub user |

- Pure `decide(requirement, facts)` in `src/server/domain/authz.ts`. `requirement` is `org_admin` or `repo_admin`; `facts` is `{ orgAdmin, repoAdmin, hasRoleInInstallation }`. `org_admin`: allow when `orgAdmin`; otherwise `forbidden` when `repoAdmin` or `hasRoleInInstallation`; otherwise `not_found`. `repo_admin`: allow when `orgAdmin` or `repoAdmin`; otherwise `forbidden` when `hasRoleInInstallation`; otherwise `not_found`. The switch is exhaustive and an unknown requirement returns `not_found` (deny by default).
- A role-in-installation is, by definition, org admin, or admin on at least one repository of that installation that carries a repo-scoped CLA document (the discovery rule E14-S01 and E15 rely on). A viewer with no such role never learns that the installation exists.
- Table test over all 16 combinations (two requirements, three boolean facts) asserting the exact output, plus a type-level test that `decide` cannot be called with an unknown requirement.
- A route-table test also asserts that every `tenant` route is `mode: 'read'` or `mode: 'write'`, and that every `POST`, `PUT`, `PATCH` and `DELETE` tenant route is `write` (a write route never reads the role cache, E11-S04).
- Built as: `src/server/adapters/http/route-access.ts` (declarations, constants, the `onRoute` table in `app.routeAccess`, `RouteAccessError` from an `onReady` hook, so every offender is named at once), `route-access-guard.ts` (the `preHandler` after the CSRF check) and `src/server/domain/authz.ts` (`decide`). The static page handler joins `PUBLIC_ROUTES` with its route in E17-S03, because no such route exists yet and the test pins the set exactly. A `tenant` or `operator` route answers `401` without a session and the uniform `404` with one until E11-S05 and E11-S08 replace that step, so a route declared early denies everyone. Tests that add a route to the app declare `config: { access: 'public' }` (`PUBLIC_ROUTE` in `src/server/test-support.ts`).

**E11-S02 — Org admin resolved from GitHub by numeric id** ✅ Done
Acceptance criteria:
- The role fact uses `getOrgMembership(githubInstallationId, org, login)` from E05-S04 (`GET /orgs/{org}/memberships/{username}` with the installation token, Members: read; zod-parsed `state`, `role` and `user.id`). This story adds no port method and no second adapter call. The exemption lookup of E07-S10 reads the same call, and the two caches stay separate because they serve different freshness needs (role facts 60 seconds here, exemption facts 10 and 2 minutes there).
- For an `Organization` installation the viewer is `org_admin` only when the answer is HTTP 200, `state === 'active'`, `role === 'admin'` and `user.id === viewer.githubId`. The viewer's login is only the lookup handle: a recycled login returns another user's id and is refused. `404`, `state: 'pending'` and `role: 'member'` are not admin.
- The org is `installations.account_login` (a display snapshot that E05 refreshes on each sync); the viewer's login is `users.login` as refreshed at the last login. A renamed login or org therefore fails closed with a `404` until the next login or sync; this is documented, not worked around.
- For a `User` installation the viewer is `org_admin` iff `installations.account_id === viewer.githubId`. No GitHub call is made.
- A 403 is split like E07-S10: `x-ratelimit-remaining: 0` or `retry-after` throws `GitHubRateLimitedError`; any other 403 is a missing permission, logs `members_permission_missing` with the numeric installation id and resolves as not admin (fail closed). 5xx, timeouts (5 s) and network errors throw `GitHubUnavailableError`. The public-members endpoints are never used (an MSW handler fails the test on `/public_members/`).
- The token always belongs to the requested installation: `InstallationTokens.get(installation.github_installation_id)` of E05-S03. A call for a rejected, deleted or suspended installation hits the E05 `InstallationGate` and throws before any request; E11-S07 maps that.
- Contract fixtures (active admin, active member, pending, 404, 403 permission, 403 rate limit, id mismatch) live next to the adapter, typed through the zod schema.
- Cross-tenant test: the same viewer is admin of installation 1 and member of installation 2; each lookup uses its own installation token and returns its own answer.
- Built as: `createOrgAdminLookup` in `src/server/services/org-admin.ts` (`(installation, viewer) => Promise<boolean>`, the installation as its stored row reads, the viewer as `{ githubId, login }`), the 5 s deadline of every role lookup in `src/server/services/role-deadline.ts` (`withRoleDeadline`: the client port waits up to its own 10 s per attempt and repeats a read twice, so the request path stops waiting itself and throws `GitHubUnavailableError`), and the membership fixtures in `src/server/adapters/github/membership-fixture/test-support.ts` (each with what the adapter, and then the lookup, makes of it; E07-S10 reads the same list). The lookup is not wired into a route yet: E11-S04 puts the cache in front of it and E11-S05 calls it from the tenant guard.

**E11-S03 — Repository admin resolved from GitHub, and repo-admin discovery** ✅ Done
Acceptance criteria:
- The port gains `getRepositoryPermission(githubInstallationId, owner, repo, login)` (`GET /repos/{owner}/{repo}/collaborators/{username}/permission`, installation token, parsed with zod: `permission`, `user.id`). The viewer has `repoAdmin` only when the answer is 200, `user.id === viewer.githubId` and `permission === 'admin'`. `maintain`, `write`, `triage`, `read` and `none` are not admin; `role_name` is ignored because custom roles map onto the base `permission` field.
- An org admin satisfies any repository requirement without this call.
- Owner and name come from `repositories.full_name`, which E05 keeps fresh; a `404` is a denial. A repository with `removed_at` set is never probed.
- `discoverRepoAdminRole(viewer, installationId, budget)` implements the role-in-installation rule of E11-S01: it takes up to `budget.remaining` repositories of that installation with a repo-scoped document (`cla_documents.repository_id is not null`, repositories not removed), ordered by repository id, probes them with concurrency 5, and stops at the first admin hit. `ProbeBudget` is a per-request counter created with 100 (E14-S01) or 50 (E15) and decremented per uncached GitHub call; cache hits are free; when it is exhausted the result is `{ role: 'none', truncated: true }`.
- The denial path (choosing between 403 and 404, E11-S05) uses a separate small budget of 10 probes, so a stranger hitting endpoints costs at most 10 GitHub calls per installation per cache window.
- Error classes are those of E11-S02, and the same fixtures exist for the permission endpoint.
- Tests: `admin`, `maintain`, `none`, a recycled login (id mismatch), 404 on a renamed repository, discovery stopping at the first hit, discovery with 150 repositories and a budget of 100 returning `truncated: true`, and a removed repository skipped.
- Built as: `getRepositoryPermission` on the port (`src/server/services/ports/github.ts`) with its zod schema and request in the Octokit adapter (the repository name is checked against GitHub's character set, `.` and `..` included, before any request), its row in `FakeGitHub` and in the contract suite, and the permission fixtures in `src/server/adapters/github/permission-fixture/test-support.ts` (a custom role over `write` or `admin` shows that `role_name` is ignored). `createRepoAdminLookup` and `repoAdminFact` are in `src/server/services/repo-admin.ts`: a 403 that is a missing permission logs `repository_permission_missing` with the numeric installation id, and `repoAdminFact(orgAdmin, lookup)` is the rule that an org admin makes no repository call. `ProbeBudget` and `PROBE_BUDGETS` (100, 50 and 10) are in `probe-budget.ts`, the candidate query in `repo-admin-candidates.ts`, `createRepoAdminDiscovery` in `repo-admin-discovery.ts`. The budget is passed to the lookup, which spends one probe right before it asks GitHub; the role cache of E11-S04 sits in front of that lookup, so a hit is free. The probes are always the first `budget.remaining` repositories by id, which is what bounds a stranger to 10 calls per cache window. Discovery answers `{ role: 'repo_admin', truncated: false }` on a hit. A probe that fails is thrown after those in flight settle, unless one of them found an admin. Neither function is wired into a route yet: E11-S04 caches them and E11-S05 calls them.

**E11-S04 — Role cache with invalidation and fail-closed errors** ✅ Done
Acceptance criteria:
- `RoleCache` is keyed `(installationId, viewerGithubId, scope)` with `scope` either `org` or `repo:{githubRepoId}`. Positive and negative results live 60 s, at most 10 000 entries with least-recently-used eviction. Errors are never cached and there is no stale-if-error: after the TTL a failing GitHub means a failing request. Fake-timer tests at 59.999 s (hit) and 60 s (miss).
- Single flight: 20 simultaneous identical lookups produce one GitHub request (MSW counter). Lookups for different keys never wait on each other.
- Routes with `mode: 'write'` call the lookup with `fresh: true`: the cached value is ignored and replaced. Reads use the cache. A test shows a write route sees a demoted admin immediately while a read route may still see the old role for up to 60 s.
- Invalidation API: `invalidateViewer(githubId)`, `invalidateInstallation(installationId)` and `invalidateAll()`. This story adds the two call sites in E10-S06 (logout, in the handler that logs `auth.logout`) and E10-S07 (`revoke-user-sessions`) with tests.
- Error mapping at the HTTP edge through `AppError` (E10-S03): `GitHubUnavailableError` becomes `502 github_unavailable`; `GitHubRateLimitedError` becomes `503 github_rate_limited` with the `retry-after` header (seconds from GitHub, capped at 300). Endpoints never answer an empty or `none` result because GitHub failed (E14-S01 depends on that).
- Per-viewer protection of other tenants' GitHub budgets: at most 30 uncached lookups per minute per viewer, then `429 too_many_requests` with `retry-after`. Test with 31 distinct installation ids.
- The cache holds numeric ids and booleans only. It is in memory, per process; the `docs/security.md` (Auth model) notes that a restart clears it.
- Built as: `RoleCache` in `src/server/services/role-cache.ts` (single flight, `fresh`, the three invalidations; an answer lives 60 s from the moment its question was sent, and a lookup that is displaced by a fresh one or invalidated while under way answers its own callers but keeps nothing), its entries and LRU in `role-cache-entries.ts` and its keys in `role-key.ts` (`RoleKey`, `ORG_SCOPE`, `repoScope`; numbers only). `createRoleLookups` in `role-lookups.ts` puts it in front of the lookups of E11-S02 and E11-S03 and returns `{ read, write }` keyed by the route mode, so E11-S05 calls `lookups[mode]`; `write` is `fresh: true`. A `User` installation is decided by comparing ids, so it bypasses both the cache and the budget. The per-person limit is `createViewerLookupBudget` in `role-lookup-budget.ts` (30 uncached lookups per sliding minute, org and repository lookups together, over `createFailureThrottle`; the 31st throws `RoleLookupThrottledError` before GitHub is asked, and a failed lookup counts). The HTTP mapping is `upstreamFailure` in `src/server/adapters/http/upstream-failure.ts`, applied by `rejectRequest`: `502 github_unavailable`, `503 github_rate_limited` and `429 too_many_requests`, the last two with `retry-after` (300 at most for GitHub's wait), logged as a warning without a stack. `buildApp` creates one cache and exposes it as `app.roleCache` (`AppOptions.roleCache` injects one); `logoutRoutes` takes `roles` and forgets the caller in both forms of logout, and `createRevokeUserSessionsHandler` takes `roles` (required, so whoever binds the job in E07-S03 passes `app.roleCache`) and forgets the person after their sessions are deleted. `RepoAdminCandidate` gained `github_repo_id` and the discovery takes a `CachedRepoAdminLookup` (the bare lookup of E11-S03 still fits), so a discovery behind the cache spends no probe on a hit. The lookups and the budget are not wired into a route yet: E11-S05 builds them with the GitHub client and calls them from the tenant guard.

**E11-S05 — Tenant guards and the uniform denial convention** ✅ Done
One guard, used by every tenant route.
Acceptance criteria:
- `tenantAccess({ mode, resolve })` is the `config.access` value for tenant routes. `resolve(request)` returns `null` or `{ installationId, repositoryId: number | null, requirement }`, with `requirement` either `org_admin` or `repo_admin` (which needs a `repositoryId`). Helpers `byInstallationParam` and `byRepositoryParam` ship here; E12, E14, E15 and E16 add resolvers for documents, signatures and entries and compute the requirement from the resource's scope (`docs/security.md` matrix).
- Resolvers read with `installation_id` and `repositories.removed_at is null`. An unknown id, a removed repository and a tenant the admission policy rejected all resolve to `null`.
- In every path, `:installationId` is the internal `installations.id` (the surrogate key behind the composite foreign keys, `audit_log.installation_id` and the `id` of E14-S01), never GitHub's installation id, which appears in no URL. E12 to E18 use it that way; a non-numeric value is `400`, an unknown one the uniform `404`.
- Order: `requireAuth` (401), `resolve`, tenant state (E11-S07), role facts (cache, or fresh for writes), `decide`, then the 409 state check for writes, then the handler. The result is `request.tenant = { installationId, repositoryId, role }`; handlers read the installation id from it and never from body, query or path again. Strict body schemas reject an `installationId` field.
- Denials follow one table:

  | Situation | Response |
  |---|---|
  | No session | `401 unauthorized` |
  | Resource unknown, removed, tenant rejected, or the viewer has no role in the installation | `404 not_found` |
  | The viewer has a role in the installation or admin on the repository, but too low for the call | `403 forbidden` |
  | Role sufficient, tenant suspended or deleted, write call | `409 installation_suspended` or `409 installation_deleted` |
  | GitHub failed while deciding | `502 github_unavailable` or `503 github_rate_limited` (E11-S04) |

- The four `404` causes are indistinguishable: a test compares status, headers and body (apart from `requestId`) byte for byte for an unknown id, another tenant's id, a rejected tenant's id and a viewer without a role.
- The guard never reveals the viewer's role in an error body, and never runs the handler on a denial. A test asserts zero database writes and zero GitHub write calls on every denial.
- Table test: every row of the denial table for one `GET` and one `POST`, for an org admin, a repo admin of the target, a repo admin of another repository, an org member without admin, and an outsider.
- Built as: `tenantAccess`, `TenantResolver`, `TenantTarget` (a `repo_admin` target cannot be written without a repository), `requireTenant` and the `request.tenant` slot in `src/server/adapters/http/tenant-access.ts`; `config.access` of a tenant route now requires its `resolve`, and the boot check names a tenant route that has none. The resolvers `byInstallationParam(db)` and `byRepositoryParam(db)` in `tenant-resolvers.ts` take the database (the plugin that registers the route has it): `:installationId` and `:repositoryId` are `installations.id` and `repositories.id` in plain digits within 2^53, anything else is `400 bad_request`; a path with both parameters reads the repository with that installation, a path with `:repositoryId` alone takes the installation from the repository row; a requirement that follows the scope of the resource (E14) is a resolver of its own. The reads are in `src/server/services/tenant-queries.ts` (`findTenantRows` in any state, `findAdmittedTenantRows` for the resolvers, `installationOfRepository`). `guardTenant` in `tenant-guard.ts` is called by the access `preHandler` (`guardRouteAccess(app, { db, authorize })`) after `requireAuth`; it reads the tenant again, so a rejected tenant is the `404` here too whatever a resolver said. The role step is `createTenantAuthorization` in `services/tenant-authorization.ts` (org admin fact, repository fact for anyone who is not one, the discovery with the denial budget of 10 only when the first decision is `not_found`, then `decide`), wired by `createTenantAuthorizer` in `tenant-authorizer.ts` over `createRoleLookups` and the application's role cache; `AppOptions.github` carries the client (`boot` passes the client of the App; with no App, `roleGitHubNotWired` fails every role call as `502 github_unavailable`, so a user account still works and an organisation is never allowed). A suspended or deleted tenant is read from the database on every request and no role is asked of GitHub for it (its tokens are refused): only the owner of a user account is known (`account_id`), reads are served and writes get `409 installation_suspended` or `409 installation_deleted`, everyone else the `404`, until the ledger of E11-S07 adds the org admins of an organisation at that point (`inactiveFacts`). A lookup that throws `InstallationNotAdmittedError` (the state changed between the read and the lookup) is the uniform `404`. The `409` of an org admin of a suspended organisation therefore needs the ledger of E11-S07; E11-S05 shows it for the owner of a user account.

**E11-S06 — Tenant-scoped data access and the cross-tenant matrix** ⬜ Todo
The mandatory cross-tenant tests are generated from the route and query registries, so a new endpoint or query cannot ship without one.
Acceptance criteria:
- Every data function over a tenant table (`repositories`, `cla_documents`, `cla_versions`, `signatures`, `signer_pii`, `commit_overrides`, `allowlist_entries`, `pr_evaluations`, `audit_log` reads) takes the installation id as a required parameter (a `TenantScope` `{ installationId }` in new code). Modules are listed in `TENANT_MODULES` and every exported function in `TENANT_QUERIES` with a fixture-argument factory.
- A source-scan test (TypeScript compiler API) fails when a file under `src/server/adapters/db/` calls `selectFrom`, `insertInto`, `updateTable` or `deleteFrom` on a tenant table and is not in `TENANT_MODULES`; another fails when an export of a listed module is missing from `TENANT_QUERIES`.
- The generated query test seeds `seedTenant(db, 1)` and `seedTenant(db, 2)` (E04-S02) and, for each registered query: called with tenant 1's scope and tenant 1's ids it returns tenant 1 rows only; called with tenant 1's scope and tenant 2's ids it returns nothing and changes nothing (rows affected 0; table checksums unchanged). Lookups by `github_repo_id` also filter `removed_at is null`.
- Route matrix: `CROSS_TENANT_CASES` has one entry per `tenant` route, keyed `METHOD path`, with an endpoint class (`installation_read`, `installation_write`, `repository_read`, `repository_write`, `document_read`, `document_write`) and a request builder. A test over the route table fails with the route name when an entry is missing, so adding a route without its case fails the build.
- For each case the matrix asserts: tenant 2's admin gets `404` on tenant 1's resource, identical to an unknown id; tenant 1's repo admin of another repository gets `403` where the table says so; the tenant's own admin gets the expected success; after every denied call, row counts and checksums of all tenant tables are unchanged.
- `authenticated` routes that return tenant data by design (E13 `GET /api/sign/:githubRepoId`, `GET /api/me/signatures`) are covered by a second table, `ISOLATION_CASES`, asserting that the viewer's result never contains another tenant's rows and ignores injected ids. Same completeness check as above.
- The fixture `twoTenants(db)` extends `seedTenant` and returns tenants 1 and 2 plus users `admin1`, `admin2`, `repoAdmin1` (admin only on a repo-scoped-document repository of tenant 1), `member1` (org member, not admin) and `outsider`, with a `StubRoleLookup` implementing the role port from a table. Adapter-level tests use MSW instead.
- A background-work helper `assertRepositoryInTenant(scope, repositoryId)` throws `TenantMismatchError` when the repository belongs to another installation; jobs use it before any write.

**E11-S07 — Suspended, deleted and rejected tenants, removed repositories and transfers** ⬜ Todo
Retention is E05's job (nothing is deleted); this story decides what access means while a tenant is not active.
Acceptance criteria:
- Pure `tenantState(installation)` in `src/server/domain/tenant-state.ts` with precedence `rejected` (`admission_status = 'rejected'`), `deleted` (`deleted_at` set), `suspended` (`suspended_at` set), `active`. A test shows it agrees with the installation-level reasons of E05-S06 `evaluationEligibility` for all 8 combinations.
- Rejected tenants are invisible: every tenant route answers the uniform `404`, for admins too. No ledger applies.
- GitHub refuses installation tokens for suspended and deleted tenants (the E05 `InstallationGate` throws before any request), so live role lookups are impossible. For `User` installations the owner is derivable from `account_id` and needs no lookup. For `Organization` installations a forward-only migration adds `installation_admin_seen (installation_id, user_github_id, seen_at, primary key (installation_id, user_github_id))`, numeric ids only, with the composite tenant convention of E04-S06 and runtime grants (select, insert, update, delete) given only when `cla_app` exists.
- The ledger is written on every live positive org-admin result (at most once per 60 s per pair) and the pair is deleted on a live negative result. It is read only for suspended and deleted tenants, and only entries from the last 14 days (`INACTIVE_ADMIN_WINDOW_DAYS`) count. Decision recorded: this is the one bounded exception to live verification, so that admins can still read and export signature evidence while the App is suspended or removed; the cost is that a demoted admin keeps read access for at most 14 days in that state. A ledger admin is `org_admin` for reads and gets `409 installation_suspended` or `409 installation_deleted` for every write. Without a ledger entry the answer is `404`.
- Repository admins cannot be verified on an inactive tenant, so only org admins (live or ledger) pass `repo_admin` requirements there.
- Repositories with `removed_at` set (E05-S09) are `404` on repository routes. Their repo-scoped documents and signatures stay reachable through document and signature routes for org admins only, because permission on a repository that left the installation cannot be checked.
- Transfer: after the repository moves between two admitted tenants, the old tenant's org admin gets `404` for the repository row of the new tenant and the new tenant's admin for the old row; a signature made under the old tenant's document does not appear in the new tenant's queries. Tested in both orders of the two sync events (E05-S09), as a cross-tenant test.
- The matrix of E11-S06 runs once more per inactive state: each `read` tenant route returns its normal success to a ledger admin, each `write` route returns the `409`, and a viewer without a ledger entry gets `404`. Ledger tests: day 13 passes, day 15 does not, a live negative removes the entry, the table holds no login or name.
- The role cache is bypassed for non-active tenants and the state is read from the database on every guarded request, so no invalidation hook is needed from E05's transitions.

**E11-S08 — Instance operator role** ⬜ Todo
E05-S07 ships `listInstallationsForOperator()` without a route; this story decides who the operator is and exposes it.
Acceptance criteria:
- `OPERATOR_GITHUB_IDS` is an optional comma-separated list of positive integers (whitespace trimmed, duplicates collapsed, at most 20; invalid input is a `ConfigError` naming the variable). When unset, the operator is the App owner's numeric id from the E05-S02 self-check if the owner type is `User`; if the owner is an `Organization` and the variable is unset, there is no operator. The start-up log prints the effective operator ids and the `docs/configuration.md` table documents the variable in the same change.
- Access kind `operator`: a pure `isOperator(githubId, policy)` decides; identity is the numeric id from the session, never the login. A non-operator and an unauthenticated caller of an operator route get `404 not_found` for a logged-in user and `401` without a session.
- `GET /api/operator/installations` returns the rows of `listInstallationsForOperator()` (E05-S07) plus `tenantState` from E11-S07. It carries no personal data (ids, display snapshots of account login and type, times, counts) and is read-only.
- Operator is not tenant admin: an operator who is neither org admin nor ledger admin of a tenant gets the uniform `404` from every tenant route (a test iterates the route table, so later routes are covered automatically). Operating the platform grants no access to signatures or personal data.
- Tests: owner `User`, owner `Organization` without and with the variable, a listed id, an unlisted id, `0`, `-1` and a string id (all refused), and the cross-tenant check above.
