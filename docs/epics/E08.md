# E08 — PR evaluation engine

**Bounded Context:** BC-04
**Priority:** 🔴 Must have
**Status:** ⬜ Todo

**Goal:** A pure, exhaustively tested function that decides whether a pull request is covered by the repository's CLA, from facts handed to it as plain data. It records why every actor is covered, and the same facts always give the same answer.
**Depends on:** E04
**Out of scope:** Any I/O: fetching the PR, commits, membership and signatures, and the head SHA discipline (E07-S04). Rendering fix hints and the failure text as markdown (E09, with the hostile-name escaping). Writing signatures (E13), allowlist entries (E14), commit overrides (E15). Corporate approvals as a covering basis (E21). Matching bots by app slug (the allowlist stores numeric ids only). The `in_progress` and `cancelled` states (E07).

---

**E08-S01 — Evaluation vocabulary, input types and stored-details schema** ✅ Done
Acceptance criteria:
- `src/server/domain/evaluation/types.ts` declares readonly types. `Account { id, type, appSlug? }` where `id` is a positive safe integer and `type` is `User`, `Bot`, `Organization`, `Mannequin` or `Unknown` (`Unknown` only for co-authors resolved from a trailer). `appSlug` is display-only. `Account` carries no login, name or email, so classification cannot depend on them.
- `CommitFacts { sha, parents, author, committer, message, rawAuthor, rawCommitter }`. `author` and `committer` are `Account | null`; `null` means an unlinked identity (the adapter maps GitHub's `null` and `{}` to it, E07-S04). `rawAuthor` and `rawCommitter` (`{ name, email }`) are display-only and are the only personal data in the input.
- `EvaluationInput { headSha, opener, commits, listing, policy, signatures, allowlist, orgMembers, overrides }`. `listing` is `complete` or `exceeded`. `policy` is `{ documentId, activeMajor }` or `null` (no active CLA). `signatures` are `{ id, githubId, documentId, versionId, major, revoked }`. `allowlist` are `{ id, kind, githubId, scope }` with `kind` in (`user`, `bot`, `org_members`) and `scope` in (`installation`, `repository`). `orgMembers` maps an org id to the set of user ids known to be members. `overrides` maps a commit SHA to a `commit_overrides` id.
- Closed constants: `FAILURE_CODES` (`no_active_cla`, `unsigned_contributor`, `bot_not_allowlisted`, `unlinked_identity`, `commit_limit_exceeded`), `ROLES` (`opener`, `author`, `committer`, `co_author`) and `FIX_CODES` (`sign_cla`, `allowlist_bot`, `allowlist_account`, `link_commit_email`, `maintainer_override`, `split_pull_request`). `CoveringBasis` is a discriminated union on `kind` (`signature` with `signatureId`, `versionId`, `major`; `allowlist` with `entryId`, `entryKind`, `scope`), written so E21 can add `corporate_approval` without touching existing branches.
- `src/shared/pr-evaluation-details.ts` exports the zod schema `PrEvaluationDetails` (strict, `version: 1`) for `pr_evaluations.details`: `outcome`, `failureCodes`, `documentId`, `activeMajor`, `commitCount`, `mergeCommitsSkipped`, `listing`, `actors[{ githubId, roles, covered, basis }]`, `unlinked[{ sha, role, overrideId }]`, `advisories[{ code, sha }]`. It holds numeric ids and codes only: no name, login or email.
- `parseStoredDetails(value)` never throws: an unreadable or unknown-version value returns `{ ok: false }`, so an old row cannot break a dashboard.
- Purity is enforced by lint, not by habit: ESLint `no-restricted-imports` for `src/server/domain` forbids `node:*`, `src/server/adapters`, `src/server/services` and `src/web` (added here if missing), and the domain code uses no `Date`, `Math.random` or `process`.
- Schema tests: a valid sample round-trips; every field wrongly typed, an extra key, a login smuggled into `basis`, and version 2 are refused or reported `{ ok: false }`.

**E08-S02 — Actor extraction and commit exemptions** ✅ Done
Acceptance criteria:
- `extractActors(input)` returns the distinct actors that must be covered, each with its roles and the commit SHAs it appears in, plus unlinked findings and a merge-commit count. Output is sorted by id, SHAs sorted.
- The PR opener is always an actor with role `opener`, whatever the commits say, so a contributor cannot ride on someone else's commit emails.
- A commit with more than one parent is skipped entirely (author, committer and trailers). A root commit and a single-parent commit are normal.
- Author: linked gives an actor with role `author`; `null` gives an unlinked finding `(sha, role: author)`.
- Committer is exempt when its id equals the author's id, or equals GitHub's `web-flow` id. Otherwise a linked committer is an actor with role `committer` and a `null` committer is an unlinked finding `(sha, role: committer)`. The `web-flow` id is the constant `GITHUB_WEB_FLOW_ID`, expected `19864447`; verify it once with `GET /users/web-flow` and record the date next to the constant (this is the Verify criterion for the `web-flow` id). The test pins the value.
- A person who is opener and author, or author and committer, is one actor with several roles. A user whose login is `web-flow` but whose id differs is not exempt (no login is ever compared).
- Table tests: opener only, opener equals author, author unlinked, committer unlinked and author linked, both unlinked, committer web-flow, committer equals author, a merge commit whose author and committer are both unsigned (skipped), a root commit, 0 commits, two commits by the same person, 250 and 2,000 commits.

**E08-S03 — Account classification and allowlist matching** ✅ Done
Acceptance criteria:
- `classifyAccount(account)` returns `bot` when `type` is `Bot`, `human` when `User`, `unknown` when `Unknown`, and `other` for `Organization` and `Mannequin`. It reads only `type`. A test passes an account whose display data would say `dependabot[bot]` but whose type is `User` and gets `human`, and a `Bot` with an ordinary-looking name and gets `bot`. An app slug, if supplied, is display metadata only and changing it changes nothing.
- `matchAllowlist(actor, entries, orgMembers)` returns the matching entry or `null`. A `user` entry matches `human`, `unknown` and `other` accounts with the same id. A `bot` entry matches `bot` and `unknown` accounts with the same id. An `org_members` entry matches `human` and `unknown` accounts when `orgMembers.get(entry.githubId)` contains the actor id. A bot is never matched by `org_members`.
- A kind and type mismatch never matches: a `bot` entry whose id belongs to a `User` account, and a `user` entry whose id belongs to a `Bot`.
- No membership fact for an org means not a member, so a failed membership lookup cannot grant coverage. The caller fails the job instead of passing partial facts (E07-S04).
- When several entries match, the choice is deterministic: repository scope before installation scope, then kind order `user`, `bot`, `org_members`, then the lowest entry id.
- Membership exempts only the member. A non-member co-author of a member's commit is evaluated on their own.
- A table of at least 30 rows covers the above, plus the same id listed under two kinds, both scopes, an empty allowlist, and ids at the edges (1 and `Number.MAX_SAFE_INTEGER`).

**E08-S04 — Signature coverage and covering basis** ✅ Done
Acceptance criteria:
- With `policy === null` the outcome is `failure` with code `no_active_cla`. Actors are still listed, all uncovered with `basis: null`, and no other failure code is added.
- An actor is covered by a signature when a fact has `githubId` equal to the actor id, `documentId` equal to `policy.documentId`, `major` equal to `policy.activeMajor`, and `revoked` false. A lower major and a higher major are both uncovered (a rollback publishes a new version, so equality is the rule). A fact for another document is ignored, and so is a revoked one (defence in depth, the loader already filters them). If two facts match, the lowest signature id is the basis.
- Bots are covered only by a `bot` allowlist entry. A signature fact whose `githubId` belongs to a `Bot` account is ignored: a bot cannot consent.
- Basis precedence for humans: a signature wins over an allowlist match (explicit consent is stronger and survives the entry being removed), then the allowlist match of S03. The stored basis is the first that applies.
- An uncovered `human`, `unknown` or `other` actor adds `unsigned_contributor` and a fix `sign_cla { githubId }` (for `other`, `allowlist_account { githubId }`). An uncovered `bot` adds `bot_not_allowlisted` and `allowlist_bot { githubId }`.
- The opener is covered or the outcome is `failure`, independent of the commits.
- Table tests: matching major, lower, higher, other document, revoked, two matching facts, signed and allowlisted, bot with a signature fact, bot with a `bot` entry, bot with only a `user` entry, minor versions (not an input, and nothing in the rule may depend on one).

**E08-S05 — Unlinked identities and per-commit overrides** ✅ Done
Acceptance criteria:
- Each unlinked finding from S02 is matched against `overrides` by commit SHA (compared lowercase). A matching finding is `overridden` with that override id and does not fail the PR. An override on a SHA that is not in the PR is ignored.
- An override covers only the unlinked identities of that commit. A linked but unsigned author or committer of the same commit still needs coverage. An override never creates a signature, never adds an actor, and never changes an actor's `covered` or `basis`.
- A commit with both author and committer unlinked produces two findings and one override resolves both.
- A finding without an override adds `unlinked_identity` and the fixes `link_commit_email { sha, role }` and `maintainer_override { sha }`. The fixes carry no email address; the display-only `rawAuthor` or `rawCommitter` stays on the in-memory finding for the renderer (E09) and is never written to the stored details.
- The domain never maps an email to an account. The only email parsing in the engine is the noreply form of a trailer (S06).
- Overridden findings are listed in the stored details as `{ sha, role, overrideId }` so the audit trail shows which commits passed by override.
- Table tests: unlinked author, unlinked committer, both, overridden, overridden with a second unsigned linked author, override for another commit, override SHA in uppercase, override for a SHA of 64 hex characters, the same SHA twice in the commit list.

**E08-S06 — Co-authored-by trailers** ✅ Done
Acceptance criteria:
- `parseCoAuthors(message)` reads only the final paragraph of the commit message (text after the last blank line, CRLF normalised). A line is a trailer when its key is `co-authored-by` (case-insensitive) followed by `:` and `Name <email>`. At most 20 trailers per commit are read; more produce one advisory `too_many_trailers` for that commit.
- Resolution accepts only `ID+login@users.noreply.github.com` (case-insensitive domain, `ID` a positive safe integer, a login of at most 39 characters with an optional `[bot]` suffix). Verify the form against GitHub's documentation before the code relies on it (this is the Verify criterion for the noreply form; `docs/github-app.md`, Rules, asks for the same check). The numeric id is the identity; the login part is never used.
- A resolved co-author becomes an actor with role `co_author`, type `Unknown`, merged by id with existing actors, and is covered by the same rules as anyone else (S03, S04). An unsigned one fails with `unsigned_contributor`.
- Everything else is advisory only and never blocks: the legacy `login@users.noreply.github.com` form without id, any other email, a malformed trailer, an id of `0`, an id above the safe range. Each gives one advisory `{ code: 'co_author_unresolved', sha }`. The advisory stores no name or email.
- Bot and AI trailers are ignored before resolution and give neither an actor nor an advisory: a login ending in `[bot]`, and the entries of an `IGNORED_TRAILER_IDENTITIES` table (for example `noreply@anthropic.com` and GitHub Copilot's noreply form). This is the single place text is matched. The code comment states why it is allowed: a trailer is spoofable text, and ignoring it only removes a requirement that the same text could add.
- Trailers of skipped merge commits are not read.
- Table tests (at least 25 rows): key in four cases, `Co-Authored-By`, two trailers, a trailer in a non-final paragraph, 21 trailers, missing angle brackets, an id with 20 digits, an id with a leading zero, a login of 40 characters, a `[bot]` login, an AI address, a hostile name (markdown, `@mention`, `#12`, RTL override) that must not change any result, and a trailer repeating the PR author's own id.

**E08-S07 — Commit listing strategy for large PRs** ⬜ Todo
GitHub's PR commits endpoint returns at most 250 commits. These pure functions turn the paging rules into inputs so the I/O loop in E07-S04 holds no decision logic.
Acceptance criteria:
- `planCommitListing(prCommitCount)` returns `{ strategy: 'pull_commits', pages }` with `pages = ceil(n / 100)` for `n` from 0 to 250 (250 gives 3 pages of 100, 100 and 50; 0 gives 0 pages), `{ strategy: 'repo_walk' }` for 251 to 2,000, and `{ strategy: 'refuse', code: 'commit_limit_exceeded' }` above 2,000.
- `verifyListing(prCommitCount, receivedShas)` returns `ok` or `mismatch`; a different count or a duplicate SHA is a mismatch (a push landed mid-listing, so the job refetches once, E07-S04).
- `collectRepoWalk({ headSha, mergeBaseSha, commits, pagesFetched, exhausted })` is a graph walk from the head over `parents` using the commits fetched so far (pages in any order, duplicates tolerated). It stops at, and excludes, the merge base. Results: `complete` with the sorted SHAs, `need_next_page` when a needed parent or the head is not fetched yet, `exceeded` when more than 2,000 commits are collected or `pagesFetched` reaches 25 pages of 100, and `inconsistent` when the listing is `exhausted` and a parent is still missing.
- A root commit reached before the merge base ends the walk as `complete` (unrelated histories). A head equal to the merge base is `complete` with no commits. An ancestor that appears on a later page than its descendant (commit dates are not topological) yields `need_next_page`, never a wrong `complete`.
- The `refuse` and `exceeded` results map to `listing: 'exceeded'` in the input, which S08 turns into a failure with the fix `split_pull_request`. Exceeding a limit always fails closed; the engine never evaluates a partial list as complete.
- Table tests: 0, 1, 100, 101, 250, 251, 2,000 and 2,001 commits; linear history of 300; merges inside the PR; merge base on page 1 and on page 6; interleaved dates; missing parent with and without `exhausted`; duplicate commits across pages; the head missing from all pages.

**E08-S08 — Evaluation composition, determinism and the exhaustive suite** ⬜ Todo
Acceptance criteria:
- `evaluatePullRequest(input)` in `src/server/domain/evaluation/evaluate.ts` composes S02 to S07 in a fixed order: policy check, listing check, actor extraction, co-authors, unlinked findings, classification, allowlist and signature coverage, aggregation. The outcome is `success` exactly when `failureCodes` is empty, otherwise `failure`. Both outcomes carry every actor, its basis, the advisories and the fixes, so a passing result still records why it passed.
- The result is fully ordered and deterministic: failure codes sorted and unique, actors by id, findings by SHA then role, fixes by code then id or SHA. A seeded test shuffles commits, signatures and allowlist entries 100 times over a 50-commit fixture and asserts deep equality of the result.
- `toStoredDetails(evaluation)` produces the S01 `PrEvaluationDetails`. A test puts distinctive personal strings (names, emails, logins, a markdown payload) into every input field and asserts that the serialised details contain none of them. A worst case of 2,000 commits stays under 256 KiB.
- Golden scenarios as inline snapshots (at least 14): opener and all authors signed; unsigned author; unsigned opener with signed authors; the attacker case, an unsigned opener whose commits use a signer's noreply identity (must fail); non-allowlisted bot opener; allowlisted bot opener; org member; unlinked author with and without override; committer `web-flow`; unsigned third-party committer; merge commit skipped; resolved unsigned co-author; listing exceeded; no active CLA; major bump (signed v1, active v2).
- Monotonicity property, seeded loop without a new dependency: adding a valid signature fact or a matching allowlist entry never turns a `success` into a `failure`, and removing one never turns a `failure` into a `success`.
- Mutation readiness: `src/server/domain/evaluation/` is the first scope of the Stryker floor (E20). Each rule has a row that fails when its condition is flipped, including the 250 and 251 boundary, `major` equal versus greater, committer equals author, `parents.length > 1`, and revoked.
- The engine never throws on a well-typed input, including empty lists. The suite obeys the structure caps: flat `test()` and `test.each()` tables, at most 4 fixtures per test, files split by rule.
