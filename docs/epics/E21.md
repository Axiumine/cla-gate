# E21 — Corporate CLA (later)

**Bounded Context:** BC-03
**Priority:** 🟢 Could have
**Status:** ⬜ Todo

**Goal:** Post-MVP (not in v0.1): let a company sign a corporate CLA once through an authorised signatory, who becomes its CLA manager and approves employees by GitHub username, verified email domain or GitHub org, so those employees are covered without signing individually. Corporate coverage is added to the evaluation engine as one more covering basis and is fully audited.
**Depends on:** E13, E15.
**Out of scope:** Anything in the MVP (individual CLA only). Additional or delegated CLA managers and transfer of management to another person; one signatory acting for several companies at the same CLA major; e-signature providers and PDF contracts; private org membership checks (only public membership is verifiable without a second installation); agreements shared across tenants (an agreement belongs to exactly one tenant, the GitHub App installation of the org that published the corporate CLA); sending e-mail notifications (the product sends none); shipping any corporate CLA text (maintainers upload their own).

**E21-S01 — Corporate agreement and approval schema** ✅ Done
Post-MVP. A forward-only migration adds the corporate tables with the same immutability and personal-data rules as the signature core.
Acceptance criteria:
- A new migration `NNN_corporate_cla.sql` (next unused number; `001_initial.sql` is never edited) creates `corporate_agreements` (`id`, `installation_id`, `signature_id` UNIQUE, `document_id`, `major`, `created_at`). The signatory's consent is an ordinary `signatures` row with `signer_type = 'corporate'` (version id, text hash, consent text id, name/email/login in `signer_pii`), so the immutable signature core is reused rather than duplicated. A BEFORE INSERT trigger rejects an agreement whose signature is not corporate, or whose installation or document differs from the signature's.
- `corporate_agreement_pii` (`agreement_id` PK, `company_name`, `signatory_title`) holds the erasable text; `corporate_approval_pii` (`approval_id` PK, `login`) holds the login snapshot of an approved user or org. No other table copies their values: `audit_log` metadata and `pr_evaluations.details` carry numeric ids only.
- `corporate_approvals` has `id`, `installation_id`, `agreement_id`, `kind` in (`user`, `email_domain`, `github_org`), `subject_github_id` bigint, `subject_domain` text, `source` in (`manager`, `rule`), `approved_by` (users FK, required iff `source = 'manager'`), `derived_from_approval_id` (self FK, required iff `source = 'rule'`), `approved_at`, `expires_at` (required iff `source = 'rule'`), and `revoked_at`, `revoked_by`, `revoke_reason` (at most 500 characters, no personal data). CHECK constraints: kind `user` or `github_org` has a numeric `subject_github_id` and no domain; kind `email_domain` has a lower-case domain matching a dotted hostname pattern and no id; `source = 'rule'` implies kind `user`.
- A partial unique index allows one active (not revoked) approval per (`agreement_id`, `kind`, subject). Composite foreign keys tie `corporate_approvals` to the agreement of the same `installation_id`, so a row can never point at another tenant's agreement.
- `repositories` gets a nullable `corporate_document_id` with a composite FK (`corporate_document_id`, `installation_id`) to `cla_documents`, and a trigger that requires that document's `kind` to be `corporate`. A null value means the repository accepts individual signatures only.
- Triggers: `corporate_agreements` blocks UPDATE, DELETE and TRUNCATE; `corporate_approvals` allows only a single transition of `revoked_at`, `revoked_by`, `revoke_reason` from null to set, and blocks DELETE and TRUNCATE. The runtime role `cla_app` gets INSERT and SELECT on all four tables, UPDATE only on the three `revoked_*` columns of `corporate_approvals`, and no DELETE or TRUNCATE anywhere.
- The same migration replaces the three-argument `erase_signer_pii(bigint, bigint, bigint)` of E16-S04 (`create or replace` with the same signature, so no overload appears; E16-S04 must be merged first) so it also deletes the `corporate_agreement_pii` rows of agreements whose signature belongs to the erased person and the `corporate_approval_pii` rows of approvals whose subject is that person; cores stay. The audit row still carries counts only. A schema test lists triggers and grants before and after the migration and shows nothing from `001` was weakened.
- Tests run on PGlite and on real Postgres: each trigger rejects its forbidden change with the expected error; an approval referencing an agreement of another tenant fails; revoking an approval twice fails; the erase function removes both PII tables' rows and leaves every core row.

**E21-S02 — Corporate signing and the CLA manager role** ✅ Done
Post-MVP. An authorised signatory signs the corporate CLA for a company and thereby becomes its CLA manager.
Acceptance criteria:
- This story flips the constant `CORPORATE_KIND_ENABLED` (E12-S01) to `true`: the `src/shared` schema already accepts `kind: 'corporate'`, and the document create route stops answering `422 kind_not_supported` (E12 tests are updated in the same change). `PUT /api/installations/:installationId/repositories/:repositoryId/corporate-document` with `{ "documentId": <id> | null }` sets `repositories.corporate_document_id`; it needs the org-admin role from E11, returns 422 `document_not_corporate` for a document of another kind, and writes audit action `repository.corporate_document_set`.
- `GET /api/corporate/repositories/:githubRepoId/document` returns the active corporate version (sanitised HTML via the E12 pipeline, `versionId`, `major`, `contentSha256`) for any authenticated user, or 404 `corporate_cla_not_configured` when the repository has none or is not enabled.
- `POST /api/corporate/agreements` (session, CSRF token and `Origin` check) takes `{ githubRepoId, versionId, contentSha256, companyName, signatoryTitle, typedName, authorityConfirmed }`. The server re-verifies the version id and hash against the repository's active corporate version exactly as the individual flow of E13 does (409 `version_outdated` on a stale major). `authorityConfirmed` must be the literal `true`; `companyName` is 1 to 200 and `signatoryTitle` 1 to 100 characters after Unicode NFC and trim, with control and bidi-override characters rejected as 422 `validation_failed`.
- One transaction inserts the `signatures` row (signer type `corporate`), its `signer_pii` row, `corporate_agreements`, `corporate_agreement_pii`, a manager-sourced `user` approval covering the signatory personally, and the audit row `corporate_agreement.signed` (numeric ids and major only). A failure injected at the last insert leaves no row in any of those tables.
- A second agreement for the same user, corporate document and major returns 409 `agreement_exists` (the `signatures_active_unique` violation, SQLSTATE 23505, mapped); it does not leak the existing agreement's id.
- Manager authority is "signatory of an unrevoked agreement" and needs no GitHub role. `GET /api/corporate/agreements` lists only the session user's agreements; `GET /api/corporate/agreements/:agreementId` returns 404 `not_found` for any agreement that is not theirs, byte-identical to a missing id.
- Org admins see all agreements of their tenant with `GET /api/installations/:installationId/corporate-agreements` (paginated: id, `signed_at`, major, company name, signatory numeric id and login snapshot, active approval count, revoked flag). Revocation reuses E15's signature revocation; a revoked agreement makes every manager mutation return 409 `agreement_revoked`.
- Writes for a suspended installation return 409 `installation_suspended`; reads keep working.
- SPA routes `/corporate/sign/:githubRepoId` and `/corporate/agreements` render in the E17 shell. Tests: cross-tenant (a manager in tenant A sees nothing of tenant B; an org admin of A gets 404 for B's agreement ids) and a hostile-name test (a `companyName` of `<img src=x onerror=alert(1)>` and one with `=HYPERLINK(...)` are shown as inert text).
- Built as: the server half is `corporateRoutes` (`corporate-routes.ts`, which registers `corporate-sign-routes.ts`, `corporate-agreement-routes.ts` and `corporate-tenant-routes.ts`), the paths and schemas are in `src/shared/corporate.ts`, the cleaning of the company name and the title in `src/shared/corporate-text.ts`, the rules in `services/corporate-sign.ts` (its transaction in `corporate-agreement-write.ts`), `corporate-agreements.ts` and `repository-corporate-document.ts`, the statements in `corporate-agreement-queries.ts` and `corporate-repository-queries.ts`. The consent text is `corporate-v1` (`src/shared/consent.ts`). The tenant routes are resolved by `byRepositoryParam(db, 'org_admin')` and `byInstallationParam`; the two person routes are `authenticated` with the budget `corporateSign` (10 a minute, per person). The text of the version is returned as the stored source (`contentMd`) and not as HTML, because the pipeline of E12-S07 is not run on a request path (its cost is not linear): the page draws it with `renderClaTree` through `src/web/corporate/ClaText.tsx`, which E18-S01's markdown view replaces. The request has no email field, so the signatory's address is the primary verified email of the session (else the first; none is `422 no_verified_email`), and the typed name is checked by the rules of E13 (`422 invalid_name`); the company, the title and the box answer `422 validation_failed` with the field in `details`. A request is not re-evaluated by a job and records no network metadata: the engine reads corporate approvals only from E21-S05. `GET /api/corporate/agreements` and the tenant list carry the `signatureId`, which an org admin revokes through `POST /api/installations/:installationId/signatures/:signatureId/revoke` of E15-S03. `requireManagedAgreement` (`corporate-agreements.ts`) is the one place a manager action finds its agreement and answers `404 not_found` or `409 agreement_revoked`; the routes that use it are E21-S03's, so no manager mutation exists yet. The pages are `/corporate/sign/$githubRepoId` and `/corporate/agreements` of the router (the shared paths spell the parameter `:githubRepoId`); no navigation entry points at them yet. A signed-in person who is a plain member of the organisation gets `404` from the two org-admin routes, as the guard table says for every org-admin route.

**E21-S03 — Employee approvals by username, verified email domain and GitHub org** ✅ Done
Post-MVP. The CLA manager decides who is covered by the agreement.
Acceptance criteria:
- `POST /api/corporate/agreements/:agreementId/approvals` takes a discriminated union: `{ "kind": "user", "login": string }`, `{ "kind": "email_domain", "domain": string }` or `{ "kind": "github_org", "login": string }`. Only the agreement's signatory may call it; any other caller gets 404 `not_found`. Returns 201 with the approval id; audit action `corporate_approval.added` (numeric ids and kind only).
- Kind `user`: the login must match GitHub's login pattern, is resolved to a numeric id with `GET /users/{login}` on the tenant's installation token, 404 becomes 422 `github_user_not_found`, a non-`User` account type becomes 422 `not_a_user`. The numeric id goes in `corporate_approvals`, the login snapshot in `corporate_approval_pii`. Kind `github_org`: resolved with `GET /orgs/{login}`, the org's numeric id is stored.
- Kind `email_domain`: lower-cased, converted to punycode, must contain a dot and match the hostname pattern, and is matched by exact equality with the part after `@` of a verified email (no implicit subdomains). Free-mail domains (`gmail.com`, `googlemail.com`, `outlook.com`, `hotmail.com`, `live.com`, `msn.com`, `yahoo.com`, `icloud.com`, `me.com`, `proton.me`, `protonmail.com`, `aol.com`, `gmx.com`, `mail.com`, `yandex.com`, `zoho.com`) are refused with 422 `domain_not_allowed`; the list lives in one file in `src/shared`.
- `GET /api/corporate/agreements/:agreementId/approvals` lists active and revoked approvals, paginated (default 50, maximum 200). `DELETE /api/corporate/agreements/:agreementId/approvals/:approvalId` with an optional `reason` (at most 500 characters) revokes it; the revocation is prospective and writes `corporate_approval.revoked`.
- Revoking an `email_domain` or `github_org` approval revokes, in the same transaction, every `source = 'rule'` user approval derived from it (one audit row each).
- Limits: at most 500 active approvals per agreement (422 `approval_limit`), 60 mutating requests per minute per session (429 with `Retry-After`). Mutations on a revoked agreement or a suspended installation return 409 `agreement_revoked` or `installation_suspended`.
- `POST /api/corporate/agreements/:agreementId/approvals/carry-over` with `{ "fromAgreementId": id }` copies the caller's own active manager-sourced approvals from their earlier-major agreement to the new one (two agreements of the same signatory and corporate document only), one audit row per copy, so a major bump does not make the manager retype the roster.
- Tests: cross-tenant (a manager cannot add or list approvals under another tenant's agreement id, and a domain approval in tenant A covers nobody in tenant B); lookalike inputs (`Acme.com ` with whitespace, an IDN domain, `acme.com.evil.test`) normalise or are rejected as specified; GitHub 404, 403 and rate-limit responses are mapped (`Retry-After` honoured, 503 `upstream_unavailable`) with no partial write.
- Built as: `corporateApprovalRoutes` (`corporate-approval-routes.ts`, registered by `corporate-routes.ts` after the agreement routes) holds four routes, one file each (`corporate-approval-list-route.ts`, `corporate-approval-add-routes.ts` for add and carry-over, `corporate-approval-revoke-route.ts`), with the shared path readers and the options of a changing route in `corporate-approval-route-options.ts`. The paths and schemas are in `src/shared/corporate-approvals.ts` (the discriminated request is strict: a key the kind does not know is `400`), the free-mail list in `src/shared/free-mail-domains.ts`, the revoke reason cleaning in `corporate-text.ts` (`cleanRevokeReason`: 1 to 500 code points and no `@`, because a stored reason cannot be erased). The domain rules are pure in `src/server/domain/corporate-domain.ts`: `normaliseDomain` refuses a path, port, scheme, address or invisible character before the URL host parser converts to punycode, then holds the result to the hostname pattern; `emailMatchesDomain` is the exact-equality match that E21-S04 and E21-S05 use. The rules are `services/corporate-approval-add.ts`, `-revoke.ts`, `-carry-over.ts` and `-list.ts`; the lookup is `corporate-approval-lookup.ts` (the GitHub client port gained `getOrganizationAccount`, `GET /orgs/{org}`; both lookups run before the transaction opens, under a 5 second deadline). The statements are `corporate-approval-queries.ts`, `-coverage-queries.ts`, `-write-queries.ts`, `-lock-queries.ts` and `-revoke-queries.ts`, all entered in the tenant registry. Every change runs in one transaction that first locks the agreement's signature row `FOR UPDATE`, so the 500 limit, the uniqueness (`approval_exists`) and the revocation of the agreement are decided one request at a time; the audit row is written in that transaction (`corporate_approval.added`, `corporate_approval.revoked`, one per derived approval, metadata with kind, numeric id, signature id and a code `carried_over` or `parent_revoked`, never a login, domain or reason). New rules: `github_user_not_found`, `github_org_not_found`, `not_a_user`, `domain_not_allowed`, `approval_limit` (422), `approval_exists`, `already_revoked` (409) and `upstream_unavailable` (503; any GitHub failure, a rate limit also sets `Retry-After` to GitHub's wait, capped at 300). The three mutating routes carry the budget `corporateApproval` (60 a minute for each signed-in person, as the other corporate routes count), have no route schema for path and body (a schema runs before the Origin, session and CSRF guards, so the handlers parse them), and answer `Cache-Control: no-store`. The list is newest first by approval id, with an opaque cursor, and is served for a revoked agreement and a suspended installation. A carry-over copies the manager-sourced approvals in force of an earlier major of the same corporate document, all or nothing under the limit, and skips what the target already has.

**E21-S04 — Employee flow: claim coverage under an employer's agreement** ⏳ In progress
Post-MVP: a contributor whose employer has an agreement can be covered without signing individually, and coverage is materialised as a numeric-id approval so PR evaluation stays pure.
Acceptance criteria:
- A migration adds `sessions.verified_email_domains text[] not null default '{}'`. The login callback of E10 fills it with the distinct lower-cased domains of the user's verified emails (domains only, never addresses) and nothing else is kept of the user token; the column is deleted with the session.
- `GET /api/corporate/repositories/:githubRepoId/availability` returns `{ "corporateAvailable": boolean }`, true only when the repository has a corporate document and at least one valid agreement (unrevoked signature, major equal to the active corporate major). It never names companies.
- `POST /api/corporate/repositories/:githubRepoId/claims` with `{ "confirm": true }` evaluates the valid agreements of the repository's tenant in ascending agreement id and, per agreement, in the order existing `user` approval, `email_domain` rule (session domains), `github_org` rule (public membership via `GET /orgs/{org}/public_members/{username}` on the installation token, 204 meaning member). The first match wins.
- On a rule match it inserts a `source = 'rule'` `user` approval for the session user's numeric id with `derived_from_approval_id` and `expires_at` 365 days later, writes audit action `corporate_approval.derived`, and returns 201 `{ "status": "covered" }`. An existing active user approval returns 200 `{ "status": "already_covered" }`. No match returns 409 `no_matching_approval` with a fixed message that says to ask the employer's CLA manager and names no company.
- After a successful claim the user's open PRs in that tenant are re-evaluated using the same job E13 enqueues after an individual signature.
- Limits: 10 claims per hour per user (429 with `Retry-After`); membership-check failures return 503 `upstream_unavailable` with no partial write; domain matching never calls GitHub.
- The E13 signing page shows "Contributing for an employer?" only when `corporateAvailable` is true; the success screen says "Covered by a corporate CLA" and shows no company name.
- Tests: an expired derived approval covers nobody; claims against a revoked agreement or an outdated major fail with `no_matching_approval`; a user in tenant A cannot be covered by tenant B's agreement through a matching domain (cross-tenant); case and lookalike domains (`ACME.COM`, `evilacme.com`) behave as specified in E21-S03.
- Open: the E13 signing page does not exist (`src/web` has no individual sign page, which E18-S01 owns), so the entry "Contributing for an employer?" is built and tested as the embeddable `EmployerClaim` component (shown only when `corporateAvailable` is true) and as a page of its own at `/corporate/claim/$githubRepoId`, but it is not mounted on the signing page yet.
- Built as: migration 021 adds `sessions.verified_email_domains` (a check holds each element to a bare lower-case domain, at most 20) and the E10 callback fills it through `domainsOfEmails`. The paths and schemas are in `src/shared/corporate-claims.ts`; the routes are `corporate-claim-routes.ts` (registered by `corporate-routes.ts`, which now takes the job enqueuer). The service is `corporate-claim.ts`: `corporateAvailable` is a read that answers `false` for every rule failure, so it teaches nothing about which tenants exist; `claimCoverage` lists the valid agreements (`corporate-claim-queries.ts`), matches (`corporate-claim-match.ts`) and writes (`corporate-claim-write.ts`). The match runs before any transaction: domains are the exact equality of `domainApprovals` and never call GitHub; the organisation rule asks `GET /users/{login}` once (the login of the session must still lead to the numeric id of the session), then `GET /orgs/{login}` (the login of the approval must still lead to the approval's id) and `GET /orgs/{org}/public_members/{username}` (the port gained `isPublicOrgMember`; only the status 204 is a member), at most 25 organisations per claim; any GitHub failure is `503 upstream_unavailable` with no write. The write runs under the signature lock of the matched agreement and checks the match again there (a revoked agreement or a parent approval that is gone is `no_matching_approval`); an expired derived approval of the person is revoked first (reason `expired`) because the unique index still holds its place. The audit row is `corporate_approval.derived` and the evaluations are the `evaluate-pr` job under a per-action key (`corporate_claim`), sent for both 201 and 200. The refusal is `409 no_matching_approval`; its fixed hint is in `details.hint` and the message stays the status text. The budget is `corporateClaim` (10 an hour for each person). The page is `/corporate/claim/$githubRepoId`.

**E21-S05 — Corporate coverage in PR evaluation, reporting and exports** ⬜ Todo
Post-MVP. The evaluation engine treats a valid corporate approval as one more way to cover an author, and maintainers can see and export what is in force.
Acceptance criteria:
- The pure coverage function in `src/server/domain` gains a `corporateCovered` set of numeric ids and a basis `corporate_approval`; precedence when several apply is allowlist rule, then individual signature, then corporate approval, so the recorded basis is deterministic. The `docs/architecture.md` sentence (How a pull request is checked) "a valid individual signature or a valid corporate approval covers an author" is implemented exactly; the PR opener and every non-exempt commit author and committer still each need a basis.
- One adapter query per evaluation loads the covered ids: approvals not revoked and not expired whose agreement's signature is not revoked and whose agreement major equals the active major of the repository's corporate document, always filtered by installation id. A partial index on `corporate_approvals (installation_id, agreement_id, kind)` where `revoked_at is null` serves it (it already exists: migration 020 of E21-S01 creates it, because this epic has only two migration numbers).
- `pr_evaluations.details` records per author `{ "basis": "corporate_approval", "agreementId": id, "approvalId": id }`; the schema is a zod type in `src/shared`, and rows written before this epic still parse.
- The Check Run summary and PR comment say "covered by a corporate CLA" and never print a company name, a domain or an org login (privacy: an employer relationship is not published on a PR). When an author is uncovered only because an agreement is outdated, the failure text says to ask the CLA manager to sign the current version.
- Tests: opener covered by approval but one commit committer unsigned still fails; revoking the agreement's signature or an approval makes the next evaluation fail for a PR that was `success` (after the re-evaluation E15 triggers); a property test shows adding approvals never turns a covered author uncovered and removing them never covers one; the new domain code has no surviving mutants under E20.
- `GET /api/installations/:installationId/corporate-agreements.csv` and `.../approvals.csv` (org-admin role, E16's CSV writer) export agreements (id, signed_at, major, company name, signatory numeric id and login, revoked) and approvals (id, agreement id, kind, subject numeric id or domain, source, approved_at, expires_at, revoked_at). Cells starting with `=`, `+`, `-`, `@`, tab or CR are prefixed; a `toMatchFileSnapshot` case with company name `=HYPERLINK("http://x","y")` and a login-like name with `@` is mandatory.
- Every state change in E21 has an audit action (`corporate_agreement.signed`, `corporate_approval.added`, `corporate_approval.revoked`, `corporate_approval.derived`, `repository.corporate_document_set`) and is readable through the audit-log API of E16 under that action name; a test inserts each action and shows the stored metadata contains no name, email, login or domain.
