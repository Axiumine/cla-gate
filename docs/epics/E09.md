# E09 — Check Run and PR comment reporting

**Bounded Context:** BC-04
**Priority:** 🔴 Must have
**Status:** ⬜ Todo

**Goal:** Turn an evaluation outcome into what contributors and maintainers see on GitHub: one `license/cla` Check Run per head SHA and one upserted PR comment with the sign link and exact fix steps. The output is built from user-controlled names, so encoding, length limits and stale-write protection are part of the contract, and this epic implements the `EvaluationReporter` port that E07 calls.
**Depends on:** E05, E07, E08
**Out of scope:** Deciding who is covered (E08). Fetching PR state, the head-SHA discipline of the job, `pr_evaluations.result` and `details` writes, retries and the dead-letter wiring (E07-S04, E07-S05). Webhook verification and routing of `pull_request`, `issue_comment` and the re-request events (E06-S04). The exact-line `/recheck` rule and its rate limit (E07-S07). The sign page and its API (E13). Per-commit overrides (E15). CSV export encoding (E16). The `finalise-check` job that decides when to call `enforcementDisabled` (E14-S04). Merge queue checks (E22, which reuses the Check Run writer of E09-S05).

**E09-S01 — Output encoding for user-controlled text** ✅ Done
Every login, name and trailer that reaches GitHub-visible output goes through these pure functions. Nothing else formats user text.
Acceptance criteria:
- `renderName(raw)` in `src/server/domain/reporting/encode.ts` returns exactly one Markdown inline code span. Cleaning order: replace lone surrogates with U+FFFD (`toWellFormed()`); remove C0 and C1 control characters, U+2028, U+2029, every bidi control (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069) and the tag block (U+E0000 to U+E007F); collapse each whitespace run to one space; trim; truncate to 64 Unicode code points and append `…` when cut; insert U+200B after every `@` and `#` (applied even inside the span, so a renderer that ignores the span still cannot mention or link) and between the `<` and the `!--` of every `<!--` (added by E09-S03, so that a name from the hostile corpus cannot spell the comment marker of E09-S07 and the marker appears 0 times in check output).
- The fence is one backtick longer than the longest backtick run in the text; text that starts or ends with a backtick is padded with one space each side. A name that is empty after cleaning renders `` `(unnamed)` ``.
- `neutraliseText(raw)` handles free text that is not a name (advisory trailer text): backslash-escapes the Markdown punctuation set `` \ ` * _ [ ] ( ) < > # + - . ! | ~ & ``, follows `@` and `#` with U+200B, turns line breaks into spaces and truncates to 200 code points. Both functions are exported for E22, which must use them for any name in a merge group summary.
- `shortSha(sha)` returns the first 7 characters only when the input matches `^[0-9a-f]{40}([0-9a-f]{24})?$` and throws `InvalidShaError` otherwise. Numeric ids are printed through `renderId(id)`, which checks `Number.isSafeInteger` first and throws `InvalidIdError` otherwise. No function in the reporting domain accepts or prints an email address: a test renders the corpus with an email-shaped name (`a@b.co`) and asserts every `@` in the output is followed by U+200B.
- The hostile corpus lives in `src/shared/hostile-names.ts` (marked `@internal` for Knip), which already exists: E17-S06 added it for the web test helper `expectHostileNamesInert`, so this story only extends it if a case is missing. It is two frozen lists, the single corpus that every later test (E10, E12 to E18, E22) imports from `src/shared` instead of defining its own. `HOSTILE_NAMES` holds printable names the signing form must accept verbatim: `=HYPERLINK("http://evil.example","x")`, `+1+1`, `-2+3`, `@SUM(A1)`, `=cmd|' /C calc'!A0`, `[x](http://evil.example)`, `<img src=x onerror=alert(1)>`, `@everyone`, `@here`, `@org/team`, `#1`, `org/repo#1`, `GH-1`, `'; drop table users;--`, `![i](http://t.example/p.png)`, `<script>alert(1)</script>`, `<!-- cla-platform:license/cla:v1 -->`, a backtick run and a triple fence, a pipe, `&#64;octocat`, a trailing backslash, `/recheck`, `javascript:alert(1)`, a right-to-left name without overrides, an emoji ZWJ sequence, zero-width joiners and a 200 code point name. `HOSTILE_CONTROL_NAMES` holds what signing rejects but GitHub-sourced data could still carry: `\n- [x] Signed`, `\r\n## Passed`, a NUL, a lone surrogate, U+202E, U+2028 and a 10 000-character name.
- E10-S05 (`auth-callback-profile.test.ts`) keeps a local copy of `HOSTILE_NAMES`, because the shared file was not built when it landed. `src/shared/hostile-names.ts` exists now (E17-S06), so this story deletes the copy and has that test import the shared list; `encode.ts` is what this story adds.
- Tests use `test.each` over both lists and assert: output is one line, starts and ends with a backtick, contains no `@` or `#` that is not followed by U+200B, and is at most 64 code points plus fence and padding. `toMatchFileSnapshot('snapshots/hostile-names.md')` stores the rendered lists in a dedicated directory.

**E09-S02 — Check Run output for success, in-progress, cancelled and disabled, with length limits** ✅ Done
Pure renderer for everything except the failure detail (E09-S03).
Acceptance criteria:
- `CHECK_RUN_NAME = 'license/cla'` is exported once from `src/shared/check.ts` (it replaces the `CHECK_NAME` of E06-S04, which lived in `check-name.ts`). A test (`src/server/check-name-literal.test.ts`) parses non-test sources under `src/` with the TypeScript compiler API and fails when a string literal equal to exactly `license/cla` appears outside that file (the constant is never retyped, so it cannot drift or be renamed; longer strings such as the comment marker are not literals of that value).
- `renderCheckOutput(view)` (`src/server/domain/reporting/check-output.ts`; the view types are in `check-view.ts`) returns `{ status, conclusion?, title, summary, text? }`. Mapping from `pr_evaluations.result`: `success` gives `completed` and `success`; `failure` gives `completed` and `failure`; `in_progress` gives `in_progress` with no conclusion; `cancelled` (the E07-S06 lifecycle value) gives `completed` and `cancelled`. A fifth view, `enforcement_disabled`, gives `completed` and `neutral`. The conclusion type is the union `'success' | 'failure' | 'neutral' | 'cancelled'`, so `skipped`, `timed_out`, `action_required` and `stale` cannot be emitted. GitHub counts `success`, `skipped` and `neutral` as passing for a required check; `cancelled` does not (documented in E09-S09).
- Titles are fixed strings of at most 100 characters: `CLA check passed`, `Checking CLA signatures`, `CLA check cancelled`, `CLA enforcement is disabled for this repository` and, for failure, `CLA signature required: N unsigned, M unlinked` (a zero count is omitted; with both zero, as for `no_active_cla` or `commit_limit_exceeded`, the title is `CLA check failed`).
- The success summary names no people. It states the count per covering basis, omitting zero counts, for example `4 contributors covered: 2 by signature, 1 by allowlist rule, 1 by maintainer override.`; the head SHA appears as `shortSha`. `text` is omitted. The in-progress summary is ``Evaluating commit 1a2b3c4. This updates automatically. Comment `/recheck` to run it again.`` The cancelled summary is `This pull request was closed before the check finished.`
- The `enforcement_disabled` summary is exactly ``The maintainers turned CLA enforcement off for this repository. If `license/cla` is a required check in branch protection, remove it from the required checks or ask the maintainers to re-enable enforcement.`` This is the one place the string is fixed; E14-S04 reuses it through `EvaluationReporter.enforcementDisabled` and adds none of its own.
- `summary` and `text` are each capped at 60 000 UTF-16 code units (GitHub allows 65 535). Lists show at most 50 entries, then one line `…and N more (list truncated)` after a blank line (a line straight after a bullet would be folded into it by Markdown). Truncation happens only at entry boundaries, so a code span is never cut.
- The failure view carries its `summary` and optional `text` as `OutputPart`s (`output-parts.ts`: text kept whole, lists cut at an entry boundary by `renderParts`) that E09-S03 builds from already encoded entries; with no part at all the summary is one sentence naming the short SHA and `/recheck`, because GitHub wants a summary. `coverageCounts(evaluation)` (`coverage-counts.ts`) gives the counts of the success summary; `override` counts commits with a waived unlinked identity.
- Boundary tests: lists of 0, 1, 50, 51, 250 and 10 000 entries, plus one entry with a 10 000-character name, assert the caps and the exact truncation line. Inline snapshots for each view.

**E09-S03 — Failure output: unsigned authors, unlinked emails and exact fix steps** ✅ Done
The failure summary tells each person precisely what to do. It is also the body source for E09-S07.
Acceptance criteria:
- Sections appear in this order and only when non-empty: sign link, `Not signed (N)`, `Email not linked to a GitHub account (M)`, `How to fix`, `Not blocking`.
- The sign link is `[Sign the CLA](URL)` with `URL = ${PUBLIC_BASE_URL}/sign/{githubRepoId}?pr={prNumber}`, built by `signPath(githubRepoId, prNumber)` in `src/shared/sign-link.ts` (E13 serves the SPA route and the context endpoint). `githubRepoId` is `repositories.github_repo_id` (stable across renames), `prNumber` an integer from 1 to 2147483647; both are validated before formatting. The link never contains a login, email, token or SHA. It is omitted when no one is unsigned.
- Each unsigned person appears once, keyed by numeric GitHub id, as ``- `octocat` (GitHub id 583231): opened the PR, commit author``, with roles from `opened the PR`, `commit author`, `committer`. The numeric id is shown so a recycled login cannot be mistaken for the signer. Logins come from the data the job already fetched (a `DisplayNames` lookup passed to `publish`, never persisted). An account the job saw no login for (a co-author named only by a trailer) shows as `(unnamed)` beside its id; a role the story does not list, `co_author`, reads `co-author`. A bot or an organisation that is not allowlisted is listed too, with the note `(a bot cannot sign; a maintainer can add it to the allowlist)` or `(this account cannot sign; a maintainer can add it to the allowlist)`, and the sign link is only offered when someone who can sign is unsigned.
- Each unlinked commit appears as ``- commit `a1b2c3d`: authored as `Jane Doe` (email not linked to a GitHub account)``. The email address is never printed; the fix text tells the author how to read it with ``git log -1 --format=%ae <sha>``. A commit with a maintainer override (E15) is not listed; the count of overridden commits appears as one line. A commit with both identities unlinked is one entry (`authored as ..., committed as ...`); an unlinked committer reads `committed as`.
- `How to fix` contains these numbered steps verbatim: (1) add and verify the commit email at `https://github.com/settings/emails`; (2) or set a linked address and rewrite the commits with ``git config user.email "<linked email>"``, ``git rebase <base> --exec 'git commit --amend --reset-author --no-edit'`` and ``git push --force-with-lease``; (3) or ask a maintainer to record an exception for the listed commits (an exception never counts as a signature). Steps (1) to (3) appear only when at least one unlinked commit exists. A closing line always appears: ``After fixing, comment `/recheck` or use Re-run. `/recheck` can be used once per minute.`` (the limit is E07-S07's, stated here because no reply comment is posted when it is hit).
- `Not blocking` lists unresolved `Co-authored-by` trailers (at most 10, names only, via `renderName`) under the sentence `These do not change the result.` Bot and AI trailers never appear. The engine's advisory holds only the commit and the code, so the names travel in `DisplayNames.coAuthors`, read by `unresolvedCoAuthorNames(message)` in the E08-S06 trailer parser (the text before the last `<`, never the address; exactly the trailers that give `co_author_unresolved`). A name repeated on several commits is shown once; names beyond the tenth end in the `…and N more (list truncated)` line.
- A failure with only unlinked commits has no sign link and no `Not signed` section. A failure with only unsigned people has no fix steps 1 to 3. `no_active_cla` (nobody can sign, so no person and no commit is listed) and `commit_limit_exceeded` each get one fixed sentence, because the story gives them no section; the closing line comes after the fix steps and before `Not blocking`.
- Tests: `toMatchFileSnapshot` for four representative outcomes (unsigned only, unlinked only, both, 300 commits) and for both hostile lists (E09-S01) placed in every name slot. The corpus run asserts: no line equals `/recheck` (it appears only inside the closing sentence), no `@` or `#` without U+200B outside the fixed text, no raw `<` outside code spans, and the marker `<!-- cla-platform:license/cla:v1 -->` appears 0 times in check output.

**E09-S04 — Check Run and comment ids on pr_evaluations** ✅ Done
E07 owns `result` and `details` of the row; this story owns the two reporting columns and the reads the reporter needs.
Acceptance criteria:
- `src/server/adapters/db/pr-evaluation-links.ts` exposes `recordCheckRunId(db, scope, key, id)` and `recordCommentId(db, scope, key, id)` (`db` first, as every data function of the tenant registry takes it), where `key` is `(repositoryId, prNumber, headSha)`. Each is one `update` that sets the column and `updated_at` and nothing else, filtered by `installation_id`, `repository_id`, `pr_number` and `head_sha`; it never touches `result` or `details`. A missing row throws `EvaluationRowMissingError` (E07-S04 step 3 inserts the row before `started`).
- `findCommentIdForPr(db, scope, repositoryId, prNumber)` returns the `comment_id` of the most recent row of that PR that has one (the row touched last: `updated_at`, then the row id), so a new head SHA keeps editing the same comment instead of opening a second one.
- `findRowsForSha(db, scope, repositoryId, headSha)` returns `(prNumber, result, checkRunId)` for every row with that head SHA, used for the shared-SHA rule in E09-S05.
- `hasNewerHeadRow(db, scope, key)` is true when another row of the same PR, with a different head SHA, has a later `updated_at` than this row. It is the database-only stale-write guard used before the comment write (E09-S07).
- Bigint columns go through the E04 int8 parser. Every query filters by `installation_id`; the composite foreign key `(repository_id, installation_id)` makes a mismatched pair unwritable.
- Cross-tenant tests (mandatory): tenant 1's scope cannot read, record or detect ids on tenant 2's rows, even when both tenants have PR number 7 and the same head SHA.
- Real-Postgres-only test (`realPostgresOnly`, E20-S03, which fails instead of skipping under `REQUIRE_REAL_POSTGRES=1`; a direct `skipIf` on the engine flag is refused by `real-postgres-usage.test.ts`): 20 parallel `recordCheckRunId` calls for one key leave one value and never revert it to null; the 20 calls and a concurrent E07 `result` update do not overwrite each other's column.
- The runtime role `cla_app` can run every statement in the module (an `asRuntimeRole` test). Nothing here deletes rows: `pr_evaluations` rows record why a PR was accepted and are kept (E22-S04 deliberately leaves them alone).

**E09-S05 — Check Run writer and the started/publish lifecycle** ⏳ In progress
Create, reuse and complete the Check Run, one per head SHA, with a low-level writer that knows nothing about pull requests.
Acceptance criteria:
- The E05 GitHub port gains `createCheckRun`, `updateCheckRun`, `getCheckRun` and `listCheckRunsForRef` (`POST /repos/{owner}/{repo}/check-runs`, `PATCH .../check-runs/{id}`, `GET .../check-runs/{id}`, `GET /repos/{owner}/{repo}/commits/{sha}/check-runs?check_name=license%2Fcla&filter=latest`), each with a zod schema that keeps only the fields used; `FakeGitHub` implements them and the shared contract suite runs against the fake and the Octokit adapter backed by MSW.
- `CheckRunWriter.upsert({ githubInstallationId, owner, repo, headSha, view, externalId?, detailsUrl?, forceNew? })` in `src/server/services/reporting/check-run-writer.ts` has no dependency on `pr_evaluations`, so E22 can call it with a merge group SHA. It finds the newest run of this App for the SHA (a supplied `existingId` via `GET`, a 404 meaning recreate; otherwise the listing, taking the first run whose `app.id` equals the configured App id), then `PATCH`es it, or `POST`s a new one when none exists, when `forceNew` is set, or when the `PATCH` is refused with 404 or 422. It returns `{ checkRunId }`.
- `EvaluationReporter.started(target)` (target: installation, repository ids, PR number, head SHA, trigger): no run for the SHA means `POST` a run with `status: in_progress`, `started_at` and `external_id` = the `pr_evaluations` row id as a string; an existing run that is not completed is reused untouched, so a job retried after a crash between create and the database write creates no second run; an existing completed run is left as it is (the previous verdict stays visible until the final write), except for the triggers `check_rerequested` and `recheck`, which `POST` a fresh `in_progress` run because the person asked for a visible re-run. The id is stored with E09-S04.
- `EvaluationReporter.publish(target, evaluation)` `PATCH`es the recorded run with `status: completed`, `conclusion`, `completed_at` and the output of E09-S02 and E09-S03, and `details_url` set to the sign link when one exists. If no run is recorded it creates one already completed. `evaluation` is the E08 outcome plus a `DisplayNames` lookup (E09-S03: numeric id to login, lower-case commit SHA to the names of its unresolved co-author trailers; `publish(target, evaluation, names)`, built by `displayNamesOf` in `services/evaluate-pr/display-names.ts` from data the job already fetched).
- Several open PRs can share one head SHA, and the run belongs to the SHA. The run's conclusion is the worst `result` among the rows from `findRowsForSha` (`failure` over `in_progress` over `success`) of the pull requests that still stand at the SHA (`liveSiblings` in `services/reporting/shared-sha.ts`); each PR keeps its own row and comment. A row is left out when its result is `cancelled`, when the pull request has a row touched later at another head SHA (`superseded`: its head moved on), and when GitHub lists the pull request for the commit (`listPullRequestsForCommit`, asked once and only when a row is left to ask about) as closed or with another head SHA; a pull request GitHub does not list stays in, so a listing that misses a failing PR never turns its check green. A finished row of a closed PR is never rewritten, so without this a stale `failure` or `in_progress` row would decide the run of an open PR for good. Test with two rows, one of them failing, and with a closed PR's `failure` row.
- The reporter never calls `getPullRequest`: E07-S04 re-checks the head before `publish` and accepts a newer job overwriting an older one. The SHA written is always `target.headSha`, never one read elsewhere. Whether GitHub accepts a `PATCH` on a completed run is unverified: verify it against a live repository in this story (a Verify criterion) and record the result in the pull request; the 404 and 422 fallback above keeps the check correct either way.
- Logs carry installation id, repository id, PR number, head SHA, run id and status codes only; never tokens, names, emails or bodies.
- Concurrency: the same PR is serialised by E07-S02, so the reporter takes no lock. Two PRs sharing one head SHA can run at once and, at worst, each creates a run; each row records its own run id, and a finished verdict is also written to the newest run of the App on the SHA (`writeSharedRun` in `report-write.ts`: one listing, a write only when that run is not the one just written), so both runs end with the worst-of conclusion whichever pull request finishes first. A verdict that is still `in_progress` converges nothing: the pull request still running settles the runs when it finishes. Asserted for both finishing orders.
- Tests with MSW and `FakeGitHub`: first run, retry after a crash (listing finds the run), re-run on a completed run, `check_rerequested` fresh run, `PATCH` 404 then recreate, two PRs on one SHA (sequential and simultaneous).
- Open: whether GitHub accepts a `PATCH` on a completed run needs a live check with the real GitHub App (a maintainer step, not a mock), and its result goes in the pull request; the writer already recreates the run on a 404 or 422, so the check stays correct either way. The reporter is built by `createCheckRunReporter` and is bound at boot by `boot-evaluation.ts` (E09-S06).

**E09-S06 — Failed, cancelled and disabled reports, and error classification** ✅ Done
A check must never stay `in_progress` forever, and one bad response must not lose a verdict.
Acceptance criteria:
- `EvaluationReporter.failed(target, code)` completes the run with `conclusion: failure`, title `CLA check could not complete` and summary ``Something went wrong while checking this pull request. Comment `/recheck` to try again.`` (a sixth view of the renderer of E09-S02, `evaluation_failed`). `code` is the closed type `'evaluation_failed'` (E07-S05). It writes no comment and no `pr_evaluations` columns (E07 sets the row to `failure`). A guard skip never throws: every method of the port now answers `Promise<ReportOutcome>`, `{ status: 'reported' }` or the `skipped` outcome of the table below.
- `EvaluationReporter.cancelled(target)` completes a run that is still `in_progress` with `conclusion: cancelled` (E07-S06); a completed run is left untouched. No comment is written. When another open pull request stands at the SHA (`liveSiblings`, E09-S05) the run is not cancelled, because it is not this pull request's alone: it is left running while another one is still being evaluated (that one finishes it, log `report.cancel_left_to_sibling`), and otherwise completed with the worst of the remaining rows (`settledView` in `shared-sha.ts`, log `report.settled_for_siblings`), the counts of a pass read from the stored details of the first passing row and zero when they cannot be read. A pull request that finished while this one was running left the run `in_progress` for this one's end to settle, and nothing publishes for it again.
- `EvaluationReporter.enforcementDisabled(target)` completes the run with `conclusion: neutral` and the `enforcement_disabled` view (E09-S02), and, only when a comment exists, rewrites it to the one-line notice `CLA enforcement is disabled for this repository.` after the marker (`COMMENT_MARKER` and `disabledCommentBody()` in `src/server/domain/reporting/comment-body.ts`; the port gained `updateIssueComment` for it). The comment follows the rules of E09-S07: the Check Run is written first, `comment_skipped_stale` when a newer head SHA of the pull request has been evaluated, `comment_skipped` with the status for a 403, 404 or 422 on the comment, a rate limit or an outage rethrown. It is what the E14-S04 `finalise-check` job calls.
- The error mapping uses the E05 classes. In a table test, one row per line:

  | Error from the GitHub port | Reporter behaviour |
  |---|---|
  | `GitHubRateLimitedError`, `GitHubUnavailableError`, `GitHubAuthError` | rethrown unchanged; E07 retries (E05 already retried idempotent reads, and every write here is idempotent by the reuse rule of E09-S05) |
  | `GitHubNotFoundError` on the repository or on `POST /check-runs` | return `{ status: 'skipped', reason: 'repository_gone' }`, log, no retry |
  | `InstallationSuspendedError`, `InstallationGoneError`, `InstallationNotAdmittedError` | return `{ status: 'skipped', reason: 'installation_unavailable' }`; tenant state is E11's concern |
  | `GitHubUnprocessableError` (the 422 mapping in the E05 adapter, added in E09-S05) | minimal-output fallback below |
  | `GitHubForbiddenError` (for example Checks: write missing) | log `checks_permission_missing`, throw `ReportRejectedError` |

- Minimal-output fallback: when a `POST` or `PATCH` is answered with 422, retry once with the title only and a summary of at most 500 characters holding the counts and the `/recheck` hint, no names (`minimalCheckOutput`, `check-output-minimal.ts`; the writer takes it as `minimal: true`). If that is rejected too, throw `ReportRejectedError`. The conclusion is always sent, so rejected text never leaves a run pending. The reporter is bound at boot by `boot-evaluation.ts`, so the evaluation jobs and the dead-letter handlers run whenever a GitHub App is configured.
- Tests are failure-injection tests with MSW: one `test.each` row per mapping above, a 422 followed by a successful minimal retry, a 422 twice, a `retryAfterSeconds` of 120 surfacing unchanged, and an idempotency test running `publish` twice against a MSW state that records exactly one run and one final `PATCH` pair.

**E09-S07 — Single upserted PR comment with the sign link** ✅ Done
One comment per PR, edited in place, from `Pull requests: write` only.
Acceptance criteria:
- The E05 port gains `listIssueComments` (one page of 100 with a `last` flag, so the reporter asks for pages 1 to 5) and `createIssueComment` (`GET .../issues/{n}/comments?per_page=100`, `POST .../issues/{n}/comments`) with zod schemas, in `FakeGitHub`, the mocked GitHub of the adapter tests and the contract suite; `GitHubIssueComment` carries `appId`, the `performed_via_github_app.id` (null for a comment a person wrote); `updateIssueComment` (`PATCH .../issues/comments/{id}`) came with E09-S06 for `enforcementDisabled`, and the `comment_skipped` rule below is `writeCommentSoftly` in `services/reporting/comment-guard.ts`.
- The body starts with the marker line `<!-- cla-platform:license/cla:v1 -->` (`COMMENT_MARKER`, `src/server/domain/reporting/comment-body.ts`, built from `CHECK_RUN_NAME`). Failure body (`commentBody`): heading `## CLA check failed`, sign link, the E09-S03 sections and fix steps, and a closing line naming the check `license/cla`. Success body (only when a comment already exists): `All contributors have signed the CLA for commit 1a2b3c4.` The comment always says the verdict of its own pull request (`RunReport.comment`), whatever other pull requests at the same SHA make the Check Run say.
- Upsert (`upsertComment`, `services/reporting/comment-upsert.ts`, called by `publish` after the Check Run is written), in order: (1) `findCommentIdForPr` (E09-S04) then `PATCH`; 404 falls through. (2) List comments for at most 5 pages of 100 and pick the oldest comment whose body starts with the marker and whose `performed_via_github_app.id` equals the configured App id. (3) Otherwise `POST` when the result is `failure`, and do nothing when it is `success`. The id found or created is stored with `recordCommentId`.
- A passing PR that never failed gets no comment (the Check Run is the signal). `started`, `failed` and `cancelled` never touch the comment.
- Stale-write guard: before writing, `hasNewerHeadRow` (E09-S04) is checked (first thing in `publish`, before the run id is recorded, because any recorded id touches `updated_at` of the row); when a newer head SHA has been evaluated for the PR, the comment write is skipped and logged `comment_skipped_stale`, because the comment is shared by all SHAs of the PR and the newer job writes it.
- A comment forged by anyone else, including one that begins with the marker, is ignored because the App id test fails. The body is rendered with both hostile lists in every name slot and the marker appears exactly once.
- Body length is capped at 60 000 UTF-16 code units (GitHub allows 65 536) with the entry-boundary truncation of E09-S02.
- Comment failures: `GitHubForbiddenError`, `GitHubNotFoundError` or 422 on the issue (locked conversation, archived repository) log `comment_skipped` with the status and do not change the Check Run, which is always written first; `GitHubRateLimitedError` and `GitHubUnavailableError` are rethrown for E07's retry. A human edit of the comment is overwritten by the next evaluation (documented in E09-S09).
- Failure-injection and idempotency tests: comment deleted by a maintainer (stored id 404, recreated, new id stored), two stale duplicates (the oldest is updated, the other left alone), 6 pages of unrelated comments (stops after 5 and creates), success path creates nothing, a newer SHA row present (no write).

**E09-S08 — Re-run and Re-run all checks end in a fresh run** ✅ Done
E06-S04 routes the two events and E07-S07 resolves the head SHA; this story proves the reporting side end to end and owns the observable behaviour.
