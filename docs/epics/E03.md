# E03 — Structure-cap ratchet tool

**Bounded Context:** BC-08
**Priority:** 🟠 Should have
**Status:** ✅ Done

**Goal:** A native Node script measures file, function, class, parameter and nesting size on the TypeScript syntax tree and fails on any new or grown violation against a committed baseline. Structural debt can then only go down, which keeps the 100% coverage and mutation gates cheap to satisfy honestly.
**Depends on:** E02.
**Out of scope:** Cognitive and cyclomatic complexity (Biome and ESLint, E02-S03 and E02-S04), FTA scoring (E02-S06), and any non-TypeScript or non-JavaScript language. Markdown, SQL and CSS files are not measured. Growing the baseline is never a feature: hard rule 1 forbids it.

---

**E03-S01 — Measure file, function and class length** ✅ Done
Caps are `file` 500, `function` 50 and `class` 300 lines; a value above the cap is a violation. They live in `CAPS` in `scripts/code-caps/types.ts`.
Acceptance criteria:
- A file is measured by its line count, where a trailing line break does not start a new line, and lines split on `\n`, `\r\n`, `\r`, U+2028 and U+2029. A file of 500 lines passes and 501 records `file` with name `-` on line 1, listed before any function violation.
- A function is any function-like node with a body: declarations, expressions, arrows, methods, constructors, accessors and class static blocks. Overload signatures, `declare` functions and abstract methods have no body and are not measured.
- A function spans from the first line of the node, with decorators and modifiers included, to its last line. 50 lines pass and 51 violate; the reported line is the first one of the span, decorators included.
- A class (declaration or expression) is measured the same way: 300 lines pass and 301 violate, and a nested class is measured on its own as well as inside its parent.
- A construct that exceeds several caps reports one record per cap (for example `function`, `params` and `nesting` for the same function).
- Each file is parsed in the mode its extension implies: JSX is valid in `.tsx` and `.jsx` and a syntax error in `.ts`; TypeScript syntax in a `.js` file is a syntax error.
- A syntax error throws `CapsError` with the message `<path>:<line>: <diagnostic>`, found through a one-file `ts.createProgram` and `getSyntacticDiagnostics`.
- An expression too deep for the walker (a 50,000-term sum) is reported as `<path>: cannot measure: RangeError...` as a `CapsError`, never as a raw stack.
- The tool needs the `typescript` 6.x package and uses the default import only (`import ts from 'typescript'`), because named imports are unverified under native type stripping.

**E03-S02 — Count parameters and nesting depth per function** ✅ Done
Acceptance criteria:
- Parameter cap is 4. A fake `this` parameter is free; a rest parameter counts one; a destructured parameter counts one; optional and defaulted parameters count; constructor parameter properties count. A class static block has zero parameters.
- Nesting cap is 4, counted per function over `if`, `for`, `for-in`, `for-of`, `while`, `do`, `try`, `switch` and `with` statements. Four nested blocks pass and five violate.
- `else if` stays on the parent's level, while `else { if (...) }` is a real extra level.
- `try`, `catch` and `finally` blocks each hold one level; a `switch` is one level whatever its clauses; every loop kind counts one level.
- Bare blocks and labels are transparent. Statements without braces count like blocks.
- Nested functions, callbacks and classes inside a block are measured on their own and do not add to the enclosing function's depth. A function with an expression body has depth 0.
- Only statements are walked, so a deeply nested expression cannot inflate the depth.
- The record for params and for nesting carries the same qualified name and line as the function record (E03-S03).

**E03-S03 — Name every measured construct stably** ✅ Done
Baseline keys are `<path>::<kind>::<name>`, so a name must not change when unrelated code moves.
Acceptance criteria:
- Names are qualified by their container: `Class.method`, `outer.inner`, `Namespace.fn` (`A.B.f` for a dotted namespace) and `config.handler` for a function inside a named object literal. An unnamed object literal adds nothing to the name.
- A function takes its own name; an arrow or unnamed expression takes the name of the variable, property or assignment target that receives it (`x.y` for `x.y = () => {}`). Parentheses, `as`, `satisfies`, `!` and `<T>` wrappers are looked through.
- Special names: `constructor`, `static` for a static block, `get v` and `set v` for accessors, `default` for a default export (function or class), and `<anonymous>` when nothing names the function.
- A callback passed to a call is named from the call, not from its position: `describe("outer title")`, `test.each(TABLE)("works %s")`, `items.map()`, `setTimeout()`. The callee is cut at 40 characters, whitespace is collapsed, and a string or template-literal title is cut at 40 characters.
- Fixing one callback never renumbers the baseline keys of its siblings, because the name does not depend on how many callbacks exist.
- A repeated qualified name within one file gets `#2`, `#3` on the repeats and never on the first (`foo()`, `foo()#2`).
- Baseline keys sort by code point, not by locale, so the order is identical on every machine.

**E03-S04 — Select the files to measure** ✅ Done
Acceptance criteria:
- Measured extensions are `.ts .tsx .mts .cts .js .jsx .mjs .cjs`; the result is a list of posix paths relative to the root, sorted by code point (uppercase first).
- Inside a git work tree the list is `git ls-files --cached --others --exclude-standard`, so tracked files and untracked-but-not-ignored files are measured, `.gitignore` is honoured, and a tracked file deleted from the work tree is skipped. A listing larger than 1 MiB is read in full, so `.gitignore` still applies.
- Output directories are not pruned by name in git mode, which is why `.gitignore` must list `coverage dist build reports playwright-report test-results .stryker-tmp .vitest` (E01-S05). A directory named `build` that holds real source is still measured when git tracks it.
- Outside git the tool walks the directory and prunes both the tool directories and the output directories by name.
- The tool directories in `TOOL_DIRS` (`.git`, `.claude`, `.idea`, `.yarn`, `node_modules` and one local code-index state directory) are skipped at any depth in both modes, including a tracked path below one of them.
- A directory whose name looks like a source file (`dir.ts/`) is not a file and is skipped.
- A source file whose name is not valid UTF-8 cannot be opened by its decoded name, so it fails with `file name is not valid UTF-8: <escaped name>` (exit 2) and is never silently skipped.
- Names printed in reports escape control characters as `\xNN`, so a hostile file name such as `x<ESC>[31m.ts` cannot forge terminal output.
- A nonexistent `--root` exits 2.

**E03-S05 — Ratchet violations against a committed baseline** ✅ Done
Acceptance criteria:
- `.code-caps-baseline.json` has the shape `{"version": 1, "caps": {...}, "violations": {"<path>::<kind>::<name>": value}}`, written with two-space indentation, keys sorted by code point and a trailing newline. The committed baseline today is `"violations": {}`.
- A missing baseline file is read as empty. A file that is not JSON fails with the file name and the parse reason; a file whose top level or `violations` is not an object, or holds a value that is not an integer, fails with `<file> is not a valid code-caps baseline`. Both are `CapsError` and exit 2.
- A baseline write is atomic: the JSON goes to `<file>.<pid>.tmp` and is renamed over the baseline, leaving no temporary file.
- Comparison classifies each current violation as `added` (key not in the baseline), `grown` (value above the allowed one), `improved` (below) or equal. Baseline keys that no longer occur are `fixed`, listed in code-point order.
- Only `added` and `grown` fail the check; an equal, improved or fixed entry passes.
- The ratchet lowers each surviving entry to `min(old, now)`, drops fixed entries and never adds one.
- Baseline `version` is not validated and huge files or symlinks pointing outside the root are not guarded; CLAUDE.md lists these as accepted limits, together with lenient UTF-8 decoding of file contents and the rejection of sloppy-mode octal literals.

**E03-S06 — Report results through a command line with exit codes** ✅ Done
Acceptance criteria:
- `node scripts/check-code-caps.ts` runs natively and sets `process.exitCode` from `main(argv, repoRoot)`; the default root is the repository root, one level above `scripts/`.
- Flags are `--root <dir>`, `--init`, `--force` and `--update-baseline`; any other option is rejected with exit 2 and no `--help` exists.
- Exit codes: `0` ok, `1` new or grown violation, `2` unusable input (syntax error, unmeasurable file, corrupt baseline, unknown option, `--init` over an existing baseline).
- A failing check prints one line per problem on stderr, for example `NEW   big.ts:1: function 'huge' = 60 lines (cap 50)` or `GREW  ... (baseline 60)`, then `code caps FAILED: new or grown violations (see above)`. Counted caps print without the `lines` unit (`params 'f' = 5 (cap 4)`).
- A passing check prints `code caps ok (N tolerated violation(s) in the baseline)` on stdout, preceded by `better: <key> 60 -> 55 (run --update-baseline to lock it in)` and `fixed: <key> (run --update-baseline to drop it)` lines when they apply.
- `--init` writes the baseline from the current violations and prints `wrote .code-caps-baseline.json with N tolerated violation(s)`; if the file exists it prints `.code-caps-baseline.json exists: use --force to overwrite` and exits 2; `--init --force` overwrites.
- `--update-baseline` writes the ratcheted baseline and prints `.code-caps-baseline.json updated`, or refuses with the report plus `refusing to update: fix new/grown violations first` (exit 1) when any violation is new or grown.
- Every failure path prints `code caps: <message>` with no stack trace, including a thrown value that is not an `Error`.
- CLAUDE.md states that agents never run `--init`, `--force` or `--update-baseline` to hide a violation: the code is fixed instead.

**E03-S07 — Wire the tool into hooks, CI and the coverage gate** ✅ Done
Acceptance criteria:
- `package.json` has `"caps": "node scripts/check-code-caps.ts"`, and `yarn caps` prints `code caps ok (0 tolerated violation(s) in the baseline)` on the repository today.
- The tool runs in `pre-commit` (in the parallel group), in `pre-push` (in the static-analysis group) and as the "Code caps" step of the CI `static` job (E02-S07, E02-S08).
- The modules are `types`, `naming`, `nesting`, `collector`, `measure`, `files`, `baseline`, `report` and `cli`, with the entry script `scripts/check-code-caps.ts`; tests are co-located and shared helpers live in `scripts/code-caps/test-support.ts`.
- The caps are mirrored by ESLint (`max-lines` 500, `max-lines-per-function` 50, `max-params` 4, `max-depth` 4) with counting options that agree with the tool, and the comment in `eslint.config.mjs` says to change both together. There is no ESLint class-size rule and no ratchet there: this script stays the gate for class size.
- Knip treats `scripts/*.ts` as production entry points and negates `test-support.ts` from the production project (E02-S06). Exports that only tests use carry `@internal`.
- The 144 tests in 8 files cover all 11 non-test files under `scripts/` (the entry script, nine modules and the shared test helpers) at 100% statements, branches, functions and lines, and the tool's own files stay under FTA 50 (highest 48.46).
- The tests obey the caps they enforce: flat `test()` and `test.each()` tables, no `describe` wrapper around a whole file, split by topic (`naming`, `nesting`, `measure`, `files`, `baseline`, `cli`, `types`, `entry`).
- Tests cover the entry script itself: it runs the check, sets the exit code and defaults the root to the repository root.
