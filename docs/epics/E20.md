**E20-S01 — Semgrep security scan gate** ⬜ Todo
Semgrep runs locally (pre-push, skipped when the binary is absent) and in CI (mandatory, never skippable), with the rulesets named in `docs/development.md` (Commands, `yarn semgrep`) and an offline rules cache that is never committed.
Acceptance criteria:
- `package.json` gets `"semgrep": "semgrep scan --config p/typescript --config p/javascript --config p/react --config p/nodejsscan --config p/secrets --error --metrics off --disable-version-check"`; `semgrep ci` is never used (it ignores `--config` and targets the platform). Any finding makes the command exit non-zero.
- `.semgrepignore` replaces Semgrep's defaults, so it re-lists `node_modules`, `dist` and `build` and adds `coverage`, `reports`, `.yarn`, `.stryker-tmp`, `.vitest`, `playwright-report`, `test-results` and `rules`. Co-located `*.test.ts` files are not ignored: they are scanned like any other source.
- `yarn semgrep:rules` (entry `scripts/fetch-semgrep-rules.ts`, logic in `scripts/semgrep-rules/`) downloads `https://semgrep.dev/c/p/<name>` for the five rulesets into `rules/<name>.yaml`; `yarn semgrep:offline` runs `semgrep scan --config rules/ --error --metrics off --disable-version-check`. The fetch logic takes an injected `fetch`; tests cover success, an HTTP 404 and a network error (non-zero exit, message names the ruleset) at 100% coverage.
- `rules/` stays git-ignored (it already is) and is never uploaded as a CI artifact or placed in a cache shared outside the repository, because the Semgrep Rules License v1.0 restricts redistribution; a test in the scripts project asserts `.gitignore` contains `rules/`.
- The first run over `scripts/` and `src/` ends with zero findings. Each fix is a code change; the only allowed suppression is an inline `// nosemgrep: <rule-id> -- <reason>` on the flagged line. No rule is disabled repository-wide.
- `lefthook.yml` `pre-push` gets a job named exactly `semgrep` in the parallel static-analysis group, running `yarn semgrep`, with a `skip` rule that fires when `semgrep` is not on `PATH`; the name matters because `LEFTHOOK_EXCLUDE=trivy,semgrep` is the sanctioned offline exception. It is not added to `pre-commit`.
- `ci.yml` gets a job `semgrep` with no `needs`, on `[self-hosted, Linux, X64]`, that installs Semgrep with `pipx install semgrep==<exact version>` under `$RUNNER_TEMP` (`PIPX_HOME` and `PIPX_BIN_DIR`, never the runner user's home) (the same exact version is pinned in `mise.toml`) and runs `yarn semgrep` after the standard Node, Corepack and `yarn install --immutable` steps. `permissions` stays `contents: read`; no SARIF upload.
- `docs/development.md` (Commands table) and `docs/toolchain.md` (tool table, hook table, CI job table) mark Semgrep as wired in the same PR.
- CI jobs, containers and ports of this story follow [CI runners, ports and fork approval](../ci-runners.md): shared self-hosted runners, literal `runs-on`, random free loopback port above 32768, timeouts and cleanup, release/scorecard on GitHub-hosted.

**E20-S02 — Trivy vulnerability, secret and misconfiguration gate** ⬜ Todo
Trivy runs as two passes: vulnerabilities (HIGH and CRITICAL, fixed only) and an unfiltered secret plus misconfiguration pass. The pinned version avoids the compromised releases recorded in `docs/tooling-gotchas.md` (Trivy).
Acceptance criteria:
- `yarn trivy` runs, in order, `trivy fs --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 .` and `trivy fs --scanners secret,misconfig --exit-code 1 .` (no `--severity` on the second pass, because `--severity` also filters secrets). `--exit-code 1` is spelled out in both because the default is 0.
- `yarn trivy:dev` is the first pass plus `--include-dev-deps` (used only by the scheduled CI run); `yarn trivy:secrets` is `trivy fs --scanners secret --exit-code 1 .` (needs no vulnerability database; used by `pre-commit`).
- `trivy.yaml` at the repo root sets `scan.skip-dirs` for `node_modules`, `.yarn`, `coverage`, `dist`, `build`, `reports`, `.stryker-tmp`, `.vitest`, `playwright-report`, `test-results` and `rules`, so every invocation (hook, CI, by hand) scans the same files.
- Trivy is pinned exactly to `0.76.1` or later in `mise.toml`, and CI installs it with `aquasecurity/setup-trivy` (v0.2.6 or later, pinned by full commit SHA with the version in a trailing comment) and then runs `yarn trivy`, so the command has one source. `trivy-action` is not used. A scripts-project test fails if anything under `.github/`, `mise.toml` or `lefthook.yml` mentions Trivy `0.69.4`, `0.69.5`, `0.69.6` or a `trivy-action` tag from `0.0.1` to `0.34.2`.
- `.trivyignore` is created only when the first ignore is needed. Every entry has a comment line above it with the reason and carries `exp:YYYY-MM-DD` no more than 90 days after the commit date; a scripts-project test fails on an entry without a reason or expiry, on an expired entry, and passes when the file does not exist.
- `lefthook.yml`: a job named `trivy` in the `pre-commit` parallel group running `yarn trivy:secrets`, and a job named `trivy` in the `pre-push` static-analysis group running `yarn trivy`. Neither has a missing-binary skip: an operator without Trivy uses `LEFTHOOK_EXCLUDE=trivy,semgrep`.
- `ci.yml` gets a job `trivy` with no `needs`, caching the Trivy cache directory (`TRIVY_CACHE_DIR` under `$RUNNER_TEMP`, not `~/.cache/trivy`) per calendar day, and `on:` gains `schedule` (nightly cron `17 3 * * *`, runs on the default branch). On the `schedule` event the job additionally runs `yarn trivy:dev`, so dev-only vulnerabilities fail the nightly run but not pull requests.
- The misconfiguration pass reads the Dockerfile and compose file once E19 adds them as plain files; findings are fixed in those files, never ignored. No image is built or scanned.
- `docs/development.md` and `docs/toolchain.md` mark Trivy as wired; the Trivy supply-chain note in `docs/tooling-gotchas.md` stays as written.
- CI jobs, containers and ports of this story follow [CI runners, ports and fork approval](../ci-runners.md): shared self-hosted runners, literal `runs-on`, random free loopback port above 32768, timeouts and cleanup, release/scorecard on GitHub-hosted.

**E20-S03 — Real-Postgres job and concurrency test harness** ⬜ Todo
E04 and E23-S06 add the informative `postgres` job that runs `yarn test` against a Postgres 18 container started by `scripts/ci/postgres.ts`. This story makes that run trustworthy and gives later epics a way to test races that PGlite (single connection) cannot reproduce.
Acceptance criteria:
- `src/server/adapters/db/test-support.ts` exports `realPostgresOnly`, the one helper that wraps the gating expression `test.skipIf(!realPostgres)` which E04 and later stories write directly; this story replaces each direct use by the helper, and a test fails on any remaining direct use. A test marked with it is skipped with the reason `needs real Postgres` when the database kind is `pglite`, and fails (never skips) when `REQUIRE_REAL_POSTGRES=1` is set and the kind is `pglite`. Unit tests cover both branches. The `postgres` job sets `REQUIRE_REAL_POSTGRES=1`.
- Tests that create or alter cluster-wide roles (E19-S03) use the companion `realPostgresRolesOnly`, which additionally needs `CLA_ROLE_TESTS=1` and skips with the reason `needs CLA_ROLE_TESTS=1`; the `postgres` job sets both variables against its disposable container.
- A line covered only by a real-Postgres-only test fails the 100% gate in the PGlite `coverage` job, because the test is skipped there; the rule "real-Postgres-only tests add assertions, never the only coverage" is written into `docs/quality-gates.md` (Testing).
- `withConnections(count)` in `test-support.ts` opens `count` independent connections to the throw-away `cla_test_<hex>` database and returns a promise-based `barrier()` that releases all of them at once. Interleavings never rely on `setTimeout`; "blocked" is observed through `pg_locks` rows with `granted = false`.
- Self-test 1 (real Postgres only): two connections inserting the same key into a table with a partial unique index (the `signatures_active_unique` shape: unique on three columns where `revoked_at is null`) produce exactly one success and one `23505`, in either order.
- Self-test 2 (real Postgres only): connection B running `select ... for update` on a row held by connection A is observed blocked in `pg_locks` until A commits, then proceeds and sees A's committed value.
- Failure-injection self-test (real Postgres only): `pg_terminate_backend` on a connection in the middle of a transaction makes the pool surface an error, leaves no partial rows, and the next query on a fresh connection succeeds.
- A test on both drivers asserts `show server_version_num` is at least `180000` and below `190000`, so a drifting service image or PGlite pin fails loudly. The job writes `select version()` to `$GITHUB_STEP_SUMMARY`.
- `docs/quality-gates.md` "How a test gets a database" (Testing) documents `realPostgresOnly`, `withConnections` and the env flag; the `docs/toolchain.md` CI table keeps describing `postgres` as advisory until E20-S12 promotes it.
- CI jobs, containers and ports of this story follow [CI runners, ports and fork approval](../ci-runners.md): the `postgres` job and the real-Postgres harness use the container that `scripts/ci/postgres.ts` starts on a random free loopback port above 32768, with a per-run name and cleanup in an `if: always()` step, and `withConnections` connects only to the throw-away `cla_test_<hex>` database.

**E20-S04 — StrykerJS mutation gate for server and shared code** ⬜ Todo
Mutation testing proves the 100% coverage is real: tests that only execute lines die here.
Acceptance criteria:
- `@stryker-mutator/core`, `@stryker-mutator/vitest-runner` and `@stryker-mutator/typescript-checker` are devDependencies pinned to the same exact version, 10.1.0 or later. `--logLevel debug` is never used (crashes on Vitest 5, Stryker issue 6272).
- `stryker.config.mjs` (typed with JSDoc against `PartialStrykerOptions`, inside the node-config tsconfig project) sets `testRunner: 'vitest'`, `checkers: ['typescript']`, `tsconfigFile` to the server tsconfig project, `coverageAnalysis: 'perTest'`, `mutate` of `src/server/**/*.ts` and `src/shared/**/*.ts` minus `*.test.ts`, `test-support.ts` and `global-setup.ts`, `thresholds: { high: 95, low: 90, break: 90 }`, `incremental: true`, `incrementalFile: 'reports/stryker-incremental.json'`, `tempDirName: '.stryker-tmp'`, and the `clear-text`, `html` (`reports/mutation/index.html`) and `json` reporters.
- `vitest.stryker.config.ts` selects only the node `server` project (Stryker forces coverage off and cannot drive jsdom or Browser Mode); `yarn mutate` is `stryker run --incremental`.
- The `break` value is committed as 90 only if the first full run in this repository scores at least 90; otherwise tests are added until it does. The threshold is never lowered afterwards. A surviving mutant is killed with a behaviour assertion, or, when provably equivalent, suppressed with `// Stryker disable next-line <Mutator>: <reason>` on the same line; each suppression is listed in the PR description.
- Determinism check: two consecutive `--force` runs on the same commit report identical killed and survived counts. If they differ (Stryker issue 6073), `coverageAnalysis` is set to `all` and the reason is written next to the setting and in `docs/quality-gates.md` (Testing, Stryker bullet).
- `ci.yml` gets a job `mutation` with `needs: static` and `timeout-minutes: 45`. It restores `reports/stryker-incremental.json` with a cache whose key prefix includes `hashFiles('yarn.lock', '.nvmrc', 'stryker.config.mjs', 'vitest.config.ts')` and whose `restore-keys` is that same prefix, so a dependency, Node or config change starts from a fresh run. `on:` gains `workflow_dispatch` with a boolean `force` input that adds `--force` (needed after snapshot or env changes); the nightly `schedule` run (added in E20-S02) always adds `--force`.
- The job uploads `reports/mutation/` as artifact `mutation-report` with 7-day retention, also when the job fails. Mutation never runs in a git hook.
- Verify: `@stryker-mutator/vitest-runner` 10.1.x runs against Vitest 5.0.x in this repository's layout (the node `server` project only, through `vitest.stryker.config.ts`). The first green `yarn mutate` run is the evidence, and the Stryker bullet in `docs/quality-gates.md` (Testing) is updated with what the run showed.
- `docs/development.md` (Commands), `docs/quality-gates.md` (Thresholds, Testing) and `docs/toolchain.md` (tool and CI tables) are updated in the same PR; Knip stays at zero issues in both modes.
- CI jobs, containers and ports of this story follow [CI runners, ports and fork approval](../ci-runners.md): shared self-hosted runners, literal `runs-on`, random free loopback port above 32768, timeouts and cleanup, release/scorecard on GitHub-hosted.

**E20-S07 — memlab leak scenarios with a failing wrapper** ⬜ Todo
memlab has no leak-based exit code (unverified, see the memlab bullet in `docs/quality-gates.md`, Testing), so a wrapper turns `leaks.length` into the exit code, and a positive control proves the wrapper can fail.
Acceptance criteria:
- `memlab` and `@memlab/api` are devDependencies pinned exactly. First step: a smoke run on Node 26.13.0 whose outcome is written into the memlab bullet of `docs/quality-gates.md` (Testing). If memlab fails on Node 26, the `leaks` job runs memlab inside the pinned Playwright container (Node from the image), started from a `run:` step through a `scripts/ci/` helper rather than a job-level `container:`, and the exception is recorded; the sentence "Node 26 compatibility is unverified" in that bullet is replaced by the outcome either way.
- `tests/leaks/run.ts` (logic-free, erasable syntax only, excluded from coverage by the fixed list) runs every `tests/leaks/scenarios/*.ts` through `@memlab/api` `run()`, prints the leak count and trace summary per scenario, sets `process.exitCode = 1` when any scenario has `leaks.length > 0`, and exits 2 on a memlab or browser error. It never exits 0 after an error.
- A scenario default-exports memlab's `{ url, action, back }` shape. Fixtures are served by a loopback `node:http` server on a random free port above 32768 from `pickSystemFreePort()` (never port 0); scenario files never hard-code a port.
- `yarn leaks` is `node tests/leaks/run.ts`. `yarn leaks:control` runs `tests/leaks/control/`: a deliberately leaking fixture (detached DOM nodes retained in a global array) must produce at least one leak, and a clean fixture must produce zero; the command exits 0 only when both hold. This is the guard against a memlab that silently reports nothing.
- The canary scenario `tests/leaks/scenarios/canary-navigation.ts` navigates in the clean fixture and back, and reports zero leaks. Scenarios for real application screens are added by the epic that ships the screen.
- Chromium: the wrapper hands memlab the Chromium executable that Playwright installed, so CI downloads one browser; if memlab cannot use it, memlab's own download is used and the extra cost is noted in the memlab bullet of `docs/quality-gates.md` (Testing).
- `ci.yml` `on:` gains `push` of tags matching `v*` (release candidates); `schedule` (E20-S02) and `workflow_dispatch` (E20-S04) already exist. The job `leaks` has `needs: coverage`, runs only for `schedule`, `workflow_dispatch` and `v*` tag events, runs `yarn leaks:control` and then `yarn leaks`, has `timeout-minutes: 30`, and uploads `reports/leaks/` on failure with 7-day retention.
- Diagnosis on demand, not in the gate: `docs/quality-gates.md` (Testing) documents `vitest --logHeapUsage`, `node --heap-prof` and `node --cpu-prof` as the first tools for a leak or slow-test report, and the `leaks` job uploads any `*.heapprofile` found in `reports/leaks/` together with the traces.
- `leaks` is documented as never required (`docs/toolchain.md` CI table, CONTRIBUTING.md Repository protection); the note "No leak-based exit code was found (unverified)" in the memlab bullet of `docs/quality-gates.md` is replaced by the verified behaviour once `leaks:control` proves the wrapper's exit codes.
- CI jobs, containers and ports of this story follow [CI runners, ports and fork approval](../ci-runners.md): shared self-hosted runners, literal `runs-on`, random free loopback port above 32768, timeouts and cleanup, release/scorecard on GitHub-hosted.

**E20-S09 — CI stability definition, promotion template and contract test** ⬜ Todo
