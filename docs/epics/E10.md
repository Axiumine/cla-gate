# E10 — Authentication and sessions

**Bounded Context:** BC-02
**Priority:** 🔴 Must have
**Status:** ⬜ Todo

**Goal:** Anyone with a GitHub account can log in through the GitHub App's user authorization and get a server-side session that the SPA never sees as a token. The same login serves every org on the instance, because a session identifies a person by numeric GitHub id and says nothing about tenants (E11 decides what that person may do in each installation).
**Depends on:** E04, E05
**Out of scope:** What a logged-in user may do per org or repository (E11). Signing and the sign page (E13). The login-failed and dashboard screens (E17, E18). Webhook intake and the routing of `github_app_authorization` to a `revoke-user-sessions` job (E06-S04; E10-S07 supplies the handler). Storing or refreshing GitHub user tokens (a non-goal: the token is used once and discarded). Shared rate-limit stores for several processes (one instance runs as one process per server).

---

**E10-S01 — Authentication configuration and the session store** ✅ Done
Server-side sessions in `sessions`, addressed by a hash of a 256-bit random id.
Acceptance criteria:
- `loadConfig` (E04-S01) requires `SESSION_SECRET` (at least 32 characters), `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` when `NODE_ENV=production`; a missing one is a `ConfigError` naming the variable, never a value. In `development` and `test` they stay optional and the auth routes are registered only when all three are set, the pattern E05-S01 uses for the App credentials, so the E04 boot test still starts without them. Two optional integers are added: `SESSION_IDLE_SECONDS` (default 28800) and `SESSION_ABSOLUTE_SECONDS` (default 604800), each at least 300, with idle at most absolute. `.env.example` and the `docs/configuration.md` table list all five in the same change.
- `src/server/domain/session.ts` holds the pure rules: `newTimes(now, config)`, `isLive(row, now)` (a session is dead at `idle_expires_at <= now` or `absolute_expires_at <= now`) and `slide(row, now, config)`, where the new idle expiry is `min(now + idle, absolute_expires_at)` so the table check `idle_expires_at <= absolute_expires_at` always holds.
- `src/server/adapters/db/sessions.ts` creates a session with a 32-byte `crypto.randomBytes` id (base64url, 43 characters) and stores only `session_hash = hex(sha256(id))`, plus a 32-byte random `csrf_secret`. The plain id exists in the return value and the cookie only. A test asserts the column never equals the id.
- `findLive(id, now)` looks up by hash and returns the session with its user row; a dead row is deleted and treated as absent. `touch` updates `last_seen_at` and `idle_expires_at` only when `last_seen_at` is more than 60 seconds old.
- At most 10 sessions per user: creating the 11th deletes the oldest of that user in the same statement. Each create also deletes up to 100 sessions that are idle- or absolute-expired, so the table does not grow without a scheduler.
- A forward-only migration (next free number) adds `sessions.verified_emails jsonb not null default '[]'` with a check that it is an array of at most 20 elements. It holds the verified addresses captured at login as `[{ "email", "primary" }]` for E13's sign page, because no user token is stored. Personal data in this table lives only as long as the session row; the `docs/data-model.md` table is updated in the same change. Erasure deletes these rows together with the person's other sessions (E04-S07, E16-S04), the personal-data catalog test of E04-S06 and the inventory of E16-S07 gain `sessions.verified_emails`, and CLAUDE.md hard rule 5 names this short-lived session snapshot among the places personal data may live (hard rule 10).
- Tests: boundary at exactly `idle_expires_at = now` (dead) and one millisecond before (live), sliding never exceeding the absolute limit, the 60-second touch throttle, the per-user cap, opportunistic purge, and an `asRuntimeRole` test that `cla_app` can run every statement.

**E10-S02 — Session cookie and authenticated requests** ✅ Done
New dependency: `@fastify/cookie` (MIT, Fastify organisation), registered with `secret: SESSION_SECRET`.
Acceptance criteria:
- The session cookie is `__Host-cla_session`. Its `Set-Cookie` is exactly `__Host-cla_session=<43 characters>; Max-Age=<absolute seconds>; Path=/; HttpOnly; Secure; SameSite=Lax` with no `Domain`. Only `setSessionCookie` and `clearSessionCookie` (same attributes, `Max-Age=0`) write it; a test inspects the raw header. `Secure` and the `__Host-` prefix are used in every environment; `docs/development.md` (Setup and run) notes that `http://localhost` works in Chromium and Firefox and that Safari needs an HTTPS tunnel.
- An `onRequest` hook reads the cookie. A value that is not 43 base64url characters is treated as no session without a database query; otherwise `findLive` runs and `request.auth` is `{ user: { id, githubId, login, name, avatarUrl }, sessionId, csrfSecret }` or `null`, where `id` is the internal `users.id` used for foreign keys such as `published_by` and `created_by` and `githubId` is the identity. `touch` runs on every authenticated request, throttled by E10-S01.
- `GET /api/auth/session` returns `200 { user: { githubId, login, name, avatarUrl }, expiresAt }` where `expiresAt` is `min(idle, absolute)` as ISO 8601. The schema lives in `src/shared/auth.ts`; ids are numbers. Without a live session it returns `401` with the standard error body (`code: unauthorized`); if a dead cookie was sent, the cookie is also cleared.
- Every response under `/api/auth/` carries `Cache-Control: no-store`.
- `request.auth` is the only way routes read the caller; no route parses the cookie itself. A helper `requireAuth(request)` throws the 401 used by every protected route (E11 builds its guards on it).
- Tests: a cookie with a valid id but an expired row, a forged id of correct shape, an id of the wrong length, a cookie of another name, two cookies of the same name, and `Max-Age` equal to the configured absolute lifetime.

**E10-S03 — CSRF token, Origin check, JSON-only state changes and explicit error codes** ✅ Done
Every state-changing request proves it comes from our own page.
Acceptance criteria:
- Domain codes use `AppError(status, code, details?)` from E06-S01, whose handler already sends its `code` and optional `details`. `403 origin_not_allowed`, `403 csrf_invalid` and `415 unsupported_media_type` below are its first uses in this epic, and E11, E12 and E13 throw it for theirs.
- The CSRF token is `base64url(hmac_sha256(SESSION_SECRET, "csrf:" + csrf_secret))`. It is returned as `csrfToken` in `GET /api/auth/session` and sent by the SPA in the `x-csrf-token` header (E17 reads both). Comparison uses `crypto.timingSafeEqual` after a length check, so a wrong length is rejected without throwing.
- A global `preHandler` covers `POST`, `PUT`, `PATCH` and `DELETE` in this order: (1) `Origin` must equal the origin of `PUBLIC_BASE_URL`; a missing header, `null` or any other value is `403 origin_not_allowed`; (2) a live session, else `401`; (3) a matching `x-csrf-token`, else `403 csrf_invalid` (the code E17's client answers with one session refresh and one retry). `GET`, `HEAD` and `OPTIONS` are never checked.
- A route opts out only with `config: { csrf: 'exempt' }`. The exempt set is the constant `CSRF_EXEMPT = ['POST /webhooks/github']` (`WEBHOOK_PATH` of E06-S01); boot fails when any other route sets the flag, and a test enumerates the route table with the `onRoute` hook. That route authenticates by HMAC only. A second closed constant, `SETUP_ROUTES` (the setup-mode routes of E19-S06, which run their own cookie, CSRF token and `Origin` check), is skipped by this hook too; every addition to either set is a reviewed edit with its own test.
- State-changing routes accept only `application/json`. The default `text/plain` parser is removed; `application/x-www-form-urlencoded` and `multipart/form-data` get `415` with `code: unsupported_media_type`. A request without a body needs no content type.
- Tests: cross-origin, `Origin: null`, no `Origin`, `https://app.example.com.evil.example` and `http` instead of `https` against a configured `https://app.example.com`, a token from another session, a token after logout, a token after the secret rotated, a missing token, and the exempt-set test. Table-driven, one row per case.

**E10-S04 — Start login: state cookie, PKCE and a relative-only return_to** ⬜ Todo
Acceptance criteria:
- `GET /api/auth/login?return_to=<path>` validates with zod and always redirects `302` to `https://github.com/login/oauth/authorize` with `client_id`, `redirect_uri=${PUBLIC_BASE_URL}/api/auth/callback`, `state`, `code_challenge` and `code_challenge_method=S256`. No `scope` parameter is sent (a GitHub App's permissions come from the App). The callback URL comes from one function `callbackUrl(config)` that `docs/github-app.md` and the setup kit (E19) reuse.
- `state` and the PKCE `code_verifier` are 32 random bytes each (base64url, verifier 43 characters); the challenge is `base64url(sha256(verifier))`.
- They travel in a signed cookie `__Host-cla_oauth` (`HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=600`) holding `{ s, v, r }`: state, verifier and the checked return path. A second login start overwrites the first, so the earlier tab's callback ends in `state_mismatch`.
- `safeReturnTo(raw)` is a pure function: the value must start with a single `/`, contain no backslash, control character or whitespace, be at most 512 characters, and resolve under `new URL(raw, 'http://localhost')` to origin `http://localhost`. Anything else, including a missing value, becomes `/`; it is never an error. A query string is allowed so `/sign/123?pr=45` survives.
- Table tests for `safeReturnTo`: `//evil.example`, `/\evil.example`, `\\evil.example`, `https://evil.example`, `javascript:alert(1)`, `/\t/evil.example`, `/%0d%0aSet-Cookie:x`, `/..//evil.example`, 513 characters, empty, and valid values `/`, `/dashboard`, `/sign/123?pr=45`.
- A caller who already has a live session is redirected straight to the checked `return_to` with no cookie and no GitHub round trip.
- The route performs no database write (a Kysely log hook asserts zero queries other than the session lookup) and sets `Cache-Control: no-store`. Fifty calls produce fifty distinct `state` values.

**E10-S05 — Complete login: exchange, identity, new session** ⬜ Todo
The GitHub user token lives for a few hundred milliseconds in a local variable.
Acceptance criteria:
- `GET /api/auth/callback?code=&state=` (both at most 512 characters; GitHub may send `error=access_denied` instead). The signed `__Host-cla_oauth` cookie must be present, unexpired and valid, and `state` must match by `crypto.timingSafeEqual`. The cookie is cleared on every outcome. The request log already omits the query string (E04-S03); a test confirms the `code` never appears in captured logs.
- Exchange: `POST https://github.com/login/oauth/access_token` with `client_id`, `client_secret`, `code`, `redirect_uri` and `code_verifier`, `Accept: application/json`, 10 s timeout. A 200 body carrying `error` counts as failure. The response is zod-parsed; refresh-token fields are parsed and dropped.
- Identity: `GET https://api.github.com/user` and `GET https://api.github.com/user/emails?per_page=100` with `Authorization: Bearer` and `X-GitHub-Api-Version: 2022-11-28`, zod-parsed. `type` must be `User`. `id` is a positive safe integer; `login` must match `^[A-Za-z0-9](?:[A-Za-z0-9-]{0,38})$`; `name` is cut to 255 characters; `avatar_url` is kept only when its origin is exactly `https://avatars.githubusercontent.com` (the origin E17 accepts), else `null`. Only `verified: true` emails are kept (at most 20, address as reported, `primary` flag kept).
- `users` is upserted by `github_id` (`on conflict (github_id) do update` of login, name, avatar_url and `updated_at`); login, name and avatar are display snapshots and nothing keys on them. The token is held in the E04 `Secret` wrapper, never logged or persisted, and revoked best-effort with `DELETE https://api.github.com/applications/{client_id}/token` (Basic auth with the client credentials); a revoke failure logs a warning with the status only.
- Session fixation: a session cookie presented on the callback has its row deleted, a new id is generated (its hash differs from the old one), the verified emails go into the new row (E10-S01), and the response sets the new cookie and redirects `302` to the checked `return_to`. Test: after the callback the old cookie value gets `401`.
- Failures redirect `302` to `/login/failed?reason=<code>` (the screen is E17) with `reason` one of `state_mismatch`, `access_denied`, `exchange_failed`, `github_unavailable`, `unsupported_account` (type is not `User`), `bad_request` (response fails the schemas above, for example an invalid login). The user upsert, the deletion of a presented old session and the insert of the new session share one transaction, so a failure writes nothing.
- MSW tests: happy path, tampered cookie signature, expired cookie, missing cookie, mismatched state, user-cancelled login, `bad_verification_code`, token endpoint 500 and timeout, `/user` 401, `type: Bot`, a login with invalid characters (`bad_request`, no `users` row), a hostile `name` from the printable hostile list of E09-S01 (stored verbatim, cut at 255), an avatar on another host (stored as `null`), no verified email (login succeeds with `[]`).

**E10-S06 — Logout** ⬜ Todo
Acceptance criteria:
- `POST /api/auth/logout` (session, CSRF and Origin from E10-S03) with an optional JSON body `{ "everywhere": boolean }` deletes the current session row, or with `true` every session of that user (`sessions_user_id_idx`), clears the cookie and returns `204`.
- After logout the old cookie gets `401` from `GET /api/auth/session` and the old CSRF token is rejected. A second logout with the dead cookie is `401`.
- Logout makes no call to GitHub (no token is stored).
- Another user's sessions are never touched: a test with two users deletes `everywhere` for the first and asserts the second still has all sessions.
- A body with unknown keys is `400`.
- The route declares `config.auditExempt: 'session'` (the closed reason of the E04-S09 route guard); logout is not a tenant mutation.

**E10-S07 — Delete sessions when a user revokes the App authorization** ⬜ Todo
E06-S04 turns a `github_app_authorization` `revoked` delivery into a `revoke-user-sessions` job with `{ githubUserId }`; the queue keeps those jobs until this story registers the handler (E07-S03).
Acceptance criteria:
- `deleteSessionsByGithubId(githubId)` removes every session of that user across the instance and returns the count; the `users` row stays (signatures reference it). It is idempotent, and an unknown id returns `0`.
- The `revoke-user-sessions` handler is registered in E07's `registerHandlers`. It validates its envelope with the job-payload schema of E07-S03 (a positive safe integer `githubUserId`), calls the function above and logs the numeric id and the count, never a login. The event carries no installation, so the deletion is instance-wide by design.
- The wrapper of E07-S03 marks the delivery processed on success; a handler error is retried and, after the limit, dead-lettered (E07-S05) and logged at error without personal data.
- Jobs queued before this story merged are consumed on first start (test: three jobs enqueued first, then the handler registered, all three processed).
- Tests: a user with three sessions revokes, then `GET /api/auth/session` with each old cookie is `401`; a second user is unaffected; a job for an unknown id completes with count `0`.

**E10-S08 — Rate limiting with a correct client address** ⬜ Todo
New dependency: `@fastify/rate-limit` (MIT, Fastify organisation), in-memory store.
Acceptance criteria:
- Registered globally: 600 requests per minute per client IP. Overrides: `GET /api/auth/login` and `GET /api/auth/callback` 20, `POST /api/auth/logout` 20, `GET /api/auth/session` 120. Routes may override the key (E13 keys signing on the session user) through route `config.rateLimit`.
- The key is `request.ip`, which follows `TRUST_PROXY` (E04-S03); no code parses `X-Forwarded-For` itself.
- The 429 response uses the standard error body (`code: too_many_requests`) and carries `retry-after`; `x-ratelimit-*` headers are present.
- `POST /webhooks/github` is exempt from the global limit (`config.rateLimit: false`): GitHub delivers from a few addresses, and E06-S07 already throttles failed signatures only. A test asserts the exempt set is exactly that route.
- Tests: with `TRUST_PROXY=false` a spoofed `X-Forwarded-For` does not give a fresh budget (the 21st login start from one socket is limited); with `TRUST_PROXY=1` two different forwarded clients have independent budgets; the store holds at most 10 000 keys.
- While `TRUST_PROXY` is false and a request carries `X-Forwarded-For` or `Forwarded`, a warning `trust_proxy_suspected` is logged at most once per minute (misconfiguration behind a reverse proxy would otherwise rate-limit every user together). Neither the IP nor the header value is logged or stored (network metadata policy).
- `docs/security.md` (Security and privacy) states that the in-memory store is correct for one process and that running several processes would need a shared store.
