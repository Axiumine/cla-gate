# E15 — Revocation, overrides and pending PRs

**Bounded Context:** BC-06
**Priority:** 🟠 Should have
**Status:** ⬜ Todo

**Goal:** Maintainers can take a signature out of force for future pull requests, unblock a single commit whose author email GitHub cannot link, and see which open pull requests are stuck and why. All of it is audited, prospective, authorised per tenant, and re-evaluates the pull requests it affects.
**Depends on:** E11, E13
**Out of scope:** Signing and re-signing itself (E13). The role computation and its cache (E11). The allowlist (E14). The evaluation engine, including how an override or a revoked signature changes a result (E08), and Check Run and comment rendering (E09). The audit writer and viewer, CSV export and erasure of personal data (E16). Screens for any of this (E18). Un-revoking: it does not exist by design, a contributor signs again instead.

---

**E15-S01 — Open or closed state on PR evaluations** ✅ Done
The pending-PRs view and the re-evaluation after a revoke must only touch open pull requests, and GitHub is not asked per row.
Acceptance criteria:
- A forward-only migration adds `pr_evaluations.pr_state text not null default 'open'` with `check (pr_state in ('open', 'closed'))` (merged counts as closed) and an index on `(installation_id, repository_id, pr_state, result)`. No immutability trigger is involved: `pr_evaluations` stays an updatable table for the runtime role
- The `evaluate-pr` job writes `pr_state` from the pull request it re-fetched, on every upsert of the (repository, PR number, head SHA) row. The `pull_request` `closed` handling (E07) sets `pr_state = 'closed'` on all rows of that (repository, PR number), and `reopened` sets `'open'`, each in one statement that filters by installation id
- A shared query function `latestEvaluationPerPr(installationId, repositoryIds)` returns the newest row per (repository, PR number), newest meaning `updated_at desc, id desc`, using `DISTINCT ON`. E15-S03 to E15-S07 use it; its test covers a PR that returned to an older head SHA (the upserted older row is newer by `updated_at`)
- The E07 reconciliation sweep, after it has fetched every page of a repository's open PR listing successfully, sets `pr_state = 'closed'` on the latest rows of PRs missing from that listing (a missed `closed` delivery). A listing that fails on page 2 changes nothing (failure-injection test)
- The candidate query of E13-S07 (`findFailingEvaluations` in `src/server/services/failing-evaluation-queries.ts`) gains `and pr_state = 'open'`, with a regression test that a closed PR's failing row is no longer enqueued after its author signs
- Existing rows default to `open`; no backfill job is needed, because the next sweep corrects them
- Cross-tenant test: closing PR 7 in tenant 1 leaves PR 7 of tenant 2 (same number, different repository) `open`
- Built as: the migration is `016_pr_evaluation_state.sql` (column, named check `pr_evaluations_pr_state_check`, index `pr_evaluations_state_result_idx`). `latestEvaluationPerPr(db, installationId, repositoryIds)` is in `src/server/services/current-evaluation-queries.ts` (the file is not called `latest-...` because the mutation-gate test treats any file name that contains `test` as a test file) and returns a query to build on, not rows: the stories after it wrap it, `db.selectFrom(latestEvaluationPerPr(...).as('latest'))`, and put their filters (`result`, `pr_state`, `details`) and paging on the outer query, because a `where` inside would pick the newest of the rows that pass it; an empty `repositoryIds` finds nothing. The `close-pr` job and the sweep's reaper close through `prunePullRequest` (after the queue cancel, before the reports, so a failed report that is retried still leaves the pull request out of the open views), and `setPullRequestState` never touches `updated_at`, which decides the latest row. The `reopened` delivery is routed to `evaluate-pr`, so that job sets `open` on every row of the pull request right after it saw the pull request open, before the repeated-delivery rule (a reopen at a head SHA that has a result and a Check Run is answered `unchanged` and must still reopen the rows); the timeline of the protocol gained that statement. The dead-letter write (`failEvaluation`) keeps the state a row has and creates a row `open`: it has no pull request to read. The sweep (`reconcilePullRequestStates`, in `sweep/sweep-state-rows.ts`, split from `sweep-rows.ts` for the FTA cap) closes the latest row of a pull request that a complete listing does not show, only when the row was not touched after the listing began and never for a listing cut at 1,000; it also opens the latest closed row of a pull request the listing shows (a missed `reopened`, or a close that ran after a reopen), which no criterion names and which the sweep log counts as `markedClosed` and `markedOpen`.

**E15-S02 — Find signatures to act on** ⬜ Todo
Maintainers need to look a signer up before revoking, and they see the personal data that the signer gave, which only they may.
Acceptance criteria:
- `GET /api/installations/:installationId/signatures?documentId=&state=&githubUserId=&login=&limit=&cursor=` with a session. `state` is `active`, `outdated`, `revoked` or `all` (default `all`); `limit` is 1 to 100 (default 50); order is `signed_at desc, id desc` with an opaque keyset cursor that zod validates (a tampered cursor is `400`). `login` is an exact, case-insensitive match on the `signer_pii.login` snapshot; `githubUserId` is an exact match on `users.github_id`
- Authorisation is by document: an org admin sees every document of the installation; a viewer who is only repo admin sees the signatures of repo-scoped documents whose repository they administer (E11, at most 50 repositories checked per request). A `documentId` that is not in the installation, or not in the viewer's authorised set, is `404`
- Item: `{ id, githubUserId, document: { id, name }, version: { major, minor }, signedAt, source: { repositoryFullName, prNumber } | null, state, revokedAt, revokedByGithubId, revokeReasonCode, signer: { login, name, email } | null, piiErased }`. `state` uses the same pure `signatureState` function as E13-S06. When the `signer_pii` row is gone (erasure, E16) `signer` is `null` and `piiErased` is `true`; the identity key `githubUserId` is always present
- Strings are returned verbatim and are not escaped here. Hostile-name test: every entry of `HOSTILE_NAMES` (E09-S01) signed through the real sign path comes back byte for byte in `signer.name`
- Every query filters by the path's installation id. Cross-tenant tests: an admin of tenant 1 requesting tenant 2's installation id gets `404` (same body as an unknown id); `documentId` of tenant 2 under tenant 1's path is `404`; a signature of the same GitHub user in tenant 2 never appears in tenant 1's result
- Pagination test with 120 rows and ties on `signed_at`: no duplicate, no gap. Filter tests: `state=outdated` returns only active signatures whose major is below the document's active major; `login` matches regardless of case and never matches by prefix
- The endpoint is read-only: it writes no audit row (exports are audited in E16-S03)

**E15-S03 — Revoke a signature** ⬜ Todo
Revocation is prospective: the signature stops covering future evaluations, contributions already accepted stay licensed.
Acceptance criteria:
- `POST /api/installations/:installationId/signatures/:signatureId/revoke` with body `{ "reasonCode": "signer_request" | "maintainer_decision" | "legal_request" | "other" }`, behind session, CSRF and `Origin` checks. The code set is the database check on `signatures.revoke_reason` (migration 001): a revoked row can never be edited, so it cannot hold free text or personal data, and any other value is `400`
- Role: the signature's document scope, per the `docs/security.md` matrix: org admin for an installation-scoped document, admin on the document's repository for a repo-scoped one (E11). No role in the tenant is `404`, a lower role is `403`. The signature is loaded with `where id = $1 and installation_id = $2`
- One transaction runs `update signatures set revoked_at = now(), revoked_by = <actor users.id>, revoke_reason = $reasonCode where id = $1 and installation_id = $2 and revoked_at is null` (only the three revocation columns, the only ones the runtime role may update) and appends audit `signature.revoked` with subject `signature`/id and metadata `{ document_id, version_id, major, user_github_id, reason_code }`, no name. Zero rows updated on an existing signature is `409 already_revoked`, with no second audit row and no change
- Un-revoking does not exist: no route, service function or SQL path clears `revoked_at`. A route-table test asserts there is no `PUT`, `PATCH` or `DELETE` on `/signatures/:signatureId`, and a raw `update` that clears `revoked_at` as the runtime role fails on the immutability trigger
- Prospective only, proven by tests: `pr_evaluations` rows of closed PRs and their stored `check_run_id` values are untouched; no Check Run is rewritten for a closed PR; the signature core columns are byte-identical before and after (compare `to_jsonb(signature) - revoked_*`)
- Re-evaluation, in the same transaction through a shared function `enqueueAffectedPrs`: it finds, via `latestEvaluationPerPr` (E15-S01), open PRs of repositories whose `cla_document_id` is the signature's document, whose latest result is `success` and whose recorded covering basis (E08 `pr_evaluations.details`) names this signature id or the signer's numeric id as covered by signature, and enqueues one `evaluate-pr` job each (keyed per repository and PR, E07). Above 100 matches it enqueues one `sweep-repository` job (E07-S09, reason `signature_revoked`) per affected repository instead. Response `200 { "signature": { "id", "state": "revoked", "revokedAt" }, "reevaluating": <jobs enqueued> }`
- Integration test with GitHub stubbed by MSW: signer's open PR is `success`; revoke; the job runs; the `license/cla` Check Run becomes `failure` and the comment lists the signer as unsigned (E09). The signer then signs again (E13-S04): a new row is created, the revoked row stays as it is, and the PR returns to `success`
- Failure injection: an enqueue failure rolls the revocation back (`500`, signature still active). Real-Postgres-only test: two simultaneous revokes of one signature give one `200` and one `409`, and exactly one audit row
- Cross-tenant tests: tenant 1's admin revoking tenant 2's signature id under tenant 2's path is `404`; under tenant 1's path with tenant 2's signature id is also `404`

**E15-S04 — Invalidate all signatures of a document major** ⬜ Todo
When a maintainer needs everyone to sign again without publishing a new major (for example a withdrawn clause), they can invalidate a major in one audited step.
Acceptance criteria:
- `GET /api/installations/:installationId/documents/:documentId/invalidation-preview?major=<n>` returns `{ "major", "activeSignatures", "affectedRepositories" }` (counts only, no personal data). `POST .../documents/:documentId/invalidations` takes `{ "major", "reasonCode", "expectedCount" }` with the reason-code rule of E15-S03. Role as in E15-S03, by the document's scope; the document is loaded with its installation id
- One transaction runs a single `update signatures set revoked_at = now(), revoked_by = <actor>, revoke_reason = $reasonCode where document_id = $1 and installation_id = $2 and major = $3 and revoked_at is null`. If the affected row count differs from `expectedCount` the transaction rolls back with `409 count_changed` and nothing is revoked. Zero rows is `409 nothing_to_invalidate`
- Exactly one audit row `signatures.invalidated` is appended: subject `document`/id, metadata `{ major, count, reason_code }`. Each signature's own `revoked_at`, `revoked_by` and `revoke_reason` carry the per-signature record; this decision avoids thousands of audit rows. The response is `200 { "invalidated": <count> }`
- Contributors are not deleted or notified: their next evaluation reports a missing signature for the document (E08) and they sign again through E13. No `cla_versions` row changes and no new version is created
- Re-evaluation: one `sweep-repository` job (E07-S09, reason `signatures_invalidated`) for every enabled repository whose `cla_document_id` is the document, keyed per repository, enqueued in the same transaction
- Real-Postgres-only tests: an invalidation racing with a revoke of one of the same signatures revokes every signature exactly once (the `revoked_at is null` predicate is re-evaluated after the row lock); a bulk invalidation of 1,000 signatures completes in one transaction
- Cross-tenant tests: a document id of tenant 2 under tenant 1's path is `404`; invalidating major 1 of tenant 1's document leaves the same-numbered major of tenant 2's document untouched
- Boundary tests: `major` 0 and a major that has no signatures are rejected (`400` and `409 nothing_to_invalidate`); `expectedCount` 0 is `400`

**E15-S05 — Record a per-commit override** ⬜ Todo
The documented escape hatch for the commonest real-world failure, a commit whose email is not linked to any GitHub account.
Acceptance criteria:
- `POST /api/repositories/:repositoryId/commit-overrides` with `{ "commitSha": string, "reason": string }`, behind session, CSRF and `Origin` checks. Role: the repository-action rule of E14-S01. `commitSha` is 40 or 64 hexadecimal characters, normalised to lowercase (the `commit_sha` check constraint); abbreviated SHAs are `422 invalid_commit_sha`. `reason` is 1 to 2,000 characters after trimming and is required
- The commit must exist in the repository: the server calls `GET /repos/{full_name}/commits/{sha}` with the installation token (5 second timeout) using the current `full_name` snapshot. `404` or `422` from GitHub is `422 commit_not_found`; rate limiting is `503 github_rate_limited`; any other failure is `502 github_unavailable`. A commit of another repository in the same tenant therefore cannot be pre-approved by mistake
- The insert stores `installation_id` and `repository_id` from the resolved repository, `commit_sha`, `reason`, `created_by` (the actor's `users.id`) and `created_at` from the database. A second override for the same (repository, SHA) is `409 override_exists`. Response `201 { "override": { id, repositoryId, commitSha, reason, createdBy: { githubId, login }, createdAt } }`
- An override never implies a signature: the test asserts that `signatures` and `signer_pii` are unchanged by the call, and that E08 still requires the PR opener and every other commit's author and committer to be covered. The override only waives the check for that commit's author and committer: E08 lists the commit in `details.unlinked` as `{ sha, role, overrideId }` (it is not a covering basis), and the E09 summary counts it as covered by maintainer override
- Audit `commit_override.created` in the same transaction: subject `commit_override`/id, metadata `{ repository_id, commit_sha }`. The reason text stays out of the audit row because it is free text
- Re-evaluation in the same transaction: the latest evaluation per PR of that repository with `result = 'failure'` and `pr_state = 'open'` is enqueued as `evaluate-pr` (E07 keys), at most 100, else one `sweep-repository` job (E07-S09, reason `override_changed`). Integration test with MSW: a PR failing on an unlinked author email (`author: null`) turns `success` after the override when the opener is covered, and stays `failure` when the opener is not
- A disabled repository or a suspended installation accepts no new override (`409 repository_disabled`, `409 installation_suspended`)
- Cross-tenant tests: tenant 2's repository id is `404`; the same SHA can carry an override in both tenants' repositories independently; a tenant 1 override never changes tenant 2's evaluation of an identical SHA

**E15-S06 — List and remove overrides** ⬜ Todo
Overrides stay visible, and a maintainer can withdraw one that was a mistake.
Acceptance criteria:
- `GET /api/repositories/:repositoryId/commit-overrides?limit=&cursor=` (limit 1 to 100, default 50, order `created_at desc, id desc`, keyset cursor) returns items `{ id, commitSha, reason, createdBy: { githubId, login }, createdAt }` for that repository, with the same role as E15-S05. `login` is the `users` snapshot; strings are returned verbatim
- `DELETE /api/repositories/:repositoryId/commit-overrides/:overrideId` returns `204`. It deletes with `where id = $1 and repository_id = $2 and installation_id = $3` (the runtime role holds `DELETE` on `commit_overrides`); an unknown, foreign or already deleted id is `404`
- The history of a removed override is the audit row `commit_override.deleted` (subject `commit_override`/id, metadata `{ repository_id, commit_sha }`) together with the earlier `commit_override.created` row, written in the same transaction as the delete
- Removing an override can turn a green check red, so the same transaction enqueues the re-evaluation of E15-S05, selecting open PRs whose latest result is `success` and whose `details.unlinked` (E08) lists this commit SHA with an `overrideId`; it enqueues `evaluate-pr` jobs, or above 100 matches one `sweep-repository` job (E07-S09, reason `override_changed`). Failure injection: an enqueue failure rolls the delete back
- After a delete the same SHA can be overridden again (new row, new audit row); the unique key (`repository_id`, `commit_sha`) is not blocked by history
- Cross-tenant tests: deleting tenant 2's override id under tenant 1's repository is `404` and leaves the row; tenant 1's list never contains tenant 2's rows, even for an identical SHA
- Hostile-text test: a `reason` containing markup, a formula prefix and a newline is returned unchanged by the list endpoint and absent from `audit_log.metadata`

**E15-S07 — Pending PRs view** ⬜ Todo
One list of the open pull requests that are blocked by `license/cla`, with the reason and who must act.
Acceptance criteria:
- `GET /api/installations/:installationId/pending-prs?repositoryId=&reason=&limit=&cursor=` with a session. It returns the latest evaluation per (repository, PR) from `latestEvaluationPerPr` where `result = 'failure'` and `pr_state = 'open'`, only for enabled repositories of a non-suspended installation. Order `updated_at desc, id desc`, limit 1 to 100 (default 50), opaque keyset cursor
- Item: `{ evaluationId, repository: { id, fullName }, prNumber, headSha, evaluatedAt, checkRunId, reasons: [{ code, githubId, login, commitSha }] }`, derived from `PrEvaluationDetails` (E08-S01) by one pure function. `code` is one of `no_active_cla`, `unsigned_contributor` (one reason per uncovered human actor, with `githubId`; an outdated or revoked signature is also `unsigned_contributor`, because E08 does not tell them apart), `bot_not_allowlisted` (an uncovered bot actor, with `githubId`), `unlinked_identity` (one reason per `details.unlinked` entry that has no `overrideId`, with `commitSha`, which is what the override form of E15-S05 needs) and `commit_limit_exceeded`; the dead-letter code `evaluation_failed` (E07-S05) and any unknown code are returned as `other`. `githubId` and `commitSha` are present only where they apply. `login` is the `users` display snapshot of `githubId` when such a row exists (an erased user shows `erased-<id>`), otherwise `null`: the stored details hold no login, and a contributor who never logged in has no `users` row. It is returned verbatim
- `reason` filters on `code`; `repositoryId` filters to one repository of the installation (a repository of another tenant is `404`)
- Role: an org admin sees every enabled repository of the installation. A viewer who is only repo admin sees the repositories with a repo-scoped document that E11 confirms; permission is checked only for repositories that actually have pending rows, at most 50 per request, with `truncated: true` in the body when more were skipped
- `in_progress` rows are not listed. A job that dies ends in `failure` through the dead-letter handler (E07); if its `details` hold no recognised reason, the item is listed with `reasons: [{ "code": "other" }]` rather than being hidden
- Every query filters by the path's installation id. Cross-tenant tests: tenant 2's failing PRs never appear for tenant 1's admin, including a PR with the same number and head SHA; an admin of both tenants sees each tenant only under its own path
- Boundary tests: a PR whose latest row is `success` is absent even if an older head SHA row is `failure`; a closed PR (E15-S01) is absent; a disabled repository's PRs are absent; an unsigned contributor with no `users` row is listed with `login: null`; pagination with 120 rows and equal `updated_at` has no duplicate and no gap
- The list performs no GitHub call and no write
