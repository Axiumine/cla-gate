# E12 — CLA documents and versions

**Bounded Context:** BC-03
**Priority:** 🔴 Must have
**Status:** ⏳ In progress

**Goal:** Maintainers bring their own CLA text (no legal text ships) and publish it as immutable, hashed versions per document. A document belongs to one tenant, either to the whole installation or to a single repository, and always points at its active version; a rollback publishes a new version, a major bump forces re-signing and a minor bump does not.
**Depends on:** E04, E11
**Out of scope:** Attaching a document to a repository and enabling enforcement (E14-S02, E14-S03). Signing and the sign page (E13; it reads the active version this epic publishes). Coverage rules that compare a signature's major with the active major (E08). Revocation and invalidation (E15). CSV export (E16-S03). The audit writer itself (E04-S09; this epic only adds action names and calls it). Corporate documents (E21 widens the `kind` the schema already carries). The editor, history and diff screens (E18). Fan-out re-evaluation logic of the sweep job (E07, E14).

**E12-S01 — Create, list, read and rename documents** ✅ Done
A document is a named CLA container for one tenant. No text is created here and none ships with the product.
Acceptance criteria:
- `POST /api/installations/:installationId/documents` with a strict body `{ "name": string, "kind": "individual" | "corporate", "repositoryId"?: number }`. Without `repositoryId` the document is installation-scoped (requirement `org_admin`); with it, repo-scoped (`cla_documents.repository_id` set, requirement `repo_admin` on that repository; an org admin also passes). The route uses the E11-S05 guard in `write` mode with a resolver that reads the validated body. A repository that is not in the path's installation, or is removed, resolves to the uniform `404`.
- The schema in `src/shared/cla.ts` accepts both kinds (E21 relies on it); the service answers `kind: 'corporate'` with `422 kind_not_supported` while the constant `CORPORATE_KIND_ENABLED` is `false` (E21 flips it). Responses use the E10-S03 `AppError` codes named in each criterion.
- `name` is NFC-normalised, trimmed, whitespace runs collapsed, 1 to 100 code points; control characters and bidi overrides give `422 invalid_name`. Anything else printable is stored verbatim (hostile names from `HOSTILE_NAMES`, E09-S01, are accepted and returned unchanged; escaping is each output's job). A duplicate in the same scope is `409 document_name_taken`, decided by the existing `unique nulls not distinct (installation_id, repository_id, name)` constraint so two simultaneous creates also yield one `409`. The same name is allowed in two tenants.
- At most 100 documents per installation, else `422 document_limit_reached`.
- `201 { "document": { id, name, kind, scope: "installation" | "repository", repositoryId, activeVersion: null, createdAt, updatedAt } }`. In the same transaction the audit row `cla_document.created` is appended through the E04-S09 writer (metadata `{ document_id, repository_id, kind }`, no name). The action name is added to `AUDIT_ACTIONS` in this change and the route declares `config.audit`.
- `GET /api/installations/:installationId/documents?limit=<1..100>&cursor=<opaque>` (org admin) lists every document of the installation, order `name asc, id asc`. `GET /api/installations/:installationId/repositories/:repositoryId/documents` (repo admin) returns `{ repositoryScoped: [...], installationScoped: [...] }`; installation-scoped entries carry only `id`, `name` and `activeVersion` labels, never text.
- `GET .../documents/:documentId` returns the document with `activeVersion: { id, major, minor, contentSha256, publishedAt } | null` and `hasDraft`. `PATCH .../documents/:documentId` with `{ "name" }` renames under the same validation and audits `cla_document.renamed` (`{ document_id }`). Both resolve the requirement from the document's scope (`docs/security.md` matrix) and look the document up by `id` and `installation_id`.
- A fresh database holds no legal text: after `migrate`, `cla_documents`, `cla_versions` and the draft table have 0 rows (test), and the repository contains no CLA wording as a seed, fixture outside tests, or default asset.
- Cross-tenant tests (mandatory): tenant 2's document id under tenant 1's path is `404`, tenant 2's repository id in the body is `404`, a repo admin gets `403` creating an installation-scoped document, and a suspended tenant gets `409 installation_suspended` (E11-S05).

**E12-S02 — Canonical text and content validation** ✅ Done
The stored text is the text that is hashed and shown, so it is canonicalised once, in one place.
Acceptance criteria:
- `canonicalise(md)` in `src/shared/cla-text.ts` removes a leading BOM, converts CRLF and lone CR to LF and ensures exactly one trailing LF. Nothing else changes: no trimming of inner lines (trailing double spaces are Markdown line breaks), no Unicode normalisation. It is idempotent and shared by server and web, so the editor and the server agree.
- `validateClaText(md)` runs on the canonical text: more than 204 800 UTF-8 bytes is `422 content_too_large` with `details: { limitBytes, actualBytes }`; no non-whitespace character is `422 content_empty`; a NUL or another C0 control character other than LF and TAB, or a lone surrogate, is `422 content_invalid_characters`. Errors never echo the content.
- `sha256Hex(canonicalText)` on the server uses `node:crypto` over the UTF-8 bytes and must equal the database check `content_sha256 = encode(sha256(convert_to(content_md, 'UTF8')), 'hex')`; a test inserts texts with emoji, CJK and combining marks and lets the database verify the hash.
- The CLA routes of this epic accept `application/json` only and set a route `bodyLimit` of 512 KiB so JSON-escaped text of the maximum size fits; larger bodies get the E04 `413`. Uploading a `.md` file is done by the browser (E18), which reads it and sends `contentMd`.
- Boundary tests: exactly 204 800 bytes accepted, 204 801 refused, a multi-byte character straddling the limit, CRLF and LF input giving one hash, a BOM, whitespace only, NUL, a lone surrogate, text already ending in several newlines (collapsed to one).
- Property test (a seeded random generator, seed printed on failure): `canonicalise(canonicalise(x)) === canonicalise(x)` and the hash of the canonical text is stable across 1 000 inputs.

**E12-S03 — Drafts with optimistic concurrency** ⏳ In progress
Published versions are immutable, so work in progress lives in a separate, mutable table.
Acceptance criteria:
- A forward-only migration (next free number) creates `cla_drafts (document_id bigint primary key, installation_id bigint not null, content_md text not null, revision integer not null default 1 check (revision >= 1), updated_by bigint not null references users (id) on delete restrict, updated_at timestamptz not null default now())` with the composite foreign key `(document_id, installation_id)` to `cla_documents (id, installation_id)` on delete restrict. Grants to `cla_app` (select, insert, update, delete) are made only when the role exists. `schema.ts` with its catalog test and the `docs/data-model.md` table are updated in the same change. The immutability triggers of 001 are untouched.
- `GET .../documents/:documentId/draft` returns `200 { "draft": { contentMd, revision, updatedAt } | null }`.
- `PUT .../documents/:documentId/draft` with `{ "contentMd": string, "expectedRevision": number | null }` validates the text (E12-S02). `expectedRevision: null` means "no draft exists yet". A mismatch is `409 draft_conflict` with `details: { currentRevision }`. Success is `200 { "draft": { revision, updatedAt } }` with `revision` incremented, written in one statement guarded by `where revision = $expected`.
- `DELETE .../documents/:documentId/draft` returns `204`, also when no draft exists (then without an audit row).
- The editor saves only on an explicit action (no autosave); each save appends audit `cla_draft.saved` (`{ document_id, revision }`) and each discard `cla_draft.discarded`, both added to `AUDIT_ACTIONS` here, and the routes declare `config.audit`. Rate limit: 30 saves per minute per user, keyed on the user id.
- One draft per document, shared by every admin of its scope; the role follows the document's scope. A draft never changes `active_version_id` and is never returned by any contributor-facing route (test: E13's sign context for a repository with a draft contains no draft text).
- Real-Postgres-only test: two simultaneous `PUT`s with the same `expectedRevision` give exactly one `200` and one `409`. Sequential PGlite tests cover the same outcome.
- Cross-tenant tests: tenant 2's admin gets `404` on tenant 1's draft routes; the composite foreign key refuses a raw insert pairing tenant 1's document with tenant 2's installation id.
- Open: the clause "(test: E13's sign context for a repository with a draft contains no draft text)" of the sixth criterion cannot be shown yet, because the sign context is not built (E13). What it protects holds today and is tested for every route that exists: `document-draft-surface.test.ts` sweeps every `GET` of the application (the ids of a document that has a draft filled in; a parameter the sweep does not know fails it) and the create and rename answers for the text of two drafts, checks that the audit rows and the log lines hold none of it, and pins the files that may name `cla_drafts` and read a draft (the statements, the draft service, the draft routes), so a contributor-facing route added later cannot read one without that list changing in the open. Still to do when E13 builds the sign context: add its own case (a repository whose document has a draft; the answer holds none of the draft's text) next to the route, then mark this story done.

**E12-S04 — Publish a version** ✅ Done
The single mutation that creates `cla_versions` rows and moves the active pointer.
Acceptance criteria:
- `POST .../documents/:documentId/versions` with a strict body `{ "source": { "type": "draft", "revision": number }, "bump": "major" | "minor", "rationale": string, "expectedActiveVersionId": number | null, "acknowledgeResigning"?: boolean }`. `rationale` is trimmed, 1 to 2000 characters, stored in `cla_versions.rationale` and never copied into audit metadata. The source is the saved draft; a draft revision that does not match is `409 draft_conflict`. E12-S06 adds the second source type.
- One transaction: `select ... from cla_documents where id = $1 and installation_id = $2 for update`; `expectedActiveVersionId` must equal `active_version_id` (null for the first version), else `409 stale_active_version` with `details: { activeVersionId }`; the next number is computed under the lock; the version is inserted with the canonical text, its SHA-256 and `published_by` = the session user's internal id; `active_version_id` and `updated_at` are set; the draft row is deleted (when the source is the draft; a rollback, E12-S06, leaves it); audit `cla_version.published` is appended. Any failure rolls all of it back.
- Numbering: the first version must use `bump: 'major'` and is `1.0` (`422 first_version_must_be_major` otherwise); `major` gives `(active.major + 1).0`; `minor` gives `active.major.(active.minor + 1)`. The active version is always the latest, so the unique constraint `(document_id, major, minor)` is the backstop: a violation that slips past the lock is mapped to `409 version_conflict`.
- A `minor` bump whose canonical text equals the active text is `422 content_unchanged`. A `major` bump with identical text is allowed on purpose (it forces re-signing without a wording change).
- Re-signing guard: for a `major` bump over an existing version the response first counts non-revoked signatures at the previous major (`affectedSignatures`). When the count is above 0 and `acknowledgeResigning` is not `true`, nothing is written and the answer is `409 resign_confirmation_required` with `details: { affectedSignatures }`.
- `201 { "version": { id, major, minor, contentSha256, publishedAt }, "requiresResigning": boolean, "affectedSignatures": number }`, where `requiresResigning` is true for a major bump over an existing version. Audit metadata `{ document_id, version_id, major, minor, bump, affected_signatures }`; the action is added to `AUDIT_ACTIONS` and the route declares `config.audit`.
- A minor publish writes no signature row and changes none: a test counts and checksums `signatures` before and after, and shows the coverage rule's input (the active major) is unchanged. A major publish changes the active major and nothing else in `signatures` (revocation is E15's).
- Enqueue in the same transaction through the `JobEnqueuer` port (E06-S06): for a major bump, the `sweep-repository` job (E07-S09) with reason `cla_version_published`, once per enabled repository attached to the document, keyed per repository; a minor bump enqueues nothing. A throwing enqueuer rolls the publish back (`500`, no version row, no audit row, pointer unchanged). Production wiring needs the E07 adapter; tests use the fake.
- Real-Postgres-only test: 5 simultaneous publishes with the same `expectedActiveVersionId` give exactly one `201` and four `409 stale_active_version`, with no gap or duplicate in the numbering. A runtime-role test (`asRuntimeRole`) shows `cla_app` issues only `select` and `insert` on `cla_versions`; a direct `update` or `delete` stays refused by the E04 triggers.
- Note: E07-S09 has landed, so the send is its `enqueueSweepRepository` (`services/repository-job-enqueue.ts`), called once per enabled attached repository with the reason `cla_version_published` and the key `sweep-repository:cla_version_published:<versionId>:<githubRepoId>`. E07-S09 coalesces per repository: while a sweep of the repository waits for a worker a second major sends nothing, because that run reads the newer policy when it starts; once the run has started a new one is queued (both are tests). The job schema and the set of reasons are E07-S09's (`domain/repository-jobs.ts`, `domain/job-envelope.ts`); this epic adds no member to the job catalogue. The app sends through the enqueuer of its job queue when the process has one; without a queue (tests) it is `notWiredEnqueuer`, so a major publish over an enabled attached repository answers `500` there and a document with no such repository publishes normally.

**E12-S05 — Version history and exact text** ✅ Done
Acceptance criteria:
- `GET .../documents/:documentId/versions?limit=<1..100>&cursor=<opaque>` lists versions by `major desc, minor desc`: `{ id, major, minor, contentSha256, publishedBy: { githubId, login }, rationale, publishedAt, active, signatureCount }`. `login` comes from the `users` snapshot (an erased user shows `erased-<id>`); `signatureCount` is the number of non-revoked signatures on that exact version id. The cursor is a zod-validated opaque value; a tampered one is `400`.
- `GET .../documents/:documentId/versions/:versionId` returns the same fields plus `contentMd`, the canonical stored text, with `Cache-Control: no-store`. The query is `where v.id = $1 and v.document_id = $2 and d.installation_id = $3`; a version of another document or tenant is the uniform `404`.
- Integrity on read: the server recomputes the SHA-256 of `contentMd` and compares it with `contentSha256`; a mismatch answers `500` with the E04 body and logs `cla_version_integrity_failed` with ids only. The database check makes this unreachable in normal operation, so the test injects a tampered row through a repository double.
- Strings (`rationale`, logins) are returned verbatim; escaping is the screen's job (E18). A hostile rationale from `HOSTILE_NAMES` round-trips unchanged.
- Role follows the document's scope (`docs/security.md` matrix); reads use the cached role (E11-S04). No route accepts `PUT`, `PATCH` or `DELETE` on a version: a route-table test asserts the version path has `GET` and `POST` (publish) only, so immutability is not a convention.
- Cross-tenant tests: a version id of tenant 2 requested under tenant 1's document is `404`; the listing for tenant 1 never contains tenant 2's versions even when both have version `1.0` with identical text and hash.

**E12-S06 — Roll back by publishing a copy** ✅ Done
A rollback never reactivates an old row; it publishes a new version with the old text.
Acceptance criteria:
- The publish body of E12-S04 accepts a second source `{ "type": "version", "versionId": number }`. The source version must belong to the same document and installation, else the uniform `404`. The new row's `content_md` and `content_sha256` equal the source's, byte for byte; the source row is not touched.
- `active_version_id` always points at the new row: with history `1.0`, `1.1`, `2.0`, a rollback to `1.1` with `major` creates `3.0`, whose hash equals that of `1.1`, and `1.1` stays inactive. A test asserts the pointer, both hashes and that no row of `cla_versions` was updated.
- Bump rule: `minor` is allowed only when the source's major equals the active major (reverting an edit inside the same major line, so current signers stay covered); a source from another major with `minor` is `422 rollback_requires_major`, because it changes the legal terms of people who signed the current major. A rollback to the text already active with `minor` is `422 content_unchanged`.
- `rationale` is required as in E12-S04, the same locking, `expectedActiveVersionId`, re-signing confirmation (`resign_confirmation_required`) and enqueue rules apply (one shared transaction function, not a copy).
- Audit `cla_version.published` carries the extra metadata key `rolled_back_from_version_id` (an integer), and nothing else changes in the action set.
- Tests: the history above, a rollback to the active version with `major` (allowed, forces re-signing), a rollback across majors with `minor` (refused), a rollback source from tenant 2's document (`404`), and an `affectedSignatures` count that excludes revoked signatures.
- Note: the rollback is the `source.type = 'version'` branch of `publishWithin` (`cla-publish-source.ts` reads the text, `cla-publish-checks.ts` decides). The source is read with `findVersion` (E12-S05), the text and the hash are copied as stored, and the database check on `content_sha256` is the integrity guard of the copy. Two interpretations the story leaves open: a rollback leaves the saved draft alone (only the publish made from the draft consumes it), and a `minor` rollback across majors is `rollback_requires_major` even when the two texts happen to be equal (the major is decided before the text).

**E12-S07 — Sanitised Markdown rendering** ✅ Done
What signers and maintainers see is rendered from the stored source text through one HTML-sanitising pipeline; the hash stays over the source.
Acceptance criteria:
- New dependencies, each justified in the PR (hard rule 8), MIT-licensed and pinned after `yarn npm info`: `unified`, `remark-parse`, `remark-rehype`, `rehype-sanitize` and `hast-util-to-html`. No `rehype-raw` and no GFM plugin: CommonMark only. Knip stays clean in both modes.
- `src/shared/cla-markdown.ts` exports `renderClaTree(md)`, a sanitised hast tree, and `renderClaHtml(md)`, the same tree serialised, for non-React consumers such as the E21 endpoint. The web renders the tree into React elements (E18) so `dangerouslySetInnerHTML`, which Biome forbids, is never needed.
- Raw HTML in the source is converted to literal text before the tree is built, so a placeholder such as `<company name>` stays visible to the signer; it is neither dropped nor interpreted.
- Allowed elements: `p`, `h1` to `h6`, `ul`, `ol`, `li`, `blockquote`, `pre`, `code`, `em`, `strong`, `br`, `hr`, `a`. Allowed properties: `href` on `a`, `start` on `ol`. An `href` must use `http:`, `https:` or `mailto:`; any other link is unwrapped to its text. Every anchor gets `rel="noopener noreferrer nofollow"` and `target="_blank"`. Images are never rendered; the alt text remains as plain text.
- Hostile-input table, at least 20 rows, each walking the output tree: `<script>`, `<img src=x onerror=alert(1)>`, `<iframe>`, `<style>`, HTML comments, `[x](javascript:alert(1))`, mixed-case `JaVaScRiPt:`, `java\tscript:`, entity-encoded `&#106;avascript:`, `data:text/html,...`, `vbscript:`, protocol-relative `//evil.example`, `![](http://t.example/p.png)`, `<svg><p><style><a title="</style><img src onerror=alert(1)>">`, autolink `<javascript:alert(1)>`, reference-style links, raw `<a href="javascript:x">`. Assertions: only allowed tag names and properties, no `on*` property, every `href` protocol allowed, no `img`, `script`, `style` or `iframe` node.
- `validateClaText` (E12-S02) gains a depth rule: block quote and list nesting above 50 levels is `422 content_too_deeply_nested`, measured with the same parser. Tests: depth 50 renders, depth 51 is refused, a 100 KiB run of `[` and a 100 KiB run of `*` render without stack overflow.
- The editor preview, the sign page and the history view use the same function on the same canonical text: a test renders the draft text and the later published text of equal bytes and expects identical trees.
- `toMatchFileSnapshot` stores the sanitised HTML of a representative multi-section document (headings, lists, a link, a code block) in `src/shared/snapshots/cla-markdown/`.
- Note: `src/shared/cla-markdown.ts` is the one pipeline (`cla-markdown-parse.ts` holds the two remark-parse setups, `cla-markdown-nesting.ts` the depth rule and its limits). Interpretations the story leaves open: raw HTML is made literal text by switching off the parser's `htmlFlow` and `htmlText` constructs, so a placeholder, a comment and a tag are all shown as written (a comment is not hidden from the signer); a link is kept only when its address starts with lower-case `http://`, `https://` or `mailto:`, so a relative, protocol-relative, fragment or capitalised-scheme link is its text; `rel` is the list `['noopener', 'noreferrer', 'nofollow']`; the language class of a fenced block is dropped (only `href`, `rel`, `target` and `start` remain). The depth rule is measured by a line scan of the containers (`cla-markdown-containers.ts` with `cla-markdown-lines.ts`), not by the parser, and the parser is not called anywhere on a request: `validateClaText` runs on the one thread that serves every tenant, and the parser is not linear. Measured with node 26: 20 KiB of one-line setext headings (`a`, `=`) take about 1 s of CPU, 40 KiB about 4.5 s, and 200 KiB more than 100 s (the time grows with the square of the number of lines, because micromark scans the whole event list for every underline); lazy quote lines (`> a`, `b`) and runs of `[a]` behave alike with smaller factors. The scan follows the CommonMark rules for quotes, list items (marker, content indent, empty items, the rule that an item interrupting a paragraph is numbered 1 and not empty), lazy lines and fences, in time linear in the size of the text; `cla-text-budget.test.ts` validates 200 KiB of each of those texts in under two seconds, and the tests let the scan and the parser agree on a corpus and on 3 000 seeded generated texts. They differ in odd corners (about one generated text in 30 000: an empty marker after indented code, a reference definition followed by an `=` line), by one level; the rendering measures the tree it parsed as well, so such a text cannot overflow the stack. A line that opens more than 100 container markers is still refused before the rendering parses (a run of 100 000 `>` takes about 20 seconds to parse). In the rendering, a text that nests above 50 levels of quote or list, or of emphasis, strong text or link, is returned as one `pre > code` block with its own words, so an unvalidated preview cannot overflow the stack. Residual cost: `renderClaTree` still uses the parser, so the adversarial 200 KiB texts above, which validation accepts, take from seconds to minutes to render. Nothing in this epic renders on a request; E21 must render in a worker thread with a time limit, once per content hash, and keep the result (whether to also refuse such texts at publish is for the maintainer). `src/shared/snapshots` is outside Biome (generated output).
