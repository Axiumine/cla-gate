# E14 — Repository enablement and allowlist

**Bounded Context:** BC-06
**Priority:** 🔴 Must have
**Status:** ✅ Done

**Goal:** Maintainers choose which repositories of their org enforce the CLA, attach the CLA document that applies, and exempt trusted accounts (named users, bots, org members) by numeric GitHub id. Every setting is scoped to one tenant (GitHub App installation), so one instance serving several orgs keeps their choices and exemptions apart.
**Depends on:** E11, E12
**Out of scope:** Creating and publishing CLA documents and versions (E12). Computing and caching roles (E11; this epic only calls its checks). Creating `installations` and `repositories` rows from `installation` and `installation_repositories` events (E05, E06). Matching allowlist entries against PR authors and committers (E08 domain code). The sweep, `evaluate-pr` and Check Run writers themselves (E07, E08, E09). Signature revocation and per-commit overrides (E15). The audit writer and viewer (E16). Screens (E18). Corporate documents and approvals (E21).

**E14-S01 — List administered installations and repositories** ✅ Done
A maintainer sees the orgs and repositories they can administer on this instance, and nothing else.
Acceptance criteria:
- `GET /api/installations` (session required) returns `[{ id, accountLogin, accountType, role, suspended, repositoryCount, enabledCount, truncated }]`, where `id` is `installations.id` (E11-S05). `role` is `org_admin` when E11 reports org admin (membership role `admin` for an `Organization` installation; the account owner, `account_id` equal to the viewer's GitHub id, for a `User` installation). Installations the instance admission policy has not admitted are never listed; suspended ones are listed with `suspended: true`
- A viewer who is not an org admin gets `role: 'repo_admin'` for an installation only when E11 reports admin permission on at least one repository of it that carries a repo-scoped CLA document. At most 100 such repositories are checked per request across all installations; when more exist, `truncated` is `true` and the unchecked ones are left out. Decision: repo-level admins are discovered only through repo-scoped documents, because probing every repository of every tenant per page load does not scale
- `GET /api/installations/:installationId/repositories?limit=<1..100>&cursor=<opaque>&q=<text>&enabled=<true|false>` returns `{ items, nextCursor }`, each item `{ id, githubRepoId, fullName, enabled, canAdminister, document }`, where `document` is `null` or `{ id, name, scope: 'installation' | 'repository', activeVersion: { major, minor } | null }`. An org admin sees every repository of the installation; a `repo_admin` sees only the repositories E11 confirms. Default `limit` is 50, order is `full_name asc, id asc`, the cursor is validated by zod
- The repository-action rule, defined once as a pure function `requiredRoleForRepository(repository, document)` and reused by E14-S02 to E14-S07 and by E15: the role is **org admin** when the repository's attached document is installation-scoped or none is attached, and **admin on that repository** when the attached document is repo-scoped (`docs/security.md` role matrix). An org admin satisfies it always. `canAdminister` is that rule applied to the viewer; table tests cover the three document states and both roles
- `q` is a case-insensitive substring match on `full_name`; `%`, `_` and `\` in `q` are escaped, so `q=%` returns only repositories whose name contains a literal percent sign (test)
- Every query filters by the path's installation id. A viewer with no role in an installation, or an unknown id, gets `404 not_found` with an identical body; a viewer with a role that is too low for the call gets `403 forbidden` (E11 denial convention)
- Cross-tenant tests: a viewer who is org admin of tenant 1 and a plain contributor of tenant 2 sees only tenant 1 in the installation list, receives `404` for tenant 2's repositories, and no page of tenant 1's listing ever contains a tenant 2 row, even with `q` matching a tenant 2 name
- When E11 cannot determine a role because GitHub fails or rate-limits, the endpoints answer `502 github_unavailable` (or `503 github_rate_limited` with `retry-after`) instead of an empty list, which would read as "you administer nothing". Only E11 role lookups call GitHub here; listing rows is database-only
- Built as: the two routes are in `src/server/adapters/http/installation-routes.ts` and `repository-list-routes.ts`, their paths, query and answers in `src/shared/installations.ts`. The repository-action rule is `requiredRoleForRepository` and `satisfiesRole` in `src/server/domain/repository-action.ts`; `canAdminister` is `satisfiesRole(role, requiredRoleForRepository(repository, document))`, and a repo-scoped document that names a different repository is not trusted (the rule falls back to org admin). `GET /api/installations` is an `authenticated` route: `findRoles` (`installation-roles.ts`) reads the org admin fact of every admitted, not uninstalled installation through `tenantFacts`, the guard's own facts (cached lookup for a live tenant, stored row and ledger for a suspended one), five at a time, then searches repository admins installation by installation in login order with one `ProbeBudget(100)` shared by the request; a suspended installation is listed for its org admins only and never searched. `truncated` is a property of the request and is repeated on every row. An installation GitHub stops serving under the lookup is left out. A deleted installation is not listed, because it has nothing left to enforce, though a ledger admin may still read it through the guard. The repository list is a `tenant` route with the new requirement `any_role` in `decide` (`authz.ts`): an org admin, a discovered repo admin and anyone the guard finds to hold a role pass, everyone else is the uniform `404`; its discovery gets the 50-probe budget of the repository list. An org admin's page is one query (`repository-list-queries.ts`, every statement names the installation id, `(full_name, id) >= cursor` with an opaque zod-validated cursor in `repository-cursor.ts`, `ilike ... escape` over an escaped `q`); a repo admin's page takes the repositories that carry a repo-scoped document, asks the cached lookup about at most `min(limit, 50)` of them five at a time (`map-concurrently.ts`) and keeps the confirmed ones, so a page may hold fewer than `limit` rows and still have a `nextCursor`; a failing lookup fails the page. No role of the lists is "too low": any role passes, so the `403` of the denial convention is not reachable on these two routes (the guard's `403` is covered by the E11 tests and the matrix), and the cross-tenant matrix has a new endpoint class `installation_role_read` and an isolation case for `GET /api/installations`. The repository list spends the guard's 30 uncached lookups a minute per person, and a person who needs more than that gets `429 too_many_requests` there. The installation list does not: it asks every live installation once per cache lifetime, and the answers it pays for expire (60 s) as fast as the minute lets it pay again, so a budget of 30 would have refused it for good on an instance of 31 organisations. It spends a budget of its own, `INSTALLATION_LIST_LOOKUPS` (300 a minute per person, `role-lookup-budget.ts`) over the same role cache, for the org admin facts and for the search of repository admins (`TenantAuthorizationDeps.lookups.list` and `discoverForList`, a `LookupPurpose` of `list`), and a person who has used even that gets what was found with `truncated: true` and not an error. The wiring of the probe budgets is asserted at route level (`installation-list-budgets.test.ts`, `installation-list-many.test.ts`): 100 probes at most across installations with `truncated: true` on every row and the installation past them left out, 50 for the repository list's discovery (a repository admin whose repository is the eleventh candidate gets in; the guard's own search for a role elsewhere asks 10), and a list that is answered, and answered again a minute later, on an instance of 41 live organisations.

**E14-S02 — Attach and detach a CLA document** ✅ Done
A repository enforces one CLA document; this story chooses which.
Acceptance criteria:
- `PUT /api/repositories/:repositoryId/cla-document` with body `{ "documentId": <number> | null }` (`null` detaches). Behind session, CSRF and `Origin` checks (E10)
- Roles: attaching or detaching an installation-scoped document (`cla_documents.repository_id is null`) needs org admin; a repo-scoped document needs admin on that repository (E11). Detaching follows the role of the currently attached document. Org admins satisfy both. No role is `404`, a lower role is `403`
- A document can be attached only when it belongs to the repository's installation, is `kind = 'individual'` (corporate documents arrive with E21), and, if repo-scoped, belongs to this very repository. Unknown ids, documents of another tenant, another repository's repo-scoped document and corporate documents all return the same `422 document_not_attachable`, so the response reveals nothing about other tenants. A same-tenant document without `active_version_id` is `409 document_unpublished`
- The database composite foreign key `(cla_document_id, installation_id)` is the second line of defence; a test inserts a foreign-tenant document id with raw SQL and expects a foreign key violation
- Re-attaching the document that is already attached returns `200` with `changed: false`, and writes no audit row and enqueues no job. A real change returns `200` with `changed: true`
- A change in one transaction updates `repositories.cla_document_id`, appends audit `repository.cla_document_attached` with metadata `{ repository_id, document_id, previous_document_id }` (E04-S09 writer), and, if the repository is enabled, enqueues the `sweep-repository` job (E07-S09) with reason `cla_document_changed`. Signatures made under the previous document stop covering the repository because coverage requires the same document (E08)
- Detaching while `enabled = true` is `409 repository_enabled` (disable first, E14-S04). A successful detach appends `repository.cla_document_detached`
- A suspended installation rejects the call with `409 installation_suspended`. Cross-tenant tests: the viewer's repository id combined with the other tenant's document id is `document_not_attachable`; the other tenant's repository id is `404`
- Built as: the route is `repositoryDocumentRoutes` in `src/server/adapters/http/repository-document-routes.ts` (path and zod schemas in `src/shared/repository-document.ts`), a `tenant` route in `write` mode resolved by `byRepositoryParam`, so the guard lets in a repo admin or an org admin and the precise role is checked by the service. The service `changeRepositoryDocument` (`repository-document-attach.ts`) runs one transaction that takes `select ... for update` on the repository row (`repository-document-lock-queries.ts`), reads the attached document in a second statement (a locking read returns the newest version of the locked row only, so a joined document would be stale for the second of two simultaneous changes), finds the document to attach (`repository-document-queries.ts`: same installation, `kind = 'individual'`, installation-wide or this repository), judges the role with the pure `requiredRoleForDocumentChange` (`domain/repository-document-change.ts`) and only then reports `document_unpublished` or `repository_enabled`, so the role decides what a person learns. The role needed is the scope of the document attached after the change, and when a document is replaced also the scope of the one it leaves: an admin of one repository can attach or detach its own document, but cannot swap out the organisation's document, and detaching with nothing attached is org admin only (the policy then is the organisation's). A role too low under the lock is `403 forbidden` (the new rule `forbidden` of `ClaRuleError`); `document_not_attachable` is `422`, `document_unpublished` and `repository_enabled` are `409`. `changed: false` writes nothing, audits nothing and enqueues nothing. A change touches `updated_at`, appends the audit row (`document_id` is `null` on a detach) and, for an enabled repository on an attach, sends one `sweep-repository` job with reason `cla_document_changed` under the key `sweep-repository:cla_document_changed:<githubRepoId>:<updated_at in ms>`, in the transaction, so a throwing queue rolls the change back; sweeps are coalesced per repository, so two changes while the first sweep waits send one job. A detach sends none (enforcement is off by then). Tests include the raw-SQL foreign key violation (`23503`), the cross-tenant matrix case for the route (with `crossable: false`, because the path carries no installation id) and two real-Postgres lock-order tests (`repository-document-race.test.ts`).

**E14-S03 — Enable a repository** ✅ Done
Turning enforcement on is explicit, and it immediately evaluates the pull requests that are already open.
Acceptance criteria:
- `POST /api/repositories/:repositoryId/enable` with an empty body. Role: the repository-action rule of E14-S01 (the policy is the attached document's scope). The repository is resolved first and the viewer is then authorised against its installation; every following query filters by that installation id
- Preconditions: installation not suspended (`409 installation_suspended`); `cla_document_id` set and the document's `active_version_id` not null (`409 no_active_cla`, with a message naming the fix: attach and publish a CLA first)
- The state change is E05-S06 `setRepositoryEnabled(installationId, githubRepoId, true, actor)`, conditional on `enabled = false`, so concurrent calls change it once; this story adds no update and no audit insert of its own. When it reports `changed: false` the call is `200 { "enabled": true, "changed": false }` and enqueues no job
- On a real change, in the same transaction as the E05-S06 call (which writes the audit row `repository.enabled` with metadata `{ repository_id, document_id }`): exactly one `sweep-repository` job (E07-S09) with reason `repository_enabled`, keyed per repository. The sweep lists open PRs through GitHub and enqueues `evaluate-pr` per PR; this endpoint makes no GitHub call. Response `200 { "enabled": true, "changed": true }`
- Failure injection: an enqueue port that throws leaves `enabled = false`, no audit row and `500`; a retry then succeeds
- Real-Postgres-only test: five simultaneous enable calls produce one `changed: true`, one audit row and one sweep job
- Integration test with GitHub stubbed by MSW: a repository with two open PRs (one covered, one not) is enabled; after the sweep the `license/cla` Check Runs are `success` and `failure` respectively (E08, E09)
- Cross-tenant tests: the other tenant's repository id is `404`; a repo admin of repository X (repo-scoped document) cannot enable repository Y of the same installation (`403`, unless also org admin), and a repo admin gets `403` for a repository whose attached document is installation-scoped
- Built as: the route is `repositoryEnableRoutes` in `src/server/adapters/http/repository-enable-routes.ts` (path and zod schemas in `src/shared/repository-enabled.ts`; the answer schema is for E14-S04 to reuse), a `tenant` route in `write` mode resolved by `byRepositoryParam`, so the guard checks the installation, the suspension (`409 installation_suspended`) and lets in a repo admin or an org admin, and the precise role is checked by the service. The service `enableRepository` (`repository-enablement.ts`) runs one transaction that takes the same `select ... for update` on the repository row as the attach and the detach (`lockRepositoryForDocumentChange`, which now also reads the attached document's `active_version_id`), so a detach cannot slip in between the check that a CLA is attached and the flag that turns enforcement on. The checks are in `repository-enablement-checks.ts` (`requireActionRole`, the repository-action rule on the document read under the lock, and `requireActiveCla`, for E14-S04 to reuse): the role is judged first and only then is the missing CLA reported, so the role decides what a person learns. A role too low under the lock is `403 forbidden`; a repository that left the tenant since the guard read it is the uniform `404`. `no_active_cla` is a new `ClaRuleError` rule with status `409` (`CLA_RULE_STATUS`); the message stays the status text and the fix travels in `details.hint` (attach a document and publish a version first), as for the other rule errors. The change is `setRepositoryEnabled` (E05-S06) in the caller's transaction; when it reports `changed: false` the call writes nothing and enqueues nothing. On a change `sendEnableSweep` (`repository-enablement-sweep.ts`) reads the `updated_at` the change wrote (`readRepositoryChangedAt` in `repository-document-queries.ts`) and sends one `sweep-repository` job with reason `repository_enabled` under the key `sweep-repository:repository_enabled:<githubRepoId>:<updated_at in ms>`, coalesced per repository, in the same transaction, so a throwing queue rolls the change back, and the endpoint makes no GitHub call. Tests: the route, rules, jobs (failure injection, retry, coalescing) and tenant suites in `src/server/adapters/http/repository-enable-*.test.ts` over the shared fixture `repository-enable-fixture/`; the cross-tenant matrix case for the route (`crossable: false`, because the path carries no installation id, prepared as an already enabled repository so the case sends no job); a real-Postgres race of five simultaneous calls (`repository-enable-race.test.ts`) and of an enable against a detach (`services/repository-enablement-race.test.ts`); and the MSW flow (`repository-enable-flow.test.ts`) that enables a repository with two open pull requests, runs the sweep and the evaluations through the real adapter and reads `success` for the covered one and `failure` for the other from the writes the mocked GitHub recorded (`HttpWorld.checkRunWrites`).

**E14-S04 — Disable a repository** ✅ Done
Turning enforcement off must not leave pull requests stuck behind a pending or failing check that no one will ever update.
Acceptance criteria:
- `POST /api/repositories/:repositoryId/disable`, same role and error rules as E14-S03. Disabling an already disabled repository is `200 { "enabled": false, "changed": false }` with no side effect
- It sets `enabled = false` and keeps `cla_document_id`, signatures, allowlist entries and all `pr_evaluations` history untouched (no row is deleted or rewritten)
- In the same transaction as the E05-S06 `setRepositoryEnabled(..., false)` call (which writes the audit row `repository.disabled`): one `finalise-repository` job (E07-S09) keyed per repository. This story registers the handlers of `finalise-repository` and `finalise-check`. The first walks the latest `pr_evaluations` row per PR whose `result` is `in_progress` or `failure`, in batches of 50, and enqueues one `finalise-check` job per PR under the same per-(repository, PR) key that serialises `evaluate-pr` (E07-S02). That key only keeps two finalisations of one pull request apart: a pg-boss policy holds within one queue, so a `finalise-check` does not wait for an `evaluate-pr` that is already running (shown by a real-Postgres test in E07-S09); the guard below is what closes that race. Rows with `result = 'success'` are not touched
- A `finalise-check` job re-fetches the PR and head SHA. For an open PR it calls `EvaluationReporter.enforcementDisabled` (E09-S06): the `license/cla` Check Run completes with conclusion `neutral` and the fixed title and summary strings of E09-S02, and the PR comment (E09 upsert) is rewritten to its one-line notice. A closed PR is skipped. `pr_evaluations.result` gets no new value; `neutral` exists only on GitHub
- Guard in the evaluation path: the `evaluate-pr` job re-reads `repositories.enabled` together with its head SHA re-check, and writes neither Check Run nor comment when the repository is disabled. The read of `enabled` is the last step before the write and the write is skipped, not rolled back, so a `finalise-check` that completes the run `neutral` while an evaluation is between its last read and its write is the one case to prove with a real-Postgres interleaving test. Test: disabling between the job's fetch and its write produces no GitHub write call
- A `pull_request` webhook for a disabled repository is recorded and processed normally but creates no Check Run (MSW asserts no `POST /check-runs`). Re-enabling (E14-S03) sweeps all open PRs and restores real results
- Real-Postgres-only test: a disable racing with an in-flight evaluation never leaves a `failure` or `in_progress` Check Run on the final head SHA of an open PR
- Cross-tenant test: disabling tenant 1's repository enqueues nothing for tenant 2 even when both have PRs with identical numbers and SHAs
- Built as: the route is `repositoryDisableRoutes` (`repository-disable-routes.ts`), a `tenant` route in `write` mode resolved by `byRepositoryParam`, audited as `repository.disabled`, with the path and the empty-body schema in `src/shared/repository-enabled.ts` and the answer schema of E14-S03. Enable and disable share one transaction, `switchRepository` (`repository-switch.ts`, its types in `repository-switch-types.ts`): the `select ... for update` lock of the repository row (the one attach, detach and enable take), the repository-action rule on the document read under the lock, the direction's own check (a CLA to enforce for the way on, nothing for the way off), `setRepositoryEnabled` and the direction's job, all or nothing; `enableRepository` is now a thin wrapper and `answerSwitch` (`repository-switch-route.ts`) the shared route body. `disableRepository` sends one `finalise-repository` job under the key `finalise-repository:<githubRepoId>:<updated_at in ms>`, so off, on, off is two finalisations. `finalise-repository` (`services/finalise/finalise-repository.ts`) reads the stored rows only: per page of 50 pull requests (`unfinishedPullRequests`: the latest row per PR, by `updated_at` then `id`, whose result is `in_progress` or `failure`, after the last number of the previous page) one transaction sends a `finalise-check` job per PR under `finalise-check:<jobId>:<githubRepoId>:<prNumber>`, which the queue serialises per (repository, PR). `finalise-check` re-reads the repository, the pull request and its head SHA, finds the `pr_evaluations` row of that head SHA and calls `enforcementDisabled`; a closed or missing PR, a head SHA with no row, a repository that is on again (`repository_enabled`) and every unserved tenant state are `skipped:<reason>`; if the repository was turned on while the report was written the PR is sent to be evaluated once more. The handlers (`finalise/finalise-handlers.ts`) are bound by `registerHandlers` on the ports of the evaluation jobs through one helper, `onEvaluationPorts`, so they fail closed without a GitHub App like the other jobs that run on them (the handlers of the delivery-driven jobs moved to `evaluation-handlers.ts` to keep `job-handlers.ts` under the FTA cap). The guard (`evaluate-pr/enforcement-guard.ts`, `handOverIfOff`) reads `repositories.enabled` after the verdict row is stored and before `publish`: a repository that is off writes neither Check Run nor comment (the job ends `skipped:repository_disabled`, the stored verdict stays) and sends a `finalise-check` job from a transaction of its own after the read; it reads again after `publish` and hands over again if the repository went off in between. The finalisation of a switch-off that committed before the first read is thus never overtaken by a verdict, and one that committed after the second read is sent after the commit, so the last write to the run is `neutral` in every order (a `neutral` written before the verdict is written over and completed again; completing a run that is `neutral` already is idempotent). A job that fails and is retried does not lose the hand-over: a report that fails after the Check Run was written (`publishAndHandOver` in `evaluate-open.ts`) hands the pull request over before the job fails (a failed send there is logged as `evaluate_pr.hand_over_failed`, and the failure of the report is the one the queue sees), and a retry (`attempt > 0`) that finds the repository off sends the `finalise-check` job before it ends `skipped:repository_disabled` (`handOverRetry`), because the attempt before it may have started or written the run and failed before its own hand-over. `repository-disable-retry.test.ts` runs the three failures (the report fails after the write, the hand-over after it cannot be sent either, the verdict is written and its hand-over cannot be sent) through the real adapter and reads `neutral` after the retry. The batch of the walk is pinned: `FINALISE_BATCH` is 50 and a walk of 120 pull requests sends 50, 50 and 20 to a transaction each. Tests: the route, rules, jobs and tenant suites in `src/server/adapters/http/repository-disable-*.test.ts` over `repository-disable-fixture/`; the service and its real-Postgres races in `services/repository-disablement*.test.ts`; the jobs and the guard in `services/finalise/*.test.ts` and `evaluate-pr-switch-off.test.ts`; the MSW flow (`repository-disable-flow.test.ts`: enable, evaluate, disable, finalise, re-enable), the webhook for a disabled repository (`webhook-disabled-repository.test.ts`: no GitHub request at all), the interleaving at three cuts with the real reporter (`repository-disable-interleaving.test.ts`: the writes of the run are `in_progress, neutral, neutral`, `in_progress, neutral, failure, neutral` and `in_progress, failure, neutral, neutral`), and the real-Postgres race on two connections (`repository-disable-evaluation-race.test.ts`: the disable holds its transaction open while the evaluation writes). The app worlds of the route tests are PGlite always, so races that need a second session are made at service level on connections of their own.

**E14-S05 — Members permission probe** ✅ Done
The org-member exemption lookup that E08 consumes is E07-S10; this story adds only the permission probe that the allowlist form needs before it accepts an `org_members` entry.
Acceptance criteria:
- The port (E05-S04) gains `probeMembersPermission(githubInstallationId)`: it calls `GET /orgs/{org}/members?per_page=1` with the installation token and returns `true` on `200` and `false` on a `403` that is not rate limiting. The org is the installation's own account (`installations.account_login`); an installation of type `User` never reaches this call because E14-S06 refuses it first.
- `x-ratelimit-remaining: 0` or a `retry-after` header on a `403` throws `GitHubRateLimitedError`; `5xx`, timeouts (5 s) and network errors throw `GitHubUnavailableError`. These are the E05 error classes, and the response shape is parsed with zod (an unexpected shape throws `GitHubResponseError`).
- The result is not cached: an operator who accepts the updated App permissions retries at once and must see the change. The public-members endpoints are never used (an MSW handler fails the test on `/public_members/`).
- Cross-tenant test: the installation token used is always the one of the requesting installation, and a probe for installation 1 never answers for installation 2.
- Contract fixtures (200, 403 permission, 403 rate limit, 5xx) live next to the adapter, typed through the zod schema, and run against `FakeGitHub` and the MSW-backed adapter.
- Built as: `probeMembersPermission(githubInstallationId)` on the port (`services/ports/github.ts`), implemented by `OctokitGitHubClient` and `FakeGitHub`. The installation is checked first (the gate and the token provider, so a refused installation sends no request, the App's own included), then the adapter asks GitHub for the organisation: the port takes the installation id only and the adapter has no database, so the org is the `account.login` of `GET /app/installations/{id}` (signed as the App) and not the stored `installations.account_login`, which is a display snapshot that a rename leaves behind (so a renamed org is asked about under its new name). An account that is not an `Organization` (a user, an enterprise), a login GitHub cannot hold and an installation GitHub no longer has are a `GitHubNotFoundError` and no members request is sent. The members request is `fetchMembersPermission` (`octokit-installation-calls.ts`, `per_page=1`) over `answeredUnlessForbidden` (`octokit-request.ts`, beside `readOrNullWhenForbidden`): a 403 that is a refusal is `false`, a rate limit (`retry-after`, `x-ratelimit-remaining: 0`, a 429 or the words of a limit; waited out up to 60 s by the limiter, then `GitHubRateLimitedError`) is not a refusal, and the answer must be a list of `{ id }` (`membersProbeSchema`, nothing of the members is kept) or it is a `GitHubResponseError`. Nothing is cached in the adapter. Tests: the fixtures of the five answers the contract scripts (granted, missing, rate_limited, unavailable, malformed) and of six more answers of the adapter test are in `adapters/github/members-probe-fixture/test-support.ts` (the 200 bodies typed through the schema, `membersProbeRoute` the MSW route of the HTTP world); the contract cases in `services/github-members-probe-contract/test-support.ts` run against `FakeGitHub` (`scriptMembersProbe`, default granted) and the MSW-backed adapter (not cached, one installation never answers for another, a user's installation, a signal, the refusals of the gate); `octokit-client-members-probe.test.ts` reads each answer, shows the two requests and their tokens, the 500, 503, network and timeout outages, the rename and the two tenants with their own tokens; `start-timeouts.test.ts` shows the 5 s; `http-world.test.ts` shows the route refuses what GitHub refuses. The mocked GitHub fails any test that reaches a `/public_members/` path.

**E14-S06 — Add an allowlist entry** ✅ Done
Entries are typed as a login but stored as a numeric GitHub id, so a renamed or recycled login can never inherit an exemption.
Acceptance criteria:
- `POST /api/installations/:installationId/allowlist-entries` (installation scope, org admin) and `POST /api/repositories/:repositoryId/allowlist-entries` (repository scope, the repository-action rule of E14-S01). Body is a discriminated union, `.strict()`: `{ "kind": "user", "login": "ada" }`, `{ "kind": "bot", "login": "dependabot[bot]" }`, `{ "kind": "org_members" }`
- A forward-only migration adds `allowlist_entries.login_snapshot text null` for display only. It is never used for matching, never in `audit_log`, and is shown as a snapshot. Matching uses `github_id` alone
- For `user` and `bot` the login must match `^[A-Za-z0-9](?:[A-Za-z0-9-]{0,38})(?:\[bot\])?$` before any request is made, then the server calls `GET /users/{login}` with the installation token, URL-encoding the segment. The response is parsed with zod; `id` must be a positive integer, `login` must match the same pattern, otherwise `502 github_unavailable`, so a malformed response cannot plant markup in `login_snapshot`

**E14-S07 — List and remove allowlist entries** ✅ Done
Maintainers can review what is exempt and take an exemption away.
Acceptance criteria:
- `GET /api/installations/:installationId/allowlist-entries` returns the installation-scoped entries (org admin). `GET /api/repositories/:repositoryId/allowlist-entries` returns `{ "own": [...], "inherited": [...] }` (the repository-action rule of E14-S01): `own` are entries with that `repository_id`, `inherited` are the installation's entries, flagged read-only. Both accept `limit` (default 100, max 200) and an id cursor, ordered `kind asc, login_snapshot asc nulls last, id asc`
- Each item: `id`, `scope`, `repositoryId`, `kind`, `githubId`, `loginSnapshot`, `createdBy: { githubId, login }` (login from the `users` snapshot), `createdAt`. Strings are returned verbatim; escaping is the screen's job (E18)
- `DELETE /api/installations/:installationId/allowlist-entries/:entryId` returns `204`; the query filters by both ids. The role follows the entry's scope (installation scope needs org admin; repository scope follows the repository-action rule of E14-S01). An unknown id, another tenant's id and an already deleted id are all `404`
- The delete is a hard delete (the runtime role holds `DELETE` on `allowlist_entries`); the history is the audit row `allowlist_entry.deleted` with subject `allowlist_entry`/entry id and metadata `{ scope, repository_id, kind, github_id }`, written in the same transaction
- In the same transaction the delete enqueues the same per-repository sweeps as E14-S06, because removing an exemption can turn a green check red. Failure injection: an enqueue failure rolls the delete back
- The E07-S10 membership cache holds GitHub facts, not policy, so entry changes leave it alone; the policy itself is read fresh from `allowlist_entries` on every evaluation (E08), and the sweeps above make a change visible on open PRs
- Cross-tenant tests: tenant 1's admin cannot list or delete tenant 2's entries by any id; an entry deleted in tenant 1 leaves an identical `(kind, github_id)` entry of tenant 2 in place
- Hostile-input test: a `login_snapshot` coming from a stubbed GitHub response with markup characters is rejected at creation (E14-S06), and list output is asserted to contain only strings matching the login pattern
- Built as: the lists are `allowlistListRoutes` (`allowlist-entry-list-routes.ts`) and the removal is `removeEntryRoute` (`allowlist-entry-remove-route.ts`), both registered by the plugin of E14-S06. The paths, the query (`allowlistQuerySchema`, strict: a plain-digit `limit` of 1 to 200, 100 by default, and a `cursor`) and the answers (`allowlistPageSchema` `{ entries, nextCursor }`, `repositoryAllowlistPageSchema` `{ own, inherited, nextCursor }`; each item is the entry of E14-S06 plus `createdBy { githubId, login }` and `readOnly`, true for the inherited ones) are in `src/shared/allowlist.ts`. The lists are `read` routes, the removal a `write` route whose resolver (`allowlist-entry-resolver.ts`) finds the entry by both ids and takes the requirement from its scope: an org admin for an entry of the installation or of a repository that left it, the repository-action rule for the document the repository enforces otherwise; an unknown, another tenant's or already deleted id is `404` before any role is judged. The list statement (`allowlist-entry-list-queries.ts`) and the find and delete statements (`allowlist-entry-remove-queries.ts`) name the installation, joins `users` for the login of the author and orders `kind, login_snapshot nulls last, id`; the cursor is the position `[kind, login, id]` (`[section, kind, login, id]` for a repository, whose page runs through `own` and then `inherited` under one limit), read with a zod schema (`allowlist-entry-cursor.ts`), so the nulls-last order pages without skipping or repeating and a made-up cursor is `400`. The removal (`allowlist-entry-remove.ts`) finds the entry, locks the repository row when it has one, judges the role again under that lock (the same order as the add, so the two cannot deadlock), deletes with `returning` (the loser of two simultaneous removals is `404`), appends `allowlist_entry.deleted` and sends the sweeps of E14-S06 with the change `deleted:<id>`, in one transaction. Nothing in the removal reads GitHub or the membership cache (a test reads the imports).
