# E06 — Webhook intake

**Bounded Context:** BC-05
**Priority:** 🔴 Must have
**Status:** ⬜ Todo

**Goal:** GitHub's webhook deliveries are authenticated, deduplicated and turned into exactly one durable job each, inside the 10 second response budget and without a single GitHub API call in the request path. A forged, replayed, oversized or malformed delivery never reaches the queue.
**Depends on:** E04, E05
**Out of scope:** The pg-boss runtime, queue policy, workers and the `processed_at` writer on job completion (E07). What a job does with its ids (E05-S08 for installations, E07 for evaluation, E10 for session revocation). The exact `/recheck` line rule and its rate limit (E07-S07). CSRF registration with this route exempted (E10). Pruning old `webhook_deliveries` rows (the MVP keeps them; E22-S04 owns the purge). Subscribing to events beyond the `docs/github-app.md` Events row (for example `repository`).

---

**E06-S01 — Raw-body HMAC verification with two accepted secrets** ✅ Done
Acceptance criteria:
- `POST /webhooks/github` is registered with `fastify-raw-body` for this route only (`global: false`, buffer encoding), so the verified bytes are the bytes GitHub sent. The route has no session, cookie or CSRF dependency and works with no `Origin` header. Its path is the shared constant `WEBHOOK_PATH = '/webhooks/github'` in `src/shared/routes.ts`, which E10 (`CSRF_EXEMPT`), E11 (`webhook` access) and the E19 App manifest import instead of retyping.
- `AppError(status, code, details?)` is introduced here in `src/server/adapters/http/errors.ts`: the E04 error handler sends its `code` (and `details`, a plain JSON object, only when given) while `message` stays the standard status text, and `errorResponseSchema` gains the optional `details`. Unknown errors behave as before. Every `webhook_*` code below is thrown this way, and E10 to E16 reuse it for their domain codes.
- `GITHUB_WEBHOOK_SECRET` is required in production and `GITHUB_WEBHOOK_SECRET_PREVIOUS` is optional, both at least 16 characters and held as `Secret`. Previous equal to current is a `ConfigError` naming the variable. The `docs/configuration.md` table is updated in the same change.
- The `X-Hub-Signature-256` header must be `sha256=` plus 64 lowercase hex characters (GitHub always sends lowercase). The server computes `HMAC-SHA256(secret, rawBody)` for each configured secret and compares with `crypto.timingSafeEqual` on equal-length Buffers (length checked first, because `timingSafeEqual` throws on unequal lengths). Both secrets are always computed. A delivery passes if either matches.
- A match on the previous secret logs one WARN `webhook.secret_previous_used`, at most once per minute, so the operator can tell when rotation is finished.
- Any failure (header missing, wrong prefix, wrong length, non-hex, mismatch) gives `401` with the E04 error body and code `webhook_signature_invalid`, identical for every cause. The request body is not parsed, and a request carrying only the legacy `X-Hub-Signature` (SHA-1) header is refused.
- Known-answer test: secret `It's a Secret to Everybody`, body `Hello, World!`, header `sha256=757107ea0eb2509fc211221cce984b8a37570b6d7586c22c46f4379c8b043e17` is accepted.
- Hostile tests: one flipped byte in the body, re-serialised JSON with different whitespace, uppercase hex, header with a trailing space, a body signed by neither secret, a body signed by the previous secret after that secret was removed. Each is `401`. An empty body carrying the valid signature of the empty string passes this story and is refused by S02 with `400` `webhook_payload_invalid`. A spy asserts `crypto.timingSafeEqual` is called on every accepted request and that no JSON body parser runs on a rejected one.
- Secrets never appear in logs or error bodies; the log-capture assertion of S07 covers it.

**E06-S02 — Request envelope: headers, size, media type and JSON** ✅ Done
Acceptance criteria:
- Check order is fixed: body size (413), signature (401, S01), headers (400), media type (415), JSON syntax (400), schema (400, S03). Nothing after the signature check runs for an unsigned request.
- Body limit for this route is 10 MiB (`10_485_760` bytes). Over it gives `413` with code `webhook_payload_too_large` and the body is not buffered past the limit. Other routes keep their E04 limit.
- Required headers after the signature check: `X-GitHub-Event` matches `^[a-z_]+$` and is at most 64 characters; `X-GitHub-Delivery` is a UUID (stored lowercased, within the 1 to 128 length check of `webhook_deliveries.delivery_id`). A missing, repeated or malformed header gives `400` `webhook_header_invalid`.
- `Content-Type` must be `application/json` (any charset parameter). `application/x-www-form-urlencoded`, GitHub's alternative, gives `415` `webhook_unsupported_media_type` with a message telling the operator to set the content type to `application/json` in the App settings.
- If `X-GitHub-Hook-Installation-Target-ID` is present it must equal `GITHUB_APP_ID`, and if `X-GitHub-Hook-Installation-Target-Type` is present it must be `integration`. Otherwise `400` `webhook_wrong_app`: the secret is shared with another App.
- The body is decoded as UTF-8 with fatal errors and parsed as JSON. Invalid UTF-8, invalid JSON, and a top-level value that is not an object (array, `null`, number, string) give `400` `webhook_payload_invalid`.
- Failures never echo any part of the body or header values in the response or the log line.
- Tests: exactly 10 MiB accepted for size purposes, 10 MiB plus 1 byte refused, BOM prefix, lone surrogate bytes, NUL bytes, 1 MiB of `[` nesting (returns 400, process alive), repeated `X-GitHub-Event` header, form-encoded body with a valid signature.

**E06-S03 — Event payload schemas and hostile payload suite** ✅ Done
Acceptance criteria:
- One zod schema per supported event in `src/server/adapters/github/webhook-schemas.ts`. Objects strip unknown keys and declare only the fields the router needs. GitHub ids are `z.number().int().positive().max(Number.MAX_SAFE_INTEGER)`.
- Fields per event. `pull_request`: `action`, `number`, `pull_request.number`, `pull_request.head.sha`, `pull_request.user.{id,type}`, `repository.id`, `installation.id`. `check_run`: `action`, `check_run.{id,name,head_sha,app.id}`, `repository.id`, `installation.id`. `check_suite`: `action`, `check_suite.{id,head_sha,app.id}`, `repository.id`, `installation.id`. `issue_comment`: `action`, `issue.number`, optional `issue.pull_request`, `comment.{id,body}` (body at most 65,536 characters), `sender.type`, `repository.id`, `installation.id`. `installation` and `installation_repositories`: `action`, `installation.{id,account.{id,type}}`. `github_app_authorization`: `action`, `sender.id`.
- The `action` of a known event is a plain string, so an action nobody handles still validates and is ignored by the router (S04) rather than rejected as malformed.
- A schema failure gives `400` `webhook_payload_invalid`. The response and the log list the zod issue paths only, never values.
- Fixtures are trimmed from GitHub's documented payload examples with fictitious ids; no real user, email or token appears in them.
- Hostile table (at least 25 rows): string id, float id, negative id, `0`, `2**53`, `1e400`, id as a 20-digit numeric string, missing `installation`, `installation` as an array, `__proto__` and `constructor` keys (asserts `Object.prototype` is untouched and the key is stripped), RTL override, NUL and lone surrogate in `full_name` and in `comment.body`, comment body of 65,537 characters, `pull_request` of the wrong type, duplicate JSON keys (last one wins, as `JSON.parse` does), event header `pull_request` with an `issue_comment` body.
- Failure injection: a schema that throws a non-zod error gives `500` through the E04 handler and the log holds no body.
- Every schema field has a table row proving a wrong type is refused, so removing a field from the schema fails a test.

**E06-S04 — Event routing table** ✅ Done
Maps each validated delivery to zero or one job. The job names and their id-only payloads are the shared catalogue that E07 implements.
Acceptance criteria:
- Pure `routeWebhook(event, action, payload, context)` in `src/server/domain/webhook-routing.ts`, with `context` = `{ appId, deliveryId }` (the caps allow four parameters), returns `{ kind: 'job', job }` or `{ kind: 'ignored', reason }`, and `{ kind: 'pong' }` for `ping`. No I/O. Job payloads carry numeric ids only (`githubInstallationId`, `githubRepoId`, `prNumber`, `commentId`, `headSha`, `githubUserId`) plus the `deliveryId`. The payload is never copied into the job. The catalogue is `jobSchema` in `src/server/domain/jobs.ts`: one strict zod object per job, which E07-S03 validates job data against.
- Routing (the contract for the table test):
  ```text
  pull_request   opened, reopened, synchronize, edited, ready_for_review -> evaluate-pr {trigger: pull_request}
  pull_request   closed (merged or not)                                    -> close-pr
  pull_request   any other action                                          -> ignored unsupported_action
  check_run      rerequested, name == license/cla, app.id == GITHUB_APP_ID -> evaluate-head-sha {headSha}
  check_suite    rerequested, app.id == GITHUB_APP_ID                      -> evaluate-head-sha {headSha}
  check_run / check_suite  anything else                                   -> ignored foreign_check or unsupported_action
  issue_comment  created, issue.pull_request present, sender.type != Bot,
                 body contains "/recheck"                                  -> recheck-comment
  issue_comment  anything else                                             -> ignored
  installation, installation_repositories  (every action)                  -> sync-installation
  github_app_authorization  revoked                                        -> revoke-user-sessions {githubUserId}
  ping                                                                     -> answered 200 {status: pong}, no row
  any other event                                                          -> ignored unsupported_event
  ```
- `issue_comment` uses a deliberately loose prefilter (the body contains the text `/recheck`, sender is not a Bot) to avoid a job per PR comment. The exact-line rule and the rate limit are decided by the job after it re-fetches the comment (E07-S07).
- Every check re-run resolves to the head SHA, not to the PR numbers in the payload, because `check_run.pull_requests` is empty for fork PRs. The job lists the open PRs for that SHA at run time (E07-S07).
- Invariant: every routed delivery maps to exactly one job. A test iterates the whole table and asserts it. `revoke-user-sessions` jobs wait in their queue until E10 registers the handler; nothing is lost meanwhile.
- A constant `SUBSCRIBED_EVENTS` lists the event names of the `docs/github-app.md` Events row, and a test fails if the router handles an event outside it or a listed event has no row.
- Drafts are evaluated like any other PR. `edited` is routed in full; the cost is bounded by E07 coalescing.
- Exhaustive `test.each` over (event, action) pairs, including every ignored pair, `check_run` for a name other than `license/cla`, a `check_suite` from another App id, a Bot sender, and `issue_comment` with `/recheck` as a substring of another word.

**E06-S05 — Tenant and admission filter** ✅ Done
Acceptance criteria:
- Applies to `pull_request`, `check_run`, `check_suite` and `issue_comment` jobs. It looks up the installation by `payload.installation.id` (a database read, no GitHub call) and uses the E05 installation state.
- Decision: admitted and active, proceed. Rejected: `202` ignored `installation_not_admitted`, no job. Deleted: ignored `installation_deleted`. Suspended: ignored `installation_suspended`. No PR data of a rejected tenant is enqueued or processed.
- Unknown installation: the delivery becomes a `sync-installation` job for that id (it self-heals a missed `installation.created`) and the PR event itself is ignored. The E07-S08 sweep picks the PR up afterwards.
- A repository that is already stored under a different installation than the payload names (stale transfer state) also becomes a `sync-installation` job for the payload's installation, and the event is ignored with `repository_installation_mismatch`.
- `installation`, `installation_repositories` and `github_app_authorization` bypass the filter: they are how installations and revocations are learned, including the `installation.created` of an account the policy will reject (E05-S07 records it).
- Repository `enabled` is not checked here. The job re-checks eligibility at run time (E05-S06), which also avoids losing an event that arrives before the repository row exists.
- Rejected-tenant WARN logs are limited to one per installation per minute and carry numeric ids only.
- Tests, with three installations (admitted, rejected, suspended) plus a deleted one: each decision for each event type; cross-tenant test with a payload naming installation A and a repository stored under B; a table of lifecycle events from a rejected account that still reach `sync-installation`.

**E06-S06 — Transactional delivery recording and enqueue** ✅ Done
Acceptance criteria:
- Port `JobEnqueuer` in `src/server/services/ports/jobs.ts`: `enqueue(tx, job, { idempotencyKey, dedupeKey?, dedupeWindowSeconds? })` returns `'queued'`, `'already_queued'` (a job sent under the same idempotency key is still alive, so it will finish the delivery) or `'deduplicated'` (a dedupe window dropped the send, so no job will run), and answers `already_queued` before `deduplicated` when both apply. It receives the Kysely transaction so the adapter can send on the same connection. The pg-boss adapter is E07-S01, which re-runs this story's shared contract suite against it. Until then this story is verified with a fake enqueuer that writes into a test table inside the transaction.
- One transaction does: `insert into webhook_deliveries (delivery_id, event, action) ... on conflict (delivery_id) do nothing`; on conflict `select processed_at ... for update`; then enqueue with `idempotencyKey = delivery_id`; commit. No payload is stored.
- Outcomes. New row: `202 {"status":"accepted"}`. Existing row with `processed_at` set: `200 {"status":"duplicate"}`, no enqueue. Existing row with `processed_at` null (the earlier job failed, was dead-lettered or expired): enqueue again under the same idempotency key, so at most one live job exists per delivery, `202`. Enqueue returns `'already_queued'` (the first job is still alive, or 20 identical deliveries arrive at once): the row is left unprocessed for that job to finish, answer `200 duplicate`, so a redelivery after the job is lost, failed for good or dead-lettered still requeues. Enqueue returns `'deduplicated'` for a row this call just inserted: `processed_at` is set in the same transaction, since no job will ever do it; a row recorded earlier keeps its state, which keeps the delivery within five statements.
- Ignored deliveries (S02 to S05) insert no row at all. `ping` answers `200 {"status":"pong"}` and inserts nothing.
- An enqueue error rolls the transaction back, so a row never exists without its job, and answers `503` `webhook_enqueue_failed`. GitHub's delivery log shows the failure and a manual redelivery works.
- `markDeliveryProcessed(deliveryId)` sets `processed_at = now()` only where it is null and is idempotent. E07-S03 calls it when the delivery's job completes; a dead-lettered job does not call it, so a redelivery requeues.
- Real-Postgres-only tests (PGlite is single connection): 20 parallel identical deliveries produce one row, one job and the rest `200 duplicate`; a connection killed between the insert and the commit leaves neither row nor job. A failure-injection test with a throwing enqueuer asserts the rollback.
- Every statement is parameterised Kysely; `delivery_id` comes from the validated UUID, never straight from the header string.

**E06-S07 — Request-path guarantees, failed-signature throttling and logging** ✅ Done
Acceptance criteria:
- For every row of the routing table the route runs with a GitHub port whose methods throw and with MSW `onUnhandledRequest: 'error'`. The test asserts no outbound request and no port call, so the request path provably makes no GitHub API call.
- The handler runs at most 5 SQL statements per delivery (installation lookup, repository lookup, insert, select for update, enqueue), checked with a Kysely log plugin in the test. It has an 8 second deadline: on expiry it rolls back and answers `503` `webhook_timeout`, leaving GitHub's 10 second limit unreached.
- Failed-signature throttling: more than 30 failed verifications from one client address within 60 seconds give `429` with `Retry-After` for that address until the window slides. Only failures count, so GitHub's bursts of valid deliveries are never throttled. The store is in memory (one instance per server), holds at most 10,000 addresses (least recently used evicted), and the address is never logged or persisted. The address comes from `request.ip`, so `TRUST_PROXY` (E04) decides which one is used.
- One structured line per delivery, `webhook.received`: `event`, `action`, `deliveryId`, `githubInstallationId`, `outcome` (`accepted`, `ignored`, `duplicate`, `rejected`), `reason`, `durationMs`. A test captures the pino output of the whole hostile suite and asserts it contains no body fragment, no header value, no signature and neither webhook secret. The route mints its own request id (the `genReqId` of its encapsulated scope, which Fastify asks for the route the router matched), so a caller's `X-Request-Id` never reaches a line, however the path is spelled: percent-escapes, a fragment or the absolute form of the target.
- `GET /webhooks/github` and every other method answer `404` with the E04 error body (Fastify's answer for an unregistered method on a known path); no route handler runs.
- An integration test on real Postgres posts the full fixture set of S03 through the route and asserts the exact rows and jobs created per event, with the repository-less events (`installation`, `github_app_authorization`) included.
