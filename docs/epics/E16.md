# E16 — Compliance, audit and data protection

**Bounded Context:** BC-07
**Priority:** 🔴 Must have
**Status:** ⬜ Todo

**Goal:** Every mutation leaves a tamper-evident audit row without personal data, maintainers can export signature evidence safely, personal data can be erased without touching the immutable signature core, and optional network metadata has a hard retention limit. On an instance that serves several orgs, each tenant sees only its own audit trail and can erase only the data held for its own installation.
**Depends on:** E04, E11
**Out of scope:** The audit writer, the closed action set and the route guard (E04-S09), and the mutations that call them (E05 and E12 to E15 each add their own action names and calls; this epic checks the catalogue is complete). Recording network metadata at signing time and the `RECORD_NETWORK_METADATA` flag (E13-S05). Session cleanup (E10-S01) and webhook-delivery cleanup (E22-S04). Self-service erasure requested by the data subject through the UI: the subject contacts the maintainers and an org admin runs E16-S04 (a later phase can add a request flow). Public signature verification (E22). Corporate agreement data (E21). Legal advice: retention periods and lawful bases are the operator's choice, with counsel.

**E16-S01 — Audit action catalogue and conformance** ⏳ In progress
The writer, the closed action set and the route guard come from E04-S09; this story proves that, once every mutation epic has landed, the catalogue is complete and nothing bypasses it.
Acceptance criteria:

Each must be a member of `AUDIT_ACTIONS`, and each member must be written by at least one call site or sit in an explicit `RESERVED_ACTIONS` map in the test with a one-line reason, so an unused name cannot hide a missing mutation.
- Metadata conformance: a fixture per audit call site, the exact object that call writes, passes the zod schema of E04-S09 and the database check `audit_metadata_is_clean` when inserted through the migrated PGlite database. A key a call site writes that is in neither check fails here, not in production.
- Final route-guard state: the guard test of E04-S09 runs against the application with every epic registered and has no `auditExempt` reason beyond `webhook`, `session` and `setup`. Each mutating route named in E11 to E16 and E19 resolves to the audit action its own story documents.

- Open: the final route-guard state (fourth criterion) needs the routes of E12 to E15 and E19 in the application, which are not merged yet. `src/server/adapters/http/audit-route-state.test.ts` holds the table of the documented routes (`DOCUMENTED_MUTATIONS`) and shows the built ones (the webhook and logout exemptions) resolving to what their stories say; the others are marked `built: false` and the test fails the moment one is registered until its row says `built: true`. The eleven action names the story lists but the tuple lacked were added to `AUDIT_ACTIONS` here; with `data_export.created` and `network_metadata.purged` they sit in `RESERVED_ACTIONS` of `audit-catalogue.test.ts` until their call sites land (a reserved name that a call site writes fails the test). **E16-S02 — Audit log viewer API** ✅ Done
Org admins can read their tenant's audit trail, filtered and paginated.
Acceptance criteria:
- `GET /api/installations/:installationId/audit-log?action=&actorGithubId=&subjectType=&subjectId=&from=&to=&limit=&cursor=` with a session. Only an org admin of that installation (E11; for a `User` installation, the account owner) may read it. A viewer with no role in the tenant gets `404 not_found`, a viewer with a lower role (repo admin only) gets `403 forbidden`
- Filters are validated by zod: `action` must be an `AUDIT_ACTIONS` member (other values are `400`), ids are positive integers, `from` and `to` are ISO 8601 timestamps with an explicit offset or `Z`. `from` is inclusive and `to` is exclusive; boundary tests put rows exactly at `from` (returned), at `to` (not returned) and one millisecond either side
- Order is `occurred_at desc, id desc`; `limit` is 1 to 200 (default 50, `0` and `201` are `400`); `nextCursor` is an opaque base64url encoding of `(occurred_at, id)` that zod validates, and a tampered cursor is `400`. Pagination test with 250 rows that share one `occurred_at`: no duplicate, no gap
- Item: `{ id, occurredAt, action, actor: { githubId, login } | null, subject: { type, id } | null, metadata }`. `login` is read from the `users` snapshot at request time and is never stored in the audit table; a system action has `actor: null`. An erased user (E16-S04) shows the scrubbed `erased-<id>` login. Metadata is returned as stored
- Rows with a null `installation_id` (instance-level actions) are never returned by this endpoint; operators read them with the owner database role. A test inserts one and asserts its absence
- Every query filters by the path's installation id. Cross-tenant tests: an admin of tenant 1 requesting tenant 2's id gets `404`; filters such as `subjectId` never match another tenant's rows; an admin of both tenants sees each tenant's entries only under that tenant's path
- The endpoint is read-only and writes no audit row. Index check: the query plan for the default listing uses `audit_log_installation_occurred_at_idx` (asserted by an `explain` test on real Postgres)
- Built as: the route is `src/server/adapters/http/audit-log-routes.ts` (a tenant route in `read` mode behind `byInstallationParam`), the query string is read by `src/server/adapters/http/audit-log-query.ts` and the cursor by `src/server/domain/audit-cursor.ts`, the statement is `src/server/services/audit-log-queries.ts`, and the page shape and path are in `src/shared/audit-log.ts`. Choices the criteria leave open: an unknown query parameter is a `400` (a misspelt filter must not list everything); `from` and `to` take at most three decimals (the comparison is made at the millisecond, so more digits would be rounded silently); the cursor keeps the microsecond instant the database stores (`["2026-11-02T10:00:00.123456Z",42]` as base64url), because two rows of one millisecond can be told apart only by it, and it is not signed (it names a position inside the tenant's own rows, so forging one reveals nothing); `login` is `null` only when the instance holds no `users` row for the actor id, which no flow produces; `action` in the answer is a plain string, so a row written by an older release stays readable. The `explain` test (`src/server/adapters/db/audit-log-plan.test.ts`) skips on PGlite and runs in the `postgres` CI job; the plan is an index scan on `audit_log_installation_occurred_at_idx` under an incremental sort, with the cursor as an index condition.

**E16-S03 — Signature CSV export** ⬜ Todo
Signature evidence leaves the system as a file that spreadsheet software cannot turn into a command.
Acceptance criteria:
- `GET /api/installations/:installationId/documents/:documentId/signatures.csv?state=&from=&to=`. `state` is `active`, `outdated`, `revoked` or `all` (default `all`); `from` and `to` filter `signed_at` (inclusive, exclusive). Role by the document's scope as in E15-S03 (org admin for an installation-scoped document, repository admin for a repo-scoped one). A document outside the installation is `404`. Rate limit: 6 per minute per user
- Header row, in this order: `signature_id,github_user_id,login,name,email,document_id,document_name,version_major,version_minor,content_sha256,consent_text_id,signer_type,signed_at,source_repository,source_pr_number,state,revoked_at,revoked_by_github_id,revoke_reason_code,pii_erased`. Timestamps are ISO 8601 UTC with milliseconds. Network metadata columns are deliberately not exported. For a signature whose `signer_pii` row was erased, `login`, `name` and `email` are empty and `pii_erased` is `true`
- A pure module `src/server/domain/csv.ts` encodes RFC 4180: CRLF line endings including after the last row, fields containing `"`, `,`, CR or LF are quoted, `"` is doubled, UTF-8 without BOM. Before quoting, every cell that begins with `=`, `+`, `-`, `@`, a tab or a carriage return is prefixed with a single quote (`'`). The rule applies to every cell, user-controlled or not
- Hostile-name tests are mandatory: every entry of `HOSTILE_NAMES` (E09-S01), plus an email local part beginning with `+` and `-` and a name containing a comma, a double quote and an embedded newline. A unit table asserts, for each of the six trigger characters, that the encoded cell starts with `'` and that no cell in the output begins with a trigger character. The full export of a seeded hostile dataset is asserted with `toMatchFileSnapshot` into the dedicated directory `src/server/services/export/csv-snapshots/`
- The response has `Content-Type: text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="signatures-<documentId>-<YYYY-MM-DD>.csv"` (built only from the id and the UTC date, never from user text) and `Cache-Control: no-store`. The body streams in batches of 1,000 rows read by keyset on `id` inside one read-only `repeatable read` transaction, so a concurrent signing cannot produce a torn file. A failure mid-stream destroys the connection instead of ending the file normally (test with an injected error on the second batch)
- The audit row `signatures.exported` (subject `document`/id, metadata `{ state, row_count }` with `row_count` counted in the same snapshot) is appended before the first byte is sent, so an aborted download is still on record
- Cross-tenant tests: tenant 1's export never contains a tenant 2 row, including rows of the same GitHub user; a document id of tenant 2 under tenant 1's path is `404`; a repo-only admin cannot export an installation-scoped document (`403`)
- Boundary tests: a document with zero signatures returns the header row only; 1,000, 1,001 and 2,500 rows exercise batch edges with stable order and no duplicate

**E16-S04 — Erase a signer's personal data** ⬜ Todo
An org admin can erase the personal data the tenant holds for one person, through the one audited SQL function, while the signature core stays as legal evidence.
Acceptance criteria:
- A forward-only migration drops `erase_signer_pii(bigint, bigint)` and creates `erase_signer_pii(p_github_id bigint, p_actor_github_id bigint, p_installation_id bigint) returns integer`, `security definer`, search path pinned, `revoke all from public`, `execute` granted to the runtime role when it exists (as in the initial migration). A test queries `pg_proc` and finds exactly one function named `erase_signer_pii`. The previous signature's tests are rewritten for the new one, not deleted. Decision: with several orgs on one instance, erasing across tenants from one org admin's request would reach other orgs' data, so the function is scoped to an installation
- The function deletes `signer_pii` rows only where the joined `signatures.installation_id` equals `p_installation_id` and the user matches; sets `allowlist_entries.login_snapshot = null` for that user's entries in that installation; scrubs the `users` display snapshot (`login = 'erased-<github_id>'`, `name` and `avatar_url` null) and deletes the user's `sessions` rows (E10-S01 keeps `verified_emails` there, which is an email address) only when no `signer_pii` row of that user remains in any tenant; appends one audit row `signer_pii.erased` with `installation_id = p_installation_id`, `actor_github_id`, subject `user`/`p_github_id` and metadata `{ signer_pii_rows }`; and returns the number of deleted rows. An unknown user raises `no_data_found`
- `GET /api/installations/:installationId/erasure-preview?githubUserId=<n>` returns `{ githubUserId, signatures, signerPiiRows }` for that installation only, with counts and no personal data. `POST /api/installations/:installationId/erasures` with `{ githubUserId, expectedRows }` runs the function and returns `200 { "erasedRows": n }`. Role: org admin of the installation only (personal data spans documents, so a repo admin gets `403`). A user with no signatures in this installation is `404`; an `expectedRows` that differs from the live count is `409 count_changed` and changes nothing
- Erasure is not revocation and not a ban: signatures stay valid and keep covering the person, their `signatures` rows are byte-identical before and after (compare `to_jsonb`), the CSV export (E16-S03) shows them with `pii_erased = true`, and the person can sign again later, which creates a fresh `signer_pii` row. The privacy notes (E16-S07) say how to revoke as well (E15)
- Runtime-role test (`asRuntimeRole`): the role can execute the function, while a direct `delete from signer_pii` and a direct `update signer_pii` fail on missing privileges, so the function is the only way to remove or change personal data in that table. The same test shows that `truncate` and `delete` on `signatures` and `audit_log` still fail after the migration (it must not weaken the earlier guarantees)
- Completeness test: after erasing a seeded person, a scan driven by `information_schema` over every text and jsonb column of every application table searches for the person's login, name and email strings (seeded as unique sentinels, including inside `pr_evaluations.details` as E08 writes it) and finds none. Any table that keeps a login snapshot must be handled by the function, so a later epic that adds one fails this test until it does
- Cross-tenant tests (mandatory): the person has signatures in tenants 1 and 2; erasing through tenant 1 leaves tenant 2's `signer_pii` rows and the `users` snapshot intact; tenant 1's admin cannot erase through tenant 2's path (`404`); tenant 2's admin cannot see tenant 1's audit row
- The erasure request itself, the expected count and the result are never logged with names or emails; the log line holds the numeric ids and counts only (log-capture test)

**E16-S05 — Network metadata retention** ⬜ Todo
Optional IP and user agent values are kept for a short, enforced period and then removed, whether or not recording is still switched on.
Acceptance criteria:
- A new environment variable `NETWORK_METADATA_RETENTION_DAYS` is validated by the zod env schema: an integer from 1 to 90, default 30; anything else is a start-up error naming the variable. It is documented in `.env.example` and the `docs/configuration.md` table in the same change. It applies to the columns `signer_pii.ip_address` and `signer_pii.user_agent` created in E13-S05, so this story is built after that one
- A forward-only migration creates `purge_signer_network_metadata(p_cutoff timestamptz) returns integer`, `security definer`, search path pinned, `revoke all from public`, `execute` granted to the runtime role. It sets both columns to `NULL` on `signer_pii` rows with `created_at < p_cutoff` where either column is not null, returns the count, and appends audit `network_metadata.purged` (no actor, no installation, metadata `{ rows }`) only when the count is above zero. The runtime role still has no `update` on `signer_pii` (privilege test)
- A scheduled job on the queue `purge-network-metadata`, added to `QUEUES` and registered through the E07 scheduler, runs daily at 03:17 UTC, computes the cutoff as the injected clock's now minus `NETWORK_METADATA_RETENTION_DAYS` days, and calls the function. It runs even when `RECORD_NETWORK_METADATA` is `false`, so switching recording off never strands old values
- Boundary tests with a fixed clock: a row exactly at the cutoff is kept; rows 1 ms older and 1 day older are purged; a row with only `user_agent` set is purged; rows with both columns `NULL` are untouched and produce no audit row. The purge never touches `name`, `email`, `login` or the `signatures` core (byte-identical comparison)
- Idempotence: a second run on the same data returns 0 and appends no audit row. Failure injection: an error in the function fails the job and is retried within the bounded `retryLimit` (E07); no partial state is possible because the update is one statement
- Cross-tenant behaviour is stated and tested: the purge is instance-wide by design (retention is an instance setting), and rows of both tenants older than the cutoff are purged in one run; neither tenant's audit viewer shows the instance-level row
- Config interplay test: `RECORD_NETWORK_METADATA=true` with the default retention writes values at signing (E13-S05) and the job removes them after 30 days of fake time

**E16-S06 — Data subject export of own signatures** ⬜ Todo
Any signed-in person can download everything this instance holds about them, across all orgs.
Acceptance criteria:
- `GET /api/me/export` with a session. There is no user id in the path or query: the subject is the session user, and any query parameter is `400`. The response is JSON with `Content-Disposition: attachment; filename="cla-data-<githubId>.json"` and `Cache-Control: no-store`. Rate limit: 5 per hour per user (`429` with `retry-after`)
- Body, validated against `dataExportSchema` in `src/shared`:
  ```json
  {
    "schemaVersion": 1,
    "exportedAt": "2026-11-01T10:00:00.000Z",
    "user": { "githubId": 1234, "login": "ada", "name": "Ada Lovelace", "createdAt": "..." },
    "signatures": [{
      "id": 9, "installation": { "githubInstallationId": 55, "accountLogin": "acme" },
      "document": { "id": 7, "name": "Individual CLA" },
      "version": { "id": 31, "major": 2, "minor": 0, "contentSha256": "<64 hex>" },
      "consentTextId": "individual-v1", "signerType": "individual", "signedAt": "...",
      "source": { "repositoryFullName": "acme/widgets", "prNumber": 45 },
      "revokedAt": null, "revokeReasonCode": null,
      "personalData": { "name": "Ada Lovelace", "email": "ada@example.org", "login": "ada", "ipAddress": null, "userAgent": null }
    }],
    "allowlistEntries": [{ "installation": { "accountLogin": "acme" }, "scope": "installation", "kind": "user", "createdAt": "..." }],
    "auditEntries": [{ "occurredAt": "...", "action": "signature.created", "installationId": 55, "subject": { "type": "signature", "id": 9 } }]
  }
  ```
- `personalData` is `null` for a signature whose `signer_pii` row was erased. `revoked_by` (another person's identity) is not included. `auditEntries` are the rows where the subject is the actor or the audit subject (`user`/own GitHub id), newest first, at most 1,000, with `truncated: true` in the body when more exist. `allowlistEntries` are the entries whose `github_id` is the subject's
- All tenants are included on purpose: it is the person's own data and the person is not a member of any tenant. Rows are selected only by the subject's user id, so there is no way to name another person
- Isolation test with two users across two tenants: user 1's export contains none of user 2's signatures, personal data, audit entries or allowlist entries; the export of a user with no data is `200` with empty arrays
- The audit row `data_export.created` (actor and subject are the user, instance-level, metadata `{ signature_count }`) is appended in a transaction that also reads the data, so the record and the export agree
- The JSON for a seeded subject (fixed clock) is asserted with `toMatchFileSnapshot` in the dedicated API snapshot directory. Hostile-name test: every entry of `HOSTILE_NAMES` (E09-S01) appears as a `JSON.parse`-stable string, byte for byte, in `personalData.name`
- Network values (`ipAddress`, `userAgent`) appear only when stored (E13-S05), and `null` otherwise

**E16-S07 — Privacy notes for operators** ⬜ Todo
Operators of a self-hosted instance get a plain description of the personal data it holds and what they must do about it, kept true by a test.
Acceptance criteria:
- `docs/privacy.md` exists and is linked from `docs/security.md` (Security and privacy section) in the same change. It states at the top that it is operational guidance and not legal advice, and that the operator decides lawful basis, controller and processor roles, and retention with counsel
- A data inventory table, between the markers `<!-- inventory:start -->` and `<!-- inventory:end -->`, with the header `| Column | Purpose | Visible to | Retention | Erasable |` and the separator `|---|---|---|---|---|`, has one row per personal-data column: at least `users.login`, `users.name`, `users.avatar_url`, `signer_pii.name`, `signer_pii.email`, `signer_pii.login`, `signer_pii.ip_address`, `signer_pii.user_agent`, `allowlist_entries.login_snapshot` and `sessions.verified_emails`
- A drift test (`src/server/docs/privacy-inventory.test.ts`) migrates a PGlite database, parses the inventory table, and fails when a live column whose name matches `name`, `email`, `login`, `avatar`, `ip_address`, `user_agent` or `snapshot` is in neither the inventory nor an explicit `NOT_PERSONAL` map in the test (each entry with a one-line reason, for example `installations.account_login`: organisation login, not a signer). It also fails when the inventory lists a column that no longer exists
- Sections cover: what is never collected (user tokens, request bodies, IP and user agent unless `RECORD_NETWORK_METADATA=true`, with the legitimate-interest and short-retention requirement and the `NETWORK_METADATA_RETENTION_DAYS` setting); the erasure runbook (preview, execute, what stays and why: the signature core is kept as legal-claims evidence, GDPR Art. 17(3)(e)); answering an access request with `GET /api/me/export`; and the audit log, which is append-only, holds numeric ids only and is never purged
- A backups section states that erased data survives in backups until they expire, that restoring a backup taken before an erasure brings the personal data back, and that operators must keep an external list of erased GitHub ids (ids only, no other data) and re-run the erasure after any restore. It also states that the one free-text field a maintainer writes, the commit override `reason`, must not contain personal data (revocation reasons are a fixed code set and cannot)
- A multi-org section states that erasure is per installation, that each org's maintainers see only their own audit log and exports, and that an instance operator with database access can see everything, so operators should tell org maintainers who has that access
- The retention table in the document matches the code defaults (`NETWORK_METADATA_RETENTION_DAYS` default 30, maximum 90; audit log and signatures kept indefinitely; sessions per E10 expiry); a test reads the default from the env schema and compares it with the number in the document
