# E18 — Contributor and maintainer screens

**Bounded Context:** BC-03 / BC-06
**Priority:** 🔴 Must have
**Status:** ⏳ In progress

**Goal:** Give contributors one clear page to read and sign the CLA, and give maintainers every administration screen the MVP promises (repositories, CLA publishing, allowlist, signatures, pending PRs, overrides, audit log). Every screen renders user-controlled data inertly and is scoped to one tenant (one GitHub App installation, that is one organisation or account served by this instance) at a time.
**Depends on:** E12, E13, E14, E15, E16, E17.
**Out of scope:** The endpoints, validation and authorization behind each screen (E12 to E16; this epic fixes only the fields it needs from them, listed in the stories). The Playwright harness, the container image pin and the CI job (E20-S06 and E20-S07; the screen specs and baselines are E18-S12, which uses the routes, roles and labels defined here, so no `data-testid` attributes are required). A manual re-evaluate button (a pull request is re-checked by the `/recheck` comment of E09, or by the automatic jobs of E14 and E15). Corporate CLA screens (E21). Merge queue, badge and public verification pages (E22). The first-run setup page (E19). Contributor self-service revocation or erasure (admin-run in the MVP, see E15 and E16). Languages other than English.

**E18-S01 — Sign page: read the CLA and consent** ✅ Done
Route `/sign/$githubRepoId` (the numeric GitHub repository id, stable across renames) with the optional search parameter `pr` (pull request number): this is the sign link that E09 puts in the PR comment and E13-S02 resolves.
Acceptance criteria:
- The page loads `GET /api/sign/:githubRepoId?pr=` (E13-S02) through the typed client and shows the document name, the version as `major.minor`, the publication time (`<Timestamp utc>`) and the CLA text through `<MarkdownView>`. The page has exactly one `h1` (the document name, via `UserText`); headings inside the CLA are demoted by one level.
- `<MarkdownView>` (`src/web/components/markdown/`) renders the sanitised hast tree from `renderClaTree` (E12-S07) into React elements and adds no markdown library of its own, so the sanitisation rules (no raw HTML, `http:`, `https:` and `mailto:` links only, anchors with `rel="noopener noreferrer nofollow"` and `target="_blank"`, images replaced by their alt text) are defined once and `dangerouslySetInnerHTML` is never needed. The same component renders the editor preview and the history view (E18-S05, E18-S11). Tests feed the E12-S07 hostile-input table through the component: raw `<script>`, `<img onerror>`, `[x](javascript:alert(1))`, `data:` links and nested HTML leave no `script`, `img` or unsafe `href` in the DOM, and the placeholder `<company name>` stays visible as text.
- The page shows the text fingerprint as `sha256:` plus the first 12 characters of `content_sha256`, with the full value in a `<details>` disclosure and the sentence that the hash covers the exact source text shown.
- The consent form uses React Hook Form with the zod schema of E13's sign request from `src/shared`. Fields: a required checkbox whose label is the consent text returned by the server (its `consent_text_id` is sent back unchanged); a typed full name (`autocomplete="name"`, trimmed, 1 to 200 characters); and a `RadioGroup` of the verified GitHub emails from the context response, preselected only when there is exactly one. Free-typed email is not possible.
- The submit request carries the version id and `content_sha256` of the text on screen, so E13 can verify them server-side. The button is disabled until the form is valid, shows `loading` while pending, and a double click or Enter key repeat results in exactly one request (MSW counts requests).
- Success (`201`, or `200` with `created: false` when the same major was already signed in another tab) replaces the form with a confirmation: heading with focus, signing time in UTC, version, the typed name via `UserText`, and, when the context carries a `prUrl` that starts with `https://github.com/`, a link to the pull request. It states that the check on the pull request will update shortly and that the page can be closed. The form values are discarded, so browser back never shows a filled form.
- Validation errors from the server (`422` with `invalid_name`, `email_not_verified` or `no_verified_email`, E13-S03) are shown on the matching `Field`; `409 stale_version` is handled by E18-S02, and every other failure goes through `ErrorState`. Pending state never loses the typed name.
- Hostile-name tests: every value of `HOSTILE_NAMES` (E09-S01) as typed name, document name and rationale renders inert in the form, the confirmation and the `h1`. The page passes `expectNoA11yViolations`; the CLA text region is a labelled `article` with `tabIndex={0}` so keyboard users can scroll it.

Built as: `src/web/sign/` (route `/sign/$githubRepoId?pr=`, `SignPage`, `ConsentForm`, `Confirmation`, `Fingerprint`; a `?pr=` that is not a positive integer is dropped and the page still loads) and `src/web/components/markdown/` (`MarkdownView` over `renderClaTree`, drawn by `drawTree` with no attribute copied from the tree). `react-hook-form` is the one new dependency (MIT, no peer beyond React). The hostile CLA table moved to `src/shared/test-support.ts` (`HOSTILE_CLA_ROWS`) so the E12-S07 test and the component test read the same rows. `Heading` gained `ref` and `focusable` so the confirmation heading can take focus. `409 stale_version` and `409 no_active_cla` are states of their own since E18-S02; `422 hash_mismatch` still shows the general `errors.unknown` message in the `ErrorState`.

**E18-S02 — Sign page: login, already-signed, stale and blocked states** ✅ Done
Every non-happy path of the sign page is a distinct state with its own heading, message and next action.
Acceptance criteria:
- Unauthenticated: the context endpoint answers `401`, so no CLA text is ever loaded; the page explains what signing involves and offers "Log in with GitHub" with `return_to` equal to the current relative URL including `pr`. After the login round trip (MSW toggles the session) the same page loads with the same search parameters.
- `state: already_signed`: the page shows version and signing time (UTC) from `signature`, "No action needed", a link to the pull request when `prUrl` is present, and a link to `/me/signatures`. No form is rendered.
- `state: resign_required`: the page shows a notice naming the signed major (`signature.major`) and the new version, and the rationale of the new version (`version.rationale`) via `UserText`, then the form. `state: ready` with a non-null `revoked` shows a notice that revocation applies to future pull requests only, then the form.
- Stale: a `409` with code `stale_version` on submit keeps the typed name, unchecks the consent box, and shows a banner "The CLA changed while you were reading". Its "Review the new version" button refetches the context (the response carries `current`, E13-S04) and scrolls to the top. A `409 stale_consent` is handled the same way. Test: after a stale response no request is ever sent with the old hash, and consent must be given again.
- `canSign: false` with `blockedReason: no_verified_email`: the form is replaced by instructions and a link to `https://github.com/settings/emails`, plus a "Check again" button that refetches. There is no field to type an email.
- No active CLA: `409 no_active_cla` (no document attached or no published version) renders a neutral message and no form. `404` renders the not-found `ErrorState` with the request id, identical for an unknown repository, a suspended tenant and a tenant the instance does not admit, so the page reveals nothing about which tenants exist.
- `429` shows the countdown state of `ErrorState` and keeps the form values. Errors are announced with `role="alert"`, informational states with `role="status"`, and focus moves to the state heading on each transition (user-event test).
- The state table is exhaustive: the context response `state` (`ready`, `resign_required`, `already_signed`) and `blockedReason` are zod enums and the component switches over them with a `never` check, so a new value from E13 fails `tsc`. One MSW-driven test per state asserts the visible heading, the presence or absence of the form, and axe cleanliness.

Built as: `src/web/sign/`. `SignPage` sorts a failed first load: `401` is `LoginPrompt` (the page's `h1`, a `status` region, the three steps of signing and "Log in with GitHub" whose `return_to` is `signReturnTo(githubRepoId, pr)`, built from the parsed route values so a dropped `?pr=` stays dropped), `409 no_active_cla` is `NoActiveCla` (also when it comes from the reload of a page that had data, or from the sign request), and everything else is `ErrorState` at level 1, so `404` shows the request id and the catalog text only. A loaded context goes through `situationOf` (`sign-situation.ts`): one `switch` over `state` and one over `blockedReason`, neither with a default branch and both with a return type that has no `undefined`, so a value added to either zod enum fails `tsc` (`sign-situation.test.ts` also fails until its rows cover the contract). The situation picks a notice (`SignNotice`: already signed with version, time and the links; new major with `signature.major`, the version in force and the rationale through `UserText`; revocation applies to future pull requests only) and an action (`ConsentForm`; `NoVerifiedEmail` with the link to `https://github.com/settings/emails`, "Log in again" and "Check again"; `CannotSign` for `canSign: false` with no reason; nothing for `already_signed`). A stale or `stale_consent` refusal withdraws the consent, keeps the name, shows `StaleBanner` (alert, heading focused) and blocks every submit until "Review the new version" has loaded the context in force or the text on screen changed; the identity of the text is now the version id, its hash and the consent id, so a changed consent sentence is also withdrawn. Focus moves to the heading of the new state when the state changes after the page opened (`useFocusOnChange`) or when a state appears because of an action (`useFocusOnMount`); the state that is there on load does not take focus. Deviations: the rationale row moved from the header into the notice, `/me/signatures` was a plain anchor until E18-S03 registered the route (it is a router link since), "Check again" re-reads the verified addresses that the session captured at login (E13-S02), so the instructions also offer "Log in again", and `Heading` takes `ref={undefined}`.

**E18-S03 — My signatures** ✅ Done
Route `/me/signatures` (`authenticated`).
Acceptance criteria:
- Lists the signed-in user's own signatures from `GET /api/me/signatures` (E13-S06): document name (`UserText`), the account login snapshot of the installation it belongs to (a `Suspended` badge when `installation.suspended`), version `major.minor`, signing time (UTC), source repository and pull request when recorded, and a status `Badge` from `state`: `Active`, `Revoked` (with the revocation date) or `Outdated` (a newer major is required).
- The endpoint is keyed on the session's numeric GitHub id; the page sends no user id parameter at all (MSW asserts the request URL carries none), so one user cannot ask for another's list.
- `Outdated` and `Revoked` rows link to the item's `resignPath` (`/sign/$githubRepoId`) when it is not `null`; `Revoked` rows also show the revocation date. No revocation reason is shown, because the API never returns one to the signer.
- Newest first, cursor pagination with `CursorPager` (page size 25), the cursor stored in the `cursor` search parameter so reload and back work; an invalid cursor value falls back to the first page.
- Empty state: "You have not signed any CLA yet" with a short explanation. Loading, error and refetch behaviour come from `QueryBoundary`.
- A catalog notice states exactly what maintainers can see: the name you typed, your GitHub login and the verified email you chose. A "Download my data" button links to `GET /api/me/export` (E16-S06, a same-origin download); a `429` shows the countdown state of `ErrorState`.
- The table is a semantic `DataTable` with a caption. Tests: MSW with active, revoked and outdated rows, an empty list, a failing endpoint; `HOSTILE_NAMES` (E09-S01) as document names and account logins; axe.

Built as: `src/web/me/` (route `/me/signatures?cursor=`, `authenticated`; `MySignaturesPage`, `SignaturesTable` with `SignatureCells` and `SignatureStatus`, `MaintainerNotice`, `DownloadMyData`). The request is `GET /api/me/signatures?limit=25&cursor=` through `ownSignaturesRoute` and nothing else, so the address of the page cannot carry a person to the request (`?userId=` and the like are dropped by the search schema, and a test asserts the parameters of every request). `?cursor=` is a text of 1 to 1024 characters (the bound of the endpoint, read from its descriptor) and anything else is dropped; a cursor of the right shape that the server answers with `400` on a page that was opened with it (a reload, a pasted link) replaces the address with the first page, while a `400` or any failure on a click leaves the page on screen and the pager says so (`useSignaturesPage`; a failed page is asked for again by the cursor the address already holds, so the pager's Next calls `refetch`). Each page is kept under its cursor and asked for on every visit (`staleTime: 0`), so a signature made since the last visit is listed. A row's "Sign again" is a router link to `/sign/$githubRepoId` and is drawn only when the id in `resignPath` is one the sign page takes. "Download my data" is a request through the typed client (`dataExportRoute`, added to `src/shared/data-export.ts`) whose answer is handed to the browser as `cla-data-<githubId>.json` by `saveAsFile` (now with a media type argument); the document is never kept in the query cache, the mutation cache or the state of the page, and a refusal stays on screen with its countdown while the next attempt runs. Deviations: the download is a request and not a plain link, because a `429` (five an hour) must reach `ErrorState` with its countdown instead of an error document in the downloads folder; the main navigation gained "My signatures" (`nav.signatures`); the link of "already signed" on the sign page (E18-S02) is now a router link to this route. No server change: every field the screen needs was already in the E13-S06 contract.

**E18-S04 — Installations and tenant switcher** ✅ Done
Routes `/installations` and `/installations/$installationId`, where `$installationId` is the internal `installations.id` returned by E14-S01. A tenant is one installation (one organisation or account) and one instance serves several; every E18 maintainer route is registered with `staticData.access: 'authenticated'` (E17-S08), and the server filters every query by installation id whatever the URL says (E11).
Acceptance criteria:
- `/installations` lists the response of `GET /api/installations` (E14-S01): account login (`UserText`), account type, `repositoryCount` and `enabledCount`, the role as a `Badge` (`Org admin` or `Repo admin`) and a `Suspended` badge when `suspended` is true. Installations that the instance admission policy has not admitted are never returned, so the page has no "not admitted" state. When `truncated` is true a catalog notice says that repository-level roles may be incomplete. With exactly one installation the page navigates straight into it with `replace`.
- With no installation the empty state explains how to install the App; the link is the `installUrl` of `GET /api/meta` (E17-S09), rendered only when it starts with `https://github.com/apps/`, and the same link appears as "Install on another organisation" on the list. When `installUrl` is `null` the empty state tells the operator to finish the first-run setup (E19) instead.
- `Suspended` shows a read-only banner "Suspended on GitHub; signatures are retained", and the write controls of the other screens are disabled for that tenant (the server answers `409 installation_suspended`). A `502 github_unavailable` or `503 github_rate_limited` from the list renders `ErrorState` (with the countdown for `503`) and never an empty list, which would read as "you administer nothing" (E14-S01).
- The shell's `headerSlot` (E17-S09) holds a tenant switcher listing the same installations, with `aria-current` on the active one. Choosing another installation navigates to the same sub-page of that installation when it exists, otherwise to its repository list.
- Cross-tenant isolation tests (mandatory): every installation-scoped query key starts with `['installation', installationId]`; with MSW serving different data per installation, switching from A to B never renders any A row, including while B is loading (B shows `LoadingState`; `placeholderData` is not used); logout clears the cache; opening an installation the user cannot access shows E11's `forbidden` or `not_found` state and renders no data.
- Hostile account names (`HOSTILE_NAMES`, E09-S01) render inert in the list, the switcher and `document.title`; axe passes on the list and on the switcher in its open state.

Built as: `src/web/installations/` (routes `/installations` and `/installations/$installationId`, both `authenticated`; `InstallationsPage`, `InstallationList`, `InstallationsTable`, `NoInstallations`, `TenantOverview`, `TenantLayout`, `SuspendedBanner`, `TenantSwitcher`). The list and the switcher share one query (`installationsQueryOptions`, key `['installations']`); every query of one tenant starts with `installationKey(id)` = `['installation', id]` (the overview asks `GET /api/installations/:id/repositories?limit=10` under `['installation', id, 'repositories', {limit}]`), none uses `placeholderData`, so a tenant that is loading shows `LoadingState` and never the rows of the one before, and logout clears the whole cache. The id in the address is a positive integer or the route does not match; an installation the person cannot open is answered by the server with the same uniform `404` as one that does not exist, and the page shows `ErrorState` with no data (the summary of the list only decorates: title, banner, badge). A single installation is entered with `<Navigate replace>`, behind `LoadingState`. `installUrl` of `GET /api/meta` is read through `installLinkOf` (`link` only for the `https://github.com/apps/` prefix, `setup` for `null`, `unknown` while it is not loaded or for anything else, which draws nothing); the link opens in a new tab with `rel="noopener noreferrer"`. `502 github_unavailable` and `503 github_rate_limited` are domain codes of `src/shared/error-codes.ts` now, have their own messages, and `503` carries the countdown (`waitSeconds` reads `Retry-After` for `429` and for that `503`). The switcher is `tenantPage(title)` = `withAccess('authenticated', { title, headerSlot: <TenantSwitcher /> })`: a disclosure button that opens a list of links with `aria-current` on the active installation, closed by Escape, a click or focus outside; the target is `switchTarget(TENANT_SECTIONS, TENANT_START, here, role)`, the same screen when the table holds it for the role in the chosen installation, else `TENANT_START`. The tab title of a tenant screen is "<screen>: <account login> · CLA" through `usePageSubject` (a context set by `AppShell`, with `visibleText` on the login so a hostile name stays inert in the title and in the live region). Deviations: the overview of an installation (account facts, role, suspended badge, the first ten repositories with `enabled`) stands where the repository list of E18-S10 will be, because no screen of an installation exists before it, and `TENANT_START` is the one line that story repoints; the write controls of the other screens are not built yet, so the banner states the rule and `useInstallation(id)?.suspended` is the single flag they read; `QueryBoundary` gained `errorLevel` so that the error of a screen that has no heading of its own is its `h1`; the main navigation gained "Installations" (`nav.installations`); `Org admin` and `Repo admin` are badge statuses (`org_admin`, `repo_admin`). No server change: every field was already in E14-S01.

**E18-S05 — CLA documents, editor and publisher** ✅ Done
Routes `/installations/$installationId/documents` and `/installations/$installationId/documents/$documentId` (tabs "Editor" and "History", the latter built in E18-S11). No legal text ships by default: the editor starts empty or from the active version, never from a template.
Acceptance criteria:
- Documents list from `GET /api/installations/:installationId/documents` (E12-S01): name, scope (installation-wide or a repository `full_name`), kind (only `individual` until E21), active version `major.minor` with publication time, and a "Draft saved" badge from `hasDraft`. "New document" opens a dialog (name 1 to 100 characters, scope select: installation-wide or one repository) calling the create endpoint; the codes `invalid_name`, `document_name_taken`, `document_limit_reached` and `kind_not_supported` show on the matching field. A repo admin reaches repository-scoped documents through the repository screen (E18-S10), which uses `GET .../repositories/:repositoryId/documents`.
- Editor tab: a monospace `Textarea` and a live preview rendered with the same `<MarkdownView>` contributors see, prefilled from the server draft (`GET .../documents/:documentId/draft`) and otherwise from the active version, with the size shown against the limit E12 returns. Drafts live on the server and are shared by every admin of the scope; nothing is written to Web Storage. Saving is an explicit "Save draft" (`PUT .../draft` with `expectedRevision`), never automatic, and "Discard draft" uses an `AlertDialog` and `DELETE`. Unsaved local edits trigger a router blocker and `beforeunload`.
- `409 draft_conflict` (another admin saved meanwhile) keeps the local text in the editor and shows a banner with "Load latest", which replaces the text only when the admin chooses it. A `422` content error from E12-S02 is shown under the editor with its code message.
- "Publish" is enabled only when the local text equals the saved draft (otherwise the dialog asks to save first) and opens a dialog: a `RadioGroup` `minor` (clarification or typo; existing signatures stay valid) or `major` (everyone must sign again; forced and pre-selected when no version exists, `first_version_must_be_major`), a required rationale (trimmed, 1 to 2000 characters), the resulting version number computed from the active version (display only, the server is authoritative) and the SHA-256 of the text computed in the browser with `crypto.subtle.digest`, shown as a preview.
- Re-signing confirmation: a `major` publish sends `{ source: { type: 'draft', revision }, bump, rationale, expectedActiveVersionId }`. On `409 resign_confirmation_required` the dialog shows `details.affectedSignatures`, requires a checkbox "I understand that these contributors must sign again", and resubmits with `acknowledgeResigning: true`. The confirmation states that a published version is immutable and cannot be edited or deleted; a mistake is fixed by publishing a new version.
- Outcome states, each with a test: `201` shows the new active version, clears the draft state and, when `requiresResigning` is true, a banner that checks on open pull requests will be re-evaluated; `422 content_unchanged` (a `minor` with the same text) and `409 stale_active_version` (another admin published meanwhile, with a "Load latest" action) keep the draft on screen. The publish button shows `loading` and a double click sends one request.
- Hostile CLA text and document names render inert in the editor preview and the list; roles follow E11 (a `403` keeps the text on screen); axe passes on the list, the editor and the publish dialog.

Built as: `src/web/documents/` (routes `/installations/$installationId/documents` and `/installations/$installationId/documents/$documentId`, both `authenticated` through `tenantPage`; `DocumentsPage`, `DocumentsTable`, `NewDocumentDialog` with `NewDocumentForm`, `NameField`, `ScopeRepositories` and `KindField`, `DocumentPage`, `DocumentEditor`, `EditorPanel` with `EditorText`, `EditorPreview`, `EditorButtons`, `EditorNotices` and `ReloadBanner`, `PublishDialog` with `PublishForm`, `PublishFields`, `PublishPreview`, `ContentHash`, `ResignConfirmation` and `SaveFirst`, `LeaveDialog`). The route descriptors of the documents API are in `src/shared/cla-routes.ts`, built on the paths and schemas of E12, so the screens and the server cannot drift apart. The editor opens from one query (`editorSeedQueryOptions`: the document, its draft and the text of its active version, read by the version id because the detail has no text) kept under `['installation', id, 'documents', documentId, 'editor']` with `gcTime: 0`, `staleTime: 0` and no refetch on focus or reconnect, so the text on screen is never swapped behind the person's back. Everything the editor holds (text, saved draft with its revision, active version, `conflict`, `stale`, the open dialog, the last notice) is one reducer (`editor-state.ts`) above the tabs, so the History tab of E18-S11 will not lose it. A save sends `{ contentMd, expectedRevision }` (`null` while no draft exists) and records the text that was sent, so what is typed while the request is out stays unsaved; a discard changes the text only after the `204`; nothing is optimistic and nothing is written to Web Storage. Unsaved work holds the navigation with `useBlocker` (`enableBeforeUnload`, only while dirty; `LeaveDialog` is an `AlertDialog` whose focus starts on "Stay", Escape does nothing) and the browser's own `beforeunload` prompt. `ApiError` now keeps the `details` object of the error body, parsed per rule (`document-rules.ts` tells a rule by its status and code together, `CLA_RULE_STATUS`): `content_too_large` shows the two sizes, `resign_confirmation_required` the number of signatures; the sentences are in `src/web/i18n/messages-documents.ts`, a catalog of its own spread into the main one to keep that file under the cap. Publishing sends `{ source: { type: 'draft', revision }, bump, rationale, expectedActiveVersionId }` with the rationale trimmed by `normaliseRationale`, and `acknowledgeResigning: true` only on the retry after `409 resign_confirmation_required`; the SHA-256 preview is `crypto.subtle.digest` over the canonical text (`canonicalise`), the text the server hashes, and a browser without `crypto.subtle` says so instead of failing. A double click sends one request (`useSingleFlight`, a ref guard, next to `Button loading`). Server changes, small, additive and read-only: the items of `GET .../documents` carry `hasDraft` and `repositoryFullName` (`claListedDocumentSchema`; `findDraftedDocumentIds` reads the flag for the documents of the page only, and the repository name is a sub-select on the id and the installation of the document), with entries in the tenant registry and the cross-tenant matrix. A tenant navigation (`TenantNav`, driven by `TENANT_SECTIONS` and its new `sectionLabel`) makes the screen reachable and shows "CLA documents" to org admins only. Deviations: the document screen has the one tab "Editor" until E18-S11 adds "History", because a tab with nothing behind it would be a placeholder; "Publish" is always enabled and opens the dialog, which holds the form only when the text on screen is the saved draft and otherwise asks to save first (with "Save draft" in the dialog); the scope select lists the first 100 repositories of the tenant and says so when there are more, a document of another repository being made from the repository screen (E18-S10); `document_limit_reached` is shown on the name field, where the person was typing; the editor header says "One repository" for a repository-scoped document, because `GET .../documents/:documentId` does not carry the name (the list does); the name of a new document is sent as `normaliseDocumentName` stores it.

**E18-S06 — Allowlist manager** ✅ Done
Route `/installations/$installationId/allowlist` with a scope selector (installation-wide or one repository).
Acceptance criteria:
- Lists the entries of E14-S07 (`GET /api/installations/:installationId/allowlist-entries` for the installation scope, `GET /api/repositories/:repositoryId/allowlist-entries` for a repository, which returns `own` and `inherited`): kind (`user`, `bot`, `org_members`), subject (login snapshot via `UserText` and the numeric GitHub id in `<code>`; for `org_members` the organisation), scope, who added it (`createdBy.login` via `UserText`) and when. The empty state explains that allowlisted accounts are exempt from signing, that bots are matched by account type and numeric id, and that logins are display snapshots only.
- "Add entry" dialog calls one endpoint per scope (E14-S06): the admin picks the kind and, for `user` and `bot`, types a GitHub login that is checked against the shared pattern before any request. The server resolves the login to the numeric id; the screen has no separate look-up step and no email field. On `201` the dialog closes and the new row shows the stored login snapshot and numeric id.
- Server errors map to field or dialog messages from the catalog: `422 github_account_not_found` under the login field; `422 kind_mismatch` with the hint to pick the right kind (an organisation is pointed to `org_members`); `409 allowlist_entry_exists` as an inline error with no duplicate row; `422 no_organization`; `422 members_permission_missing` with instructions to accept the updated App permissions on the organisation's installation page and a "Try again" button; `502` and `503` through `ErrorState` (with the countdown for `503`).
- `org_members` is offered once per scope and is disabled, with an explanation, for an installation whose account type is `User`. Adding it opens an `AlertDialog` stating that every current and future member of the organisation, including private members, becomes exempt.
- Remove opens an `AlertDialog` naming the entry via `UserText` and calls `DELETE .../allowlist-entries/:entryId`; an entry that is already gone (`404`) shows an info message and refetches. On a repository scope, `inherited` entries are shown in a read-only section "Applies from the installation", so the admin sees the effective list.
