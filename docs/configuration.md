# Configuration

Environment variables of the server and what the foundation guarantees. The code that reads them is `src/server/config/` (`env-fields.ts`, `env-github.ts`, `operator-ids.ts`, `auth-fields.ts`, `env-schema.ts`, `env.ts`, `github-config.ts`, `auth.ts` for the login settings, `migrate-config.ts` for `yarn db:migrate`); the start-up order is in [`architecture.md`](architecture.md) (Rules).

The server reads only environment variables, validates them with zod at start-up, and exits with the NAMES of the invalid variables (never a value). An empty variable counts as unset. No dotenv file is read.

| Variable | Default | Meaning |
|---|---|---|
| `NODE_ENV` | `development` | `development`, `test` or `production`. Production requires an `https://` `PUBLIC_BASE_URL` |
| `HOST` | `127.0.0.1` | Interface to listen on. Containers set `0.0.0.0` |
| `PORT` | `3000` | TCP port, 0 to 65535. `yarn dev` sets a random free one above 32768 unless you set it |
| `LOG_LEVEL` | `info` | pino level: `fatal`, `error`, `warn`, `info`, `debug`, `trace`, `silent` |
| `DATABASE_URL` | none, required | `postgres://` connection string of the unprivileged runtime role `cla_app`. A secret: it is masked in logs and errors |
| `MIGRATION_DATABASE_URL` | falls back to `DATABASE_URL`, except in production where it is required | Owner connection used by `yarn db:migrate` only; the app never reads it. Tables created by the runtime role would be owned by it, and an owner can disable the immutability triggers |
| `PUBLIC_BASE_URL` | `http://localhost:<PORT>` | Origin the public reaches the app on (no path); required, as `https://`, in production |
| `TRUST_PROXY` | `false` | `true`, `false`, a hop count (`1`), or a comma separated list of IPs and CIDRs of trusted proxies. A typo is a start-up error, so it never silently trusts every proxy. Set it correctly behind a load balancer or every client looks like the proxy; the rate limit keys on this address. While it is `false`, a request that carries `X-Forwarded-For` or `Forwarded` logs `trust_proxy_suspected` at most once a minute (no address, no header value) |
| `WEB_ROOT` | `dist/web`, next to `dist/server` | Directory of the built single-page app (`yarn build`), made absolute against the working directory. The server serves it unless `NODE_ENV=development` (there the Vite dev server does) and only when it holds an `index.html`; start-up logs `web.serving`, or a WARN `web.not_served` when the directory has no build, so an image that forgot `dist/web` is not a silent 404 |
| `SOURCE_URL` | `https://github.com/Axiumine/cla-gate` | The repository that holds the corresponding source of this running version (AGPL section 13): an `https://` address with no credentials, query or fragment (one trailing slash is forgiven). The footer of every page and `GET /api/meta` carry it; a fork sets its own |
| `SOURCE_COMMIT` | none | The 40 character commit this version was built from (the image build passes it). Empty, blank or `unknown` means not known: the footer then links to the repository itself and not to a tree. Anything else is a start-up error naming the variable |
| `SESSION_SECRET` | none; required in production | At least 32 characters. A secret: it signs the cookies and derives the CSRF token, so rotating it ends every login attempt in flight and invalidates every CSRF token |
| `SESSION_IDLE_SECONDS` | `28800` | Seconds a session may sit idle (8 hours). Digits only, 300 to 999999999, never above `SESSION_ABSOLUTE_SECONDS` (both names are reported otherwise) |
| `SESSION_ABSOLUTE_SECONDS` | `604800` | Seconds a session lives at most (7 days), however active. Same range |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | none; required in production | The GitHub App's client id and client secret, for the user authorization of the login. The secret is masked in logs and errors. The App's Callback URL must be `PUBLIC_BASE_URL` plus `/api/auth/callback` ([`github-app.md`](github-app.md)) |
| `GITHUB_APP_ID` | none; required in production | Digits only, 1 to 20. With the key set, start-up calls `GET https://api.github.com/app` (10 s timeout) and the id GitHub returns must equal this one. A webhook delivery that names its target (`X-GitHub-Hook-Installation-Target-ID`) is checked against it, and refused when this is unset |
| `GITHUB_APP_PRIVATE_KEY` | none; required in production | PEM, PKCS#1 or PKCS#8, with real newlines or literal `\n`; RSA of at least 2048 bits. A secret: masked in logs and errors. An invalid key is a `ConfigError` naming the variable |
| `GITHUB_APP_PRIVATE_KEY_PREVIOUS` | none; optional | The key kept during a rotation. The same key as `GITHUB_APP_PRIVATE_KEY`, in any encoding, is a `ConfigError` |
| `GITHUB_ALLOWED_ACCOUNT_IDS` | none; optional | Comma separated positive integers: the numeric GitHub account ids this instance serves besides the account that owns the App. Whitespace is trimmed, duplicates collapse, at most 100 distinct, no leading zeros; a login, a negative number, `0`, an unsafe integer, an empty element or more than 100 ids is a `ConfigError` naming the variable. Unset or empty means the owner account only; there is no wildcard; a change needs a restart |
| `OPERATOR_GITHUB_IDS` | none; optional | Comma separated positive integers: the numeric GitHub user ids of the people who operate the instance and may list its installations (`GET /api/operator/installations`). Whitespace is trimmed, duplicates collapse, at most 20; anything else, or more than 20, is a `ConfigError` naming the variable. Unset or blank means the account that owns the App when it is a user, and nobody when it is an organisation or no GitHub App is configured; set means exactly these ids (the owner is not added). An operator is not a tenant admin: see [`security.md`](security.md#auth-model). A change needs a restart |
| `WORKER_CONCURRENCY` | `4` | Integer 1 to 32: how many jobs of ONE queue run at once in this process. The cap is per queue (nine queues have a handler or a worker today, so up to nine times this number of jobs can run together), not a total; the serialisation of one pull request's evaluations is the queue's own policy, whatever the number. An invalid value is a `ConfigError` naming the variable |
| `SWEEP_INTERVAL_MINUTES` | `30` | Minutes between two reconciliation sweeps: 0, 5, 10, 15, 20, 30 or 60 (0 turns the sweep off and removes the stored schedule at the next start). Any other value is a `ConfigError` naming the variable. The sweep is scheduled only when a GitHub App and an evaluation reporter are configured |
| `NETWORK_METADATA_RETENTION_DAYS` | `30` | Whole days, 1 to 90 (digits only: `1.5`, `+30` and ` 30 ` are refused), that the optional IP address and user agent of a signature (`signer_pii.ip_address`, `signer_pii.user_agent`, E13-S05) are kept (E16-S05). The purge removes the values of older rows whether or not `RECORD_NETWORK_METADATA` is on, so switching recording off never strands old values. Any other value is a `ConfigError` naming the variable |
| `GITHUB_WEBHOOK_SECRET` | none; required in production | At least 16 characters. A secret: masked in logs and errors. Signs every delivery: the server checks `X-Hub-Signature-256` (HMAC-SHA256 over the raw body) |
| `GITHUB_WEBHOOK_SECRET_PREVIOUS` | none; optional | At least 16 characters. The secret kept during a rotation: a delivery signed with either is accepted, and one signed with this logs `webhook.secret_previous_used` (at most once a minute). The same value as `GITHUB_WEBHOOK_SECRET` is a `ConfigError` naming the variable |

In production `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_WEBHOOK_SECRET`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` and `SESSION_SECRET` are required. In development and test the GitHub adapter is simply not built when either is absent, so the server starts without credentials. At start-up the server logs `github.app_configured` with the App id and `keyFingerprints` (`SHA256:<base64>`, current key then previous; compare the value with the App settings page), or `github.app_not_configured` with the missing variable names (a warning when only one of the two is set). The login routes (`/api/auth/*`) exist only when `SESSION_SECRET`, `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are all set, so a development server still starts without them; start-up logs `auth.configured` with the two session lifetimes, or `auth.not_configured` with the missing variable names (a warning when only some of the three are set). `.env.example` lists every variable, and `env-example.test.ts` fails when it misses one. The effective admission policy is `GITHUB_ALLOWED_ACCOUNT_IDS` plus the owner account id from the start-up self-check; the log line `github.admission_policy` prints the effective ids, and `github.admission_policy_pending` says the owner is not known yet because GitHub was unreachable. The operator policy is logged the same way: `github.operator_policy` prints the effective ids, `github.operator_policy_pending` says the owner is not known yet.

Shutdown: SIGTERM and SIGINT stop HTTP first (a 10 s deadline that covers requests only), then the job queue gets a 30 s grace period to finish its running jobs; a job still running then is aborted through its signal, runs again after the restart, and the process exits with code 1 (a clean drain exits 0). Octokit calls time out after 5 s per attempt (GETs repeat twice after 1 s and 2 s) and the self-check and token requests after 10 s; the 10 s of `GITHUB_APP_ID` above is the start-up `GET /app` only. The job queue needs no other variable: it uses `DATABASE_URL`.

What the foundation guarantees: every response carries a strict CSP (everything `'self'`, no inline script or style, and `img-src 'self' https://avatars.githubusercontent.com` for the avatars of GitHub users, the one origin besides our own; the fonts are the system stack, so there is no `font-src`) and the other helmet headers (HSTS only for `https://` origins); every request gets an `x-request-id` (a well-formed incoming one is kept, otherwise a UUID; the webhook route always mints its own) that appears in the log lines and in the error body; error bodies are `{ "error": { "code", "message", "requestId" } }` (plus `details`, a plain JSON object, when a route throws `AppError(status, code, details?)`) with the standard status text, so an exception message never reaches a client, and that holds for failures that never reach a route too (an invalid URL escape, an over-long parameter, garbage on the socket, oversized headers: Fastify's `frameworkErrors` and `clientErrorHandler` answer them with the same body, the request id and the same security headers); logs never hold headers, cookies, query strings, bodies or secrets. The HTTP server has explicit limits (`adapters/http/limits.ts`): 30 s for a silent socket and for a whole request, 10 s for the headers, a 65 s keep-alive, 1000 requests per connection and a 1 MiB body (a route that needs more, such as the webhook, raises it for itself). SIGINT and SIGTERM drain in-flight requests, but after 10 s (`shutdownTimeoutMs`) the open connections are dropped and the exit code is 1; a second signal does it at once. `GET /healthz` is liveness (touches nothing: no database and no session lookup, whatever cookie the browser sends), `GET /readyz` is readiness (the database answers `select 1` and the job queue is started with every declared queue present, each within two seconds, else `503 {"status":"unavailable"}`; see [The job queue](architecture.md#the-job-queue)). `GET /api/meta` (E17-S09) is public, reads no session and no database, and answers `{ sourceUrl, commit, installUrl }` with `cache-control: public, max-age=300`: the two source variables above and the address where the App is installed (built from the slug the start-up self-check verified, `null` while the App is not configured or not yet verified). The client address is neither logged nor stored (network metadata stays off unless a configuration flag asks for it).
