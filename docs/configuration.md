# Configuration

Environment variables of the server and what the foundation guarantees. The code that reads them is `src/server/config/` (`env-fields.ts`, `auth-fields.ts`, `env-schema.ts`, `env.ts`, `auth.ts` for the login settings, `migrate-config.ts` for `yarn db:migrate`); the start-up order is in [`architecture.md`](architecture.md) (Rules).

The server reads only environment variables, validates them with zod at start-up, and exits with the NAMES of the invalid variables (never a value). An empty variable counts as unset. No dotenv file is read.

| Variable | Default | Meaning |
|---|---|---|
| `NODE_ENV` | `development` | `development`, `test` or `production`. Production requires an `https://` `PUBLIC_BASE_URL` |
| `HOST` | `127.0.0.1` | Interface to listen on. Containers set `0.0.0.0` |
| `PORT` | `3000` | TCP port, 0 to 65535. `yarn dev` sets a random free one above 32768 unless you set it |
| `LOG_LEVEL` | `info` | pino level: `fatal`, `error`, `warn`, `info`, `debug`, `trace`, `silent` |
| `DATABASE_URL` | none, required | `postgres://` connection string of the unprivileged runtime role `cla_app`. A secret: it is masked in logs and errors |
| `MIGRATION_DATABASE_URL` | falls back to `DATABASE_URL`, except in production where it is required | Owner connection used by `yarn db:migrate` only; the app never reads it. Tables created by the runtime role would be owned by it, and an owner can disable the immutability triggers |
| `PUBLIC_BASE_URL` | `http://localhost:<PORT>` | Origin the public reaches the app on (no path); required, as `https://`, in production |
| `TRUST_PROXY` | `false` | `true`, `false`, a hop count (`1`), or a comma separated list of IPs and CIDRs of trusted proxies. A typo is a start-up error, so it never silently trusts every proxy. Set it correctly behind a load balancer or every client looks like the proxy; the rate limit keys on this address. While it is `false`, a request that carries `X-Forwarded-For` or `Forwarded` logs `trust_proxy_suspected` at most once a minute (no address, no header value) |
| `SESSION_SECRET` | none; required in production | At least 32 characters. A secret: it signs the cookies and derives the CSRF token, so rotating it ends every login attempt in flight and invalidates every CSRF token |
| `SESSION_IDLE_SECONDS` | `28800` | Seconds a session may sit idle (8 hours). Digits only, 300 to 999999999, never above `SESSION_ABSOLUTE_SECONDS` (both names are reported otherwise) |
| `SESSION_ABSOLUTE_SECONDS` | `604800` | Seconds a session lives at most (7 days), however active. Same range |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | none; required in production | The GitHub App's client id and client secret, for the user authorization of the login. The secret is masked in logs and errors. The App's Callback URL must be `PUBLIC_BASE_URL` plus `/api/auth/callback` ([`github-app.md`](github-app.md)) |
| `GITHUB_APP_ID` | none; required in production | Digits only, 1 to 20. With the key set, start-up calls `GET https://api.github.com/app` (10 s timeout) and the id GitHub returns must equal this one |
| `GITHUB_APP_PRIVATE_KEY` | none; required in production | PEM, PKCS#1 or PKCS#8, with real newlines or literal `\n`; RSA of at least 2048 bits. A secret: masked in logs and errors. An invalid key is a `ConfigError` naming the variable |
| `GITHUB_APP_PRIVATE_KEY_PREVIOUS` | none; optional | The key kept during a rotation. The same key as `GITHUB_APP_PRIVATE_KEY`, in any encoding, is a `ConfigError` |
| `GITHUB_ALLOWED_ACCOUNT_IDS` | none; optional | Comma separated positive integers: the numeric GitHub account ids this instance serves besides the account that owns the App. Whitespace is trimmed, duplicates collapse, at most 100 distinct, no leading zeros; a login, a negative number, `0`, an unsafe integer, an empty element or more than 100 ids is a `ConfigError` naming the variable. Unset or empty means the owner account only; there is no wildcard; a change needs a restart |
| `GITHUB_WEBHOOK_SECRET` | none | Placeholder: validated when set, required by the slice that uses it |

In production `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` and `SESSION_SECRET` are required. In development and test the GitHub adapter is simply not built when either is absent, so the server starts without credentials. At start-up the server logs `github.app_configured` with the App id and `keyFingerprints` (`SHA256:<base64>`, current key then previous; compare the value with the App settings page), or `github.app_not_configured` with the missing variable names (a warning when only one of the two is set). The login routes (`/api/auth/*`) exist only when `SESSION_SECRET`, `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are all set, so a development server still starts without them; start-up logs `auth.configured` with the two session lifetimes, or `auth.not_configured` with the missing variable names (a warning when only some of the three are set). `.env.example` lists every variable, and `env-example.test.ts` fails when it misses one. The effective admission policy is `GITHUB_ALLOWED_ACCOUNT_IDS` plus the owner account id from the start-up self-check; the log line `github.admission_policy` prints the effective ids, and `github.admission_policy_pending` says the owner is not known yet because GitHub was unreachable.

What the foundation guarantees: every response carries a strict CSP and the other helmet headers (HSTS only for `https://` origins); every request gets an `x-request-id` (a well-formed incoming one is kept, otherwise a UUID) that appears in the log lines and in the error body; error bodies are `{ "error": { "code", "message", "requestId" } }` with the standard status text, so an exception message never reaches a client, and that holds for failures that never reach a route too (an invalid URL escape, an over-long parameter, garbage on the socket, oversized headers: Fastify's `frameworkErrors` and `clientErrorHandler` answer them with the same body, the request id and the same security headers); logs never hold headers, cookies, query strings, bodies or secrets. The HTTP server has explicit limits (`adapters/http/limits.ts`): 30 s for a silent socket and for a whole request, 10 s for the headers, a 65 s keep-alive, 1000 requests per connection and a 1 MiB body (a route that needs more, such as the webhook, raises it for itself). SIGINT and SIGTERM drain in-flight requests, but after 10 s (`shutdownTimeoutMs`) the open connections are dropped and the exit code is 1; a second signal does it at once. `GET /healthz` is liveness (touches nothing), `GET /readyz` is readiness (the database answers `select 1` within two seconds, else `503 {"status":"unavailable"}`). The client address is neither logged nor stored (network metadata stays off unless a configuration flag asks for it).
