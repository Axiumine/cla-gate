# Decisions and open questions

Why the project looks the way it does, and what is still open. A changed decision updates this file in the same pull request.

## Why another CLA tool

As of 2026-11 the common options are ageing or limited:

- **CLA Assistant** (SAP): not archived but near-dormant. No commits between 2023-10 and 2026-10, Node 16 / AngularJS stack. Stores the CLA as a Gist and signatures in MongoDB. Cannot invalidate or re-sign a signature (issue #380), and re-prompts on *any* Gist edit.
- **contributor-assistant/github-action**: archived 2026-03-23. Stores signatures as JSON in a repo branch. No CLA version or text hash recorded.
- **EasyCLA** (Linux Foundation): active, but a heavyweight AWS/DocuSign platform built for LF projects.

## Decisions

| Decision | Why |
|---|---|
| TypeScript `~6.0.x`, not 7 | TS 7.0 (native Go) ships no classic compiler API; 7.1 adds a different one. typescript-eslint 8.72 peers `typescript <6.1`, and Stryker's typescript-checker, `type-coverage --strict` and `check-code-caps.ts` all need the classic JS API. Revisit when those tools support the new API |
| Kysely, not Drizzle | Drizzle 1.0 is still release-candidate (breaking changes pending); Kysely 0.29 is stable and pg-boss ships a Kysely adapter. The schema types are written by hand and a test compares them with the live catalog, so drift fails the build. The tests use a small own PGlite dialect (`kysely-pglite-dialect` sends every statement through the extended protocol, which rejects multi-statement migrations) |
| PGlite for the gated test suite, real Postgres 18 in CI | Fast and hook-friendly; CI re-runs the same suite against a real Postgres 18 container started by `scripts/ci/postgres.ts` |
| CI on the maintainer's shared self-hosted runners, the fork-PR approval gate as the only protection | Maintainer decision, 2026-11-01. Approved fork code runs as the runner user on a host shared with other repositories, and a `runs-on` expression is no boundary because the workflow file comes from the PR. Approval is `all_external_contributors`; the maintainer reads the whole diff first. `release.yml` and `scorecard.yml` stay on GitHub-hosted `ubuntu-24.04`. See [`docs/ci-runners.md`](ci-runners.md) |
| Random free loopback ports, never well-known ones | Any port CI, compose, scripts or tests need is random, free at the time of use, between 32769 and 60999, bound to `127.0.0.1`; `yarn dev` and every test that listens pick one. The one exception is the application's own default `PORT` (3000, the deployment setting of `yarn start`), recorded in `docs/ci-runners.md`. Shared hosts have 5432 taken; Docker's own assignment is sequential, so not enough |
| Check Runs, not commit statuses | Pinnable to the app, richer output, built-in Re-run button |
| `SameSite=Lax` session cookie | Contributors arrive from a cross-site link (the PR comment) and must be recognised on first navigation; compensated by CSRF token and `Origin` check. Deviates from RFC 10017's `Strict` suggestion |
| Code-based TanStack routing | No generated `routeTree.gen.ts` to exclude from every gate |
| Route access is a spread helper, `withAccess`, with no default | A helper that returned the whole route would lose TanStack's type inference; spreading keeps it. The access is required (`staticData` is a required option of every route, so a route without one does not compile) and only `public` skips the login guard |
| After `queryClient.clear()` the session hook reads an epoch counter | Clearing removes the observed queries, so the consumers re-render onto the new session query only because the epoch changed; a `401` ends a session only when one is held in the cache |
| The client turns every `401` into `unauthenticated`, reads a non-2xx as the error envelope (else `unexpected_response`), caps `Retry-After` at one day, retries a query at most twice and never after a status below 500, and never retries a mutation | A `401` means log in again whatever the server's code says; a body that is not the envelope is not trusted for words; a wait of a year is a mistake; a repeated mutation could repeat a side effect |
| Error codes are keyed `errors.<code>` with the code as it is (snake_case) | The catalog key pattern allows an underscore in a segment, so a code from `src/shared/error-codes.ts` is its own key and the type checker finds a missing one |
| The blocking theme script is bundled in its own pass, `data-theme` holds only the resolved theme, there is no `light-dark()` | A classic script cannot import a shared chunk, and `system` is resolved there, before first paint, so the stylesheet only ever sees a theme. The reduced-motion rule is unlayered so it beats the utilities without `!important`, and the forced-colors border rule sits in the base layer so a component can override it. Tailwind exposes `font-ui` and `font-code` |
| Badge statuses are a typed record over `BADGE_STATUSES`; axe's `region` and `color-contrast` rules are off in jsdom | A new status fails `tsc` until it has a look. jsdom has no layout, so contrast is judged at token level (E17-S05) and landmarks are asserted in E17-S09 |
| Dotfiles and traversal answer `404`; the SPA fallback leaves out the server paths, dot segments and the webhook path | A `403` would tell a probe that the file exists. A miss under `/api` must stay the JSON envelope, never `index.html` |
| The file routes are `public` and resolve with the reply | The access table (E11-S01) records the config a route ends with, so a scope hook may declare it; the library answers a directory with `callNotFound` and no value, and the async access guard on the 404 path would let Fastify send an empty `200` first |
| Overlays use Radix `Dialog.Content` but not `Dialog.Overlay`; scrolling is locked by the class `scroll-locked` on `html` and `--scroll-lock-gap` | Radix's overlay brings `react-remove-scroll`, which injects a `<style>` element that `style-src 'self'` blocks; the class and the custom property are set through the DOM API, which the CSP does not govern |
| Zod runs `jitless` in the browser | Its default probe of `new Function('')` is a `securitypolicyviolation` on every page load under a CSP without `unsafe-eval`; the interpreted parser gives the same results |
| The coverage exclusion for MSW handler files was dropped | The handlers of the web tests are written in covered helpers; an entry that matched no file would have exempted whatever was put there later |
| `radix-ui` primitives, not shadcn copy-in | Copied components would count toward coverage, caps and FTA |
| React Compiler off in v0 | `@vitejs/plugin-react` 6 needs `@rolldown/plugin-babel` with a peer-range mismatch; lint rules for it are still enabled via `eslint-plugin-react-hooks` |
| `as` assertions need the same written reason as `any` | Hard rule 3 lists them as escape hatches, and `type-coverage --strict` penalises them. `yarn lint:hatches` requires a comment with ` -- <reason>` on the same line or alone on the line above; the coverage-ignore form is `/* v8 ignore next -- @preserve <reason> */` |
| The mutation gate runs nightly, by hand and on release tags, and skips what has not changed | A cold sharded run holds a shared runner for hours (one at a time since 2026-11-03, two before), so one per merge would saturate the three; the nightly run (always `--force`) is the safety net, a manual run and a `v*` tag run it on demand, and a shard whose newest earlier nightly run on the same commit passed is skipped, so the nightly run pays only when something moved (E20-S04, maintainer decision of 2026-11-02). The lookup fails open: a lost record costs time, never coverage |
| Gate tools join as informative CI jobs, then become required one at a time | A job that has never run on the shared runners could block every merge. E20 wires `semgrep`, `trivy`, `postgres`, `mutation`, `e2e`, `leaks` and `qodana`; the promotion of the first six to required checks follows a stability definition and a template (E20-S09, [`CONTRIBUTING.md`](../CONTRIBUTING.md), Repository protection). `leaks` and `qodana` are never required |
| `.trivyignore` accepts CVE-2026-102990 until 2027-01-15 | `basic-ftp` 5.3.1 is a dev-only dependency of `memlab` (memlab, puppeteer, proxy-agent, get-uri, basic-ftp). It parses FTP directory listings, which only a PAC proxy script fetching over `ftp:` would reach; the leak scenarios load loopback fixtures and configure no proxy. `get-uri` still asks for `^5`, so only a new `puppeteer` release fixes it: remove the entry then. The `memlab` CLI package stays only through `ignoreDependencies` in `knip.json` |
| No user tokens stored | Least privilege and liability; identity is read once at login |
| `octokit` 5.0.5 for the GitHub client | MIT and ESM-only (transitive licences MIT, ISC, Apache-2.0), AGPLv3-compatible. Its retry plugin is registered with `retries: 0` and its throttling plugin is disabled: our own limiter decides (per installation, which the plugin cannot do). The `User-Agent` is `cla-gate/<package.json version>`, `0.0.0` until the maintainer sets releases |
| A rate-limit 403 is an outage, never "forbidden" or "removed" | A caller that reads 403 as "no access" (a repository that left the installation) would take a limit for a removal. The limiter waits out up to 60 s twice, then `GitHubRateLimitedError` goes to the job layer (E07-S03) |
| The token mint is a POST and the client does not repeat it by itself; tokens are never persisted | Only GETs are repeated (1 s, then 2 s); the mint goes through the rate limiter as a write and is repeated after a short limit only. A restart mints again on first use |
| The App owner is always served; admission is keyed on the numeric account id; no wildcard | `GITHUB_ALLOWED_ACCOUNT_IDS` is a finite list, so opening an instance to every account cannot be expressed. Admitting is audited as `installation.admitted` so every state change has an audit row. An account that is neither a user nor an organisation (read as type `Other`) is recorded as rejected whatever its id: ids of different kinds of account are no promise about each other |
| The installation sync runs in two transactions with the list fetched between | The stored gate reads through a pool of 10 connections, so holding a transaction across an HTTP call could starve it. A sync that writes nothing changes nothing, not even `last_synced_at` |
| JSON-only state changes | The `text/plain` parser is removed and every other body type gets `415 unsupported_media_type`, so a cross-site HTML form post cannot reach a route; a request no route answers stays `404` |
| The login attempt cookie carries the start time; names are cut by code points; a NUL in a name rejects the login; a refused emails endpoint fails the login | `t` lets the server refuse an attempt older than 600 s whatever the browser keeps; a cut by UTF-16 units could split an emoji; Postgres `text` cannot hold NUL; verified addresses are the point of the login, so a login without them would only fail later at the sign page |
| Budgeted GET routes have no HEAD twin, and 404s are limited from an early hook | `@fastify/rate-limit` keeps one store per registered route, so an automatic HEAD route would double the budget; a request no route answers carries no plugin hook, so an early hook gives it the global budget before anything reads the session |
| The webhook route lives at `/webhooks/github`, outside `/api` | GitHub calls it without a session, so it has no place among the `/api` routes the audit guard (`requireAuditedRoutes`) covers: it mutates no audited state (the delivery row is operational), and the jobs it starts write their own audit rows. It still declares `auditExempt: 'webhook'`. The path is `WEBHOOK_PATH` in `src/shared/routes.ts`, which E10 (CSRF exemption), E11 and E19 import; E10 matches the exemption on the routed path (`request.routeOptions.url`), not on `request.url` |
| Operator hints travel in `AppError` `details.hint`; the message stays the status text | The E04 contract keeps an exception message from ever reaching a client. Codes added by the intake: `webhook_signature_invalid`, `webhook_payload_too_large`, `webhook_header_invalid`, `webhook_unsupported_media_type`, `webhook_wrong_app`, `webhook_payload_invalid`, `webhook_enqueue_failed`, `webhook_throttled`, `webhook_timeout`. A BOM-prefixed body is refused as JSON |
| Payload limits of the webhook schemas | `action` is bounded (64 characters, no NUL or lone surrogate) because it is stored in a text column; head SHAs must be 40 lower-case hex; the `X-GitHub-Event` header, not the body, selects the schema; unknown keys are stripped |
| The `/recheck` prefilter is loose by design; a check that is not ours is `foreign_check` | The router keeps a substring match and a sender that is not a Bot, to avoid a job per comment; the job applies the exact-line rule after re-fetching the comment (E07-S07). A `check_run` event whose check is not `license/cla` is `foreign_check` before the action is considered. The router validates its own fields because the domain cannot import the adapter schemas |
| The tenant filter judges the stored admission state only | A policy lookup may call GitHub, which the request path never does. Repository `enabled` and `removed` are left to the job (E05-S06) so an event that arrives before the repository row exists is not lost. An unknown installation and a stale transfer state heal through a `sync-installation` job |
| The job enqueuer fails closed when no queue is wired; the pg-boss adapter is the queue | With no queue wired (a test, or a queue that is down), a delivery that starts a job is answered `503 webhook_enqueue_failed` and rolled back, so GitHub's delivery log shows the failure and a redelivery works once pg-boss is up. The port has three outcomes: `queued`, `already_queued` (a live job holds the idempotency key and will finish the delivery) and `deduplicated` (a limit dropped the send). Only a row recorded now whose send a limit dropped is marked processed. `PgBossEnqueuer` tells the first two apart and runs the shared contract suite (`services/jobs-contract`) on the fake and on real Postgres |
| The webhook path never keeps a client `X-Request-Id` | No header value of a delivery may reach the log, where the request id is written on every line. The webhook scope sets its own generator (`setGenReqId`), and Fastify asks the generator of the scope the router matched, so it holds for percent-escaped, fragment and absolute-form spellings of the path |
| The webhook route is outside the login's checks, and they are kept off it by its routed path | The route sets `csrf: 'exempt'` and `rateLimit: false`, both closed lists (`CSRF_EXEMPT`, `RATE_LIMIT_EXEMPT`) that name `POST` and `WEBHOOK_PATH`; the checks compare the routed pattern (`request.routeOptions.url`), never `request.url`, which can carry a query string, a fragment, a percent-escape or an absolute-form target. A delivery with a bad signature is therefore `401 webhook_signature_invalid`, never `403` from the CSRF layer, and the session lookup, the rate limit and the `no-store` header of `/api/auth` do not run on it. Failed signatures are throttled by the route's own throttle (E06-S07) and nothing else counts them, so an address is never counted twice |
| Every route declares who may call it; the kinds with no session are closed lists | `config.access` is `public`, `authenticated`, `webhook`, `operator` or `tenant`, and an app with an undeclared or invalid declaration does not start (`RouteAccessError`). `PUBLIC_ROUTES` and `WEBHOOK_ROUTES` are constants that a test pins to the real route table, so a new public route is a reviewed edit: the static page handler joins in E17-S03, `GET /api/meta` in E17-S09 and the setup routes in E19-S06. A path with a tenant parameter can only be a `tenant` route |
| The role deadline lives in the lookup, and a renamed login, organisation or repository fails closed | The client port waits up to 10 s per attempt and repeats a read twice, too long for a request path, so `withRoleDeadline` stops the wait at 5 s in the lookup and not in the port or the client timeout. The names are display snapshots used as the handle of a lookup, so a rename answers 404 (a denial) until the next login or sync; it is documented, not worked around |
| The 30 uncached lookups a minute of a person count every role lookup, org and repository | One budget per person keeps strangers from spending a tenant's GitHub quota, so a large repo-admin discovery can end in `429`. A `User` installation is decided by comparing ids, so it is neither cached nor counted. GitHub failing is `502`, `503` or `429`, never an allow; with no GitHub App every role call fails as `502 github_unavailable` except for the owner of a user account, and an id in a path that is not plain digits is `400` |
| An installation that GitHub refuses while the stored row is still active is the uniform `404` | A late webhook leaves the row active after GitHub suspended or removed the App. The token request fails, and the guard answers the `404` of a tenant that is not there (with the warning `installation_state_stale`) instead of a `500` that would tell an existing organisation from an unknown id |
| A suspended or deleted tenant asks no role of GitHub; the ledger of org admins is the one exception | GitHub refuses the tokens of such a tenant. The ledger (`installation_admin_seen`, 14 days) lets org admins keep reading and exporting signature evidence; the cost is that someone demoted meanwhile keeps read access for at most 14 days in that state. It is written on a live positive at most once per 60 s per pair (a database-level rule, `recordAdminSeen` moves only an entry seen a minute ago or earlier, so it holds across processes), deleted on a live negative, and written only by the lookup that is still the current one of its key, so an older answer cannot put a demoted admin back |
| `OPERATOR_GITHUB_IDS` replaces the App owner as operator, and an operator is not a tenant admin | When the variable is set the owner is not added, and blank counts as unset. The operator list is `no-store`. The tenant guard never reads the operator policy, so operating the platform grants no access to signatures or personal data |
| Self-hosted only, one instance per server, multi-org | One platform instance and one GitHub App per server, built from the checkout with `docker compose up --build` (no registry, no published image, no hosted service offered by the project). The instance serves several GitHub organisations and accounts; each is a tenant keyed on its GitHub installation id, and the instance admission policy (`GITHUB_ALLOWED_ACCOUNT_IDS`) decides which may use the server. The operator creates the App through the manifest flow on `/setup` and is the data controller |
| Container image built from the checkout (E19-S01) | The base is `node:<version>-trixie-slim` pinned by digest, `NODE_VERSION` equals `.nvmrc`, and a `base` stage holds the pin once. The runtime stage starts again from the bare Node image and holds `dist`, the production dependencies, `migrations`, `package.json` and `LICENSE`. `yarn build` is narrowed to the two shipped projects (`tsc -b tsconfig.server.json tsconfig.web.build.json`, then `vite build`) because the build context leaves out `e2e/`, which a whole-solution `tsc -b` needs; `yarn typecheck` is still the whole solution |
| Provisioning script (E19-S03) | `psql` reads the SQL from stdin, so the SQL never appears in argv, and the script maps a refusal to exit 3 by the prefix `provision-database: conflict: ` of the line the SQL prints. It guards more conflicts than the story lists (a role the connection logs in as, the bootstrap superuser, a `cla_app` that owns objects, a `pgboss` schema of another owner) and never drops anything |
| Optional TLS proxy (E19-S05) | The official Caddy image (Apache-2.0, a separate container, not a code dependency) pinned by minor version and digest, compose profile `tls`, on the stack's default network only. The application sends the only HSTS header, and Caddy trusts no upstream proxy |
| The unlock answers `200` with the CSRF token in the body (E19-S06) | A `204` cannot carry the token the page needs for its next `POST` |
| Setup credentials are shown once and never stored; the process refuses a second issue until restart (E19-S11) | No actor or audit identity exists before the App does, so there is nowhere safe to keep them. A lost secret means deleting the App on GitHub and restarting the container |
| Job idempotency is a deterministic job id, and a finished job is replaced | The idempotency key becomes the job id (a sha256 of the key shaped as a UUIDv5), so a second send meets the first job's row. A job that is over (completed, failed, cancelled) under that id is deleted and sent again, so a redelivery after a dead-letter is not lost; a live job answers `already_queued`. The runtime uses `schedule: false` and `reindex: false`, and `@opentelemetry/api` is a peer dependency of pg-boss |
| Two limits, because they answer two questions | A **coalesce key** drops a send only while a job of its key waits, because that job reads the state when it starts (the policy of a repository, a pull request); a job already running may have read the state before the change, so it does not stop the send. Before this rule the sweep-repository send was a throttle: the first send of a 60 s window won even after its run had read the policy, so a later change was lost, and on `evaluate-pr` the sweep, the policy change and `/recheck` shared one pg-boss slot per pull request and dropped each other. A **rate limit** (`dedupeKey` plus a window) is pg-boss's epoch-aligned throttle slot and stays for what must be limited whatever became of the job: `/recheck` and Re-run (one a minute per pull request). pg-boss has one `singletonKey` per job, so on a serialised queue both work per serialisation key. A coalesced check is a read then an insert, so two transactions at the same moment may both send: one redundant job, never a lost one |
| `evaluate-pr` serialises with the `singleton` policy | Decided on real Postgres by `serialisation-real.test.ts` and `serialisation-interleavings.test.ts`: it passes at most one active job per key, parallelism across keys, no lost send and recovery from a dead worker (300 s). `short`, `exclusive` and a `groupConcurrency` group were measured and fail. `finalise-check` is `singleton` with the same key in its own queue, so it is not serialised against an evaluation in flight (E14-S04 closes that) |
| Queues are created by the migrate step, and the scheduler's queue too | `createQueue` is DML unless a queue is partitioned, but only the owner creates queues, so `yarn db:migrate` creates every queue and `__pgboss__send-it` (the scheduler needs `INSERT` on `pgboss.queue` for its internal queue, and the schedule is enabled at run time). `job-dead-letter` is created before the queues that name it; `createQueue` is `ON CONFLICT DO NOTHING`, so the options of a queue that exists are converged with `updateQueue`. A queue of another policy is refused |
| The `sweep` queue is `exclusive`; the sweep is scheduled only when it can run | At most one sweep is created, retrying or active, so a tick that finds one running sends nothing. It is scheduled only when the sync and a reporter are wired. The reaper cancels a superseded stale head SHA, a failure of one repository does not fail the job, and a rate limit does |
| Handlers get the queue they run on | `JobContext.pending` (`PendingJobs`, `adapters/jobs/pending.ts`) finds and cancels the queue's own jobs, and `JobContext.enqueuer` sends jobs, so a later epic registers a handler and can send jobs without editing an E07 file. `GitHubClient.withSignal` (an E05 port addition) carries a job's abort signal into its GitHub calls. The binding for E10-S07 is `registry.register('revoke-user-sessions', ...)` through the `register` option of `jobWorkers` in `boot-jobs.ts`; a job whose ports are not configured (no GitHub App, no evaluation reporter) gets a fail-closed `unavailable` handler, and the types nobody registered yet (`revoke-user-sessions`, `finalise-*`) keep their jobs in the queue |
| The exemption lookup caches verdicts per process | Keyed by (installation id, user GitHub id) only: a member for 10 minutes, a non-member for 2 minutes, at most 10,000 entries (LRU), one cache per process built in `jobWorkers` because each run builds its service around a signal-bound client. Errors and `permission_missing` are never cached, a removed member stays exempt for up to 10 minutes, and the 60 s role cache of E11-S04 stays separate. The first build of the lookup in S04 was uncached, with a preliminary read of the signatures to prune the lookups |
| A manual re-evaluation is limited at the job and at the evaluation | One window per pull request, shared by `/recheck` and Re-run. The webhook intake sends the `recheck-comment` job under the limit, because that job spends three GitHub calls (repository, comment, pull request) before it can tell whether the comment is the command; the `evaluate-pr` send is under the same key. The idempotency keys are `recheck-comment:<commentId>` and `evaluate-head-sha:<jobId>:<pr>`. Open: a comment that only mentions `/recheck` also takes the slot of its minute (the router prefilters loosely) |
| The dead-letter handler keeps a verdict another run reached | A dead `evaluate-pr` writes `failure` only over a row with no result (or its own earlier write), because the head SHA may have been concluded by a sweep or a `/recheck` since. A dead `evaluate-head-sha` replaces any verdict: the Check Run of a re-run that died is completed as `failure` with the hint, so it fails closed. Which of the two a maintainer wants is open (see the open questions) |
| `AUDIT_ACTIONS` carries names ahead of their call sites | The catalogue test (E16-S01) requires the names the stories list, so eleven were added before any call wrote them. Each sits in `RESERVED_ACTIONS` with a reason, and the test fails both ways: a name with no call and no reason, and a reserved name that a call now writes. The SQL functions that write their own audit row (`signer_pii.erased`, `network_metadata.purged`) stay reserved for good. |
| The signature export commits its audit row before the snapshot, then recounts | The row `signatures.exported` is written in a transaction of its own before the first byte, so an aborted download is on record; the read-only snapshot counts again, and when a signature was added or revoked in between nothing is sent and the answer is `409 export_changed`. A refused or aborted download can therefore leave a row, which over-reports and never under-reports. Writing the row after the snapshot would let a download succeed with no record if the write failed, and writing it inside the snapshot would lose it when the client leaves. |
| Erasure is scoped to one installation | One org admin's request must not reach another org's data on a shared instance, so `erase_signer_pii` takes the installation. The `users` snapshot and the sessions are scrubbed only when no `signer_pii` row of the person is left anywhere, and the audit row is the installation's own. |
| Network metadata retention is an instance setting | `NETWORK_METADATA_RETENTION_DAYS` is read once for the whole instance, so the purge is instance-wide and its audit row has no installation; no tenant's audit viewer shows it. The purge runs whether or not recording is on. |
| The own-data export does not list its own audit row, names no other person, and the log has no subject index | The row `data_export.created` is written after the data is read, so the next export shows it. A `user` subject that is not the caller (the signer an org admin erased) is returned as `null`. `audit_log` has an index on the actor but none on the subject, so the rows about the person are found by a scan on `subject_type = 'user'`; at five requests an hour that is acceptable, and a partial index on `(subject_id, occurred_at desc) where subject_type = 'user'` is the answer if the log grows large. |
| The canonical CLA text | One function (`canonicalise`, `src/shared/cla-text.ts`) removes a run of leading byte order marks (a second call has none left to remove: idempotence), turns CRLF and lone CR into LF and ends the text with exactly one LF; nothing else changes, so two spaces at the end of a line stay a Markdown line break. DEL and the C1 controls are not refused. "Empty" means no JavaScript non-whitespace character. A lone surrogate is refused, because UTF-8 turns it into U+FFFD and two different texts would hash alike. The hash is over the canonical UTF-8 bytes and only `prepareClaText` computes it. |
| The depth of a CLA text is read by a line scan, not by the parser | The depth limit is 50 levels of quote and list (and of emphasis, strong text and link in the rendering). `validateClaText` runs on the request thread that serves every tenant, and micromark is quadratic for some inputs (measured: 200 KiB of `a`, `=` lines took over 100 s, lazy quote lines and `[a]` labels minutes), so a scan of the lines (`cla-markdown-containers.ts`) follows the CommonMark rules for containers in linear time. It agrees with the parser on a corpus and on generated texts; in odd corners it differs by one level (an empty marker after indented code, a definition followed by an `=` line), which is safe because the rendering measures its own tree too. A line that opens more than 100 markers is refused before the rendering parses, and relative and capitalised-scheme links are unwrapped. Open risk: `renderClaTree` still parses, so a server that renders (E21) must do it in a worker with a time limit, once per content hash, behind a cache; whether to also refuse such texts at publish is for the maintainer. |
| Five Markdown dependencies | `unified`, `remark-parse`, `remark-rehype`, `rehype-sanitize` and `hast-util-to-html` (all MIT, AGPLv3-compatible), pinned exact and older than the one-day age gate, plus the dev types `@types/hast` and `@types/mdast`. A hand-written sanitiser is the thing to avoid, and the pipeline is the standard CommonMark one; there is no `rehype-raw` and no GFM plugin, so raw HTML stays text and there are no tables or task lists. |
| A rename to the same name is a no-op | `PATCH` with the name the document already has (after normalisation) answers `200` with the document, leaves `updated_at` alone and writes no `cla_document.renamed` row: the audit log records changes. |
| The draft rate limit counts after the guard | 30 saves a minute per person, keyed on the GitHub id. In an Organization installation the guard's own `429` (E11-S04) answers first and carries no rate-limit headers. |
| A major version sweeps through E07-S09, once per version and repository | A major bump sends `sweep-repository` (`enqueueSweepRepository`) for each enabled repository attached to the document, keyed `sweep-repository:cla_version_published:<versionId>:<githubRepoId>` with no dedupe window; E07-S09 coalesces it per repository while one waits (that run reads the newer policy when it starts) and queues another once a run has started. The rationale of a version never enters the audit row, and a rollback is a new version with the old text (`rollback_requires_major` when it crosses a major with a minor bump). |
| `renderName` breaks `<!--` and the failure output carries no address | A login or a trailer name that spelled the comment marker `<!-- cla-platform:license/cla:v1 -->` would make a forged comment look like ours, so `renderName` splits `<!--` inside its code span (the name is in the shared hostile corpus, and the marker appears once in the comment body, outside every span). Trailer names reach the reporter only through `DisplayNames` and `renderName`, never the address, and nothing reporting-related stores them. |
| A bot or an organisation that is not allowlisted is listed under Not signed, with a note | The note says it cannot sign and that a maintainer can add it to the allowlist; the sign link is offered only when at least one listed person can sign. `no_active_cla` and `commit_limit_exceeded` get one fixed sentence each, with no people lists, because nobody fixes them by signing. |
| The reporter finds its own run in the listing of the head SHA, and a failed `PATCH` falls back to `POST` | A run id stored on `pr_evaluations` is a hint, and a re-run after a crash may have created a run the row never recorded, so `check_rerequested` and `/recheck` take the first own-App run of the `filter=latest` listing. A `PATCH` answered `404` or `422` (the run is gone, or GitHub will not take the update) creates a new run, logged `report.check_run_recreated`. That a `PATCH` on a completed run is accepted is not verified against GitHub (open question). |
| Pull requests that share a head SHA share one Check Run, and the worst state wins | The run belongs to the SHA. `failure` beats `in_progress` beats `success`. Only rows that are not `superseded` (the same pull request has not moved on to a newer head SHA) and whose pull request is still listed open count; an unlisted pull request stays live, because a wrong `success` costs more than a wrong `in_progress`. After a write that does not end in `in_progress` the reporter looks the run up again and writes the newest one when a concurrent report has landed in between, so two reports that race converge. |
| A close at a shared head SHA settles the run for the pull requests that remain, and does not cancel it | `reportCancelled` computes the view of the others: still `in_progress` leaves the run to a sibling's job (`report.cancel_left_to_sibling`), otherwise it writes their worst-of result (`report.settled_for_siblings`), with the counts of the first `success` row's stored details. Only a run nobody else stands at is written `cancelled`. |
| `PUBLIC_BASE_URL` must be an `http` or `https` origin the sign link can use | The sign link is built from it in every failure report, and a host that `new URL` takes but a Markdown link or GitHub cannot use (an underscore host, a `)`) would break the report at run time, not at start-up. `originField` runs `isHttpOrigin`, the same test as `signUrl`, so a bad value is refused when the configuration is read. |
| The signer's typed name must hold one visible character, and nothing else is refused beyond controls, bidirectional overrides and lone surrogates (E13-S03) | The name is the visible evidence of a signature, so a name of zero-width characters, the Braille blank, Hangul fillers, a combining grapheme joiner, a word joiner or lone combining marks is `invalid_name`; a hostile but printable name (a formula, markup, a mention) is a name and is kept as typed, each output encoding it for its own context. A lone surrogate is refused because the database cannot hold it. `cleanName` is unchanged, so document names keep their rule. |
| The signer's address matches the verified list by ASCII case only (E13-S03) | The Kelvin sign and the long s are not `k` and `s`, so a lookalike never matches; an address that differs in the case of a non-ASCII letter is `email_not_verified`. The stored address is the one GitHub reported, not the typed text. |
| `signatures.consent_text_id` names an entry of `src/shared/consent.ts`, and an id is never edited or removed (E13-S01) | An old signature must still say which wording was on screen. New wording is a new id (`individual-v2`), pinned by SHA-256 in a test; the web carries no copy and the sign request carries the id only. |
| Signing sends its evaluations in its own transaction, under `signature:<signatureId>:<githubRepoId>:<pr>`, with no coalesce key or window (E13-S07) | A job sent for a signature must never be dropped, and the singleton queue already serialises per pull request. Candidates are the latest `pr_evaluations` row per pull request by (`updated_at`, `id`) whose result is `failure` and whose details list the signer as uncovered, in repositories attached to the signed document and not removed; the cap is 25 and the lookup reads at most 100 rows. The rest is left to the sweep. |
| `resignPath` treats a repository GitHub no longer lists as gone (E13-S06) | For the source repository and for the fallback to the repositories of the document: a path that would lead to a repository the installation no longer has is `null`. |
| The list of installations is asked of every live installation, and has a budget of its own | GitHub cannot say where a person is an admin without a user token, which is never stored, so the list asks the org admin fact of each admitted, not uninstalled installation (E14-S01). The answers live 60 s, the same as the guard's budget of 30 uncached lookups a minute takes to refill, so a list that shared that budget would need one lookup more than it had on an instance of 31 organisations and answer `429` forever. It spends 300 a minute per person (`INSTALLATION_LIST_LOOKUPS`) over the same cache; a person who has used them gets what was found with `truncated: true`. The number is the maintainer's to confirm. |
| Repository admins are found for the list only through repo-scoped documents, with a shared budget of 100 probes | Probing every repository of every tenant per page load does not scale. `truncated` is a property of the request and is repeated on every row; the repositories past the budget are left out. A repository list page of a repo admin may hold fewer rows than `limit` and still have a `nextCursor`, because it keeps only the repositories GitHub confirms. A deleted installation is not listed (nothing is left to enforce), and a suspended one only for its org admins. |
| A repo admin cannot swap the organisation's document, and a detach of nothing is org admin only | The role of an attach, replace or detach is the scope of the document after the change and of the one it replaces (E14-S02), so an admin of one repository can attach or detach its own document and not take the organisation's out of use; with nothing attached the policy is the organisation's. |
| Enabling needs a published CLA, and the hint is not the message | `no_active_cla` is `409` and its fix (attach a document and publish a version) travels in `details.hint`, like every rule error; the role is judged before the missing CLA is reported, so the role decides what a person learns (E14-S03). |
| The evaluation hands a switched-off repository over instead of rolling back (E14-S04) | A `finalise-check` job does not wait for a running `evaluate-pr`. The evaluation reads `repositories.enabled` after the verdict row is stored and before it writes, writes nothing when it is off and sends a `finalise-check` after the read; it reads again after the write. The reporter is idempotent (completing a run that is `neutral` already is safe), so the last write is `neutral` in every order. A failed hand-over or report does not lose it: a failing report hands over before the job fails, and a retry that finds the repository off sends the `finalise-check` too. The write is skipped, not rolled back, and the stored verdict stays. |
| The test worlds of the enforcement routes are PGlite only | The races that need a second session (a disable against an evaluation, five simultaneous enables or adds) are made at service level on connections of their own and run in the real-Postgres CI job. |
| The erasure reaches an allowlisted account that never signed | The login an allowlist entry shows is personal data of a person who may have no signature and no `users` row (a bot, a maintainer). Migration 013 lets `erase_signer_pii` clear the snapshot for such an account and the preview and the erasure find a person by a signature or an entry; deleting the entry stays the other way to remove it (E14-S06). |
| The project badge is blue and the snippet links to the sign page of the repository without `?pr=` (E22-S03) | Blue says "a CLA applies here" without claiming a state, while green and grey are the signed and not signed badges of one person. The snippet is pasted once into a README and read for years by everyone, so it links to `/sign/{githubRepoId}`, which works with no pull request in hand; a pull request link would be stale at once. |
| The settings screen of the badge is the first route E18-S10 extends (E22-S03) | `/installations/$installationId/repositories/$repositoryId/settings` holds the opt-in toggle and the snippet with a copy button, and no link leads to it yet; E18-S10 is the story that adds the rest of the repository settings to the same route, so the route is not moved or renamed. |
| The public check has a third budget per installation (E22-S02) | The limits per client address and per repository bound one address and one repository, but any number of addresses can ask about made-up logins, and each login the memory does not know is a GitHub call on the one installation token, in the lane the evaluation jobs share. Thirty lookups a minute per installation, answered like an outage (`503` with `Retry-After`), keep the jobs their room; a cached login is free. |
| The retention sweep deletes operational rows only, with bounded settings (E22-S04) | A processed webhook delivery is kept at least 7 days (GitHub redelivers for 3, and a purged row inside that window would let a redelivery run twice) and at most 3650; a session is purged a day after it expired, so the row that explains a "your session expired" support request is still there. The days are an operator default, not legal advice. A run that fails part-way still writes `retention.swept` for what its committed batches deleted, so the audit log never lacks a deletion, and the next run continues. Signatures, CLA versions, allowlist entries and audit rows have no retention setting. |
| The operator's erasure command works through the audited function and covers every org (E22-S05) | A GitHub id is global, so a request to the operator reaches every installation in which the person has a signature or an allowlisted login. The command contains no SQL that changes a row: it calls `erase_signer_pii` per installation, so the audit row, the immutability and the Art. 17(3)(e) core are the function's and not the command's. The dry run is the default and `--execute` the deliberate act. A person with nothing in any installation, or an allowlisted account with no `users` row, is out of its reach; an org admin erases the latter through E16-S04. |
| A merge group of a repository with enforcement off is not evaluated (E22-S01) | `skipped:repository_disabled`, as for a pull request, writes no check. A queue that requires `license/cla` there waits, so the maintainer either switches enforcement on or takes the check out of the ruleset; whether the platform should instead report a neutral success is a product choice left open (see the open questions). |
| A merge group has no `pr_state`, and a revocation or an override does not re-evaluate one (E22-S01 with E15) | `merge_group_evaluations` is a table of its own and its rows are not pull requests: they are never open or closed, no view of E15 (`latestEvaluationPerPr`, the pending pull requests, the sweep's correction of `pr_state`) reads them, and `enqueueAffectedPrs` sends `evaluate-pr` jobs only. A group is judged when GitHub asks (`checks_requested`), by the same engine reading the signatures, revocations and overrides as they are then, so a revoked signature or a removed override fails the next judgement of a group that holds the pull request. A group already judged keeps its Check Run: a revocation is prospective only (hard rule 5). |
| The sweep corrects `pr_state` only for rows GitHub confirms (E15-S01) | The listing of the open pull requests is read page by page, so a pull request that closes after a page was read shifts the next page and leaves an open pull request out of the listing, and one that closed after the listing is still in it; trusting the listing closed an open pull request, which then no longer re-evaluated when its author signed. Each row the correction would change is asked about with `getPullRequest` (not found counts as closed), at most 50 pull requests in each direction in a run, the ones touched last first, after the evaluations are sent. The sweep also reopens the latest closed row of a pull request it lists, which no criterion names: it heals a missed `reopened` and a close that raced a reopen. |
| An action of a maintainer evaluates an open pull request whose evaluation is in flight again (E15-S03) | A run that is going read the signatures, overrides and policy before the action committed, so it can store a verdict on the old facts and nothing would correct it before the next push. The selection matches a latest row `in_progress` whatever the filter on result and details says, and the queue serialises the extra job after the running one. |
| A revocation, an override or an invalidation re-evaluates in the transaction of the action, up to 100 pull requests (E15-S03 to S06) | The action and its jobs commit or roll back together, and nothing waits on GitHub. Above 100 the work is one `sweep-repository` job per repository, which lists the pull requests itself. A re-evaluation of the removal of an override matches any non-null `overrideId` for the commit, not the id of the removed override, so a result that rests on an earlier override of the same commit, not yet evaluated again, is covered too. |
| A per-commit override checks the commit with the installation token, outside any transaction, in a fixed order (E15-S05) | Order: role, commit id, reason, repository switched off, then GitHub (`getCommit`, 5 s through `withGitHubDeadline`, the app option `commitGitHub`), so a person learns nothing from GitHub before the role is judged and no database connection waits on it; the role and the enabled flag are judged again under the row lock. A commit of another repository of the tenant is `422 commit_not_found`. |
| The search of signatures has a budget of 30 a minute per person and writes no audit row (E15-S02) | It shows the personal data of up to 100 signers a page. The story keeps the read out of the audit log (the audited read is the CSV export, six a minute); the budget keeps the page-by-page read from being a way round the export. |
| Epic E21 uses migrations 020 and 021 only, and 020 also creates the covered-ids index of E21-S05 | The partial index on `corporate_approvals (installation_id, agreement_id, kind)` where `revoked_at is null` serves the one statement of the evaluation; the epic had two migration numbers, so the index went into the first. Derived approvals may derive only from an active `email_domain` or `github_org` approval of the same agreement and tenant, and the insert guards of the two pii tables mirror `signer_pii_guard_insert`. |
| The corporate audit actions use the metadata keys that exist, with the agreement or the approval as the subject (E21) | `audit_metadata_is_clean` has no `agreement_id` or `approval_id` key, and replacing that function risks colliding with the migrations of other epics. The rows hold `kind`, `signature_id`, `major`, `document_id`, `repository_id`, `github_id` and `row_count` with `subject_type` and `subject_id` for the agreement or the approval: numeric ids and codes, never a company, a login, a domain or a reason. |
| An approval that expired but was not revoked is revoked as `expired` before a new one for the same subject is inserted (E21-S03, E21-S04) | The partial unique index `corporate_approvals_active_unique` is on `revoked_at is null`, so an expired row still holds the place of the person. The add, the carry-over and the claim revoke it in the locked transaction, by the manager or the person, with an audit row, instead of answering `approval_exists` or a unique violation the manager cannot resolve. The limit of 500 active approvals counts every active approval, derived ones included. |
| Choosing the corporate document of a repository sends the sweep, and a revocation of an approval or of the agreement does too (E21-S02, E21-S05) | The evaluation reads `repositories.corporate_document_id` and the approvals, so a change of either would leave the open pull requests with a stale `license/cla` until another event. The sweep carries the reason `cla_document_changed`, `corporate_claim` or `corporate_approval_revoked` under a per-action idempotency key, in the transaction of the change. |
| Both corporate CSV exports are audited (`corporate_agreements.exported`, `corporate_approvals.exported`) | They carry logins and company names, as the signature export does, so each download leaves a row before its first byte, with the number of rows when it began and nothing from the file. The count is taken in the transaction of the record and the file is read from a snapshot taken right after, so a row inserted in between is in the file and not in the count; the signature export recounts and answers `409 export_changed`, which was not repeated here. |
| The export of one's own data and the erasure cover the corporate rows (E21) | A person approved under an employer's agreement has a login snapshot and may have signed nothing: the preview and the erasure count the approvals of kind `user` that name them (`corporateApprovals`), the function deletes the snapshots, and the export lists the agreements they signed and the approvals that name them. It leaves out who approved, who revoked and the text of a reason, which are other people or typed by one. |
| `decodePunycode` is exported for the tests, and a hyphen at the very start is not a delimiter (E21) | A yes or a no cannot hold the constants of RFC 3492 (a wrong skew moves a letter to another letter), so the decoder is `@internal` and the tests compare the code points of the sample strings. The mutation check found that `-abc` was read as an empty basic part followed by digits, where the RFC reads the text from its first character, so the text is refused now. The mutants that remain are equivalent: `INITIAL_BIAS` plus or minus one (the first number reads thresholds at multiples of 36 from 72, where 71 and 73 clamp the same), `MAX_DELTA` times 63 or the comparison `>=` (the overflow is refused later by the largest code point in a label of at most 63 characters), and `point >= ASCII_LIMIT` to `>` (the one point it changes, U+0080, is not an allowed character). |

The corporate approval is the weakest basis (the employer's manager decided, not the person), so it comes last and only for accounts that can consent. The E21-S05 text said allowlist first; that text was changed, not the engine, because the other order would change the recorded basis of everyone who is on an allowlist and has signed, in the stored `pr_evaluations.details` that E15 reads. |

## Open questions

Resolved: self-hosted only (one platform instance and one GitHub App per server, built from the checkout, serving several orgs that are tenants keyed on their installation id, no hosted service offered, no published image), corporate CLA is not in the MVP (epic E21), hosting target and region are the operator's choice (the operator is the data controller).

- AGPLv3 "only" or "or later"? `AGPL-3.0-only` is assumed. GitNexus (dev tooling) is PolyForm Noncommercial, which matters if this becomes a commercial product.
- Is a Qodana licence and token available? Yes (answered 2026-11-02): an Ultimate Plus licence, a Qodana Cloud project and the secret `QODANA_TOKEN`. The `qodana` job runs on GitHub-hosted `ubuntu-24.04`, passes after the 13 findings of its first scan were fixed, and stays a check that is never required (epic E20, E20-S08).
- Legal: e-signature validity (ESIGN, eIDAS) and GDPR retention choices need counsel; this repo contains no legal advice.
- The wording of the consent sentence `individual-v1` (`src/shared/consent.ts`, E13-S01) is interface wording, not CLA text, and needs counsel review before release. It is not a blocker for building; if counsel changes it, the new wording is a new id.
- Whether a signer whose name is a single emoji or symbol should be accepted (E13-S03): the rule requires one visible character, not a letter or a digit, so a name of one emoji passes today (a sequence of the shared hostile corpus is exactly that). Tightening it to letters and digits is a product choice for the maintainer.
- Repository admin is looked up by the stored repository name (E11-S03). A repository that is renamed answers 404 and fails closed, but GitHub lets a new repository take the old name, and until the next sync rewrites `repositories.full_name` the permission call is answered about the new repository, so an admin of the new one would pass `repo_admin` for the old one. The fix is the id-addressed call `GET /repositories/{id}/collaborators/{username}/permission`, which is not documented for this resource: before the port switches to it, someone with the real App must check that GitHub serves it for an installation token (a 404 would deny every repo admin, which fails closed but breaks the feature).
- Strangers and a tenant's GitHub quota (E11-S04, E11-S05). The per-person budget is spent only when the tenant exists, so a stranger who sends about 31 writes to an installation id gets `429` for an existing tenant and `404` for an unknown one (the lookup's latency tells them apart anyway). The budget is per person, so several free GitHub accounts, each at 30 uncached lookups a minute, can spend one installation token's rate limit, which the PR checks share. Options: charge the person on every guarded tenant request, and a small per-installation cap on the denial-path lookups. Both change the E11-S04 rule that a cache hit is free and need a number, so they are the maintainer's choice.
- Job queue (E07), for the maintainer. (1) A dead `evaluate-head-sha` still replaces any verdict at its head SHA with `failure` (a re-run that died fails closed, and the Check Run that was re-requested is completed); a dead `evaluate-pr` leaves a verdict alone. Keep both, or make the re-run leave a final verdict alone too. (2) The `/recheck` rate limit sits on the intake of `recheck-comment`, and the router prefilters by substring, so a comment that only mentions `/recheck` also spends the minute of its pull request; the job's three GitHub calls (repository, comment, pull request) can still be spent once a minute per pull request. (3) pg-boss 12 has no archive step, so a failed job's history lasts the 7 days of `deleteAfterSeconds`; a longer record would need a table of our own. (4) Whether GitHub lists a fork pull request for the SHA of its fork head in `commits/{sha}/pulls` (the Re-run depends on it) is to be checked on the real App. (5) A `finalise-check` is not serialised against an `evaluate-pr` in flight; E14-S04 closes it with the `enabled` re-check in the evaluation path.
- Dashboard list at scale (E14-S01), for the maintainer. The installation list asks GitHub once per live organisation per minute and person (concurrency 5, 5 s each), so its latency grows with the number of organisations on the instance, and past `INSTALLATION_LIST_LOOKUPS` (300) it is cut short with `truncated: true`. Confirm the number; a design that starts from the person's own memberships needs a user token, which hard rule 7 forbids storing.
- The reason of the revocation of a corporate approval (E21-S03), for the maintainer. `corporate_approvals.revoke_reason` is free text of at most 500 characters in the immutable core, so it can never be erased, and the application only refuses an address (`@`); a name or a phone number can be written. Replace it with a fixed set of codes (as `signatures.revoke_reason`), or move it to an erasable column (a migration, and E21 has used both of its numbers).
- Budget of the approval routes (E21-S03), for the maintainer. The story says 60 mutating requests a minute per session; the rate limiter keeps one counter for each route, so add, revoke and carry-over each have 60 a minute (the criterion now says so, and a test pins it). A budget shared by the three needs a store of our own for the limiter, because `groupId` only changes the key.
- The operator's erasure command and the corporate approvals (E22-S05 with E21), for the maintainer. `readSignerFootprint` counts signatures and allowlist snapshots, so a person known only as an approved employee is "not found" by the command, and an installation where they hold only an approval is not listed; the audited function `erase_signer_pii` does delete the snapshots when it is called for that installation. The files and the wording of the command are those of E22; extend the footprint with the approvals of kind `user`, or accept that the org admin's erasure route is the way for these people.
- Merge groups of a repository with enforcement off (E22-S01), for the maintainer. The platform writes no check for them (`skipped:repository_disabled`), so a merge queue that requires `license/cla` on such a repository waits until enforcement is switched on or the check is taken out of the ruleset. The alternative, a neutral or successful `license/cla` on the group head for a repository that does not enforce, would unblock the queue but write a check on a repository the maintainers switched off on purpose; which of the two is wanted is a product choice, and the facts about the merge queue that are not verified against GitHub are in [`tooling-gotchas.md`](tooling-gotchas.md#open-verifications-without-a-story).
- Pending pull requests after a missed `reopened` (E15-S01), for the maintainer. A `reopened` delivery is routed to `evaluate-pr`, which records the reopening; when that delivery is lost, the pull request stays `closed` in `pr_evaluations.pr_state` until the next sweep corrects it (confirmed with GitHub), so for up to one sweep interval (and for ever with `SWEEP_INTERVAL_MINUTES=0`) it is left out of the pending view and of the re-evaluation after a revocation. Accept that, or ask the evaluation of a reopened pull request to be retried by a second delivery path?
- Reading personal data without an audit row (E15-S02), for the maintainer. The search of signatures shows the name, email and login of up to 100 signers a page to any maintainer in scope and, as the story says, appends no audit row; only the CSV export is audited. Keep it, or audit each page that returns signer data (a row per page would be noisy, a row per search session needs a session notion)?
- Contents permission for the override check (E15-S05), for the maintainer. `GET /repos/{owner}/{repo}/commits/{ref}` is documented under Repository: Contents: read, which the App does not request; verify on the real App (see [`github-app.md`](github-app.md)). Until then a 403 would be told as `502 github_unavailable`.
