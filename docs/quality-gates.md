# Quality gates

The thresholds every change must meet, the TypeScript setup behind them and the testing conventions. The scripts that run the gates are in [`development.md`](development.md); the hard rules that forbid bypassing them are in [`CLAUDE.md`](../CLAUDE.md).

## Thresholds

| Gate | Threshold |
|---|---|
| Vitest coverage (v8) | `thresholds: { 100: true }` (lines, branches, functions, statements); `reporter: ['text', 'lcov']` (the lcov file is the input of Qodana); `coverage.include: ['src/**/*.{ts,tsx}', 'scripts/**/*.ts']` so unloaded files count. **Fixed exclusion list (the only one):** `**/*.test.{ts,tsx}`, `**/*.d.ts`, test setup files, `e2e/`, `tests/leaks/`, root tooling config files. Application entrypoints stay in scope: keep them logic-free and cover them with a boot test (start the app on PGlite, hit a health route; `main.ts` and `migrate.ts` have one). `vitest.config.ts` has three projects, `scripts`, `server` and `web` (`src/web`, jsdom). The two test setup files on the exclusion list are `src/server/adapters/db/global-setup.ts` (`**/global-setup.ts`) and `src/web/test-support/vitest.setup.ts` (`**/vitest.setup.ts`, the setup file of the `web` project). Vitest runs the first once in the main process, outside the coverage-instrumented workers, so it can never be covered; it only creates and drops the throw-away database. The MSW handlers of the web tests are written in helpers that are covered (`src/web/test-support/render.tsx`, `src/web/api/test-support.ts`), so no entry exempts a directory of them: an entry that matches no file would exempt whatever is put there later (the one that did was removed in E17) |
| type-coverage | `--strict --at-least 100`, per tsconfig project |
| ESLint | `--max-warnings 0`; `complexity: ['error', 10]`; `max-lines` 500, `max-lines-per-function` 50, `max-params` 4, `max-depth` 4 as **errors**, with counting options (`skipBlankLines`, `skipComments`) set to match the caps script so both agree. One known difference: `max-params` also counts a typed `this` parameter, which the caps tool treats as free (ESLint is the stricter side; `@typescript-eslint/max-params` only skips `this: void`, so it would not align them). The rules apply to every extension the caps tool measures (`.ts .tsx .mts .cts .js .jsx .mjs .cjs`); a file outside every tsconfig project fails with a project-service parse error. There is no ESLint class-size rule and no ratchet: the script stays the gate |
| Biome | `complexity/noExcessiveCognitiveComplexity` level `error`, `maxAllowedComplexity: 10` (it is cognitive, not cyclomatic, and `info` by default); `--error-on-warnings` everywhere; disable sonarjs's duplicate `cognitive-complexity` |
| check-code-caps | file 500, function 50, class 300, params 4, nesting 4; ratchet vs `.code-caps-baseline.json`; fails on any new or **grown** violation. Greenfield baseline is empty. **Tests obey the same caps** (the maintainer's convention): write flat `test()` / `test.each()` tables, no `describe` wrapper around a whole file, at most 4 parameters or fixtures per test, split files by topic. Details in [`scripts/code-caps/README.md`](../scripts/code-caps/README.md) |
| FTA | `score_cap: 50`; the run fails when score is above 50 (per source code; the docs say below 50 is OK, so exactly 50 is ambiguous), which rules out the "could be better" band too. Exclude tests via `exclude_filenames` (`*.test.ts`, `*.test.tsx`, `test-support.ts`, `*.d.ts`); `fta-cli` pinned exactly |
| Stryker | `thresholds`: `high` 95, `low` 90, `break` 90, never lowered (the first run scored 87.2, a forced run 100, so 90 is earned; raise it as the score allows). `--incremental`; reporters clear-text, html and json. Packages: `@stryker-mutator/core`, `vitest-runner`, `typescript-checker` (all 10.1+), `checkers: ['typescript']` with `tsconfigFile` pointing at the scope's project. Seventeen shards with the same thresholds, each reaching `break` on its own (the list, sizes and times are in Testing, Stryker): sixteen cut by directory from `src/server` and `src/shared` minus tests, `test-support.ts` and `global-setup.ts` (`yarn mutate:shard <shard>`, `STRYKER_SHARD`), and `scripts` (`STRYKER_SCOPE=scripts`, `yarn mutate:scripts`), the caps tool; `yarn mutate` runs all of them. In CI they run on the nightly schedule, by hand and on `v*` tags, never on a pull request or a push to `main`, and the nightly run skips a shard whose commit already passed it (skip when nothing changed, E20-S04; see Testing, Stryker shards). Report in `reports/mutation/<shard>/index.html`. An equivalent mutant (one no test can tell apart, for example the lower-casing of `finding.sha` in `unlinked.ts`, because extraction already lower-cases it) is suppressed with `// Stryker disable next-line <Mutator>: <reason>` on the line above, the reason on the same line; `grep -rn 'Stryker disable' src scripts` lists them. The web project is outside the floor until a plan exists |
| Knip | zero issues in both modes |
| Trivy | HIGH and CRITICAL vulnerabilities fail; any secret or misconfiguration fails; `--exit-code 1` must be explicit (default is 0) |
| Semgrep | any finding fails (`--error`) |

## TypeScript

- Single compiler: `typescript` pinned to `~6.0.x`. **Do not upgrade to 7.x.** TS 7 ships no compiler API (7.1 adds a different one) and typescript-eslint 8.72 peers `typescript <6.1`. Stryker's typescript-checker, `type-coverage --strict` and `scripts/check-code-caps.ts` need the classic API. Revisit when typescript-eslint supports TS 7.1.
- Required compiler options: `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noPropertyAccessFromIndexSignature`, `verbatimModuleSyntax`, `erasableSyntaxOnly`. Library code uses `allowImportingTsExtensions` or `rewriteRelativeImportExtensions` as appropriate.
- Project layout: solution-style root `tsconfig.json` (`files: []`) referencing app (bundler resolution, DOM, `noEmit`), server (`nodenext`, `composite`, explicit `rootDir` and `outDir`, emit excludes `**/*.test.ts`), scripts (`nodenext`, `noEmit`), e2e (Playwright specs and `tests/leaks`, `noEmit`), and node-config (`vite.config.ts`, `playwright.config.ts`, Stryker/ESLint config, `noEmit`). Unit tests are co-located and typechecked in their owning project. Every project gets the strict flags, type-coverage and ESLint `projectService` coverage. `package.json` has `"type": "module"`. **Today** the root `tsconfig.json` references `tsconfig.server.json` (`src/server` and `src/shared`: `nodenext`, `composite`, `rootDir: src`, `outDir: dist`, `rewriteRelativeImportExtensions` so `.ts` specifiers become `.js`; excludes `*.test.ts`, `test-support.ts`, `global-setup.ts` and the PGlite adapter, which are test-only), `tsconfig.server.test.json` (`noEmit`, `allowImportingTsExtensions`, the same sources plus every test and helper: this is the project ESLint and type-coverage see for them), `tsconfig.web.json` (`src/web` and `src/shared`: `moduleResolution: bundler`, the DOM libs, `jsx: react-jsx`, `noEmit`, `types: ["vite/client"]`; no Node types, so a web test reads files with `import.meta.glob`), `tsconfig.scripts.json` (`scripts/**/*.ts`, `allowImportingTsExtensions`), `tsconfig.e2e.json` (`e2e/` and `tests/leaks/`, `noEmit`) and `tsconfig.node.json` (`*.config.ts`, `*.config.mjs` such as `stryker.config.mjs`, `vitest.projects.ts`, `types/**/*.d.ts`, `allowJs` and `checkJs` so `eslint.config.mjs` is typed and linted); both extend `tsconfig.base.json`, which holds the strict flags plus `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns` and `noFallthroughCasesInSwitch`, and keep their `tsBuildInfoFile` under `node_modules/.tmp`. Referenced `noEmit` projects work with `tsc -b` without `composite`. TS 6 defaults: `strict: true`, `types: []` (list `node` and `vite/client` explicitly), default `rootDir` is the tsconfig dir (set it).
- `tsc -b` is whole-project; gitignore `*.tsbuildinfo` (they live under `node_modules/.tmp`). Caching them in CI is deferred: `ci.yml` caches only the Yarn cache.
- Scripts run natively: `node scripts/foo.ts`. Native type stripping is stable in Node 26 but accepts **erasable syntax only**: no `enum`, no runtime `namespace`, no constructor parameter properties, `import type` for types, explicit `.ts` extensions, and Node ignores `tsconfig.json` (use `#subpath` imports, not `paths`). `typescript` is loaded from `node_modules` as plain JS, which is fine; it must be the 6.x package, and only the default import (`import ts from 'typescript'`) is verified, so do not use named imports until tested.

## Testing

- Vitest `projects`: `scripts` and `server` (node environment) and `web` (jsdom + Testing Library + user-event + jest-dom + MSW 3; `src/web`). Coverage is process-wide, run once with `yarn coverage`. The 100% gate runs in jsdom, not Vitest Browser Mode (v8 coverage is Chromium-only there).
- Test timeouts: the root config sets `testTimeout` to 60 s and the `server` project sets 30 s (PGlite). The tooling tests under `scripts/` start real processes (Semgrep, Trivy, ESLint, git, Stryker); with the default 5 s they failed whole pre-push runs on a busy machine without a wrong result, so the limit only tells slow from hung. A test that needs more sets its own (`scripts/semgrep-rules/repo-scan.test.ts` has 600 s). The scripts scope of the mutation gate reads `vitest.projects.ts`, not the root config, and keeps Vitest's default.
- Database tests use PGlite (single connection, in-memory, Postgres 18) by default. CI also runs the suite against a real Postgres 18 container via `DATABASE_URL` (the informative `postgres` job, with `REQUIRE_REAL_POSTGRES=1` and `CLA_ROLE_TESTS=1`; never set `CLA_ROLE_TESTS` against a server that others use; the suite checks `server_version_num` is at least 180000 and below 190000). `PGlite` is pinned exactly (`0.5.14` is PostgreSQL 18.6); minor upgrades may change on-disk format.
- **How a test gets a database:** import from `src/server/adapters/db/test-support.ts` and nothing else. `migratedTestDatabase()` (all migrations applied) or `emptyTestDatabase()` return `{ kind, db }` on one shared connection per test file and reset the `public` schema (`drop schema public cascade`) before each call, so tests never see each other's rows. `migratedRuntimeDatabase()` is the same with `cla_app` created first, so its grants exist, and `containing(text)` is a typed `expect.stringContaining` for error-message matchers (assert the message, not only the SQLSTATE, so a dropped trigger cannot hide behind another one that raises the same code). `seedTenant(db, n)` inserts an installation, repository, document and published version 1.0 with ids derived from `n` (two tenants: `n = 1, 2`), `seedSignature(db, tenant, githubUserId)` adds a user, signature and `signer_pii`, `publishVersion` adds a version, `ensureRuntimeRole(db)` creates `cla_app` (a cluster-wide object) and `asRuntimeRole(db, work)` runs `work` in a transaction under `set local role cla_app`, which is how tests prove what the unprivileged role can and cannot do. `realPostgres` is true when the run uses a server. A test that PGlite cannot run (a lock wait, a unique-index race, a backend that dies) is declared with `realPostgresOnly(name, body)`: skipped with the reason `needs real Postgres` on PGlite, and failing when `REQUIRE_REAL_POSTGRES=1` (the CI `postgres` job), so a misconfigured job cannot pass by skipping. `realPostgresRolesOnly` also needs `CLA_ROLE_TESTS=1` (skip reason `needs CLA_ROLE_TESTS=1`) and is for tests that create or alter cluster-wide roles. A test fails (`real-postgres-usage.test.ts`) on any direct `skipIf`/`runIf` on the engine flag, the URL, `DATABASE_KIND` or a `kind`. **Real-Postgres-only tests add assertions and are never the only coverage of a line:** a line covered only by one fails the 100% gate in the PGlite coverage job, because the test is skipped there. `withConnections(count)` returns `{ get(i), barrier(), poolErrors }`: independent one-connection pools on the throw-away `cla_test_<hex>` database, closed after each test. With `backendPid(db)`, `blockedBackends(db)` and `waitUntilBlocked(db, pid)` (polls `pg_locks` for `granted = false`) a test orders its interleavings by the barrier and by locks, never by `setTimeout`; call them only inside `realPostgresOnly`. Files run one at a time on a real server (`fileParallelism: !realPostgres`), in parallel on PGlite. Tests that need a migrations folder use `writeMigrationDirectory({ name: sql })`. Tests that check which migrations the real folder applies read the files on disk with `loadMigrationFiles(MIGRATIONS_DIRECTORY)` and never a hard-coded list, so adding a migration breaks none of them.
- **GitHub tests:** `src/server/config/test-support.ts` generates RSA keys at run time (PKCS#1 and PKCS#8) and no key material is committed, not even a throw-away one. The GitHub client is tested over HTTP with MSW 3 on the server side (`mockApp`, `mockGitHub`, `onUnhandledFrame: 'error'`), never by mocking Octokit; time comes from the injected `Clock` and the rate limiter's waits from a fixture (`fixtureLimiter`) that records them and advances a fake clock, so no test sleeps. `test-support.ts` helpers count toward the 100% coverage like any source file. A contract suite shared by two implementations (the fake and the Octokit adapter) runs from one test per implementation. Tests that need real concurrency (`installation-sync-concurrency.test.ts`, `repository-transfer-concurrency.test.ts`, the advisory-lock tests) use `test.skipIf(!realPostgres)`: PGlite has one connection, so they run in the `postgres` CI job and with `DATABASE_URL` only.
- **Domain tests:** the tests next to `src/server/domain` build their facts with `src/server/domain/evaluation/test-support.ts` (a relative import; the `src/shared` one is `src/shared/test-support.ts`). Both are negated from the Knip production project like the adapters' one. Rules that are about cost are tested by counting reads or lookups (a Proxy over the input, a spy on `Map.prototype.get`), never by a clock, because the domain code and its tests may not use `performance` or `Date`.
- **Job queue tests (E07):** the suites that need the real database run in the CI `postgres` job and skip on PGlite (`realPostgresOnly`): in `src/server/adapters/jobs/`, `queue-real`, `workers-real`, `pending-real`, `dead-letter-real`, `evaluate-pr-real`, `recheck-real`, `sweep-real`, `repository-jobs-real`, `serialisation-real` and `serialisation-interleavings` (the last two set `vi.setConfig({ testTimeout: 180000 })`, the interleavings take about 25 s) and `enqueuer-contract`. Locally they need `yarn ci:postgres start` and `CLA_ROLE_TESTS=1`. Helpers that only real-Postgres tests use stay inline in the `*.test.ts` file, because a `test-support.ts` counts toward the 100% gate and would be uncovered on PGlite. `recheck-real` waits for room in the pg-boss throttle slot (the database clock cannot be moved) and moves `singleton_on` back to simulate a later window. A floating-rejection test (`workers-real`) sets the runner's `unhandledRejection` listeners aside while it runs (`withOnlyTheApplicationsListeners`): the guard under test is the only listener then, which is what production has. The mocked GitHubs (`clientFixture`, `httpWorld`) carry `adapters/github/public-members-guard`, which fails the test when it ends if a public-members endpoint was asked; its wiring is proved with `test.fails` (Vitest treats an `onTestFinished` failure as a test failure). A rate-limited installation is also held by the E05 limiter, so repeated questions make no request.
- **Webhook intake tests:** the `JobEnqueuer` contract suite (`services/jobs-contract`) is run by the fake queue (`services/jobs-fixture`, a real implementation that writes into a test table on the transaction it is given) and by the pg-boss adapter on real Postgres (`adapters/jobs/enqueuer-contract.test.ts`); the fake implements the same coalesce and rate-limit rules in SQL, so the suite pins both to one behaviour. The real-Postgres cases of the intake (20 parallel identical deliveries, a connection killed between the insert and the commit, a row locked by another session) are in `services/webhook-deliveries-concurrency.test.ts` and skip on PGlite. The statement budget (at most 5 per delivery) is counted by a Kysely plugin in `adapters/http/webhook-routes-statements.test.ts`. Constants that look like secrets in tests (`SECRET_CURRENT`, `TEST_WEBHOOK_SECRET`) carry a `nosemgrep: ajinabraham.njsscan.generic.hardcoded_secrets.node_secret` comment with the reason on the same line, as the existing precedent does.
- **Login and webhook tests:** the real app registers the login's checks (E10) in front of every route, so a test that adds a `POST`, `PUT`, `PATCH` or `DELETE` route to `testApp` is refused with `403 origin_not_allowed` unless it sends the app's `Origin`, a session cookie and the CSRF token: use `authWorld` and `login(id).headers` (`adapters/http/auth-fixture`). The webhook route is the one exception and is tested with signed deliveries (`deliveryHeaders`, `postDelivery` in `adapters/http/test-support.ts`) and no `Origin`, cookie or token; `csrf-webhook.test.ts` pins that, for every spelling of its path.
- **Access and tenant tests:** a test that adds a route to the real app must declare `config.access`, normally with `PUBLIC_ROUTE` from `src/server/test-support.ts`; an undeclared route makes `app.ready()` throw `RouteAccessError`. Tests of tenant routes use `guardWorld` (`adapters/http/tenant-guard-fixture`: PGlite, `FakeGitHub`, seven people with sessions, probe routes under `/t`) and `shapeOf` to compare denials byte for byte. A data function in a `TENANT_MODULES` file needs a `TENANT_QUERIES` entry, and a tenant route needs a `CROSS_TENANT_CASES` entry (an authenticated route an `ISOLATION_CASES` or `NO_TENANT_DATA` entry), or the build fails (`tenant-modules.test.ts`, `tenant-queries-matrix.test.ts`, `cross-tenant-matrix.test.ts`). A test that asserts on a log line asserts on the parsed event (`eventsOf` in `services/role-fixture/test-support.ts`), never on the raw text, which holds the process id and the time. `testApp` hands every option except `env` and `db` to `buildApp` by rest spread, so a new `AppOptions` field needs an entry in `TestAppOptions` only.
- **Web tests (E17):** every string a test looks for comes from the catalog (`messages[...]`), and a test that needs a router uses `TestRoutes` from `src/web/test-support/router.tsx` and `renderWithProviders`; RTL's `render` with a `wrapper` option needs the queries passed explicitly to keep the typed result. The catalog tests pin the key pattern (`^[a-z]\w*(\.[a-z]\w*)+$`), no stray braces, and that a `.one` form has an `.other` with the same placeholders; a `@ts-expect-error` test is the proof that a wrong `t()` call fails `tsc`. Accessibility is asserted with `expectNoA11yViolations` (axe-core with `color-contrast` and `region` off, because jsdom has no layout: contrast is judged on the token pairs in `styles/tokens.css`, WCAG 2.2, light and dark, and landmarks are asserted with the shell) and, for user text, `expectHostileNamesInert` over the shared corpus. axe hangs under `vi.useFakeTimers`, so axe tests use real timers. The web project reads a stylesheet as text for the token tests through `css.include: [/\.css\?raw$/]` in `vitest.projects.ts` (Vitest turns every other CSS import into an empty module); this is not a coverage exclusion. `postcss` is the development dependency those tests parse with, and `src/web/test-support/tailwind.ts` compiles Tailwind classes to real CSS so a jsdom test can assert a computed style. jsdom's `window.scrollTo` is stubbed in `vitest.setup.ts`. A page navigation is spied with `spyOnPageNavigation()` (jsdom cannot navigate).
- **Real-server runs:** with `DATABASE_URL` set, `src/server/adapters/db/global-setup.ts` creates `cla_test_<hex>` (the user needs CREATEDB), hands the URL to the workers through Vitest's `provide`/`inject`, and drops the database afterwards. It never touches the database the URL names.
- **CI contract:** `scripts/ci-contract.test.ts` (parts in `scripts/ci-contract/`) fails unless every `uses:` in `.github/workflows/*.yml` is pinned to a full SHA with a `# vX.Y.Z` comment, no workflow uses `pull_request_target`, the jobs named as required in `CLAUDE.md` exist in `ci.yml` under their exact names without a job-level `if`, the five `package.json` script contracts hold (`semgrep` has `--error` and `--metrics off` and never `semgrep ci`; `trivy` has `--exit-code 1` twice; `mutate`, `mutate:shard` and `mutate:scripts` have `--incremental` or run `scripts/mutation-gate/mutate.ts`, which passes it to every Stryker run; `coverage` starts with `CI=1`), and the Dependabot lockstep groups exist.
- Snapshots: `toMatchInlineSnapshot` for small values; `toMatchSnapshot` only for small structural output where an inline literal would be noise; `toMatchFileSnapshot` for API JSON and CSV export, into a dedicated directory, never `__snapshots__/*.snap`. With `CI` set Vitest writes no snapshots and fails on missing ones; outside CI it writes them and passes, so the gate always runs with `CI=1` and new snapshot files must be committed.
- Vitest 5 defaults: `clearMocks: true`, fails on unawaited `expect().resolves/rejects`, no config search in parent dirs, reports under `.vitest/`. `vite` is now an explicit peer: add it as a devDependency. `@vitest/coverage-v8` must match the exact Vitest version.
- Vitest `related` needs `--run` and `--passWithNoTests`; never add `--coverage` to it (100% thresholds fail on partial runs).
- Stryker: use `@stryker-mutator/*` 10.1+ (Vitest 5 support landed in 10.1.0). It forces coverage off and one worker, so mutate only the node/unit project. Open bugs: `--logLevel debug` crashes on Vitest 5 (#6272), nondeterministic perTest verdicts (#6073); Browser Mode unsupported. Gitignore `.stryker-tmp`; CI caches one `reports/stryker-incremental-<shard>.json` per shard. Stryker rethrows every error but "no such file" when it reads that file, so a file cut short (a run stopped twice) stops every later run at start-up, and a cache save would keep it: `yarn mutate:check-incremental` deletes a file Stryker cannot read, and the CI job runs it after the restore and before the save. Incremental misses dependency, env and snapshot changes, and it does not re-run static (module-level constant) mutants: use `--force` after those, and after a test change that should kill a survivor. The split between Killed and Timeout can flip by a few mutants under load, so compare Survived and Killed plus Timeout.
- Stryker shards (E20-S04, E20-S05): one cold run of all the server and shared mutants (4631 now, 3807 on 2026-11-02) does not fit one CI job on the shared runners (2026-11-02: cancelled at 45 minutes, then stopped at the initial test run). The maintainer decided the same day to split it by directory and not to mind the total time. `scripts/mutation-gate/shards.ts` is the only place that lists the shards; `STRYKER_SHARD` selects one (unset runs the whole server scope in one go, for editors and tools that load the config; a name that is not a shard, or an empty one, throws), `yarn mutate` runs them all and `yarn mutate:shard <shard>` one. Each shard has its own incremental file, report, CI cache and CI job, and reaches the `break` threshold (90) on its own, so a strong directory cannot hide a weak one. A directory with more than about 500 mutants is cut by file name (`[a-o]*` and its complement `[!a-o]*`); the HTTP adapter was cut (`[a-v]*` and `[!a-v]*`) when the webhook intake (E06) took it to 771 mutants. `scripts/mutation-gate/shards.test.ts` fails unless every file the unsharded scope matches is in exactly one shard and no shard glob matches nothing: a new directory is a failing test until it is assigned. The target is at most about 500 mutants per shard and a cold run well inside one job (60-minute timeout, Stryker stopped after 50) on a loaded runner; the measured times below meet it on this machine (the slowest shard needs 24 min 35 s here, under a heavy load; see the runner assumption below for what that means on a runner), and the largest shard, `services-other` with 516 mutants, is a little over the target and left whole.
- Stryker in CI (E20-S04), skip when nothing changed: the `mutation` job runs on the nightly schedule (always `--force`, so always cold: the safety net), on a manual run and on a `v*` tag push, and not on pull requests or on a push to `main`, because a cold sharded run holds two shared runners for hours. On the schedule only, the step `decide` (`scripts/mutation-gate/decide-skip.ts`, `yarn mutate:decide`) compares this run's commit with the earlier nightly runs: when the newest completed run of `ci.yml` of the event `schedule` that has the same `head_sha` and a job `mutation (<shard>)` concluded that job `success`, every later step of that leg is skipped and the leg is green in about a minute. A skipped leg is `success` too, so by induction a success on a commit means a cold forced pass of that shard on it. Green means exactly that: a budget stop (`yarn mutate:shard` exits 1 when Stryker was stopped by `MUTATE_BUDGET_MINUTES`, whatever code Stryker gave), a timeout, a cancel and a score below `break` are all not `success`. The newest run decides, so an older pass on the same commit never outranks a newer failure, cancel or timeout. The rule is per shard, so one red shard reruns alone, every night, until it passes. The lookup fails open: any error (network, a status other than 200, a rate limit, a shape that is not expected, a missing job, more than three pages or ten runs) means the shard runs, so a lost record costs time and never coverage. A manual run and a tag push never skip. The decision script is a CI tool and not product code: it is outside every Stryker scope (the server scope is `src/`, the scripts scope is the caps tool), and its tests are in `scripts/mutation-gate/`.

## Escape hatches (hard rule 3)

Hard rule 3 of [`CLAUDE.md`](../CLAUDE.md) in full:

- **No escape hatches without a reason.** `any`, `as` assertions (`type-coverage --strict` penalises them), `@ts-expect-error`, `eslint-disable`, `biome-ignore`, `v8 ignore` are last resorts, each with a written justification on the same line. `reportUnusedDisableDirectives` stays on. Prefer zod parsing and type guards over assertions. The one `as` in the code base (`toExecResult` in `src/server/adapters/db/pglite/results.ts`, PGlite's untyped `exec()` rows) carries `// type-coverage:ignore-next-line -- reason`, which type-coverage honours without a flag. Any `v8 ignore` needs `-- @preserve` or the bundler strips it; the form is `/* v8 ignore next -- @preserve <reason> */`. `as` assertions follow the same rule as `any`: a comment with `-- <reason>` on the same line or alone on the line above.

**In `src/web`, three more rules, all with fixture tests** (`scripts/web/eslint-config.ts`, `scripts/eslint-layers.ts`). The inline-text rule: JSX text with a letter in it, and a string or template literal in `aria-label`, `title`, `placeholder`, `alt` or `label`, is an error, because user-visible text comes from the catalog (tests, `*.test.tsx`, and `src/web/test-support/**` are exempt). Web Storage: `localStorage` and `sessionStorage` are barred as globals and as properties of `window` or `globalThis` (`no-restricted-globals` and `no-restricted-properties`), except in `src/web/theme/storage.ts` and in tests. `dangerouslySetInnerHTML` is barred by Biome `security/noDangerouslySetInnerHtml` (the attribute and `createElement`) and by ESLint `no-restricted-syntax` selectors for the attribute and for an object property, which covers a spread.

**Enforced by:** `@typescript-eslint/ban-ts-comment` (error: `ts-expect-error` needs a description of at least 10 characters, `ts-ignore` and `ts-nocheck` are banned); `@eslint-community/eslint-comments` `require-description`, `no-unlimited-disable` and `disable-enable-pair` (error); `reportUnusedDisableDirectives` (error); Biome's `suppressions/parse` (a `biome-ignore` without an explanation); and `yarn lint:hatches` (`scripts/check-escape-hatches.ts`, in `pre-push` and the `static` job) for what no linter checks: an explicit `any`, an `as` other than `as const`, coverage-ignore comments (`v8`, `c8`, `istanbul` and `node:coverage`: they need `-- @preserve` and a reason after it), `type-coverage` ignore comments (they need `-- reason`) and Qodana `//noinspection <Name>` comments (they need `-- reason`). A justification is a comment with ` -- ` and at least 10 characters, on the same line or alone on the line above.

The gate reads the forms Vitest 5 honours. The hints `ignore next`, `if`, `else` and `file` count at the start of a real comment only (a string that holds one is not a hint). `ignore start` and `ignore stop` count on **any raw source line**: after other words of a comment, in a string, in a template literal. The gate therefore flags every such line, and a test that needs the text builds it from parts (`['v8', 'ignore', 'start'].join(' ')`).
