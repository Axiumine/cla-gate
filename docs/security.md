# Security, auth and privacy

How users are authenticated and authorised, and the security and privacy rules of the service. The rulebook form of the webhook, cookie, authorization and output-encoding rules is in [`architecture.md`](architecture.md) (Rules); the data that is stored is in [`data-model.md`](data-model.md); the GitHub App permissions are in [`github-app.md`](github-app.md).

## Auth model

Backend-for-frontend: the SPA never holds tokens. Login uses GitHub App user authorization with a short-lived `Lax` state cookie and PKCE. The API reads the identity and verified emails, rotates to a **new** session id, and issues a server-side session (Postgres) in a `__Host-` prefixed, `HttpOnly`, `Secure`, `SameSite=Lax` cookie with idle and absolute expiry. The session cookie is `Lax` rather than the `Strict` that RFC 10017 prefers because contributors arrive from a cross-site link (the sign link in the PR comment) and must be recognised on that first navigation; the deviation is compensated by a CSRF token plus `Origin` check on every state-changing request (the webhook route is exempt and relies on its HMAC). `return_to` accepts relative paths only, nothing mutates on GET, and sessions are deleted on a `github_app_authorization` revoke event.

The details, as built (epic E10): login starts at `GET /api/auth/login` with a signed `__Host-cla_oauth` cookie `{ s, v, r, t }` (Max-Age 600, Lax) and PKCE S256. `safeReturnTo` keeps `return_to` only when it begins with a single `/`, has no backslash, control character, whitespace or encoded variants of them, resolves to at most 512 characters with no `//` at the start, and becomes `/` otherwise. The callback is the one GET that writes: the user token is used once, revoked best-effort and never stored, and a failure ends at `/login/failed?reason=` with a closed reason. Two session cookies of the same name are refused, and a dead cookie is cleared by the `401` of every authenticated route, not only by `GET /api/auth/session`. State-changing requests pass the checks in fixed order (`Origin`, session, `x-csrf-token`); the token is `base64url(hmac_sha256(SESSION_SECRET, 'csrf:' + csrf_secret))`, so rotating `SESSION_SECRET` invalidates every token. Logout is `POST /api/auth/logout` behind those checks, with an optional strict JSON body `{ everywhere?: boolean }` (unknown keys are `400`): the user comes from the session only, and `everywhere` deletes by `users.id`, expired rows included. A revoked App authorization (`github_app_authorization`, action `revoked`) ends every session of that numeric GitHub id across the instance, through the `revoke-user-sessions` job; the `users` row stays and the person can log in again.

Authorization is derived from GitHub with the **installation token** and numeric ids (org role via the memberships API, repo permission via the collaborators permission API), cached with a short TTL.

| Action | Required role |
|---|---|
| View signatures, export CSV, revoke, invalidate (installation-scoped CLA) | org admin of the installation |
| Read the audit log of an installation | org admin of the installation only (a repo admin gets `403`) |
| Preview and run the erasure of a signer's personal data in an installation | org admin of the installation only (a repo admin gets `403`) |
| Same, repo-scoped CLA | repo admin (an org admin also passes) |
| Publish CLA version, edit allowlist, record override | same as above |
| Sign a CLA (`POST /api/sign`; the tenant is the one that owns the repository's CLA, 10 a minute per person, body at most 16 KiB) | any authenticated GitHub user |
| List the CLAs one signed (`GET /api/me/signatures`) | any signed-in person, own data only, across all orgs; signatures of a suspended installation stay listed |
| Download everything the instance holds about oneself (`GET /api/me/export`) | any signed-in person, own data only, across all orgs, 5 an hour |

The details, as built (epic E11). The **org admin** fact is `GET /orgs/{org}/memberships/{username}` with the installation token (Members: read), by numeric id: admin only when the answer is `state: active`, `role: admin` and `user.id` equals the session's numeric id (a login that someone else now holds answers with another id and is refused). The owner of a `User` installation is `installations.account_id`, with no GitHub call. The **repo admin** fact is `GET /repos/{owner}/{repo}/collaborators/{username}/permission` (Metadata: read): `permission` is `admin` and `user.id` is the viewer's; `role_name` is ignored because a custom role maps onto the base permission, and an org admin passes any repository requirement without the call. The organisation, the repository and the viewer's login are display snapshots used only as the handle of the lookup: a renamed login, organisation or repository fails closed (`404`) until the next login or sync. One gap is open and recorded in [`decisions.md`](decisions.md#open-questions): the repository is addressed by its stored name, so a name GitHub gave to a new repository before the next sync is answered about the new one. A missing Members: read permission logs `members_permission_missing` (`repository_permission_missing` for the permission call) with the numeric installation id and counts as not admin. Role lookups give up after 5 s. A role-in-installation is org admin, or admin of at least one repository of the installation that carries a repo-scoped CLA document; the discovery probes only the first `budget.remaining` such repositories by id, so a stranger costs at most 10 GitHub calls per installation per cache window.

The pure decision `decide(requirement, facts)` (`src/server/domain/authz.ts`), with the facts `orgAdmin`, `repoAdmin` and `hasRoleInInstallation`:

| Requirement | Allow when | Forbidden when not allowed | Otherwise |
|---|---|---|---|
| `org_admin` | org admin | repo admin, or a role in the installation | `not_found` |
| `repo_admin` | org admin or repo admin | a role in the installation | `not_found` |
| anything else | never | never | `not_found` |

Answers follow one convention (the table is in [`architecture.md`](architecture.md#authorization-and-tenant-isolation)): an unknown id, a removed repository, a rejected tenant and a viewer with no role in the installation all get the same `404` byte for byte, `403` only for a viewer who has a role there, and no error body names a role. GitHub failing is `502`, `503` or `429`, never an allow. The role cache is in memory, per process, holds numeric ids and booleans only, lives 60 s, and a restart clears it; every write asks GitHub again, logout and a revoked authorization forget the person, and a person is limited to 30 uncached lookups a minute (`429`).

The ledger of org admins (`installation_admin_seen`, numeric ids and a time) is the one bounded exception to live verification. GitHub refuses the tokens of a suspended or uninstalled installation, so it is written on a live positive result (at most once per 60 s per pair), deleted on a live negative one, and read only for a suspended or deleted organisation, counting entries from the last 14 days. A demoted admin therefore keeps read access for up to 14 days in that state; only org admins pass on an inactive tenant (reads are served, writes get `409`), the documents and signatures of removed repositories are org-admin only, and a rejected tenant is invisible. A lookup that was displaced or invalidated while it waited for GitHub writes nothing to the ledger. The instance operator (`OPERATOR_GITHUB_IDS`, or the App owner when it is a user) is identified by the numeric session id and sees only `GET /api/operator/installations`; it is not a tenant role, the tenant guard never reads it, a non-operator gets `404`, no session `401`, and while the App owner is unknown every signed-in caller gets `502 github_unavailable`.

The CLA document routes (E12) take their role from the document's scope: creating an installation-wide document and listing the installation's documents need an org admin; creating a repository document, listing a repository's documents (the installation-wide ones appear with their id, name and active version label, never text) need a repo admin of that repository (an org admin also passes); reading, renaming, drafting, publishing and reading the history of a document, and the exact text of a version, need an org admin for an installation-wide document and a repo admin of its repository (or an org admin) for a repository document. Reads use the cached role (mode `read`), writes verify live (`write`). Drafts are shared by every admin of the scope and never returned by a contributor-facing route. The audit rows of the epic are `cla_document.created`, `cla_document.renamed`, `cla_draft.saved`, `cla_draft.discarded` and `cla_version.published`: ids, numbers and the bump only, never a name, a text or a rationale. Saves are limited to 30 a minute per person, keyed on the GitHub id (after the guard; in an Organization installation the guard's `429` of E11-S04 answers first and carries no rate-limit headers). Beyond the codes of the error table, the CLA routes answer `422` `content_too_large` (details `limitBytes`, `actualBytes`), `content_empty`, `content_invalid_characters` and `content_too_deeply_nested`, and `409` `draft_conflict` (details `currentRevision`); none of them echoes the text.

Every query is filtered by installation id and covered by cross-tenant tests. Uninstall and repo transfer are handled explicitly: an uninstall sets `installations.deleted_at`, a removal sets `repositories.removed_at`, nothing is deleted and signatures are retained. A repository that moves to another installation of this instance is released under the old tenant (`removed_at` and an audit row, nothing else of that tenant's row changes) and inserted under the new one, so the order in which the two syncs run does not matter.

## Security and privacy

- Webhook: HMAC-SHA256 over the **raw body** (`fastify-raw-body`), compared with `crypto.timingSafeEqual`; reject before parsing. The secret is at least 16 characters, two are accepted during a rotation (`GITHUB_WEBHOOK_SECRET` and `GITHUB_WEBHOOK_SECRET_PREVIOUS`, both always computed) and the legacy SHA-1 `X-Hub-Signature` header is ignored. The route fails closed on an unsigned request at every step after the size check, with no `Content-Type`-dependent answer before the signature. A failed-signature throttle (more than 30 failures per `request.ip` in 60 s, 10,000 addresses LRU, in memory) answers `429 webhook_throttled` with `Retry-After` before the body is read; only failures count, and the address is never logged or persisted. Insert the `webhook_deliveries` row and enqueue the job in **one transaction**: a delivery whose job has not finished is sent again under its delivery id, so a crash between the two cannot lose an event while GitHub's redelivery is deduped away. `X-GitHub-Delivery` is unsigned, so jobs re-fetch state instead of trusting payloads. A scheduled reconciliation sweep re-evaluates open PRs to cover missed deliveries.
- Webhook logging: one `webhook.received` line per delivery (`event`, `action`, `deliveryId`, `githubInstallationId`, `outcome`, `reason`, `durationMs`) and no body fragment, header value, signature, secret or address; a test captures the pino output of the whole hostile suite. The WARN lines `webhook.tenant_refused` and `webhook.tenant_redirected` (numeric ids and a reason, one per installation per minute) show a rejected or transferred tenant that still sends events.
- Concurrency: one evaluation at a time per (repo, PR) without dropping newer work. The job reads the current head SHA at run time and re-checks it before writing the Check Run and comment, and reads signatures last, so a stale job cannot overwrite a newer result.
- Output encoding: names, logins and emails are user-controlled. CSV export prefixes cells starting with `=`, `+`, `-`, `@`, tab or CR to stop formula injection. PR comments and check summaries escape markdown, put names in code spans and neutralise `@` and `#`. Hostile-name tests (including a `toMatchFileSnapshot` CSV case) are mandatory. The failure output of the Check Run and the pull request comment prints no email address; a login and the name of a co-author trailer appear only as an encoded code span (`renderName` removes controls, the bidirectional marks and the tag block, cuts at 64 code points and breaks `@`, `#` and `<!--`), they are built for one report and never stored, and the sign link holds the numeric repository id and the pull request number only ([Reporting](architecture.md#reporting)).
- The App JWT and the PEM never appear in logs, errors or error causes; only the key fingerprint is named. GitHub errors carry fixed text, no `cause` and no response body, because the library's own messages quote the body and its request object holds the `Authorization` header.
- Installation tokens live only in a bounded in-memory map (1,000 entries) as `Secret`, never in a column, file or log. A rejected, deleted, suspended or unknown installation is refused by the installation gate before any request: the gate reads the stored row and also asks the admission policy in force, so an account removed from `GITHUB_ALLOWED_ACCOUNT_IDS` is refused at the next start before any reconciliation has re-decided its row. The admission decision is the pure function in `src/server/domain/admission.ts` (numeric account id only, no wildcard, never an account that is neither a user nor an organisation); per-installation admission and sync state is serialised with `lockInstallation` (`pg_advisory_xact_lock`).
- App private key, webhook secret and client secret come from the environment or a secret manager, never the repo. Trivy secret scan (pre-commit) and Semgrep `p/secrets` (pre-push, CI) guard this.
- First-run setup (E19-S06, S11, details in [`architecture.md`](architecture.md), Rules): the setup token is compared by SHA-256 digests with `crypto.timingSafeEqual`. Wrong tokens are limited to 5 a minute per client address and 30 in 10 minutes for the whole server (`429` with `Retry-After`, the right token included while held back). The unlock opens an in-memory session (30 minutes idle, at most 3 alive, the one used longest ago ends first, a restart ends them all) carried by the cookie `__Host-cla_setup` (`HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, `Max-Age=1800`); the CSRF token is random per session and returned in the body of the unlock. The unlock refuses an `Origin` that is sent and is not ours, so a page of another site cannot make visitors' browsers submit guesses from many addresses and go around the limit per address. Setup bodies are limited to 4 KiB, every setup answer is `no-store`, and on `/setup` and `/setup/callback` in setup mode the CSP `form-action` is `'self' https://github.com`. The manifest and `POST /api/setup/convert` need the cookie, `x-csrf-token` and `Origin`; the conversion is answered `409 setup_already_issued` once credentials were issued, until the process restarts. The credentials are shown once and never stored.
- The container image (E19-S01) runs as the numeric user `10001:10001`; the application tree belongs to root and is not writable by that user, and the server writes only to `/tmp`, so the root file system can be read-only (the compose stack sets it). The bundled proxy (E19-S05) replaces any client-supplied `X-Forwarded-*` header and trusts no upstream proxy, and the stack's default `TRUST_PROXY=172.30.30.0/24` covers exactly the network it runs in. `scripts/provision-database.sh` takes passwords from the environment or files only, never argv; see [`operations.md`](operations.md) for what a database server may still log.
- Parameterised queries only (Kysely); zod validation at every boundary; strict CSP via helmet; no `dangerouslySetInnerHTML`.
- The CSP (E17-S03) is `'self'` for everything, with `img-src 'self' https://avatars.githubusercontent.com` for the avatars. The fonts are the system stack, so there is no `font-src`. A dotfile or a path that leaves the web root answers `404` (the same envelope as a miss, not `403`). The theme script is a same-origin file served as a no-cache root file, the icon is a same-origin SVG, the overlays add no `<style>` element, and Zod runs `jitless`, so no `unsafe-inline` or `unsafe-eval` is needed and a page load raises no `securitypolicyviolation` (the e2e run of E18-S12 asserts zero).
- The browser side of the session (E17): the SPA never holds a token. It sends `x-csrf-token`, read from the session query and kept in memory only, on every state-changing request, makes one refresh and one retry on `403 csrf_invalid`, and never sends an `Authorization` header. Every `401` is `unauthenticated` on the client. Token, session and CSRF material never reach Web Storage, `document.cookie`, the DOM, the URL or the console (`flow.test.tsx` pins it). Web Storage is barred in `src/web` by ESLint except `theme/storage.ts` (`cla.theme`; tests are exempt). `return_to` is checked in the client (`buildReturnTo`) and again on the server (`safeReturnTo`). The avatar loads only from `https://avatars.githubusercontent.com`. `/login/failed` never shows the raw reason it was given.
- Output handling in the SPA: user-controlled text is shown through `UserText`. C0 and C1 controls except the newline, lone surrogates, U+200E and U+200F, U+202A to U+202E, U+2066 to U+2069 and U+FEFF are displayed as `<U+XXXX>` and never acted on; the stored value is unchanged.
- `GET /api/meta` is public (no session, no database): the source address and commit of the running version (the AGPL section 13 offer in the footer) and the address where the App is installed.
- CLA text is rendered from Markdown with one HTML-sanitising pipeline (`src/shared/cla-markdown.ts`, E12-S07); the stored hash is over the canonical source text. Raw HTML (script, event handlers, `<img onerror>`, `<iframe>`, `<style>`, comments) is never parsed: it is shown as literal text. Images are never rendered (their alt text remains), so a hostile text cannot make a signer's browser call out. Links survive only for `http:`, `https:` and `mailto:` in lower case (a relative, protocol-relative, fragment, `javascript:`, `data:`, `vbscript:` or capitalised-scheme link is its text), every anchor has `rel="noopener noreferrer nofollow"` and `target="_blank"`, and the sanitiser allows twelve elements and the attributes `href` (on `a`) and `start` (on `ol`). Quotes and lists nested above 50 levels are refused when the text is saved (`content_too_deeply_nested`), and the rendering answers one code block for a deeper tree. A hostile-input table of more than twenty rows walks the output tree for each case (`cla-markdown-hostile.test.ts`).
- Identity is the numeric GitHub id. Logins and emails are snapshots.
- Data minimisation: identity and verified email only; request nothing else from signers.
- Compliance routes (E16): the signature CSV is 6 a minute per user and the export of one's own data is 5 an hour; both write an audit row before the data leaves (`signatures.exported`, `data_export.created`). The audit log viewer shows numeric ids only, the login being read from the `users` snapshot at request time. The own-data export names no other person: a `user` subject that is not the caller (the signer an org admin erased) is `null`, and who revoked a signature or made an allowlist entry is not selected.
- Operator privacy notes (E16-S07): the data inventory, retention, the erasure runbook, backups and the several-orgs case are in [`privacy.md`](privacy.md), kept true against the schema and the configuration defaults by the tests in `src/server/docs`.
- Rate limiting (`@fastify/rate-limit`): the in-memory store (10 000 keys per store) is correct for one process; running several processes would need a shared store (Postgres or Redis). The key is `request.ip` (IPv6 by /64), which follows `TRUST_PROXY`: set it correctly behind a load balancer or every client shares the proxy's budget. Budgets per minute: 600 globally, 20 on login start, callback and logout, 120 on the session read; the answer is `429 too_many_requests` with `retry-after`.
