# Tooling gotchas

Facts and traps about the tools this repository uses, verified while building it. They are dev tooling notes, not gates; the gates and their thresholds are in [`quality-gates.md`](quality-gates.md), the scripts in [`development.md`](development.md).

- **Corepack is not bundled with Node 25+.** `npm install -g corepack` before `corepack enable` (also in Dockerfiles and CI). Node 26 Linux binaries link `libatomic`; the official `trixie-slim` image already contains it. The official Node 26 images have no Corepack and no Yarn (the `Dockerfile` installs `corepack@0.36.0` itself) and set `ENTRYPOINT docker-entrypoint.sh`, so a `CMD` is passed through it.
- **Docker build (E19-S01).** `yarn workspaces focus --all --production` has no skip-build mode and runs the root `postinstall` (the lefthook installer), so the `prod-deps` stage deletes that one script from its own copy of `package.json`; a Docker build context has no `.git`, so `yarn install --mode=skip-build` is enough for the other stages. A whole-solution `tsc -b` needs `e2e/`, which `.dockerignore` excludes, hence `yarn build` names the server and web projects. Tests that scan `scripts/` for image publication must not contain the publication words themselves: build them from parts, as `workflow-guard-permissions.test.ts` does.
- **Compose and the provisioning script (E19-S03, S04).** The Postgres image's init directory runs every `.sql` file in it by itself, so the provisioning SQL is mounted outside it and `CLA_PROVISION_SQL` names it. The health check of `postgres` is `pg_isready -h 127.0.0.1` because the server that runs the init scripts has no TCP listener, so a socket check would report healthy too early. In `psql`, `\if :flag` needs the variable to be a bare `t` or `f`, and `\quit` cannot carry an exit code: the SQL prints a prefix (`invalid:`, `conflict:`) and the shell script turns it into 2 or 3. `cla_test` (the role of `CLA_TEST_ROLE`) needs `grant cla_app to cla_test with inherit false, set true` after the script and cannot run `CLA_ROLE_TESTS=1` (`permission denied to rename role`). The `postgres` CI job also runs the real-Postgres-only test of the test-database guard.
- **Caddy (E19-S05).** `/usr/bin/caddy` carries the file capability `cap_net_bind_service`, so with `no-new-privileges` and `cap_drop: ALL` the container needs `cap_add: NET_BIND_SERVICE` or it fails with `exec: operation not permitted`. A bare placeholder that expands to nothing after `email` is a parse error: quote it (`email "{$ACME_EMAIL}"`). `caddy fmt` wants no blank line between the header comment and the global block. `skip_install_trust` avoids the trust-store error on a read-only root file system. Automatic redirect responses keep `Server: Caddy`. A bare `https://` is a valid site address that matches every host.
- **Yarn Berry never runs `prepare`.** Install hooks from root `postinstall` (`scripts/dev/install-hooks.ts` runs `lefthook install`, and skips it when `CI` is set or there is no `.git`). **CI must install no hooks**: on a persistent workspace `actions/checkout` deletes `node_modules` (`git clean -ffdx`) and then `git checkout` fires `post-checkout`, which with `assert_lefthook_installed: true` fails when Lefthook is gone (verified). Docker builds have no `.git`: the script skips there, and `yarn install --immutable --mode=skip-build` skips scripts altogether. Yarn 4.14+ defaults `enableScripts` to false, so third-party postinstalls (including lefthook's own) are skipped; root-workspace scripts still run.
- `.yarnrc.yml`: `nodeLinker: node-modules` (PnP has known Playwright bugs and unverified support elsewhere). `yarn install --immutable` in CI. **The file must be committed**: without it a clean checkout installs with Yarn's default PnP linker, and ESLint (`.pnp.loader.mjs` not found by the project service) and Vitest (`Non-utf8 buffers are not supported`, yarnpkg/berry#4942) fail. Some global git ignores list it (the maintainer's `~/.config/git/ignore` does), so the repo `.gitignore` re-includes it with `!.yarnrc.yml`; check `git status` shows it before pushing.
- Node version sources: `.nvmrc`, `mise.toml`, `devEngines.runtime`, `packageManager` (with hash, written by `corepack use yarn@4.x`). Node ignores `engines`; Yarn does not enforce it. mise ignores `.nvmrc` unless configured, so `mise.toml` is canonical. fnm `--corepack-enabled` fails on Node 25+.
- **Lefthook v2**: use `jobs:` (list order is run order). `files` is a shell command, not a pattern. Set `glob_matcher: doublestar` or `**/*.ts` misses root files. `stage_fixed` is pre-commit only. Default execution is sequential and does not stop on failure: use `piped: true` for fail-fast, `group:` for nested parallel. `parallel` and `piped` together is an error. Set `assert_lefthook_installed: true`. `skip: [merge, rebase]` on slow jobs, but only in `pre-commit`: on a `pre-push` job it would make `yarn gate` exit 0 without running anything during a rebase. A new branch without upstream makes `{push_files}` equal all tracked files. A global `core.hooksPath` blocks `lefthook install`. Lefthook substitutes its own `{1}`, `{2}` hook arguments even inside `HEAD@{1}` (leaving the bad revision `HEAD@<sha>`): `post-checkout` uses `{1} {2}`. Hooks cannot enforce themselves: CI must repeat them.
- **ESLint 10**: flat config only (`eslint.config.mjs`), `defineConfig` from `eslint/config`, `tseslint.configs.strictTypeChecked` and `stylisticTypeChecked`, `parserOptions: { projectService: true, tsconfigRootDir: import.meta.dirname }`. Do not use `--cache` (stale for type-aware rules). Use `--no-warn-ignored`. `eslint-plugin-jsx-a11y` peers stop at ESLint 9: use Biome a11y rules instead. `eslint-plugin-react-hooks` 7 `configs.flat.recommended` includes React Compiler rules. `eslint-config-biome` (third party, last published 2025-12) turns off overlapping rules: place it last and verify against the installed Biome version. Found while building the caps tool: `strictTypeChecked` rejects numbers in template literals, so set `@typescript-eslint/restrict-template-expressions` to `{ allowNumber: true }`; `sonarjs/no-alphabetical-sort` requires a comparator on every `.sort()`; `sonarjs/no-os-command-from-path` fires on `execFileSync('git', ...)` and is suppressed inline with a written reason (the argv is fixed); use `toThrow`, not the deprecated `toThrowError`; never feed `JSON.parse` output (`any`) straight into an expression, assign it to an `unknown` variable first (type-coverage).
- **Escape-hatch plugin**: `@eslint-community/eslint-plugin-eslint-comments` 4.8.1 (MIT) works on ESLint 10. `disable-enable-pair` runs with `allowWholeFile: true`. The escape-hatch block is `scripts/escape-hatches/eslint-config.ts` (negated from the Knip production project). Tests must read the resolved ESLint config in a child process (`eslint --print-config`): importing it makes V8 coverage count a native copy of the TypeScript files. `scripts/escape-hatches/ranges.ts` exists because Vitest matches `ignore start|stop` on every raw line (see [`quality-gates.md`](quality-gates.md), Escape hatches).
- **Biome 2.x**: `files.includes`, `assist.actions.source.organizeImports`, `linter.rules` presets; `rules.recommended` is deprecated. Use `biome check --write --no-errors-on-unmatched --files-ignore-unknown=true {staged_files}` in hooks, `biome ci` for read-only. Style used by the existing code: 2 spaces, single quotes, `lineWidth` 120; use `"preset": "recommended"` (the `recommended` flag is deprecated). Turn `complexity/useLiteralKeys` **off**: it rewrites `record['key']` to `record.key`, which `noPropertyAccessFromIndexSignature` forbids.
- **FTA** exits at the first file above `score_cap` without printing a report: run a second pass without the cap for the full list: copy `fta.json` to a scratch file with `score_cap` raised and run `yarn exec fta . --config-path <scratch.json> --json` (`yarn fta <args>` would append a second `--config-path`). v2 and v3 changed scoring: pin the exact version. Tests are scored unless excluded. The server foundation sits at 49.3 at most, so there is little head room: when a file nears 50, split it (this is how `config/env.ts` became `env.ts`, `env-schema.ts` and `env-fields.ts`, `pglite.ts` became a folder, and, in E06, the GitHub variables left `env-fields.ts` for `env-github.ts` and the `AppConfig.github` settings for `github-config.ts`; `adapters/http/webhook-routes.ts` sits at 49.2, so logic goes into a neighbouring file before it grows).
- **Knip**: `--strict` implies `--production` and ignores devDependencies, hence two runs. Mark production entries with `!`. Plugins exist for Vite, Vitest, Playwright, ESLint, Stryker, Lefthook, Biome (the Stryker plugin finds `vitest.stryker.config.ts`). Exit codes: 0 clean, 1 issues, 2 error. `knip.json` has `ignoreBinaries: [semgrep, trivy]` (external CLIs) and `ignoreDependencies: [memlab]` (only its CLI is used, through `@memlab/api`'s wrapper); it negates `scripts/semgrep-rules/**`, `scripts/trivy-gate/**`, `scripts/qodana-gate/**`, `scripts/e2e/**`, `scripts/leaks/**` and `scripts/ci-contract/` from the production project, because they import devDependencies or are imported only by tests (the same as `scripts/ci` and `scripts/dev`).
- **Semgrep**: use `semgrep scan --error --metrics off`, not `semgrep ci` (it ignores `--config` and targets the platform). No login needed. A custom `.semgrepignore` replaces defaults: re-list `node_modules`, `dist`, `build`. Ours is root-anchored (`/dist/` and so on; only `node_modules/` matches at any depth), so a source directory that is merely named `coverage`, `reports` or `rules` is still scanned. Default ignores skip `/test`. For offline use, `yarn semgrep:rules` downloads the five rulesets into `rules/` and **git-ignores it**: the Semgrep Rules License v1.0 restricts redistribution, so the rules must not be committed, uploaded or shared. The registry returns JSON to clients that accept gzip, so the fetch script sends `accept-encoding: identity`. Semgrep writes `~/.semgrep/settings.yml` and `semgrep.log` unless `SEMGREP_SETTINGS_FILE` and `SEMGREP_LOG_FILE` are set (the CI job points both into `RUNNER_TEMP`). A partial-parse warning (`typeof import()` type arguments) hides code from the scan: write `import type * as ns` instead. **The only allowed suppression** is `// nosemgrep: <full rule id> -- <reason>` on the flagged line or the line directly above (`scripts/semgrep-rules/suppressions.test.ts` enforces the form); never `--exclude`, `--exclude-rule` or `--disable-nosem`. `scripts/semgrep-rules/repo-scan.test.ts` runs the real binary over the repository with the offline rules when both exist, so a new finding fails `yarn test` there.
- **Trivy**: dev dependencies are skipped without `--include-dev-deps`; misconfig must be named in `--scanners`; `--severity` also filters secrets. Secret scanning needs no vulnerability DB (fast for pre-commit). **Supply-chain incident (March 2026, CVE-2026-33634):** Trivy v0.69.4 (and Docker Hub v0.69.5-6) were malicious, and `trivy-action` tags 0.0.1 to 0.34.2 plus `setup-trivy` tags were repointed. Use Trivy v0.76.1 or later pinned exactly, `trivy-action` 0.35.0 or later and `setup-trivy` v0.2.6 or later, each pinned by full commit SHA, and pin every other Action the same way. Never reference older tags. Here: Trivy 0.76.1 in `mise.toml` and the same release in CI, installed by `scripts/ci/install-trivy.ts`; neither `trivy-action` nor `setup-trivy` is used. `trivy.yaml` is the single list of skipped directories. `.trivyignore` exists only when needed: each entry has a reason comment above it and `exp:YYYY-MM-DD` within 90 days of the line's commit date, and Trivy stops honouring an entry on its expiry day (tested). Misconfiguration scanning works offline with the checks embedded in the binary (`TRIVY_SKIP_CHECK_UPDATE`). Trivy has no docker-compose scanner.
- **Trivy install in CI** (2026-11-04, upstream [aquasecurity/trivy#11537](https://github.com/aquasecurity/trivy/issues/11537), closed without a fix): `setup-trivy` fetches its tarball from `get.trivy.dev`, a domain that lapsed (NXDOMAIN, then a parking page), so every `trivy` job failed at the install step with curl exit 6. The job now downloads `https://github.com/aquasecurity/trivy/releases/download/v<version>/trivy_<version>_Linux-64bit.tar.gz` itself (`scripts/ci/install-trivy.ts`), compares its SHA-256 with a literal in the step's `env` in `ci.yml` and unpacks only the `trivy` binary into `$RUNNER_TEMP/trivy`. To bump: set the new version in `mise.toml` and `INSTALL_TRIVY_VERSION`, and `INSTALL_TRIVY_SHA256` to the `Linux-64bit.tar.gz` line of the release's `trivy_<version>_checksums.txt` (check it against the downloaded file too); a test keeps the two versions equal and requires 64 lowercase hex digits. Do not return to an installer that downloads from a host this repository does not pin.
- **Qodana**: linter `qodana-js` (image `jetbrains/qodana-js:2026.2`, pinned by tag in `qodana.yaml` and by digest in the workflow as `--linter tag@sha256:...`), `qodana.yaml` with `version: "1.0"`, `failThreshold: 0`, needs `QODANA_TOKEN` and a paid Ultimate or Ultimate Plus licence. Gate failure exits 255. Fork PRs get no secrets, so it is a maintainer-side check and never required (like `leaks`). The coverage input is `.qodana/code-coverage/lcov.info` (JavaScript reads lcov with paths relative to the project root; the defaults also look in `coverage/lcov.info`, `reports/` and `test-coverage/`); the Vitest coverage reporter is therefore `['text', 'lcov']`, and `.qodana/` is a git-ignored generated directory (also in the ESLint ignores and the FTA `exclude_directories`). There is no baseline file: a finding is fixed, excluded in `qodana.yaml` with a comment above the entry, or silenced with `//noinspection <Name> -- <reason>` (the escape-hatch gate rejects one without a reason). One inspection is excluded in `qodana.yaml`, with its reason on the line above: `ES6PreferShortImport` wants the file extension and `/index` dropped from relative imports, which the server's Node type stripping does not allow (a gate test pins the list of exclusions); `JSDeprecatedSymbols` is excluded because it flags zod's `z.iso.datetime(...)` as deprecated although TypeScript and typescript-eslint's `no-deprecated` do not, and which calls it flags changes between runs).
- **Stryker** (E20-S04, E20-S05): `@stryker-mutator/api` is a devDependency only for the type of the config. `clearTextReporter.logTests` is `false` (thousands of log lines otherwise). A stale incremental run shows bogus survivors among the static mutants: verify with `--force` before writing a test for one. `STRYKER_SCOPE` selects the scope and `STRYKER_SHARD` the slice of the server scope (see [`development.md`](development.md)). `vitest.related` defaults to true in the Vitest runner: the initial run and every mutant run execute only the tests whose imports reach the mutated files, so a shard's initial run is shorter than the whole suite and a test that reaches code only through a dynamic import is missed (NoCoverage mutants lower the score, never hide a survivor). Static mutants (module-level code) run every related test and dominate the time: on the `shared` shard 111 of 161 mutants are static and took about 97% of the run, and which mutants count as static can change between runs (Stryker issue 6073). `ignoreStatic` would cut that time but stops mutating the module-level constants and message strings, so it is not used. The initial test run is serial (one worker, forced by Stryker) and every shard repeats it: 12 min 37 s for the 7003 tests of `shared` on 2026-11-03 at a low load, 1117 of them (a fresh PGlite each) taking 92% of it; `dryRunTimeoutMinutes` is 120 ("Initial test run timed out!" was the first scheduled run hitting the 20 it had), and a budget stop during that run saves nothing, so `MUTATE_BUDGET_MINUTES` stays 50 minutes above it ([`quality-gates.md`](quality-gates.md), Testing). Stryker writes its incremental file only at the end of a run, and also on SIGINT, SIGTERM, SIGHUP or SIGABRT ("Saved a partial incremental report"), but not when the signal arrives during the initial test run; the CI runner's own cancel signal does not reliably reach Stryker, so `scripts/mutation-gate/mutate.ts` sends SIGINT itself after `MUTATE_BUDGET_MINUTES`. A second signal while Stryker writes makes it exit at once (`unexpected-exit-handler.js`), so the file can be cut short, and when Stryker reads an incremental file at start-up it rethrows every error but "no such file" (`project-reader.js`, also a valid JSON without `files`): the run then stops before its first mutant, every time, so `yarn mutate:check-incremental` deletes such a file before it can be cached. The time of a shard cannot be estimated from its mutant count: a per-mutant model fitted to two shards came out up to five times too high for the others, because the time depends on how many tests reach each file (`services-other` has 516 mutants and took 9 min 50 s, `shared` has 163 and took 14 min 43 s), so the shard table holds measurements only. Skip when nothing changed (E20-S04): the nightly run skips a shard when the newest earlier completed `schedule` run of `ci.yml` on the same commit that has the job `mutation (<shard>)` concluded that job `success`; an older pass never outranks a newer failure, a cancel or a timeout, so a red shard reruns every night until it passes (`scripts/mutation-gate/skip-decision.ts`, step `decide`). Facts that make it sound: a leg that skipped itself ends `success` too, so a success on a commit always traces back to one cold `--force` pass; Stryker exits 130 on SIGINT and `scripts/mutation-gate/mutate-cli.ts` fails a shard that the budget stopped whatever the code, so a partial run is never green; the jobs endpoint is expected to name a matrix job `mutation (<shard>)` (the `name` of the job with its matrix value; no matrix run exists on the repository yet, so the first nightly run after the change confirms it); a job-level `if` that is false reports `skipped`, not `success`, and `/runs/{id}/jobs` lists the latest attempt of a run. The lookup fails open: a network error, a status other than 200 (a rate limit is 403 or 429), a body of an unexpected shape, a missing or renamed job, a timeout (60 s for the whole lookup) and a cap (three pages of 100 per list, ten runs) all mean "run the shard"; it never fails the step and never prints the token or a response body. Rename the job or its `name` and the next nightly run finds no job of the old name and runs every shard once (a cost, not a hole). The first nightly run after the change is cold, the second on an unchanged commit should skip (open until seen, E20-S04). Needs `permissions: actions: read` on the job, which the runner guard allows at job level only (`docs/ci-runners.md`, R5). Node 26 aborts on a long IPC message (nodejs/node#66489): Stryker sends `worker.send(JSON.stringify(message))`, a string, which Node stringifies again, and V8's `JSON.stringify` fast path (default since V8 13.6) dies with `FATAL ERROR: Zone Allocation failed - process out of memory` on a flat string of 134 million two-byte or 268 million one-byte characters, at a heap of a few hundred megabytes (the `http-a-v` shard, nightly run 41817514084; the message that asks the checker to group the mutants carries the covering test ids of every mutant, twice). `--max-old-space-size` does not help, and Node refuses `--no-json-stringify-fast-path` in NODE_OPTIONS, so `scripts/mutation-gate/node-args.ts` puts it on the command line of the main process (`mutate-run.ts`) and of the checker and test runner processes (`checkerNodeArgs`, `testRunnerNodeArgs`); beyond 536 870 888 characters the stringify throws `RangeError: Invalid string length`, so a shard still has to stay under that (cut it by letter range). `yarn mutate:scripts` runs `stryker` without the flag: its shard has 587 mutants and only the tests of the caps tool reach them, far under the limits. The tests run in an instrumented copy of the repository, `.stryker-tmp/sandbox-<id>`, and the dry run of a shard (nightly run 41817514084, 2026-11-04) failed twice on that. (1) The instrumented module of a file holds every mutant behind a switch, active or not, so a regular expression literal with a mutant that is a SyntaxError fails the load of the module and every test that imports it: with the `u` flag the Regex mutator turns `\v` into `\V`, an invalid escape (`LINE_BREAK` in `domain/reporting/encode.ts`; the vertical tab is `\cK` there, because `\u000B` and `\x0B` trip `no-control-regex`). `scripts/mutation-gate/instrumented-regex.test.ts` runs Stryker's own instrumenter (`@stryker-mutator/instrumenter`, a devDependency pinned with the other Stryker packages) over every file of every scope and compiles each regular expression mutant (about 10 seconds, 457 of them on 2026-11-04, `encode.ts` the only one that failed); a new literal that fails is rewritten and never suppressed. A pattern given to `new RegExp("...")` as a string is mutated too, but fails only while its mutant is active and kills it. (2) A test that reads the text of a mutated file reads the instrumented copy: a string argument becomes a conditional expression (`selectFrom(stryMutAct_9fa48("1") ? "" : "users")`), and a scan that wants a string literal finds none. The tests that scan the server's source (`tenant-modules`, `audit-single-writer`, `audit-catalogue`, `audit-scan`) take their root from `sourceTree` (`src/server/source-tree/test-support.ts`), which maps the sandbox back to the repository, and are not excluded: their neighbours in the same files run real code and kill mutants. The other tests that read files (`no-legal-text`, `pr-evaluation-links-tenants`, `auth-wiring`, `check-name-literal`, `privacy-sections`, `allowlist-entry-remove`, `document-draft-surface`, `real-postgres-usage` and the ones that read `migrations/`, `docs/`, `scripts/`, `.env.example` or `package.json`) pass on the instrumented copy because they look for words that stay in it or for the absence of a word. A new test that parses the text of a mutated file is checked the same way: run it in a sandbox (`stryker run --dryRunOnly --cleanTempDir=false --concurrency 1`, then Vitest with `vitest.stryker.config.ts` inside `.stryker-tmp/sandbox-*`).
- **Vite 8 / React**: Rolldown + Oxc replace esbuild/Rollup (`build.rolldownOptions`, `oxc` config keys). `@vitejs/plugin-react` 6 has no Babel option. Keep React and react-dom on the identical version. TanStack Router uses code-based routes (no codegen).
- **Scaffolding with Corepack**: `corepack use yarn@x` runs an install with the default PnP linker and leaves `.pnp.cjs`, `.pnp.loader.mjs` and a `yarn.lock`; set `nodeLinker: node-modules` first (or delete the PnP files). `lefthook install` with no `lefthook.yml` writes an example one. `lefthook install` also **fails without `.git`** (verified), which is why `scripts/dev/install-hooks.ts` skips it in a Docker build context without `.git`. CI checkouts have `.git` but still install no hooks (see the `prepare` bullet). CI pins `corepack@0.36.0`, installed with `npm install --global --prefix "$RUNNER_TEMP/npm-global"` (never into the shared tool-cache Node), and the packageManager hash covers Yarn itself.
- **`yarn <name>` runs the script of that name before the binary** (see Commands in [`development.md`](development.md)). The `pre-push` jobs call the scripts, so the pre-push hook, the CI steps and `yarn gate` run identical commands. `pre-commit` instead runs staged-file variants of the binaries (`yarn biome check --write ... {staged_files}`, `yarn eslint ... {staged_files}`, `yarn vitest related --run`); only `yarn caps` is shared with it.
- **type-coverage does not follow project references**: `-p tsconfig.json` on the solution-style root (`files: []`) reports `0 / 0` and passes (verified), so it is a silent no-op. Always run it per project (`-p tsconfig.scripts.json`, `-p tsconfig.node.json`), and add a line to the `type-coverage` script for every new tsconfig project. It also resolves `typescript` through node_modules hoisting (Yarn warns YN0086 that `type-coverage` does not declare it), another reason for `nodeLinker: node-modules`.
- **fta-cli 3.1.0 ships CRLF line endings, shebang included**: `node_modules/.bin/fta` fails on Linux with `env: 'node\r'`. Run it through `yarn fta` (Yarn launches the file with `node`). Splitting a file is the only way to lower its score; `measure.ts`, `cli.ts` and the caps modules were split (`collector.ts`, `nesting.ts`, `report.ts`) to get under 50. The foundation sat at 49.3 and `boot.ts` and `env.ts` are tight, so a new option or branch there can break the cap. Splitting a file can also RAISE its score (extracting `start-check.ts` out of `adapters/github/start.ts` made it worse); one shared options object (`http` in `start.ts`) lowered it.
- **Biome 2.6 also formats Markdown and YAML.** Its Markdown formatter rewrites tables with padded separators (against the table style in the user's CLAUDE.md), so `biome.json` turns the Markdown formatter and linter off. YAML (`.github/`, `lefthook.yml`) is formatted by Biome. Biome's `lint/security/noDangerouslySetInnerHtml` exists in 2.6 with default severity `error`; `biome check --staged` exists and works without `vcs.enabled` (verified on 2.6.4; `vcs.enabled: true` without `clientKind` is a config error), but the hook passes Lefthook's `{staged_files}` instead.
- **eslint-config-biome is not used.** It switches off 557 rules, among them the type-aware `no-floating-promises`, `no-misused-promises` and `switch-exhaustiveness-check`, whose Biome counterparts are still `nursery` with severity `info` in Biome 2.6. `switch-exhaustiveness-check` is not part of `strictTypeChecked`, so `eslint.config.mjs` enables it explicitly. Where Biome and ESLint overlap, both run; revisit only if a real conflict appears.
- **eslint-plugin-security 4.2 and eslint-plugin-no-unsanitized 4.1 work on ESLint 10.** The security preset ships as `warn`; `eslint.config.mjs` escalates it to `error`. `detect-non-literal-fs-filename` and `detect-object-injection` fire in the caps tool and its tests (a CLI that opens paths, `CAPS[kind]` on a closed union) and are suppressed inline with a written reason. no-unsanitized ships no types: `types/eslint-plugin-no-unsanitized.d.ts` declares the part used. sonarjs 4.2 is LGPL-3.0-only (fine for a dev tool under AGPL-3.0); no-unsanitized is MPL-2.0.
- **pg-boss 12 facts** (verified on real Postgres while building the job queue, E07): there is no archive step: a job stays in `pgboss.job` until `deleteAfterSeconds` removes it, so "archive then delete" retention is not available. `singletonKey` is one per job, and `singletonSeconds` is an epoch-aligned slot (the first send in a slot wins, whatever became of its job). The `singleton` policy admits one active job per key and any number waiting; `short` drops a send while one waits and lets two run; `exclusive` drops a send while one runs. `createQueue` is plain DML unless the queue is partitioned and is `ON CONFLICT DO NOTHING`, so changed options need `updateQueue`; a policy cannot change on an existing queue. The scheduler needs `INSERT` on `pgboss.queue` for its internal queue `__pgboss__send-it`, so the migrate step creates it and the runtime only enables the schedule. `@opentelemetry/api` is a peer dependency. A worker's `unhandledRejection` is attributed to its job through `AsyncLocalStorage` (the store is visible in the listener, checked on Node 24 and 26).
