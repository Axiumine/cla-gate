# Tooling gotchas

Facts and traps about the tools this repository uses, verified while building it. They are dev tooling notes, not gates; the gates and their thresholds are in [`quality-gates.md`](quality-gates.md), the scripts in [`development.md`](development.md).

- **Corepack is not bundled with Node 25+.** `npm install -g corepack` before `corepack enable` (also in Dockerfiles and CI). Node 26 Linux binaries link `libatomic`; slim images may need it.
- **Yarn Berry never runs `prepare`.** Install hooks from root `postinstall` (`scripts/dev/install-hooks.ts` runs `lefthook install`, and skips it when `CI` is set or there is no `.git`). **CI must install no hooks**: on a persistent workspace `actions/checkout` deletes `node_modules` (`git clean -ffdx`) and then `git checkout` fires `post-checkout`, which with `assert_lefthook_installed: true` fails when Lefthook is gone (verified). Docker builds have no `.git`: the script skips there, and `yarn install --immutable --mode=skip-build` skips scripts altogether. Yarn 4.14+ defaults `enableScripts` to false, so third-party postinstalls (including lefthook's own) are skipped; root-workspace scripts still run.
- `.yarnrc.yml`: `nodeLinker: node-modules` (PnP has known Playwright bugs and unverified support elsewhere). `yarn install --immutable` in CI. **The file must be committed**: without it a clean checkout installs with Yarn's default PnP linker, and ESLint (`.pnp.loader.mjs` not found by the project service) and Vitest (`Non-utf8 buffers are not supported`, yarnpkg/berry#4942) fail. Some global git ignores list it (the maintainer's `~/.config/git/ignore` does), so the repo `.gitignore` re-includes it with `!.yarnrc.yml`; check `git status` shows it before pushing.
- Node version sources: `.nvmrc`, `mise.toml`, `devEngines.runtime`, `packageManager` (with hash, written by `corepack use yarn@4.x`). Node ignores `engines`; Yarn does not enforce it. mise ignores `.nvmrc` unless configured, so `mise.toml` is canonical. fnm `--corepack-enabled` fails on Node 25+.
- **Lefthook v2**: use `jobs:` (list order is run order). `files` is a shell command, not a pattern. Set `glob_matcher: doublestar` or `**/*.ts` misses root files. `stage_fixed` is pre-commit only. Default execution is sequential and does not stop on failure: use `piped: true` for fail-fast, `group:` for nested parallel. `parallel` and `piped` together is an error. Set `assert_lefthook_installed: true`. `skip: [merge, rebase]` on slow jobs, but only in `pre-commit`: on a `pre-push` job it would make `yarn gate` exit 0 without running anything during a rebase. A new branch without upstream makes `{push_files}` equal all tracked files. A global `core.hooksPath` blocks `lefthook install`. Lefthook substitutes its own `{1}`, `{2}` hook arguments even inside `HEAD@{1}` (leaving the bad revision `HEAD@<sha>`): `post-checkout` uses `{1} {2}`. Hooks cannot enforce themselves: CI must repeat them.
- **ESLint 10**: flat config only (`eslint.config.mjs`), `defineConfig` from `eslint/config`, `tseslint.configs.strictTypeChecked` and `stylisticTypeChecked`, `parserOptions: { projectService: true, tsconfigRootDir: import.meta.dirname }`. Do not use `--cache` (stale for type-aware rules). Use `--no-warn-ignored`. `eslint-plugin-jsx-a11y` peers stop at ESLint 9: use Biome a11y rules instead. `eslint-plugin-react-hooks` 7 `configs.flat.recommended` includes React Compiler rules. `eslint-config-biome` (third party, last published 2025-12) turns off overlapping rules: place it last and verify against the installed Biome version. Found while building the caps tool: `strictTypeChecked` rejects numbers in template literals, so set `@typescript-eslint/restrict-template-expressions` to `{ allowNumber: true }`; `sonarjs/no-alphabetical-sort` requires a comparator on every `.sort()`; `sonarjs/no-os-command-from-path` fires on `execFileSync('git', ...)` and is suppressed inline with a written reason (the argv is fixed); use `toThrow`, not the deprecated `toThrowError`; never feed `JSON.parse` output (`any`) straight into an expression, assign it to an `unknown` variable first (type-coverage).
- **Escape-hatch plugin**: `@eslint-community/eslint-plugin-eslint-comments` 4.8.1 (MIT) works on ESLint 10. `disable-enable-pair` runs with `allowWholeFile: true`. The escape-hatch block is `scripts/escape-hatches/eslint-config.ts` (negated from the Knip production project). Tests must read the resolved ESLint config in a child process (`eslint --print-config`): importing it makes V8 coverage count a native copy of the TypeScript files. `scripts/escape-hatches/ranges.ts` exists because Vitest matches `ignore start|stop` on every raw line (see [`quality-gates.md`](quality-gates.md), Escape hatches).
- **Biome 2.x**: `files.includes`, `assist.actions.source.organizeImports`, `linter.rules` presets; `rules.recommended` is deprecated. Use `biome check --write --no-errors-on-unmatched --files-ignore-unknown=true {staged_files}` in hooks, `biome ci` for read-only. Style used by the existing code: 2 spaces, single quotes, `lineWidth` 120; use `"preset": "recommended"` (the `recommended` flag is deprecated). Turn `complexity/useLiteralKeys` **off**: it rewrites `record['key']` to `record.key`, which `noPropertyAccessFromIndexSignature` forbids.
- **FTA** exits at the first file above `score_cap` without printing a report: run a second pass without the cap for the full list: copy `fta.json` to a scratch file with `score_cap` raised and run `yarn exec fta . --config-path <scratch.json> --json` (`yarn fta <args>` would append a second `--config-path`). v2 and v3 changed scoring: pin the exact version. Tests are scored unless excluded. The server foundation sits at 49.3 at most, so there is little head room: when a file nears 50, split it (this is how `config/env.ts` became `env.ts`, `env-schema.ts` and `env-fields.ts`, `pglite.ts` became a folder, and, in E06, the GitHub variables left `env-fields.ts` for `env-github.ts` and the `AppConfig.github` settings for `github-config.ts`; `adapters/http/webhook-routes.ts` sits at 49.2, so logic goes into a neighbouring file before it grows).
- **Knip**: `--strict` implies `--production` and ignores devDependencies, hence two runs. Mark production entries with `!`. Plugins exist for Vite, Vitest, Playwright, ESLint, Stryker, Lefthook, Biome (the Stryker plugin finds `vitest.stryker.config.ts`). Exit codes: 0 clean, 1 issues, 2 error. `knip.json` has `ignoreBinaries: [semgrep, trivy]` (external CLIs) and `ignoreDependencies: [memlab]` (only its CLI is used, through `@memlab/api`'s wrapper); it negates `scripts/semgrep-rules/**`, `scripts/trivy-gate/**`, `scripts/qodana-gate/**`, `scripts/e2e/**`, `scripts/leaks/**` and `scripts/ci-contract/` from the production project, because they import devDependencies or are imported only by tests (the same as `scripts/ci` and `scripts/dev`).
- **Semgrep**: use `semgrep scan --error --metrics off`, not `semgrep ci` (it ignores `--config` and targets the platform). No login needed. A custom `.semgrepignore` replaces defaults: re-list `node_modules`, `dist`, `build`. Ours is root-anchored (`/dist/` and so on; only `node_modules/` matches at any depth), so a source directory that is merely named `coverage`, `reports` or `rules` is still scanned. Default ignores skip `/test`. For offline use, `yarn semgrep:rules` downloads the five rulesets into `rules/` and **git-ignores it**: the Semgrep Rules License v1.0 restricts redistribution, so the rules must not be committed, uploaded or shared. The registry returns JSON to clients that accept gzip, so the fetch script sends `accept-encoding: identity`. Semgrep writes `~/.semgrep/settings.yml` and `semgrep.log` unless `SEMGREP_SETTINGS_FILE` and `SEMGREP_LOG_FILE` are set (the CI job points both into `RUNNER_TEMP`). A partial-parse warning (`typeof import()` type arguments) hides code from the scan: write `import type * as ns` instead. **The only allowed suppression** is `// nosemgrep: <full rule id> -- <reason>` on the flagged line or the line directly above (`scripts/semgrep-rules/suppressions.test.ts` enforces the form); never `--exclude`, `--exclude-rule` or `--disable-nosem`. `scripts/semgrep-rules/repo-scan.test.ts` runs the real binary over the repository with the offline rules when both exist, so a new finding fails `yarn test` there.
- **Trivy**: dev dependencies are skipped without `--include-dev-deps`; misconfig must be named in `--scanners`; `--severity` also filters secrets. Secret scanning needs no vulnerability DB (fast for pre-commit). **Supply-chain incident (March 2026, CVE-2026-33634):** Trivy v0.69.4 (and Docker Hub v0.69.5-6) were malicious, and `trivy-action` tags 0.0.1 to 0.34.2 plus `setup-trivy` tags were repointed. Use Trivy v0.76.1 or later pinned exactly, `trivy-action` 0.35.0 or later and `setup-trivy` v0.2.6 or later, each pinned by full commit SHA, and pin every other Action the same way. Never reference older tags. Here: Trivy 0.76.1 in `mise.toml` and `aquasecurity/setup-trivy` v0.3.1 in CI; `trivy-action` is not used. `trivy.yaml` is the single list of skipped directories. `.trivyignore` exists only when needed: each entry has a reason comment above it and `exp:YYYY-MM-DD` within 90 days of the line's commit date, and Trivy stops honouring an entry on its expiry day (tested). `setup-trivy` needs a literal path (an expression, not `$RUNNER_TEMP`). Misconfiguration scanning works offline with the checks embedded in the binary (`TRIVY_SKIP_CHECK_UPDATE`). Trivy has no docker-compose scanner. `setup-trivy` checks out `aquasecurity/trivy` (contrib only) into `./trivy` with the workflow token and deletes it again.
- **Qodana**: linter `qodana-js` (image `jetbrains/qodana-js:2026.2`, pinned by tag in `qodana.yaml` and by digest in the workflow as `--linter tag@sha256:...`), `qodana.yaml` with `version: "1.0"`, `failThreshold: 0`, needs `QODANA_TOKEN` and a paid Ultimate or Ultimate Plus licence. Gate failure exits 255. Fork PRs get no secrets, so it is a maintainer-side check and never required (like `leaks`). The coverage input is `.qodana/code-coverage/lcov.info` (JavaScript reads lcov with paths relative to the project root; the defaults also look in `coverage/lcov.info`, `reports/` and `test-coverage/`); the Vitest coverage reporter is therefore `['text', 'lcov']`, and `.qodana/` is a git-ignored generated directory (also in the ESLint ignores and the FTA `exclude_directories`). There is no baseline file: a finding is fixed, excluded in `qodana.yaml` with a comment above the entry, or silenced with `//noinspection <Name> -- <reason>` (the escape-hatch gate rejects one without a reason).
- **Stryker** (E20-S04, E20-S05): `@stryker-mutator/api` is a devDependency only for the type of the config. `clearTextReporter.logTests` is `false` (thousands of log lines otherwise). A stale incremental run shows bogus survivors among the static mutants: verify with `--force` before writing a test for one. `STRYKER_SCOPE` selects the scope and `STRYKER_SHARD` the slice of the server scope (see [`development.md`](development.md)). `vitest.related` defaults to true in the Vitest runner: the initial run and every mutant run execute only the tests whose imports reach the mutated files, so a shard's initial run is shorter than the whole suite and a test that reaches code only through a dynamic import is missed (NoCoverage mutants lower the score, never hide a survivor). Static mutants (module-level code) run every related test and dominate the time: on the `shared` shard 111 of 161 mutants are static and took about 97% of the run, and which mutants count as static can change between runs (Stryker issue 6073). `ignoreStatic` would cut that time but stops mutating the module-level constants and message strings, so it is not used. Stryker writes its incremental file only at the end of a run, and also on SIGINT, SIGTERM, SIGHUP or SIGABRT ("Saved a partial incremental report"), but not when the signal arrives during the initial test run; the CI runner's own cancel signal does not reliably reach Stryker, so `scripts/mutation-gate/mutate.ts` sends SIGINT itself after `MUTATE_BUDGET_MINUTES`. A second signal while Stryker writes makes it exit at once (`unexpected-exit-handler.js`), so the file can be cut short, and when Stryker reads an incremental file at start-up it rethrows every error but "no such file" (`project-reader.js`, also a valid JSON without `files`): the run then stops before its first mutant, every time, so `yarn mutate:check-incremental` deletes such a file before it can be cached. The time of a shard cannot be estimated from its mutant count: a per-mutant model fitted to two shards came out up to five times too high for the others, because the time depends on how many tests reach each file (`services-other` has 516 mutants and took 9 min 50 s, `shared` has 163 and took 14 min 43 s), so the shard table holds measurements only. Skip when nothing changed (E20-S04): the nightly run skips a shard when the newest earlier completed `schedule` run of `ci.yml` on the same commit that has the job `mutation (<shard>)` concluded that job `success`; an older pass never outranks a newer failure, a cancel or a timeout, so a red shard reruns every night until it passes (`scripts/mutation-gate/skip-decision.ts`, step `decide`). Facts that make it sound: a leg that skipped itself ends `success` too, so a success on a commit always traces back to one cold `--force` pass; Stryker exits 130 on SIGINT and `scripts/mutation-gate/mutate-cli.ts` fails a shard that the budget stopped whatever the code, so a partial run is never green; the jobs endpoint is expected to name a matrix job `mutation (<shard>)` (the `name` of the job with its matrix value; no matrix run exists on the repository yet, so the first nightly run after the change confirms it); a job-level `if` that is false reports `skipped`, not `success`, and `/runs/{id}/jobs` lists the latest attempt of a run. The lookup fails open: a network error, a status other than 200 (a rate limit is 403 or 429), a body of an unexpected shape, a missing or renamed job, a timeout (60 s for the whole lookup) and a cap (three pages of 100 per list, ten runs) all mean "run the shard"; it never fails the step and never prints the token or a response body. Rename the job or its `name` and the next nightly run finds no job of the old name and runs every shard once (a cost, not a hole). The first nightly run after the change is cold, the second on an unchanged commit should skip (open until seen, E20-S04). Needs `permissions: actions: read` on the job, which the runner guard allows at job level only (`docs/ci-runners.md`, R5).
- **Vite 8 / React**: Rolldown + Oxc replace esbuild/Rollup (`build.rolldownOptions`, `oxc` config keys). `@vitejs/plugin-react` 6 has no Babel option. Keep React and react-dom on the identical version. TanStack Router uses code-based routes (no codegen).
- **Scaffolding with Corepack**: `corepack use yarn@x` runs an install with the default PnP linker and leaves `.pnp.cjs`, `.pnp.loader.mjs` and a `yarn.lock`; set `nodeLinker: node-modules` first (or delete the PnP files). `lefthook install` with no `lefthook.yml` writes an example one. `lefthook install` also **fails without `.git`** (verified), which is why `scripts/dev/install-hooks.ts` skips it in a Docker build context without `.git`. CI checkouts have `.git` but still install no hooks (see the `prepare` bullet). CI pins `corepack@0.36.0`, installed with `npm install --global --prefix "$RUNNER_TEMP/npm-global"` (never into the shared tool-cache Node), and the packageManager hash covers Yarn itself.
- **`yarn <name>` runs the script of that name before the binary** (see Commands in [`development.md`](development.md)). The `pre-push` jobs call the scripts, so the pre-push hook, the CI steps and `yarn gate` run identical commands. `pre-commit` instead runs staged-file variants of the binaries (`yarn biome check --write ... {staged_files}`, `yarn eslint ... {staged_files}`, `yarn vitest related --run`); only `yarn caps` is shared with it.
- **type-coverage does not follow project references**: `-p tsconfig.json` on the solution-style root (`files: []`) reports `0 / 0` and passes (verified), so it is a silent no-op. Always run it per project (`-p tsconfig.scripts.json`, `-p tsconfig.node.json`), and add a line to the `type-coverage` script for every new tsconfig project. It also resolves `typescript` through node_modules hoisting (Yarn warns YN0086 that `type-coverage` does not declare it), another reason for `nodeLinker: node-modules`.
- **fta-cli 3.1.0 ships CRLF line endings, shebang included**: `node_modules/.bin/fta` fails on Linux with `env: 'node\r'`. Run it through `yarn fta` (Yarn launches the file with `node`). Splitting a file is the only way to lower its score; `measure.ts`, `cli.ts` and the caps modules were split (`collector.ts`, `nesting.ts`, `report.ts`) to get under 50. The foundation sat at 49.3 and `boot.ts` and `env.ts` are tight, so a new option or branch there can break the cap. Splitting a file can also RAISE its score (extracting `start-check.ts` out of `adapters/github/start.ts` made it worse); one shared options object (`http` in `start.ts`) lowered it.
- **Biome 2.6 also formats Markdown and YAML.** Its Markdown formatter rewrites tables with padded separators (against the table style in the user's CLAUDE.md), so `biome.json` turns the Markdown formatter and linter off. YAML (`.github/`, `lefthook.yml`) is formatted by Biome. Biome's `lint/security/noDangerouslySetInnerHtml` exists in 2.6 with default severity `error`; `biome check --staged` exists and works without `vcs.enabled` (verified on 2.6.4; `vcs.enabled: true` without `clientKind` is a config error), but the hook passes Lefthook's `{staged_files}` instead.
- **eslint-config-biome is not used.** It switches off 557 rules, among them the type-aware `no-floating-promises`, `no-misused-promises` and `switch-exhaustiveness-check`, whose Biome counterparts are still `nursery` with severity `info` in Biome 2.6. `switch-exhaustiveness-check` is not part of `strictTypeChecked`, so `eslint.config.mjs` enables it explicitly. Where Biome and ESLint overlap, both run; revisit only if a real conflict appears.
- **eslint-plugin-security 4.2 and eslint-plugin-no-unsanitized 4.1 work on ESLint 10.** The security preset ships as `warn`; `eslint.config.mjs` escalates it to `error`. `detect-non-literal-fs-filename` and `detect-object-injection` fire in the caps tool and its tests (a CLI that opens paths, `CAPS[kind]` on a closed union) and are suppressed inline with a written reason. no-unsanitized ships no types: `types/eslint-plugin-no-unsanitized.d.ts` declares the part used. sonarjs 4.2 is LGPL-3.0-only (fine for a dev tool under AGPL-3.0); no-unsanitized is MPL-2.0.
- **Knip production mode**: `entry` is `scripts/*.ts!`, `src/server/main.ts!`, `src/server/migrate.ts!`, `src/server/domain/evaluation/index.ts!`, `src/shared/pr-evaluation-details.ts!`, `src/server/domain/eligibility.ts!` and `src/server/services/installation-store.ts!` (the first two until the evaluation job and the dashboard reader import them from production code, `eligibility.ts` and `installation-store.ts` until the webhook and job code use them (E06, E07); then remove the entry; every new engine module must be reachable from `index.ts`, whose test pins its exports) (production mode does not read the `dev` and `db:migrate` scripts, so without them every server file is "unused"; default mode already finds them through those scripts and prints a harmless "redundant entry pattern" configuration hint, exit code 0). The production project negates `**/test-support.ts` (the adapters', the shared one and the domain one), `global-setup.ts` and the PGlite adapter (`pglite.ts`, `pglite/`) with `!...!`. `yarn knip` chains both modes, so `yarn knip --production --strict` really runs `knip && knip --production --strict --production --strict`: to run one mode alone use `yarn exec knip` or `yarn exec knip --production --strict`. Exports that only tests use (they are exported for unit tests) carry `@internal`, which Knip ignores in production mode. `scripts/code-caps/test-support.ts` is negated from the production project (`!...!`) but still checked in default mode.
- **Playwright image** (E20-S06): `mcr.microsoft.com/playwright:v<version>-noble` has Yarn 1 and Node 26.13.0, hence `SKIP_YARN_COREPACK_CHECK=1` in `yarn e2e:update` and the CI helper. Biome's Playwright domain is scoped to `e2e/**`. The `cla-e2e-*` containers carry the label `cla-gate.ci=e2e`, run with `--network host` as the runner user and are removed by `--rm` plus an `if: always()` step.
- **Octokit** packages are ESM-only; the server tsconfig must use `nodenext`. `octokit` 5.0.5 registers a retry plugin; it is inert here (`retries: 0`) and the throttling plugin is disabled, because `adapters/github/rate-limiter.ts` and the GET-only 1 s and 2 s repeat decide. Its error messages quote the response body and its error holds the request (with the `Authorization` header), so the adapter never passes either on: `octokit-errors.ts` builds an error with fixed text and no `cause`. A response body that fails halfway reads as `UND_ERR_SOCKET`.
- **Fastify and the webhook route** (`fastify-raw-body` 6.0.3, Fastify 5): the plugin fills `rawBody` at the end of the stream, so a hook that needs it runs in `preValidation` after a catch-all raw content type parser, not earlier. With `runFirst` it reads `request.raw` using the route-level `bodyLimit`. Fastify answers a malformed `Content-Type` with its own `415` before any `preValidation` hook, which would let an unsigned request see something other than `401`: the webhook scope holds the header off the request in `onRequest` and puts it back for the media type check that follows the signature. Node joins a repeated custom header with a comma and keeps only the first `Content-Type`. `app.setGenReqId` is encapsulated: Fastify calls the generator of the scope the router matched, which is how the webhook route mints its own request ids for every spelling of its path (percent-escapes, a fragment and the absolute form of the target all reach the route).
- **MSW 3** (server side, in `adapters/github/test-support.ts` as `mockGitHub` and `mockApp`, and in `http-world/test-support.ts`): `server.listen({ onUnhandledFrame: 'error' })` makes an unmocked request fail the test; loopback is let through with `passthrough()` so the Fastify app under test can still be called. MSW's types contain `any`, which type-coverage would count in every test: the routes stay inside the `test-support.ts` functions and the tests see typed results. Yarn prints peer-dependency warnings for MSW's optional peers; they are harmless. The handler files count toward the 100% coverage.
- **Server foundation facts** (verified while building it, 2026-11-01):
  - Dependencies: `fastify` 5.12, `@fastify/helmet` 13, `fastify-type-provider-zod` 7 (its peers `@fastify/swagger` and `openapi-types` are optional for us: Yarn prints YN0002/YN0086, accepted), `zod` 4.6, `kysely` 0.29.7 (0.29.8 was younger than the one-day age gate), `pg` 8.23, `pino` 10.4; dev `@electric-sql/pglite` 0.5.14 (exact; Apache-2.0). All are MIT except PGlite, all AGPL-compatible.
  - Fastify's `trustProxy` type has no number, but the runtime accepts a hop count: `fastifyTrustProxy` in `src/server/adapters/http/trust-proxy.ts` (called from `app.ts`) converts a count into the equivalent `(address, hop) => hop < n` function. `parseTrustProxy` returns `undefined` on a typo, which `loadConfig` turns into a start-up error naming `TRUST_PROXY`.
  - node-postgres returns bigint (int8) as a string. `pg.ts` and the PGlite client both parse it with `parseInt8` (throws `RangeError` outside the safe-integer range), so ids are numbers everywhere and the two drivers agree. Hand-written `schema.ts` types follow that, and `schema.test.ts` compares them with the live catalog.
  - PGlite 0.5.14 is PostgreSQL 18.6, enforces roles and `SET ROLE` privileges (so the runtime-role tests are meaningful on it too), starts in about half a second, and `query()` always uses the extended protocol, which rejects multi-statement scripts: the own Kysely dialect in `adapters/db/pglite*` sends parameterless SQL through `exec()`. Kysely starts its driver lazily and `destroy()` is a no-op before that, hence the `select 1` ping in `openPgliteDatabase`. It has one connection, so the dialect queues with a mutex; a test that needs two competing connections (advisory locks) must run on a real server.
  - Test resets use `drop schema public cascade; create schema public`; roles are cluster-wide and survive it. A `TRUNCATE` of a table that other tables reference fails with `0A000` before any trigger fires, so the immutability tests use `truncate ... cascade` to reach the trigger.
  - ESLint outcomes worth knowing: `sonarjs/function-return-type` accepts a function with a JSDoc `@returns` tag (used for functions that return a union by design); `security/detect-object-injection` is avoided with a `Map` (`STATUS_TEXT`) or an inline reason; `expect.any(...)`, `expect.stringContaining(...)` are typed `any` and trip `no-unsafe-assignment` inside object literals, so tests wrap them in an `unknown`-returning helper; a Fastify plugin with no `await` is written as `FastifyPluginCallbackZod` (`done()`) to satisfy `require-await`; `Promise.withResolvers<void>()` trips `no-invalid-void-type`, annotate the variable as `PromiseWithResolvers<void>` instead.
  - `docker-compose.yml` mounts the volume at `/var/lib/postgresql` (the 18 image keeps its cluster in `18/docker` below it). The host port is `${POSTGRES_PORT}` with no default (never 5432, often taken): `yarn db:up` picks a random free one; to probe by hand set `POSTGRES_PORT` to a free port, use a unique `-p <project>`, and finish with `down -v`.

## GitNexus

Dev tooling only, never a gate. `gitnexus analyze` writes `.gitnexus/` (self-ignoring) and appends a managed block to `CLAUDE.md` and `AGENTS.md` between `<!-- gitnexus:start -->` and `<!-- gitnexus:end -->` plus `.claude/skills/gitnexus-*`. Do not hand-edit inside the markers. Use `--skip-agents-md` or `--skip-skills` to keep this file untouched. ## Open verifications without a story

Facts that could not be verified when the toolchain was written and that no story in `docs/epics/` owns. Resolve each when the situation arises, then delete it from this list. The open verifications that a story owns are written as acceptance criteria in that story (pg-boss queue policy: E07-S02; the first `mutation` job run on the shared runners and its cache restore: E20-S13; the shared runners' host-side leftovers and the fork "Approve and run" prompt: E23-S11 and [`ci-runners.md`](ci-runners.md#known-unknowns-and-risks)). The legal question (ESIGN, eIDAS, GDPR retention) is in [`decisions.md`](decisions.md#open-questions).
