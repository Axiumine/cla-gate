# Operations

What an operator must keep in mind. Configuration variables are in [`configuration.md`](configuration.md); the CI runner policy is in [`ci-runners.md`](ci-runners.md).

- **Private key rotation**: the App supports multiple private keys. Generate the new key in the App settings, deploy it as `GITHUB_APP_PRIVATE_KEY` and keep the old one as `GITHUB_APP_PRIVATE_KEY_PREVIOUS`, then delete the old key in the settings once the new one works. On a 401 the previous key is tried, promoted, and `github.app_key_fallback` is logged with its fingerprint; `github.app_keys_refused` (error) means GitHub refused every key. After setting or rotating a key, compare the fingerprint in the `github.app_configured` start-up line with the App settings page.
- **Backups**: signatures are legal evidence. Daily backups plus point-in-time recovery, with a periodically tested restore.
- **Poison jobs**: bounded pg-boss `retryLimit` and a dead-letter queue whose handler sets the Check Run to `failure` with a `/recheck` hint, so a check is never stuck `in_progress`.
- **GitHub rate budget**: cache installation tokens and org membership. The platform's own rate limiter (one lane per installation plus one for the App) waits out a 429 or a rate-limit 403 of 60 s or less and hands a longer limit to the job layer; watch the WARN line `github.rate_limited` (fields `scope`, `waitSeconds`, `route`, `installationId`; `installationId` null is the App's own lane).
- **Runtime image**: it must contain `package.json` next to `dist` (the `User-Agent` version is read from it at start-up; a missing file fails the first GitHub request).
- **Webhook rotation**: set the new secret as `GITHUB_WEBHOOK_SECRET` and keep the old one as `GITHUB_WEBHOOK_SECRET_PREVIOUS`, then update the secret in the App settings; when the WARN `webhook.secret_previous_used` (at most once a minute) stops appearing, remove the previous one.
- **Webhook log lines**: one INFO `webhook.received` per delivery (`event`, `action`, `deliveryId`, `githubInstallationId`, `outcome` of `accepted`, `ignored`, `duplicate` or `rejected`, `reason`, `durationMs`); WARN `webhook.tenant_refused` and `webhook.tenant_redirected` (`githubInstallationId`, `githubRepoId`, `reason`, one per installation per minute, numeric ids only), so a rejected tenant that sends events is visible; `webhook.enqueue_failed` when the job could not be sent (until E07-S01 every delivery that starts a job); `webhook.payload_invalid`. A manual redelivery from the App's Advanced tab works once the queue is wired.
- **Role and tenant log lines**: WARN `members_permission_missing` and `repository_permission_missing` (`githubInstallationId` only) say the App lacks Members: read or Metadata: read for an installation, so its admins are not recognised; WARN `installation_state_stale` (`githubInstallationId`, `reason` `suspended` or `gone`) says GitHub refuses an installation that the stored row still shows as active, so a webhook was late or missed and the tenant answers `404` until the sync catches up.
- **Log lines to watch**: `installation.reconciled` (INFO) after each reconciliation, and the WARN lines `installation.sync_failed`, `installation.reconcile_failed`, `installation.permissions_missing` and `installation.deleted_still_listed`. Reconciliation runs once in the background after start-up.

## Multi-org operation

One instance authenticates as one GitHub App and serves several orgs. The recommended setup is to set the App visibility to Only on this account, so GitHub refuses other accounts. For a public App, `GITHUB_ALLOWED_ACCOUNT_IDS` is the second line: any other installation is recorded as rejected (`admission_status` rejected, reason `account_not_allowed`, audit action `installation.rejected`, one WARN `installation.rejected`) and never touched: no token, no repository listing, no PR data. An installation of an account that is neither a user nor an organisation (an enterprise) is rejected the same way, whatever its id.

To admit another org, add its numeric account id to `GITHUB_ALLOWED_ACCOUNT_IDS` and restart; the reconciliation then admits it. Removing an id takes effect at the restart: the installation gate refuses the account at once, and the reconciliation records the change as `policy_changed`. If GitHub is down at start-up the log shows `github.admission_policy_pending` and `github.admission_policy` appears on the first use. The operator view is `GET /api/operator/installations` (the rows of `listInstallationsForOperator` plus each tenant's state, `no-store`, read-only, `404` for anyone who is not an operator); the screen for it is E18. Who the operator is: `OPERATOR_GITHUB_IDS` when set, otherwise the account that owns the App when it is a user, and nobody when it is an organisation. The start-up line `github.operator_policy` prints the effective ids; `github.operator_policy_pending` means GitHub was unreachable and the owner is not known yet, and until it is every signed-in caller of the operator route gets `502 github_unavailable`. To run an instance owned by an organisation, set `OPERATOR_GITHUB_IDS` to the numeric ids of the people who operate it and restart.
