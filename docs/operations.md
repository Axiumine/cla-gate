# Operations

What an operator must keep in mind. Configuration variables are in [`configuration.md`](configuration.md); the CI runner policy is in [`ci-runners.md`](ci-runners.md).

The step-by-step guides are in [`operations/`](operations/install.md): [install](operations/install.md), [reverse proxy](operations/reverse-proxy.md), [upgrade](operations/upgrade.md), [backup and restore](operations/backup-restore.md), [key rotation](operations/key-rotation.md), [troubleshooting](operations/troubleshooting.md), [uninstall](operations/uninstall.md) and [data protection](operations/data-protection.md). The list below is what to keep in mind between them.

- **Private key rotation**: the App supports multiple private keys. Generate the new key in the App settings, deploy it as `GITHUB_APP_PRIVATE_KEY` and keep the old one as `GITHUB_APP_PRIVATE_KEY_PREVIOUS`, then delete the old key in the settings once the new one works. On a 401 the previous key is tried, promoted, and `github.app_key_fallback` is logged with its fingerprint; `github.app_keys_refused` (error) means GitHub refused every key. After setting or rotating a key, compare the fingerprint in the `github.app_configured` start-up line with the App settings page. The steps for the compose stack are in [`operations/key-rotation.md`](operations/key-rotation.md).
- **Backups**: signatures are legal evidence. Daily backups plus point-in-time recovery, with a periodically tested restore. The commands for the compose stack, run verbatim by the smoke test `tests/smoke/backup.test.ts`, are in [`operations/backup-restore.md`](operations/backup-restore.md).
- **Secrets of the compose stack** (E19-S04): `sh scripts/init-secrets.sh` creates `secrets/` (mode 0700) and, when there is none, `.env` (a copy of `.env.example`, mode 0600). It never overwrites, changes or deletes a file that exists, prints the names of the files it created and never a value. Generated, 64 hex characters each: `db_admin_password`, `db_owner_password`, `db_app_password`, `session_secret`, `setup_token`. Derived from the two role passwords (the files above, or the ones you wrote yourself): `database_url` (`cla_app`) and `migration_database_url` (`cla_owner`). Empty placeholders for what exists only after the first-run setup or during a rotation: `github_app_private_key`, `github_webhook_secret`, `github_client_secret`, `github_app_private_key_previous`, `github_webhook_secret_previous`. The files are mode 0444 inside the 0700 directory: a bind-mounted file secret keeps the owner and mode of the host file, and the container user (10001) could not read a 0400 file that belongs to you, so the directory is what keeps other users of the host out. A file is replaced with `install -m 0444`, never edited in place.
- **Database provisioning** (E19-S03): `scripts/provision-database.sh` creates or corrects the database, the roles `cla_owner` and `cla_app` and the `pgboss` schema on a server of your own (the compose stack runs it by itself on the first start of an empty volume). A second run prints `unchanged` for every step. Exit codes: 0 done, 2 invalid input, 3 refused because of a conflict (nothing is changed or dropped), 4 no connection, no usable `psql` (15 or later) or an SQL error. The passwords travel in the environment of `psql`, never in its arguments, but the statement that sets a role's password is executed by the server: a server that logs DDL statements (`log_statement` of `ddl` or `all`) writes it, password included, to its log. The compose stack's PostgreSQL logs no statements; on a server of your own check the setting first, or change the passwords afterwards.
- **The `tls` profile and Let's Encrypt** (E19-S05): the certificate lives in the named volume `caddy-data` and survives `docker compose down`; `down -v` deletes it, and Let's Encrypt limits the certificates it issues per name and week, so do not recreate the volume repeatedly. The profile needs `PUBLIC_BASE_URL` to be an `https` origin without a port. See [`operations/reverse-proxy.md`](operations/reverse-proxy.md).
- **Smoke test artifacts** (E19-S08): the CI job `container` (`yarn smoke`) builds the image and starts the stack in labelled containers (`cla-gate.ci=container`). When it fails, the compose logs of each scenario are uploaded as the artifact `smoke-compose-logs` (`reports/smoke/`, kept 7 days); `yarn ci:smoke stop` removes what a run left.
- **Erasure and the access request** (E16): an org admin erases a person's personal data for their org through the preview and erasure routes, and a signed-in person downloads their own data with `GET /api/me/export`; the steps, what stays and why, and what a restored backup brings back are in [`privacy.md`](privacy.md). An operator without the admin role calls `erase_signer_pii(person, actor, installation)` as the migration owner.
- **Network metadata purge** (E16-S05): `purge_signer_network_metadata(cutoff)` removes the optional IP address and user agent older than `NETWORK_METADATA_RETENTION_DAYS`. Its handler (`createPurgeNetworkMetadataHandler`) and schedule constant (`17 3 * * *`, UTC, daily) are built, but the queue `purge-network-metadata` is not in `QUEUES` and nothing schedules the job yet, so keep `RECORD_NETWORK_METADATA` off (E13-S05 adds the flag) until the story is finished. The handler logs `network_metadata_purge_done` with the row count and the cutoff.
- **Poison jobs**: five retries, a 30 s backoff doubling with jitter (the first retry comes 30 to 60 s later), a 300 s expiry, finished jobs deleted after 7 days and jobs that never ran after 14 days, and the dead-letter queue `job-dead-letter`. Its handler sets the Check Run of an evaluation to `failure` with a `/recheck` hint, so a check is never stuck `in_progress` (a row that already holds a verdict is left alone), and appends the audit action `installation.sync_failed` for a `sync-installation` that died. A dead `job_payload_invalid` job fails terminally with no retry. A dead `sweep`, `sweep-installation`, `sweep-repository`, `finalise-repository` and `finalise-check` is logged at error only, and the next re-enable, disable, `/recheck` or sweep repeats the work; `dead_letter_unhandled` (error) means the handler itself failed under the same bounds. A cancelled job is kept like any finished one and leaves its `webhook_deliveries` row unprocessed, so a GitHub redelivery requeues it (harmless: `evaluate-pr` ends `skipped` for a closed pull request, or evaluates after a reopen).
- **Job queue**: `yarn db:migrate` creates the queues with their policy (a second step after the SQL files; it prints `job queues: up to date`, `job queues created: a, b` or `job queues updated`, and a line when the role `cla_app` does not exist). A queue of another policy is refused by migrate and at boot (`Job queues have the wrong policy`): stop the workers, delete the queue (its jobs go with it) and run `yarn db:migrate` again; this is also what upgrading a database whose `sweep` queue is `standard` needs. A server that cannot find a queue exits 1 naming it, and `/readyz` is `503` while a queue is missing or pg-boss reports an error. A worker that dies mid-run delays the next evaluation of its pull request until the 300 s expiry. A job aborted at shutdown is retried after the restart and the exit code is 1.
- **pg-boss upgrade**: deploy the new build, then run `yarn db:migrate`; the step waits for pg-boss's background index builds (a failed build is read from `pgboss.bam`). The runtime role never alters the schema.
- **Sweep**: `SWEEP_INTERVAL_MINUTES` (default 30) schedules `sweep` in the `__pgboss__send-it` queue that `yarn db:migrate` creates; 0 removes the stored schedule at the next start. A sweep costs about one GitHub request per enabled repository plus one per 100 open pull requests (at most ten pages, 1,000 pull requests, per repository per run, newest first), plus one `getPullRequest` for each stale `in_progress` pull request that is missing from the listing; the limiter of E05-S05 throttles it, hence the default of 30 minutes.
- **GitHub rate budget**: cache installation tokens and org membership. The platform's own rate limiter (one lane per installation plus one for the App) waits out a 429 or a rate-limit 403 of 60 s or less and hands a longer limit to the job layer; watch the WARN line `github.rate_limited` (fields `scope`, `waitSeconds`, `route`, `installationId`; `installationId` null is the App's own lane).
- **Runtime image**: it must contain `package.json` next to `dist` (the `User-Agent` version is read from it at start-up; a missing file fails the first GitHub request).
- **Webhook rotation**: set the new secret as `GITHUB_WEBHOOK_SECRET` and keep the old one as `GITHUB_WEBHOOK_SECRET_PREVIOUS`, then update the secret in the App settings; when the WARN `webhook.secret_previous_used` (at most once a minute) stops appearing, remove the previous one. The steps for the compose stack are in [`operations/key-rotation.md`](operations/key-rotation.md).
- **Webhook log lines**: one INFO `webhook.received` per delivery (`event`, `action`, `deliveryId`, `githubInstallationId`, `outcome` of `accepted`, `ignored`, `duplicate` or `rejected`, `reason`, `durationMs`); WARN `webhook.tenant_refused` and `webhook.tenant_redirected` (`githubInstallationId`, `githubRepoId`, `reason`, one per installation per minute, numeric ids only), so a rejected tenant that sends events is visible; `webhook.enqueue_failed` when the job could not be sent (the queue is down or not migrated); `webhook.payload_invalid`. A manual redelivery from the App's Advanced tab works once the queue is wired.
- **Role and tenant log lines**: WARN `members_permission_missing` and `repository_permission_missing` (`githubInstallationId` only) say the App lacks Members: read or Metadata: read for an installation, so its admins are not recognised; WARN `installation_state_stale` (`githubInstallationId`, `reason` `suspended` or `gone`) says GitHub refuses an installation that the stored row still shows as active, so a webhook was late or missed and the tenant answers `404` until the sync catches up.
- **Reporting log lines** (E09, numeric ids and the head SHA only, never a name, an email, a token or a body): INFO `report.started`, `report.published`, `report.failed`, `report.cancelled`, `report.enforcement_disabled`, `report.check_run_created`, `report.check_run_updated`, `report.check_run_recreated` (the `PATCH` was answered 404 or 422), `report.comment_created`, `report.comment_updated` and `report.comment_disabled`; INFO `report.cancel_not_needed`, `report.cancel_left_to_sibling` and `report.settled_for_siblings` for a close at a head SHA that other pull requests share; WARN `report.skipped` (`reason` `repository_gone` or `installation_unavailable`), `report.output_rejected` (a 422 to the full output, then the minimal one is tried), `comment_skipped` (`statusCode` 403, 404 or 422 on the comment: the check is written, the comment is not) and `comment_skipped_stale` (a newer head SHA of the pull request has been evaluated, so its job writes the comment); ERROR `checks_permission_missing` (the App lacks Checks: write; the job fails and is retried) and `report.minimal_output_rejected`.
- **Log lines to watch**: `installation.reconciled` (INFO) after each reconciliation, and the WARN lines `installation.sync_failed`, `installation.reconcile_failed`, `installation.permissions_missing` and `installation.deleted_still_listed`. Reconciliation runs once in the background after start-up.
- **Version integrity**: the ERROR log line `cla_version_integrity_failed` (`installationId`, `documentId`, `versionId`) means a stored version text no longer hashes to its stored hash; the read answers `500`. Treat it as a data-integrity incident and restore from a backup: the database check on `content_sha256` and the immutability triggers make it unreachable in normal operation.

## Multi-org operation

One instance authenticates as one GitHub App and serves several orgs. The recommended setup is to set the App visibility to Only on this account, so GitHub refuses other accounts. For a public App, `GITHUB_ALLOWED_ACCOUNT_IDS` is the second line: any other installation is recorded as rejected (`admission_status` rejected, reason `account_not_allowed`, audit action `installation.rejected`, one WARN `installation.rejected`) and never touched: no token, no repository listing, no PR data. An installation of an account that is neither a user nor an organisation (an enterprise) is rejected the same way, whatever its id.

To admit another org, add its numeric account id to `GITHUB_ALLOWED_ACCOUNT_IDS` and restart; the reconciliation then admits it. Removing an id takes effect at the restart: the installation gate refuses the account at once, and the reconciliation records the change as `policy_changed`. If GitHub is down at start-up the log shows `github.admission_policy_pending` and `github.admission_policy` appears on the first use. The operator view is `GET /api/operator/installations` (the rows of `listInstallationsForOperator` plus each tenant's state, `no-store`, read-only, `404` for anyone who is not an operator); the screen for it is E18. Who the operator is: `OPERATOR_GITHUB_IDS` when set, otherwise the account that owns the App when it is a user, and nobody when it is an organisation. The start-up line `github.operator_policy` prints the effective ids; `github.operator_policy_pending` means GitHub was unreachable and the owner is not known yet, and until it is every signed-in caller of the operator route gets `502 github_unavailable`. To run an instance owned by an organisation, set `OPERATOR_GITHUB_IDS` to the numeric ids of the people who operate it and restart.
