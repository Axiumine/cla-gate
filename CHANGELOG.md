## [Unreleased]

### Added

- Planning documents: `README.md` (product, architecture, data model, GitHub App settings, security, hook pipeline) and `CLAUDE.md` (the operating contract: hard rules and the map of the other documents).
- AGPL-3.0-only licence, with an SPDX header on every source file.
- Quality-gate toolchain: Node 26.13 and Yarn 4.18 (node-modules linker), TypeScript 6.0 with strict flags, Biome and ESLint 10 at zero warnings, Vitest with 100% v8 coverage thresholds, type-coverage per project, Knip in both modes, FTA with a score cap of 50, Lefthook pre-commit and pre-push hooks.
- CI workflow with the jobs `static` and `coverage`, least-privilege permissions and every action pinned by full commit SHA; Dependabot for GitHub Actions and npm.
- Server foundation (`src/server`, `src/shared`, `migrations/001_initial.sql`): validated configuration with redacted secrets, the Fastify app with `/healthz` and `/readyz`, security headers and one error contract, Kysely over node-postgres and PGlite, the forward-only checksummed migration runner, the whole MVP schema with immutability triggers, audited erasure and the non-owner runtime role `cla_app`, ESLint layering rules, the compose stack and the informative `postgres` CI job.
- CI runner policy and tooling: `docs/ci-runners.md` (shared self-hosted runners, the fork pull request approval gate and the hygiene rules every job follows), the `yarn ci:runners` workflow guard, random free loopback ports for CI, development and tests (`yarn ci:port`, `yarn ci:postgres`, `yarn db:up`), and a `postgres` job that starts its own database container instead of a service container.
- Structure-cap ratchet tool (`scripts/check-code-caps.ts` and `scripts/code-caps/`): file, function, class, parameter and nesting caps checked against `.code-caps-baseline.json`, with 144 tests at 100% coverage.
- Branch protection on `main`: required checks `static` and `coverage`, linear history, no force pushes or deletion, rules apply to admins.
- Epics and stories work queue in `docs/epics/`, with an index in `docs/EPICS_STORIES.md`.
- Epic E23 (Self-hosted CI runners) in the work queue, and a link to the CI runner policy at the end of the acceptance criteria of every story that writes CI jobs, containers, ports or test databases.
- This changelog.
- `CONTRIBUTING.md`: the pull request flow, the commit policy, the repository protection settings and the dependency licence rules, with the rule that every pull request adds a line under `[Unreleased]` in this changelog.
- PR evaluation engine (`src/server/domain/evaluation`, E08): a pure, deterministic function that decides whether a pull request is covered by the active CLA from plain facts, recording the covering basis of every actor (signature or allowlist), unlinked commit identities with audited per-commit overrides, `Co-authored-by` trailers resolved from the GitHub noreply form, paging rules for pull requests of up to 2,000 commits (fail closed above), and a stored-details value (`pr_evaluations.details`) bounded at 256 KiB with numeric ids and codes only.
- Audit writer (`appendAudit`) that records every mutation in the same transaction as the change, with a closed set of actions, a closed allowlist of metadata keys and values (no personal data and no IP addresses, enforced in the code and by migration 002), and a guard that stops the server from starting when a mutating `/api` route declares no audit action.
- Extended quality gates (epic E20): the escape-hatch justification gate (`yarn lint:hatches`), Semgrep, Trivy, StrykerJS mutation testing of the server and the caps tool, a real-Postgres CI job with concurrency tests, Playwright end-to-end tests with visual baselines from a digest-pinned container, memlab leak scenarios, a Qodana job that skips cleanly without `QODANA_TOKEN`, a CI contract test and Dependabot groups for lockstep packages. They run as informative CI jobs (`semgrep`, `trivy`, `postgres`, `mutation`, `e2e`, `leaks`, `qodana`) until the promotion stories make them required checks.
- GitHub App core (epic E05): the instance authenticates as one GitHub App (`GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, with `GITHUB_APP_PRIVATE_KEY_PREVIOUS` for a rotation without downtime) and checks its identity with GitHub at start-up; it serves several orgs, each installation a separate tenant keyed on its numeric installation id, and serves only the App owner and the accounts in `GITHUB_ALLOWED_ACCOUNT_IDS` (every other installation is recorded as rejected and never touched, also after a restart that changes the list); installation tokens are minted on demand, held in memory only and refused for a rejected, deleted or suspended installation; all GitHub calls go through one port with an Octokit adapter, per-installation rate limiting with `retry-after` and secondary-limit waits (`github.rate_limited` WARN lines) and zod-checked responses; installations, repositories, renames, transfers between tenants and removals are synced and reconciled at start-up with an audit row for every change (migrations 003 and 004).
- Webhook intake (epic E06): `POST /webhooks/github` verifies the HMAC-SHA256 signature over the raw body (`GITHUB_WEBHOOK_SECRET`, required in production, with `GITHUB_WEBHOOK_SECRET_PREVIOUS` accepted during a rotation), checks the headers, size, media type, App target and the zod schema of each event, routes every delivery to one job or a stated reason for ignoring it, turns away deliveries of rejected, deleted, suspended, unknown or transferred installations, and records each delivery with its job in one transaction (`202 accepted`, `200 duplicate`, a redelivery requeues a lost job) inside an 8 s deadline, without a GitHub call in the request path; failed signatures are throttled per address (`429`), every delivery leaves one `webhook.received` line with no body, header or secret in it, and the route never keeps a caller's `X-Request-Id`. Until the job queue is wired (E07), a delivery that starts a job is answered `503 webhook_enqueue_failed` and GitHub's redelivery works afterwards.
- Login and sessions (epic E10): people log in with the GitHub App's user authorization (PKCE, a signed state cookie, a relative-only `return_to`; the user token is used once, revoked and never stored) and get a server-side session in the `__Host-cla_session` cookie (hashed id, idle and absolute lifetimes `SESSION_IDLE_SECONDS` and `SESSION_ABSOLUTE_SECONDS`, at most 10 per person, verified addresses kept only for the session in migration 005); `SESSION_SECRET`, `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are required in production and `.env.example` lists every variable. Every state-changing request needs the app's own `Origin`, a live session and an `x-csrf-token` and accepts JSON only; `POST /api/auth/logout` ends one session or all of the caller's; a revoked App authorization deletes a person's sessions (the handler is built, its binding to the job queue follows with E07); requests are rate limited per client address (`TRUST_PROXY` decides which) with `429 too_many_requests`.
- Authorization and tenant isolation (epic E11): every route declares who may call it and the server refuses to start with one that does not; roles are read from GitHub by numeric id with the installation token (org admin from the memberships API, repository admin from the collaborators permission API, cached for 60 s, a fresh read for every write, and a GitHub failure is `502`, `503` or `429` and never an allow); one guard answers every tenant route with a uniform denial convention (`404` for an unknown resource and for a viewer with no role, `403` for too low a role, `409` for a write to a suspended or deleted tenant); org admins keep read access to a suspended or deleted organisation for up to 14 days through a ledger of numeric ids (`migrations/007_installation_admin_seen.sql`); every data function takes a tenant scope and the cross-tenant tests are generated from registries; and `OPERATOR_GITHUB_IDS` names the instance operator, who lists installations at `GET /api/operator/installations` and has no access to any tenant's data.
- Job queue (epic E07): pg-boss in the application's Postgres runs every accepted delivery as a job (`yarn db:migrate` installs the queue schema and creates the 12 queues; the server refuses to start without them and `/readyz` reports them), one evaluation at a time per repository and pull request and always against fresh GitHub state, with `WORKER_CONCURRENCY`, graceful shutdown that aborts what does not finish in 30 s, five retries with backoff and a dead-letter handler that fails the check with a `/recheck` hint, pull request close that cancels waiting work (new evaluation result `cancelled`, migration 008), `/recheck` and Re-run limited to one a minute per pull request, a reconciliation sweep (`SWEEP_INTERVAL_MINUTES`) that catches missed deliveries and stuck evaluations, the repository-level jobs the later epics send, and a cached organisation-member exemption lookup.
- Web application shell (`src/web`, epic E17): a React 19 single-page app that the server serves from its own origin under a Content-Security-Policy without `unsafe-inline` or `unsafe-eval` (`WEB_ROOT`; images only from itself and GitHub avatars), with a typed API client on the shared route descriptors, an English message catalog, light, dark and system themes, accessible form, dialog and table primitives, a safe renderer for user-controlled text, request and error states, routing with GitHub login and logout, and a footer that links to the exact source commit (`SOURCE_URL`, `SOURCE_COMMIT`, the public `GET /api/meta`).
- Compliance, audit and data protection (epic E16): tests hold the audit action catalogue complete (a scan of every `appendAudit` call with a metadata fixture each, the state of the route guard, one writer of `audit_log`); org admins read the audit log of their installation (`GET /api/installations/:installationId/audit-log`, filters and a keyset cursor) and export the signatures of a document as a CSV that spreadsheet software cannot turn into a command (`.../signatures.csv`, streamed in batches of 1,000, 6 a minute per user, recorded as `signatures.exported`); erasure of a signer's personal data is scoped to one installation, with a preview and an erasure route for org admins (migration 009); `NETWORK_METADATA_RETENTION_DAYS` (default 30, at most 90) with the purge function and handler for the optional IP address and user agent (migration 010; the daily job is not registered with the queue yet); a signed-in person downloads everything held about them with `GET /api/me/export` (5 an hour, recorded as `data_export.created`, naming no other person); and `docs/privacy.md`, privacy notes for operators kept true against the schema and the defaults by tests.
- CLA documents and versions (epic E12): a maintainer creates, lists, reads and renames named CLA documents for the whole installation or one repository (`/api/installations/:installationId/documents`), saves a draft of the Markdown text with optimistic concurrency, publishes it as an immutable, hashed version (a major bump forces re-signing and queues a sweep of every enforcing repository, a minor bump does not), reads the version history and the exact text of each version, and rolls back by publishing a copy of an older text; the text is validated and made canonical in one place, and rendered through a sanitising Markdown pipeline that shows no raw HTML, no images and only http, https and mailto links. `migrations/011_cla_drafts.sql` adds the drafts table. No CLA text ships: the maintainer brings it. Saving or publishing a text reads it in time linear in its size (a Markdown parse of an adversarial 200 KiB text takes minutes, so none runs on a request). The sign context of epic E13 holds the published text and none of a draft, which closes the one clause of the draft story that waited for it.
- Check Run and pull request comment reporting (epic E09): every evaluated pull request gets one `license/cla` Check Run (`in_progress` while evaluating, then `success`, `failure` or `cancelled`) and, on failure, one upserted comment with the sign link and the fix steps, found by stored id and then by marker plus App id and never trusted when forged; the output is built by pure code in `src/server/domain/reporting` and every login, trailer name, SHA and id passes through `renderName`, `neutraliseText`, `shortSha` or `renderId` (controls, bidirectional marks, tag characters and `<!--` removed or broken), a disabled repository and a repository whose App lacks Checks: write are reported, pull requests that share a head SHA share one run whose state is the worst of theirs and that converges after a race, Re-run and Re-run all checks end in a fresh run, `PUBLIC_BASE_URL` must be an `http` or `https` origin the sign link can use, and `docs/legacy-status-coexistence.md` says how to move a repository from another CLA tool.
- Repository enablement and allowlist (epic E14): a maintainer lists the organisations and repositories they can administer (`GET /api/installations`, `GET /api/installations/:installationId/repositories`), attaches or detaches a repository's CLA document (`PUT /api/repositories/:repositoryId/cla-document`), turns enforcement on (`POST /api/repositories/:repositoryId/enable`, which needs a published CLA and sends a sweep, `409 no_active_cla` otherwise) and off (`POST .../disable`, which completes the `license/cla` check of every pending or failing pull request as `neutral` and leaves no red check behind, even when an evaluation races the switch or is retried), and exempts accounts by numeric GitHub id (`.../allowlist-entries`: add, list and remove; a typed login is resolved with GitHub and kept only as a display snapshot, and an `org_members` entry needs the Members permission, probed with `probeMembersPermission`). Every role follows the repository-action rule, every change is audited and re-evaluates the open pull requests, and the erasure of a person clears the login snapshot even for an allowlisted account that never signed (migrations 012 and 013).
- Self-hosting kit (epic E19): `docker compose up --build` builds one container image from the checkout (nothing is published) and starts PostgreSQL, a one-shot migration and the app, with secrets read from files (`*_FILE`), start-up diagnostics that name each wrong setting, `scripts/init-secrets.sh` for the secrets, `scripts/provision-database.sh` for the database and its roles, and an optional reverse proxy with automatic TLS (`--profile tls`, Caddy). The first-run page `/setup` creates the GitHub App through GitHub's manifest flow and shows its credentials once; the eight operator guides in `docs/operations/` cover install, upgrade, backup and restore, key rotation, troubleshooting, uninstall and data protection. The development database moved to `docker-compose.dev.yml`; the test suite refuses a `DATABASE_URL` whose database already holds `schema_migrations` (`CLA_TEST_ALLOW_APP_DATABASE=1` overrides it); the informative CI jobs `caddy` and `container` (a smoke test of the stack in real containers) were added.
- Contributor signing (epic E13): `GET /api/sign/:githubRepoId` gives a signed-in person the CLA version a repository enforces (the stored Markdown text, its hash, the consent sentence by id, their verified addresses and whether they already signed, must sign again or were revoked) and answers an unknown, suspended or not admitted repository with one `404`; `POST /api/sign` records the signature against that exact version hash in one transaction with the typed name (NFC, 1 to 200 code points, at least one visible character) and one of the person's verified addresses, writes `signer_pii` and the `signature.created` audit row, answers a repeat with `200` and writes nothing, allows 10 requests a minute per person and a 16 KiB body, and sends `evaluate-pr` jobs in the same transaction so the pull request the person came from, and up to 25 of their other failing pull requests in the tenant, turn green without waiting for a push; `GET /api/me/signatures` lists the CLAs the person signed in every org (state `active`, `outdated` or `revoked`, a path to sign again, a keyset cursor; migration 015); `RECORD_NETWORK_METADATA` (default `false`, migration 014) stores the IP address and user agent on `signer_pii` only when an operator switches it on, and the retention setting and the erasure function already cover them.

### Changed

- The `mutation` CI job survives the growth of the suite: Stryker's initial test run, which every shard repeats in one process (7003 tests, 12 min 37 s on a development machine), killed shard `shared` of the first scheduled run at its 20-minute limit, so `dryRunTimeoutMinutes` is 120 (a suite of 25 000 tests on a runner three times slower), the Stryker budget 170 and the job timeout 180 minutes; the runner guard (R4) gives that cap to this job and to no other, and `max-parallel` is 1 instead of 2 so that a cold run no longer holds two of the three shared runners (E20-S04).
- `qodana.yaml` excludes `JSDeprecatedSymbols`, with the reason above it: Qodana flags zod's `z.iso.datetime(...)` as deprecated (two calls on `main`, six on the compliance branch, a different set each run) while TypeScript and the type-aware `no-deprecated` rule of typescript-eslint, which stay on, report none.
- Qodana's two `JSDeprecatedSymbols` findings on `main` (`z.iso.datetime()` in `src/shared/auth.ts` and `src/shared/operator.ts`) are fixed by passing the default option explicitly (`{ offset: false }`, UTC only, the same rule as before).
- The `coverage` CI job may run 30 minutes instead of 15: the suite has grown to about 10 000 tests and a busy shared runner cancelled it once at 15, which is a required check.
- Tests that start a real process (Semgrep, Trivy, ESLint, git) no longer fail pre-push runs on a busy machine: the root Vitest config sets a 60 s `testTimeout` (the `server` project keeps its 30 s), where the default 5 s failed them without a wrong result.
- Qodana's 32 findings on `main` (17, then 15 more from E11) are fixed in the code (redundant locals, partial JSDoc `@param` lists, one regex group, unawaited queries now awaited together, and the Fastify reply results that are dropped with `void` (the `no-store` header through `setNoStore`) or replaced by `reply.statusCode =`, since a reply is a thenable that must not be awaited), and the `postgres` CI job's `timeout-minutes` is 45 instead of 20, because the shared runners cancelled it twice at 20 minutes while its tests were still passing.
- The `qodana` job uploads its SARIF file as a 7-day artifact (`qodana-sarif`), so the problems of a failed scan can be read without a login to Qodana Cloud; the action's own upload stays off. First scan with the real token: 13 problems, all fixed in the same pull request; E20-S08 is Done.
- The `mutation` CI job is a matrix of thirteen shards (the server and shared code by directory, plus the caps tool), each with its own incremental file, cache, report and `break` 90, at most two at a time, 60 minutes each; `yarn mutate` runs every shard, `yarn mutate:shard` one (`STRYKER_SHARD`), and `MUTATE_BUDGET_MINUTES` makes Stryker save its finished mutants before the job timeout; `yarn mutate:check-incremental` deletes an incremental file Stryker cannot read, so a broken file is never cached. Every shard was run cold in full locally (24 min 35 s at most under a heavy load, score 92.64 at least); `max-parallel` is per workflow run, and the overlap of runs is documented as accepted. The job runs on the nightly schedule, a manual run and a `v*` tag push, not on pull requests and not on a push to `main`, and the nightly run skips a shard when main has not moved: the step `decide` (`yarn mutate:decide`, GET only, `actions: read`) skips the leg when the newest earlier nightly run of the same commit that has `mutation (<shard>)` concluded it `success` (an older pass never outranks a newer failure), and fails open on any error; a shard stopped by its budget now always fails. The runner guard allows `actions: read` at job level. Replaces the single 45-minute run that never finished on the shared runners (E20-S04).
- Semgrep verified on the shared runners (E20-S01 is Done after `pipx` was installed on them) and the two failures of the mutation job recorded with their causes in E20-S04 and `docs/ci-runners.md`.
- `CLAUDE.md` is now a short operating contract; commands, quality gates, architecture rules, tooling notes and the contributing flow moved to `docs/` and `CONTRIBUTING.md`.
- `README.md` is now a landing page (product, scope, quick start, documentation map); the architecture, repository layout, auth and security, data model, GitHub App, operations, toolchain, decisions and configuration sections moved to `docs/`, and `scripts/docs/doc-size.test.ts` fails when `README.md` (10240 bytes) or `CLAUDE.md` (6144 bytes) outgrows its ceiling.
- Epic E19 (self-hosting kit) is Done: E19-S12 closed on the evidence of the `container` job, green on the self-hosted runners in pull request runs (all scenarios in about three minutes) with the compose logs uploaded when a scenario failed; `docs/epics/E19.md` records what was and was not shown.

### Fixed

- The `coverage` and `postgres` CI jobs get 45 and 60 minutes (they had 30 and 45): the shared runners differ by a factor of four in speed, and both jobs were cancelled by their timeout, tests passing, whenever the slowest runner picked them up (`docs/ci-runners.md`, Known unknowns).
- The `trivy` CI job no longer depends on `get.trivy.dev`, the download host of `aquasecurity/setup-trivy`, which lapsed (every run failed at the install step with curl exit 6, upstream aquasecurity/trivy#11537): `scripts/ci/install-trivy.ts` downloads the pinned release from GitHub, refuses it unless its SHA-256 equals the literal in `ci.yml`, and unpacks only the `trivy` binary into the runner temp directory; tests keep the version equal to `mise.toml`'s and forbid `setup-trivy` and `get.trivy.dev`.
- The backup scenario of the `container` CI job (E19-S12) no longer fails at random with "Pool overlaps with other one on this address space" (nightly of 2026-11-04): after `docker compose down -v` it starts only the database, Docker gave the `backend` network the first free /16, and that /16 could hold the random /24 of the stack's `default` network, which did not exist yet. A smoke stack now draws a subnet for `backend` as well (the /24 after the `default` one, setting `SMOKE_BACKEND_SUBNET`, given in the smoke override), so Docker never picks a pool for it; `scripts/smoke/override.test.ts` fails when `docker-compose.yml` gains a network without a subnet.
- The mutation gate (E20-S04, nightly run 41817514084): Stryker's main process no longer dies with "Zone Allocation failed - process out of memory" after the dry run (Node 26's `JSON.stringify` fast path aborts on the long IPC message that asks the checker to group the mutants, nodejs/node#66489; Stryker and its child processes now start with `--no-json-stringify-fast-path`, `scripts/mutation-gate/node-args.ts`), and the tests of the linear Markdown scan check how the time grows with the size (`slowdownOf`) instead of a bound of two seconds, which failed at 3.2 s in the dry run of the `shared` shard; the two bounds of two seconds in the tests of the health probe and of the `/readyz` timeout are dropped (they asserted nothing the test timeout does not).

### Security

- Fastify 5.12.7 to 5.12.8, the fix for GHSA-3qgw-9275-xf8w (CVE-2026-120216, medium): with a nonzero `handlerTimeout`, a streaming response that outlived the timeout crashed the process. CLA Gate sets no `handlerTimeout` (the default 0 is not affected), so it was not exposed; the update clears the finding Qodana reported on every branch.
